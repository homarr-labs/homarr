## Highest-risk evidence gaps

1. **New Statistics provider breadth has outpaced visible acceptance.** The 31-service release count is correct (30 statistics providers plus Jackett), but targeted searches found no fixture specs for these new provider modules and no specs under the Stats widget. `packages/request-handler/src/stats.spec.ts:12` contains only three demo-mode tests. Those tests bypass real Redis refresh, distributed locks, source version/auth parsing, timeout behavior and saved snapshot retention. `stats.ts:112-219` adds substantial distributed behavior: bounded pending map, four lock slots, lock renewal, identity/generation checks, failed refresh preservation and abort handling. Source exists; it needs empirical acceptance before describing all integrations as correct. Do not use populated demo cards as that evidence.
2. **Permission claims need cross-surface proofs.** The verified-email guard and provider/permission tests support the design, but mocks do not establish real LDAP/OIDC environments, cookie/proxy behavior, token revocation or coherent UI/API/Assistant/MCP denial. The captured PR already admits environment-specific cases remain unverified.
3. **Board rewrite is covered deeply at pure-model level, yet browser persistence is separate.** Engine specs are meaningful: eight-direction resize, collision/hierarchy invariants, transaction finish/cancel. Need actual pointer/touch behaviors and saved/reloaded database results, especially migrated nested sections, rails, mobile breakpoint edges and failures. Screenshot/video assets in article cannot certify the frozen candidate.
4. **Release checklist completion is not established by its text.** Captured PR still says candidate/owner/evidence pending and before-release boxes unchecked. Historic local tests and earlier SHAs are not release acceptance. Update stale checklist facts against the current head and attach evidence to each exact release gate.

## North Star suggestion

**Instance health and recovery center**, expressed as a practical “Is my dashboard ready?” screen. Reuse existing saved integrations, permission rules, task status and request error/freshness metadata. Show broken credentials, unreachable service, stale/error widget data, invalid/migration-pending Custom Widget, unavailable Workshop update, and missing required configuration; provide a direct repair link and explicit last-success timestamp. Start read-only and permissions-aware. This complements the release's direction—one configurable front door for the homelab—while making its newly broad extensibility trustworthy. It should be follow-up scope, not silently added as another GA blocker. A credible release first needs completed existing acceptance.
