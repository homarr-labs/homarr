# Prove Homarr’s lightweight migration before committing

**Homarr should test Vite + Nitro through a capability-preserving experiment, not approve a wholesale rewrite or select a lowest-RAM framework from this research.** The proposed first control is a single, non-cluster Node Nitro server using explicit request/auth adapters and existing domain services; retaining tRPC, Redis and Drizzle here isolates hosting and rendering changes, but does **not** satisfy the requested final removal of Next.js/tRPC or establish an approved final service architecture. Editable dashboards should be rendered at runtime and internally cached by revision, with authorized widget-cache reads and a coherent hydration snapshot; build-time prerendering cannot regenerate arbitrary edited boards without a build. Compare H3, Hono and Elysia under the same Nitro-managed HTTP boundary on Node and Bun only after correctness gates pass, then measure service-removal and topology changes separately. No notes contain measured Homarr RAM, image-size, speed or DX results, and no numerical performance targets have been approved. The immediate human decisions are workload/budget definitions, first-paint and freshness semantics, supported deployment concurrency, exact version pins and the bounded prototype scope. ([Runtime evidence](../research_notes/Homarr%20Nitro%20migration%20experiment/nitro-runtime.md), [Rendering evidence](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md), [Measurement design](../research_notes/Homarr%20Nitro%20migration%20experiment/performance-packaging.md))

**Evidence and authority.** This report synthesizes only the five supplied research notes, inspected on October 10, 2026 against checkout `66e2199f9cd1e4026249c3763413988bab8664c4`; it performs no new research, implementation or measurement. “Fact” means documented or source-inspected behavior, not demonstrated Homarr compatibility. “Recommendation” and “proposal” are experimental choices awaiting approval. User-approved constraints are retaining capabilities and durable data, eventual Next.js/tRPC removal, service replacement where parity is achievable, editable runtime-cached dashboards populated from widget caches, one small-container default and optional frontend/backend separation. GitHub Pages is outside scope. The [live experiment project](https://linear.app/ajnart/project/homarr-nitro-migration-experiment-815a2cca8c5c) and [Find the route to a lightweight Nitro Homarr](https://linear.app/ajnart/issue/AJN-482) are the canonical work/decision map; this report is synthesis, and the notes are evidence, not a second decision store.

## Pin the runtime before choosing an API framework

**The current production baseline is Node, already embedding HTTP, jobs and WebSockets in one application process.** Bun 1.4.2 performs installation/build work, whereas the runner starts Node 24.18.0 and ships an Alpine 3.24.2 image containing nginx, optional internal Redis, native SQLite support, CLI/migrations and assets. nginx fronts HTTP on port 7575 and forwards WebSocket upgrades to port 3001; embedded jobs and that listener do not imply separate steady-state JavaScript services. The architecture reference’s Bun-production sentence conflicts with executable sources and should not define the baseline. Removing nginx, Redis or a listener is therefore a topology/lifecycle experiment, not automatically a Nitro or router saving. ([Packaging baseline](../research_notes/Homarr%20Nitro%20migration%20experiment/performance-packaging.md), [Dockerfile](../Dockerfile), [Launcher](../scripts/run.sh), [Instrumentation](../apps/nextjs/src/instrumentation-node.ts))

Nitro is the server build/deployment/runtime layer; Vite supplies frontend tooling and low-level SSR integration. **Neither supplies a complete replacement for Next App Router, Homarr authorization or dashboard rendering.** Nitro v3’s Vite integration documents frontend HMR, isolated server-worker reloads, an SSR entry and combined `.output` builds. Homarr still needs routing/loaders, safe bootstrap data, React rendering/hydration, metadata, fonts/images, locale/RTL, navigation/error boundaries and security headers. Experimental Nitro RSC examples establish an avenue to investigate, not Next-compatible RSC behavior. Equivalent capabilities with a different rendering model remain possible, but choosing CSR, SSR or islands is a human architecture decision. ([Nitro Vite](https://nitro.build/docs/vite), [Vite SSR](https://vite.dev/guide/ssr.html), [API/frontend inventory](../research_notes/Homarr%20Nitro%20migration%20experiment/api-auth-migration.md))

### Compare transport contracts, not framework labels

H3, Hono and compiled Elysia can expose Fetch handlers under Nitro. **A nested Hono/Elysia application does not remove Nitro’s outer H3 lifecycle**, and its server entry only catches unmatched routes: security middleware placed solely there misses separately matched Nitro routes. Its own 404 response also terminates processing rather than falling through to the frontend renderer. Partition route ownership explicitly and enforce global security at a proven outer boundary. Standalone Elysia Node `.listen()` instructions are not the Nitro mounting recipe; Nitro owns the listener. Native upgrades, adapter bindings and plugins need independent validation. ([Server-entry lifecycle](https://nitro.build/docs/server-entry), [Beta application generator](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/src/build/virtual/app.ts), [Tagged Elysia entry](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/examples/elysia/server.ts))

| Candidate contract | Demonstrated/documented advantage | What Homarr still must supply |
| --- | --- | --- |
| Native Nitro/H3 | Least additional router layering; Standard Schema runtime validation; Web Request/Response handlers | Explicit browser API contract, service authorization, serialization/errors, Query lifecycle and event schemas; typed handlers alone are not end-to-end validated RPC. |
| Hono RPC | `hc<typeof routes>` infers validated request and response/status contracts; reusable Zod schemas | Chained inference, matched versions, global-error typing, large-graph IDE/typecheck cost, stream/subscription lifecycle and existing rich-value serialization. |
| Elysia/Eden | Inferred application contracts, Standard Schema support and typed WebSocket subscriptions | Nitro-mounted Node/Bun plugin/upgrade parity, permissions, cancellation/backpressure and event compatibility; native Bun fast paths are not guaranteed here. |
| Curated OpenAPI client | Framework-independent public HTTP contract; generated request/response types | Accurate runtime schemas, security execution, multipart/binary/stream contracts and an intentional MCP catalog. Nitro metadata does not inspect nested router registries automatically. |
| Temporary tRPC control | Official Fetch-adapter mounting shape; reuses current procedures, SuperJSON, metadata and clients | Next-free context/auth and stream hosting. This is an isolation control to remove later, not the final replacement choice. |

These distinctions follow [H3 validation](https://h3.dev/examples/validate-data), [Hono RPC](https://hono.dev/docs/guides/rpc), [Eden WebSockets](https://elysiajs.com/eden/treaty/websocket.html), [Nitro OpenAPI](https://nitro.build/docs/openapi), [openapi-fetch](https://openapi-ts.dev/openapi-fetch/), [Nitro tRPC example](https://nitro.build/examples/vite-trpc), and the [contract comparison](../research_notes/Homarr%20Nitro%20migration%20experiment/api-auth-migration.md). **Recommendation:** use native Nitro/H3 as the minimal hosting control; choose Hono or Eden for a demonstrated type-contract/DX benefit, not an unmeasured memory promise. Replacing tRPC requires transport-independent, authorization-enforcing services and an explicit replacement for its batching, FormData path, SSE/WS subscriptions, errors, transforms and curated MCP dispatch.

## Cache runtime-rendered boards without caching authority

**Build-time prerendering is the wrong canonical mechanism for mutable boards.** Nitro writes prerendered routes to built public assets; current routing docs say prerender wins over ISR and does not runtime-revalidate those files. A static application scaffold is useful, but an empty CSR root does not satisfy board-specific already-rendered HTML. The recommended experimental mechanism is a plain authorized handler calling a revision-keyed cached React render function; board creation/editing updates database inputs and makes a new render generation reachable without compiling application code. Function caching is preferable to whole-response caching because invalidation and authorization remain explicit; cache-handler wrappers narrow headers/cookies/query inputs and cannot infer Homarr sessions or ACL changes. ([Nitro routing](https://nitro.build/docs/routing), [Cache mechanisms](https://nitro.build/docs/cache), [Rendering analysis](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md))

Homarr already restores Redis-backed widget query snapshots, starts fresh prefetches and dehydrates a request Query client, but still renders the React board tree per request: **query-cache reuse is not stored HTML reuse**. Existing snapshots have a three-day maximum age, a 50 ms restore budget and a 512 KiB cap; restored `dataUpdatedAt` is reset to now, so it cannot certify observation freshness. Their fingerprint covers widget IDs/kinds/integrations/options, not the complete layout, theme, locale or document. Preserve current generation checks and query-input selection rather than assuming all widget data shares one universal cache DTO. These existing constants are implementation facts, not product freshness or resource targets. ([Board creator](../apps/nextjs/src/app/%5Blocale%5D/boards/%28content%29/_creator.tsx), [Query snapshot](../apps/nextjs/src/app/%5Blocale%5D/boards/%28content%29/_query-snapshot.ts), [Widget prefetch](../packages/widgets/src/server-prefetch.ts))

### First-paint semantics determine the cache artifact

Keep compiled assets, board HTML and widget result caches separate. **React’s initial hydration tree and data must match the server artifact.** Replacing cached markup’s data with a newer bootstrap snapshot without rerendering its matching boundaries violates this contract. Full hydration still requires the rendered React/Mantine/widget client logic; “prerendered” does not mean zero JavaScript. Dynamic editor loading already exists, while Custom JSX is currently explicitly client-only and charts retain interactive behavior; screenshots are not capability-equivalent replacements. ([React hydration](https://react.dev/reference/react-dom/client/hydrateRoot), [Existing editor boundary](../apps/nextjs/src/components/board/sections/grid/board-grid-editor-boundary.tsx), [Custom Widget component](../packages/widgets/src/custom-api/component.tsx), [Rendering evidence](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md))

| Proposal | Initial artifact and refresh | Requirement tradeoff |
| --- | --- | --- |
| Stable shell + client fill | Cache deterministic board framing/placeholders and matching props; hydrate those, then read authorized backend widget caches | Simplest decoupling, but widget values are absent from first HTML paint. Needs explicit approval if “populated” means first response. |
| Populated coherent snapshot | Cache HTML with exactly the data, observation/time/locale basis and bootstrap used to render it; refresh after matching hydration | Meets cached-value first paint, with declared stale-display policy and additional bootstrap bytes. Recommended first-paint experiment if that meaning is required. |
| Shell + request-time fragments | Reuse framing, authorize/read current widget caches, render fragments with matching bootstrap and intentional React ownership | Fresh cached values at response time, but additional render work and provider/island complexity. Investigate if coherent-snapshot staleness is unacceptable. |

All three are application proposals grounded in [Nitro’s React example](https://nitro.build/examples/vite-ssr-react), [renderer facilities](https://nitro.build/docs/renderer) and [React’s matching-state requirement](https://react.dev/reference/react-dom/client/hydrateRoot), not turnkey Homarr modes. The prototype should compare the selected populated experience with the current useful-board baseline; shell-only timing can be a diagnostic, not a substitute for useful widget data. Full-root hydration versus islands requires an explicit provider/context/portal/focus design and installed-version widget audit, including responsive charts, clocks, time zones, browser storage and the transition into edit mode.

### Every cache delivery needs current access checks

**Authorize before every HTML, bootstrap and widget-cache delivery, including hits.** Current board DTOs contain creator identity including email, viewer-filtered permission data and personalized section collapse state, while home selection and initial geometry depend on user/device/viewport inputs. Board ID alone cannot safely key this document. Construct a sanitized shared projection and a separately authorized personalized overlay, or partition actual personalized variants deliberately; never cache a session as board authority. Preserve public-board integration reads without exposing credentials and existing NOT_FOUND denial semantics. ([Board authorization](../packages/api/src/router/board/board-access.ts), [Board query/mutations](../packages/api/src/router/board.ts), [Layout normalization](../apps/nextjs/src/app/%5Blocale%5D/boards/_layout-creator.tsx), [Rendering security analysis](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md))

**Proposed render identity** comprises instance namespace/immutable board ID, transactional render revision, sanitized projection/ACL epoch, locale/RTL/formatting basis, branding/theme/custom CSS revision, normalized layout/viewport and any retained viewer preferences, build/render-schema/definition versions, and widget snapshot/generations only when values appear in HTML. Each dimension can instead be moved outside the shared artifact, but it cannot silently disappear. A successful rendering-affecting mutation commits data and revision together, returns the revision and optionally warms the new artifact; an old in-flight render becomes unreachable. Inventory all mutations, including placement/layout/settings/rename/delete, branding and custom-definition/source changes—not just `saveBoard`. Permission changes must stop delivery through current authorization independently of TTL, SWR or delayed purge; ACL epochs supplement, not replace, that check. ([Revision/key proposal](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md), [Integration authorization](../packages/api/src/middlewares/integration.ts))

Set explicit downstream `private, no-store` where private/personalized documents require it, while using an internal render-function cache. Suppressing Nitro’s generated cache-control headers is not itself `no-store`, and stale authorization responses are unacceptable. Bound render-cache entries/bytes, variant cardinality, TTL/stale retention and warmup work explicitly against the chosen released implementation. Define edit visibility across tabs, outage fallback and stale labeling: existing optimistic local edits do not automatically push a new revision to all viewers. Escaped serialized data and capability-filtered controls must accompany the artifact, preserving keyboard/focus, loading/error feedback, refresh/actions and view-to-edit behavior. ([Nitro cache policy](https://nitro.build/docs/cache), [Released cache evidence](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md), [Board state](../packages/boards/src/context.tsx))

## Replace hosting first, then prove state and capability parity

**Nitro abstractions do not replace real storage engines or coordination semantics.** Today SQLite through `better-sqlite3` and external PostgreSQL through `pg.Pool` provide relational storage; Drizzle supplies query/schema/migration integration. `nitro/database` uses experimental db0 connectors that still select an actual SQLite/PostgreSQL or other engine. Published db0 PostgreSQL uses a lazy `pg.Client`, not the current pool; its Drizzle integration targets v1/RC instead of Homarr `0.45.2`, and inspected asynchronous transaction implementations raise an unresolved shared-connection interleaving risk. Promise-shaped access does not establish nonblocking execution or concurrent transaction isolation. Keeping direct drivers initially is a proposed control; replacing Drizzle/db0/engines remains a deliberate unresolved tradeoff, not a requirement automatically fulfilled by choosing Nitro. ([Storage findings](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md), [Published PostgreSQL connector](https://unpkg.com/db0@0.4.1/dist/connectors/postgresql.mjs), [db0 Drizzle constraints](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/3.integrations/drizzle.md))

Unstorage KV selects memory/filesystem/Redis or another backend; its generic API does not supply SQL transactions or Redis NX leases, Lua owner-fenced writes, counters, CAS, lists and pub/sub. The published filesystem driver ignores TTL options, while default memory disappears on restart. A Redis-backed Nitro cache still runs a Redis engine, and ocache’s local single-flight Map is not distributed refresh exclusion. Croner still schedules time-based work; Nitro’s experimental task wrapper does not recreate DB-editable schedules, persisted execution recovery or Homarr status publishing. CrossWS provides upgrades/topics and optional sync adapters, not application permissions, histories or the tRPC protocol. ([Published filesystem driver](https://unpkg.com/unstorage@2.0.0-alpha.10/dist/drivers/fs.mjs), [Published ocache](https://unpkg.com/ocache@0.3.0/dist/index.mjs), [Nitro tasks](https://nitro.build/docs/tasks), [CrossWS sync](https://unpkg.com/crossws@0.4.15/dist/sync.mjs))

### Service removal must preserve lifetimes and atomic boundaries

Redis currently covers more than disposable responses: encrypted integration sessions and image mappings, statistics, log/sample history and latest task state, preview/configuration handoffs, security rate/concurrency controls, generations and fenced refresh ownership. Internal RDB persistence uses `save 60 1`, not every-write AOF durability; app-only restart leaves Redis alive, unlike whole-container failure. The SQL backup excludes Redis. Therefore preservation means explicitly matching or improving each required lifetime, including approved cold-start exceptions—not assuming all Redis state can vanish because it is called cache. ([Redis duty inventory](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md), [Redis configuration](../packages/redis/redis.conf), [Backup contract](../apps/docs/docs/management/backup.mdx))

| Responsibility | Proposed staged control | Conditional replacement and proof |
| --- | --- | --- |
| Relational data/transactions | Existing schemas, Drizzle drivers and dialect/custom migrations at existing absolute paths | Alternate ORM/driver must preserve IDs, relations, encodings, transaction isolation, SQLite locking and PostgreSQL behavior; engine replacement additionally needs an explicit data conversion. |
| Disposable response/render caches | Existing bounded L1 plus a separately bounded render cache | Explicitly keyed/serialized cache with freshness, cancellation, limits and stale-write fencing; cold-start only state approved as disposable. |
| Restart-surviving Redis state | Retain Redis while classifying lifetimes | SQL-backed encrypted state/history with retention/expiry/revisions; convert remaining TTLs and reconcile ownership under quiescence. Validate restart/crash loss boundaries. |
| Atomic limits/claims/generations | Existing Redis Lua/NX/token controls | Transaction-safe SQL adapters and application-owned guards; persist security windows where required and fence late writes with restart-safe epochs. One process still has concurrent requests. |
| Scheduling/lifecycle | Embedded Croner/JobManager, explicit startup/readiness/close ownership | Preserve DB controls, startup failures, manual runs/status and shutdown cleanup; choose overlap/recovery policy rather than inventing exactly-once guarantees. |
| Live transport/fanout | Current protocol and authorized stream services | CrossWS/SSE or another transport with coordinated client conversion, bounded queues, replay rules, heartbeat/reconnect and abort cleanup; shared coordinator if replicas remain supported. |

These are proposals, not conversions performed or final architecture choices. ([Replacement analysis](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md)) **Redis-free is plausible only after an explicit state/coordination design.** A strict singleton contract would permit local fanout and keyed guards, with durable transactional state retained in SQLite/PostgreSQL. Cluster workers, rolling replicas, external operational writers or split backend authorities invalidate purely local coordination. Published CrossWS 0.4.15 can synchronize through Redis/PostgreSQL/IPC, contradicting a blanket “no cross-process support” claim, but Nitro’s inspected presets do not automatically wire that sync from KV storage and it does not supply durable replay. ([CrossWS implementation](https://unpkg.com/crossws@0.4.15/dist/sync.mjs), [Topology conditions](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md))

Keep `/appdata`, migration ordering, encryption material and existing external PostgreSQL/Redis deployment contracts while evaluating replacements. Backup/key conversion needs special scrutiny: examined import re-encryption covers integration secrets, but does not establish complete conversion of Assistant and Custom Widget encrypted families. A copied DB file alone is not proof of full durable continuity. ## Measure comparable systems before naming a footprint winner

**There is no measured lowest-RAM, smallest-image or fastest Homarr candidate.** Framework-author minimal bundle/plaintext/router benchmarks address different boundaries and runtimes; they cannot rank a dashboard with SQL, Redis, native bindings, jobs, streams and browser interaction. Node `heapUsed` is not RSS or total container memory, and Bun JSC heap counters are not V8 counters. The current Next baseline already ships traced standalone dependencies, not a full development install. A meaningful experiment must separate framework, runtime, rendering, driver and topology effects. ([Measurement limits](../research_notes/Homarr%20Nitro%20migration%20experiment/performance-packaging.md), [Node memory semantics](https://nodejs.org/api/process.html#processmemoryusage), [Bun 1.4.2 compatibility](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/runtime/nodejs-compat.mdx), [Baseline assembly](../apps/nextjs/scripts/assemble-standalone.mjs))

### Use a six-cell matrix with fail-closed eligibility

| Tier | Comparison | Claim boundary |
| --- | --- | --- |
| Shipping reference | Current Next + Node 24.18.0, nginx and configured Redis | Whole-system user-visible baseline; preserve current flags/capabilities. |
| Primary matrix | Nitro + H3/Hono/Elysia on Node 24.18.0 and Bun 1.4.2 | Same frontend, services, fixtures, DB/cache/topology and Nitro-managed Fetch ownership. Use documented Node/Bun production presets; failing capability cells are incomplete/unsupported, not performance losers. |
| Runtime isolation | Same Node-preset output run on Node and Bun, if compatible | Separates runtime execution from Bun-preset optimizations; native dependencies still gate eligibility. |

### Provisional migration stages isolate causes and preserve rollback

**Proposal:** first extract explicit request/cookie/auth/origin/locale/query-execution adapters and authorization-enforcing domain services, with safe client/server entrypoints so Vite cannot import secrets, databases or Next transitively. Then host compatible HTTP/protocol adapters under Nitro, retaining stable paths and one external origin; move frontend routes and the chosen cached-dashboard renderer against the same services. Keeping tRPC/Redis/Drizzle during these stages is an experimental control with a recorded exit condition. A temporary dual backend behind one proxy is a rollout option, not the final small-container footprint and not a reduction to claim. ([Adapter sequence](../research_notes/Homarr%20Nitro%20migration%20experiment/api-auth-migration.md))

Next replace tRPC bounded-context by bounded-context through the selected validated contract and client adapter, preserving authoritative schemas, errors/serialization, authorization, mutation invalidations, subscriptions and separately curated MCP dispatch. Once client/server/protocol coverage is complete, retire the old transport rather than leaving “compatibility” as indefinite fulfilment. Consolidate listeners/lifecycle and evaluate nginx replacement independently. Convert Redis duties only after their atomicity/lifetime contracts and singleton/shared-coordinator decision are approved; evaluate ORM/driver replacement and Bun separately, with data/transaction/native parity. Nothing requires deleting a real SQLite/PostgreSQL engine to satisfy a lightweight server goal, and replacing Drizzle with db0 does not remove that engine. ([Contract migration](../research_notes/Homarr%20Nitro%20migration%20experiment/api-auth-migration.md), [State conversion sequence](../research_notes/Homarr%20Nitro%20migration%20experiment/storage-background.md))

A one-container target can contain one Nitro application authority plus any deliberately retained auxiliaries, serving immutable frontend assets, runtime HTML, APIs and live connections while persisting data in `/appdata` or existing external services. Optional frontend/backend separation should preserve a same-origin public boundary, build/bootstrap compatibility, forwarded URL trust, authenticated internal calls and exactly one scheduler/state authority. Static Vite files alone cannot produce the proposed runtime-populated HTML; the backend or a separately owned SSR service still renders it. Count duplicated runtimes/base layers and required external resources rather than assuming separation saves footprint. ([Deployment/render separation](../research_notes/Homarr%20Nitro%20migration%20experiment/dashboard-rendering.md), [Topology cost accounting](../research_notes/Homarr%20Nitro%20migration%20experiment/performance-packaging.md))

### Final removal is an artifact and behavior proof

**Next/tRPC removal is complete only when the final supported production graph and behavior no longer depend on either.** Inventory direct and transitive runtime/build dependencies, source imports, workspace exports, startup commands and generated/traced output; prove the shipped app, SSR renderer, browser chunks, CLI and subscriptions/MCP dispatch contain no Next server/client or tRPC transport/caller dependencies. Remove obsolete routes/providers/listeners/config only after all replacement callers are mapped; check that bootstrap/media/streaming/error paths do not secretly route back to an old service. A dependency grep is necessary evidence, not sufficient behavioral proof. The current mixed-entrypoint/transitive risks are concrete in `@homarr/common/server`, API shared SSR cookies and auth exports. ([Entrypoint risks](../research_notes/Homarr%20Nitro%20migration%20experiment/api-auth-migration.md), [Common server export](../packages/common/src/server.ts), [API shared transport](../packages/api/src/shared.ts))

Execute the complete capability ledger against both supported database modes and native platform/runtime cells, using equivalent public/API/MCP behavior, stream cancellation/reconnect and security-negative cases. Demonstrate upgrade from a copied representative durable dataset, every encrypted family and backup/restore boundary, creation/editing without application build, revocation on cache hits, app-only/container restart and agreed crash recovery. Document whether rollback can safely read post-migration data; use a quiesced backup or an explicit compatible rollback route rather than allowing competing schema writers. For each proposed Redis/ORM/nginx removal, additionally prove its production artifact/process/connection absence and the replacement lifetime/atomicity/operational contract—or record the deliberately retained dependency as an unresolved final tradeoff. Only eligible independent measurements can establish that the resulting complete deployment meets approved budgets.

## Conclusion

The useful architectural distinction is **compiled application code versus mutable authorized data**, not static versus dynamic hosting. A runtime-rendered, revision-addressed board can remain cheap to reuse while edits stay durable data operations; security and freshness must remain outside any assumption that a cached artifact is authoritative. That separation is the experiment’s strongest actionable result even if a later benchmark rejects Nitro, Bun or a particular router.

The final choice should follow the evidence’s ability to isolate causes: a faster empty shell, externalized Redis or native plaintext endpoint cannot justify a capability-preserving migration. Approving budgets and the first-paint/state contracts now makes the later prototype falsifiable; approving a framework or “smallest container” claim now would merely turn the unresolved compatibility and version risks into implementation debt.
