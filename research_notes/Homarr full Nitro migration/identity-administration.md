# Production identity and administration preservation

Research for [AJN-511](https://linear.app/ajnart/issue/AJN-511/map-production-identity-and-administration-preservation), under [AJN-482](https://linear.app/ajnart/issue/AJN-482/find-the-route-to-a-lightweight-nitro-homarr). Inspected October 10, 2026. **Recommendations, not architecture approval or demonstrated production parity.**

## Conclusion

Production authentication is a bounded migration lane, not the whole rewrite. Preserve Homarr's identity records, password/key verifiers, group and resource policy, settings and administration independently of the framework hosting login. Dashboard, widget and provider workers can proceed against explicit principal/policy/secret contracts; they do not need a finished OIDC callback or an unsafe permissive authentication substitute.

Auth.js Core is already installed and has a genuine Fetch `Request → Response` boundary. The blocker to copying today's configuration is **Homarr's custom credentials/LDAP database-session bridge**, including Next cookie writes and JWT overrides—not absence of an Auth.js Fetch API. Evaluate a bounded Core integration first; retain a deliberate custom credentials-session boundary as an alternative. Do not select Better Auth or another replacement just because Auth.js's current website mentions it. No replacement library has been shown to preserve this ledger.

Never cache a private response using only board ID. |

## 2. What is actually framework-neutral?

**Preserve behavior in existing owning packages, not necessarily today's barrel exports.**

- Identity tables and relationships: user IDs/primary provider/password/preferences; account compound provider identity/tokens; opaque session token/expiry; API-key ID/hash/user; invite token/expiry/creator; group ownership/order/default homes; group membership and explicit grants; board/integration per-user/per-group grants. Keep deletion semantics (identity-linked credentials/session/key rows cascade; owned resource semantics differ). SQLite and PostgreSQL have different timestamp/default representations; e.g. new-user `openSearchInNewTab` defaults are true in SQLite and false in PostgreSQL source. Do not normalize historical data accidentally. [SQLite](../../packages/db/schema/sqlite.ts), [PostgreSQL](../../packages/db/schema/postgresql.ts).
- Reusable algorithms/services: bcrypt verifiers, secure random tokens, expiry arithmetic, provider-scoped lookup/linking guard, profile-path extraction, LDAP bind/search/filter logic, external group reconciliation, permission inheritance/matrix/presets, board/integration constructors, principal-filtered DB permission loading, user/settings merge and validation, onboarding claim hashing and CAS, PKCE and OAuth ephemeral store.
- Adapter work within those: callbacks currently typed as `NextAuthConfig` callbacks, permissions/session helpers typed `next-auth.Session`, environment configuration imported as singletons, LDAP client construction, trusted origin parameters, theme cookies, request-local side effects, tRPC-domain error mapping and dependency-light server entrypoints. These should accept explicit dependencies and use Core types or Homarr-owned principal types where appropriate.
- Next-only replacements: `createConfiguration` calling `NextAuth`, `auth` RSC cache wrapper, `createHandlersAsync` implicit headers, request origin rewriting with `NextRequest`, direct Next cookie writes, RSC header/settings/user memoization, page/layout guards/metadata/revalidate, `next/navigation` login/error routing. `next-auth/react` is a separate compatibility candidate, not evidence that server NextAuth can remain in Nitro's graph.
- The `@homarr/common/server` barrel reexports `request.ts`, which imports Next `userAgent`; auth/security reuse through that barrel is not a clean graph guarantee. Split entrypoints at the owner rather than copying helper code into the new app. [Auth exports](../../packages/auth/index.ts), [common server](../../packages/common/src/server.ts), [common request](../../packages/common/src/request.ts), [RSC context](../../packages/api/src/rsc-context.ts).
- Deployment auth config names and documented defaults are preserved input contracts: provider selection/cookie prefix/session lifetime/logout redirect; OIDC issuer/client/name/scope/group/name paths/local-management/force-userinfo/auto-login/linking/token-auth settings; LDAP bind/search/attribute/filter settings. Public login projection only needs enabled buttons/display/auto-login and reviewed redirect behavior, never credentials. [SSO configuration docs](../../apps/docs/docs/advanced/single-sign-on/index.mdx). No real environment or secret was read here.

## 3. Auth.js Core candidate, exact source validation and alternatives

### Confirmed by installed and current official source

1. `Auth(request, config)` is publicly exported, accepts Web Request and returns Web Response. `raw` is a separate overload returning internal response metadata. Core exports `customFetch`. Official source explicitly permits direct use but labels Core experimental/actively developed. [Installed entrypoint](../../node_modules/@auth/core/src/index.ts#L73), [pinned upstream entrypoint](https://github.com/nextauthjs/next-auth/blob/a1a16a5a7780488c7449feece410033f445d0b31/packages/core/src/index.ts).
2. Core defaults the endpoint base to `/auth`; NextAuth supplies `/api/auth` plus its environment/Next URL integration. A direct port must explicitly configure the existing base path, secret/origin and provider-scoped adapter instead of assuming NextAuth's defaults survive. Missing secret or unsafe untrusted host fails configuration. Secret sourcing is a dependency supplied by the existing validated server configuration; no secret value was examined. [Core request parsing](../../node_modules/@auth/core/src/lib/utils/web.ts#L27), [NextAuth integration source](../../node_modules/next-auth/src/lib/env.ts), [Core assertion](../../node_modules/@auth/core/src/lib/utils/assert.ts).
3. Database sessions are supported for OAuth/OIDC. Core invokes adapter methods, expires/deletes invalid sessions, renews cookies, runs session callback and deletes DB session on logout. Homarr's custom schema can be passed to Drizzle adapter; it is not obliged to accept upstream default unique-email schema. The custom provider-scoped email method remains necessary. [Core session/signout](../../node_modules/@auth/core/src/lib/actions/session.ts), [installed adapter](../../node_modules/@auth/drizzle-adapter/lib/sqlite.js), [Homarr adapter](../../packages/auth/adapter.ts).
4. Credentials documentation explicitly limits sessions to JWT and does not persist credentials users automatically. Installed/current callback **always uses JWT callback/encode/chunk** for credentials after `signIn`, even with a database strategy. Config assertion rejects database+credentials-only; adding the placeholder avoids that assertion, not the callback's JWT branch. This explains Homarr's empty provider and custom encode/session callback bridge exactly. [Installed credential callback](../../node_modules/@auth/core/src/lib/actions/callback/index.ts#L325), [current pinned callback](https://github.com/nextauthjs/next-auth/blob/a1a16a5a7780488c7449feece410033f445d0b31/packages/core/src/lib/actions/callback/index.ts), [current credentials source](https://github.com/nextauthjs/next-auth/blob/a1a16a5a7780488c7449feece410033f445d0b31/packages/core/src/providers/credentials.ts), [current assertion](https://github.com/nextauthjs/next-auth/blob/a1a16a5a7780488c7449feece410033f445d0b31/packages/core/src/lib/utils/assert.ts).
5. Core `toResponse` appends each Set-Cookie and preserves Location/status. Core handles `X-Auth-Return-Redirect` as JSON `{url}`; errors redirect to configured auth/error pages, expose client-safe codes, and POST session CSRF failure returns 400/null. Fetch integration must preserve these effects, not merely return `response.json()`. [Installed Web adapter](../../node_modules/@auth/core/src/lib/utils/web.ts#L74), [installed entrypoint](../../node_modules/@auth/core/src/index.ts#L161).
6. OAuth defaults include PKCE; redirect proxy adds state. OIDC supports the provider `customFetch` symbol. No Next import is required for these Core features. The existence of state/nonce cookie names does not justify silently changing configured checks. [Core provider normalization](../../node_modules/@auth/core/src/lib/utils/providers.ts#L78), [Homarr OIDC](../../packages/auth/providers/oidc/oidc-provider.ts).

### Candidate comparison / recommendation

| Candidate | Why supported / reuse | Work and conditions |
| --- | --- | --- |
| A. Direct Core Fetch + explicitly maintained credentials database bridge | Smallest dependency/policy/data change; existing Core, Drizzle adapter, providers, cookies and DB sessions retained. Exact callback sequence is understood from source. | Build configuration per request; generate DB session in credentials sign-in callback; carry new token in a **request-local closure**, not by rereading incoming cookies or using a shared variable; emit/merge cookies once and make JWT encode return that request's newly created token. Post-login effects must have outgoing-cookie access. Audit failures after session creation, cookie duplication and cleanup. Placeholder/encode workaround remains nonstandard and release-sensitive: no promise of upstream support. |
| B. Core handles OIDC; Homarr credentials/LDAP login establishes the same opaque DB sessions through its own bounded auth service | Avoids using the unsupported Credentials database-session branch while reusing Core OIDC verification/linking/session machinery and existing password/LDAP policy. Doesn't require an entirely new auth library. | Own explicit CSRF/origin validation, rate limiting/error protocol, cookie/session creation/logout/renewal adapter and consistent shared session reader. Must preserve login client behavior and configurations; don't import private Core CSRF functions or set `skipCSRFCheck` for untrusted browser requests. One cookie/DB-session authority, not separate stores by provider. Requires focused security review. |
| C. Replace auth stack | Allowed by rewrite scope if proven to preserve capabilities/data. Could eliminate the custom bridge. | No candidate was evaluated here against equivalent provider-scoped linking, legacy bcrypt/key hashes, LDAP/local groups, DB sessions, cookie/session lifecycle, trusted Fetch and current client/MCP semantics. An advertised Drizzle/OIDC plugin is not proof. Requires a named, version-pinned candidate and separate source-backed migration/rollback plan before selection. |

**Recommended next decision:** authorize a bounded source-to-Fetch integration design/spike for A against the pinned Core release, with B as an explicitly reviewed escape hatch if the bridge cannot be made reliable. Do not block unrelated full-product work behind that spike. Neither a spike nor this note authorizes real IdP/LDAP calls or production credential access. Do not silently convert to stateless JWTs: current DB revocation and CLI behavior are part of preservation.

## 4. Minimal shared interfaces to unblock parallel work

These are **proposed contracts**, not implementations or approved package names. Keep them independent of Next, Auth.js, tRPC and oRPC. Endpoint worker maps errors/headers/protocols; identity owner resolves identity; resource owners enforce policy. Never trust permission arrays or user IDs supplied by browser input.

### Principal and request context

- `Principal = anonymous | authenticated`. Authenticated contains immutable `userId`, current expanded `GroupPermissionKey[]`, authentication provenance (`cookie-session` or `api-key`), server-only credential reference, and optional real DB session expiration. Primary account provider can be a separate profile field; a linked OIDC login must not rewrite primary credentials ownership. UI Session is a **projection**, not a token or proof.
- `RequestContext`: principal, injected DB/repository handle, trusted public origin, device class, validated locale, request/abort identifier, operation kind/read-versus-mutation and demo-read-only mode. Carry an onboarding claim as a separate optional validated setup capability, not as `admin` in the principal. Never serialize repository handles, claim token or credential reference into bootstrap.
- `resolveIdentity(request, mode, effects)` supports explicit surface mode: browser/render cookie; browser-RPC current ApiKey→cookie precedence; external-REST ApiKey only; MCP ApiKey/Bearer only; live-cookie reader. Return principal plus expiry/renewal/revocation cookie effects; resolve permissions from DB, not an indefinitely cached token snapshot. Clock injection permits later disposable expiry proof without production probes.
- `ClientSessionSnapshot`: status (`anonymous/authenticated/loading/error`), safe user ID/name/email/image/theme, effective permission keys, optional real expiration, opaque authorization/cache epoch if designed, public login/logout navigation data. Session refresh broadcasts a change event; dashboard/Query workers invalidate or mask private artifacts before rendering a different principal. Additional epoch is proposed, not an existing schema column.
- `ResponseEffects`: request-local cookie read/write/delete and response-header append interface. It must merge Core-issued and Homarr-issued effects with correct path/security/expiry/Set-Cookie behavior, including direct SSR service calls. Never use module-global mutable cookie/session state or duplicate auth singletons between SSR/API bundles.

### Authorization contract

Provide explicit deny-by-default operations, preserving denial vocabulary:

- `requireAuthenticated`, `requireGlobalPermission(key)`, `authorizeSelfOrAdmin(targetId, denialMode)`, `requireOnboardingStep(step)` and `enforceMutationMode`.
- `authorizeBoard(boardId, view|modify|full)` loads evidence filtered to current user/group membership, handles creator/public/global grants, and throws resource-masked not-found.
- `authorizeIntegrationQuery(ids, allowedKinds)` loads filtered integration grants and visible-board placement evidence for **every** requested integration. `authorizeIntegrationInteract` and `authorizeIntegrationFull` are different operations. Empty/missing/foreign-kind/bulk-selector behavior must be specified, not inferred from successful one-ID reads.
- Keep app/search/media and Custom JSX/Assistant/thread/preview/configuration-token ownership guards in owning bounded services. A middleware `authenticated` result cannot substitute for them.
- `AuthorizationDecision = allow | deny(unauthenticated|forbidden|not-found|invalid-claim|wrong-step|demo-read-only)`; public external messages can intentionally differ by surface, mapped by endpoint/UI adapters. Constructors require **principal-scoped evidence**; do not accept all ACL rows and hope the boolean constructor filters them.
- Client capability hints (`canCreate`, `canManageAll`, delegated full access, local/mixed/external membership controls, per-board/per-integration booleans) are presentation-only. Server enforces again on writes, reads, secret access and live delivery. Admin implies global grants via existing expansion, not a bypass around demo/step/secret-destination restrictions.

### Secret and settings contract

- `PasswordVerifier.hash/compare` and `ApiKeyVerifier.resolve` reuse bcrypt and preserve historical hashes. Separate irreversible verifiers from reversible application secrets. Key issue/revoke has explicit actor/current creator and safe one-time token response; no accidental API-key creation exposure through generic MCP generation.
- `SecretStore` separates safe metadata projection from server-only resolve/replace/clear. Resolution requires a prior resource-policy decision for the **same** principal/resource/action plus source/destination/network binding. Result remains inside server provider execution; there is no browser/MCP endpoint returning a generic plaintext map. Existing public-field exceptions remain explicit.
- Prefer `withAuthorizedIntegration(context, selector, action, allowedKinds, execute)` composing selection → current filtered policy → decrypt → provider execution → sanitized result, so widget/provider workers cannot accidentally reorder checks. Equivalent configuration-scoped operations protect Assistant and Custom Widget secrets. A query-level integration permission never authorizes arbitrary upstream path/method execution.
- `SettingsService.publicSnapshot` returns only current public fields (culture/branding and the root's selected board/search/Gravatar defaults); `userSnapshot` requires current user/self-admin policy; `adminRead/write` requires admin and family-specific validation. Private claim rows/internal state remain excluded. Preserve versioned header/branding parsers and SuperJSON encoding until persistence owner deliberately migrates them.

**Safe parallel behavior before login is finished:** use controlled, explicitly injected principals only in disposable fixtures, exercised through real production policy functions or deny-by-default adapters. Production-mounted protected routes remain unavailable/deny until the real resolver is connected. No `return true`, fake-admin default, browser-selected production user ID, decrypted-secret bootstrap or shared fixtureauth session is an acceptable intermediate implementation.

## 5. Coverage reconciliation, risks and human decisions

Source contradictions below are **not executed exploit claims** and were not changed. Preserve intended capabilities without cementing unsafe accidental behavior. Coordinator should track these as explicit implementation/security acceptance items.

1. **Native integration grant scoping:** management guards and `getIntegrationsWithPermissionsAsync` filter user/group ACLs, but `createOne/ManyIntegrationMiddlewareForKinds` loads `userPermissions:true, groupPermissions:true` and passes all rows to constructors that only inspect permission values, not identities. Query helper treats any supplied grant as use access; interact constructor treats any supplied interact/full grant as sufficient. This is a source-level risk of granting another principal's access, including anonymous actions. Migration must filter at repository boundary and demonstrate denial against unrelated-user/group grants before any public native endpoint is mounted. [Native middleware](../../packages/api/src/middlewares/integration.ts#L57), [constructor](../../packages/auth/permissions/integration-permissions.ts), [correct scoped management example](../../packages/auth/permissions/integrations-with-permissions.ts). It is not license to drop public-board-derived reads.
2. **Membership mutation asymmetry:** `addMember` verifies target provider local management; `removeMember` does not. Mixed deployments can allow direct external-user membership removal although UI intends only local/mixed eligible rows. Human approval should specify intended denial and next-login synchronization behavior. [Group router](../../packages/api/src/router/group.ts#L362).
3. **Expiry/revocation:** WS accepts found expired DB rows through current helper and holds a principal snapshot at connection establishment. Browser expiry timer uses bootstrap session and caps long delays; permission reload scope contains global keys but not resource ACLs. Choose unified real expiry, renewal and ongoing-stream revocation latency; endpoint worker owns delivery lifecycle, persistence/dashboard owners own cache epochs/invalidation. Do not preserve expired access as a feature. [Session helper](../../packages/auth/session.ts), [WS](../../apps/websocket/src/main.ts), [browser timer](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/session.tsx).
4. **Provider disablement:** LDAP-enabled filtering retains the basic credentials provider despite credentials registration being disabled and button being absent. Decide whether disabled means no local login or only no local-account creation; source/doc/UI are not interchangeable. [Filter](../../packages/auth/providers/filter-providers.ts), [basic auth](../../packages/auth/providers/credentials/authorization/basic-authorization.ts).
5. **Proxy trust and cookie security:** today's route rewrites unconditionally from forwarded headers, while secure flag is calculated before rewriting. Define trusted origins/proxies and HTTP/TLS local/proxy behavior centrally. Preserve deployed callback/cookie compatibility; tightening trust must have a documented deployment migration, not a silently accepted arbitrary host. [Auth route](../../apps/nextjs/src/app/api/auth/%5B...nextauth%5D/route.ts), [redirect helper](../../packages/auth/redirect.ts).
6. **Password/session semantics:** UI/API change retains existing sessions; CLI recovery removes them. Decide whether new API also revokes other/current sessions and whether key tokens survive password reset (currently keys are not deleted by those commands). Last-admin lockout prevention/recovery must be reviewed; inspected delete/group-permission writes do not demonstrate an enforced last-admin invariant. [User router](../../packages/api/src/router/user.ts#L577), [CLI](../../packages/cli/src/commands/reset-password.ts).
7. **MCP OAuth authority:** generated token is an ordinary durable API key with no per-token expiry, audience or client binding in DB; resource checks happen at authorization/exchange, not subsequent generic key verification. `mcp:tools` response metadata does not narrow the user's resource/global permissions or prevent use on other key-accepting surfaces. Token exchange doesn't verify stored client secret/client ID as a confidential client and direct authenticated authorize has no consent UI. Decide compatibility versus genuine scope/audience/consent/token-lifetime additions with endpoint owner; additions require schema/product/security work, not a protocol rename. [OAuth routes](../../apps/nextjs/src/app/api/mcp/oauth/token/route.ts), [key schema](../../packages/db/schema/sqlite.ts#L38).
8. **OAuth state and deployment:** clients expire after 24h, codes after 5m, pending auth after 10m, caps 1000/5000/5000; state/rate maps are process-local and restart loses registration. Choose explicit one-process semantics or shared TTL/CAS storage for split/multiple workers. Atomic consume/limits/cleanup ownership must survive; persistence worker selects storage, not this note. [Store](../../apps/nextjs/src/app/api/mcp/oauth/_store.ts).
9. **User/default/settings validation:** header shortcuts validate target visibility, home IDs validate caller view; ordered-group home resolver source requires both device-specific and desktop home non-null while comments describe fallback. Dedicated global-home update validates public IDs, but generic settings save uses looser record merge for board and most other families. Preserve currently stored values and decide uniform target/public-home policy with dashboard/admin owners rather than applying only form validation. [Preferences](../../packages/api/src/router/user/preferences.ts), [home resolver](../../packages/api/src/router/board.ts#L2536), [settings writes](../../packages/api/src/router/serverSettings.ts#L132).
10. **Sensitive restoration/crypto and logging:** existing encrypted material includes integrations, Assistant keys/headers, Custom Widget secrets/preview/configuration state. Earlier backup conversion evidence only established integration-secret re-encryption; no claim all families restore under a changed key. Preserve format/key first, forbid production zero-key fallback; audit sensitive debug profile/LDAP and provider error logs when porting. No value should enter browser bundle, shared render cache or error URL. [Crypto](../../packages/common/src/encryption.ts), [events debug](../../packages/auth/events.ts), [earlier backup gap](../Homarr%20Nitro%20migration%20experiment/api-auth-migration.md#1-what-nextjstrpc-coupling-and-capabilities-must-survive).

Open human choices: A/B/C auth integration; preserving logged-in sessions versus intentional one-time re-login; proxy/secure-cookie deployment policy; password reset/session/key revocation semantics; current scope-less API-key/MCP compatibility versus scoped token redesign; OAuth state durability/consent; intended disabled-provider/local-external membership/default-home rules; authorization refresh latency for cached/long-lived responses. New capabilities such as passkeys/MFA/email self-service recovery were not found in the inspected production provider/route inventory and are not migration prerequisites or grounds to remove CLI recovery.

## 7. Verifiable acceptance obligations (not run)

The ledger is source evidence, not a completed acceptance suite. Later checks should use disposable fixture data/test providers and authorized conditions, not real account probing.

1. **Data continuity:** retain IDs, provider/account links, original bcrypt passwords/key hashes, DB sessions/expiries, group/resource grants/order/homes and settings. Existing credentials and API keys still verify; deleting a key/user/session revokes the intended access; no cross-provider email collision merge. 2. **Provider parity:** credentials/LDAP/OIDC alone and mixed; disabled direct endpoints; LDAP ambiguous/missing/invalid-email/wrong-password/non-ASCII-DN/filter/group cases; OIDC existing/new/linking denied and verified opt-in, forced userinfo, nested name/group claims, custom avatar retention, missing groups, local-management toggle and group removals.
