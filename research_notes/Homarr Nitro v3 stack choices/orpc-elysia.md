# Exact oRPC 2.0.0-beta.43 on mandatory Nitro v3; optional Elysia

Research for [AJN-497](https://linear.app/ajnart/issue/AJN-497), checked 2026-10-10. Linear was not edited. Only this assigned notes file was written; no installation, implementation, prototype, benchmark, test, lint, typecheck, branch, worktree, or commit operation was performed.
Context7 resolution was attempted for oRPC, Nitro and Elysia, but all returned monthly-quota exhaustion. Evidence below instead uses official current documentation, npm metadata and exact published oRPC files. Current documentation is not a frozen beta.43 specification; exact-file citations identify release-verified behavior.
Existing capability inventory was reused rather than repeated: [Nitro runtime notes](../Homarr%20Nitro%20migration%20experiment/nitro-runtime.md) and [API/auth migration notes](../Homarr%20Nitro%20migration%20experiment/api-auth-migration.md).

## 1. Does beta.43 exist, and what types, packages and compatibility limits does it actually provide?

### Takeaway

Yes: the coordinated oRPC `2.0.0-beta.43` packages were published, while `latest` still selects v1. oRPC already provides validated, end-to-end TypeScript contracts and Query utilities without Elysia; adopting it is a transport/API migration, not just a Nitro runtime change. — [Server registry](https://registry.npmjs.org/@orpc/server); [Getting started](https://orpc.dev/docs/getting-started); [v1 migration](https://orpc.dev/docs/migrations/from-v1)

### Cited Findings

- Registry snapshot for the six core/Query/Zod packages: `beta` points to `2.0.0-beta.43`, `latest` to `1.15.5`; they were published 2026-10-09. Pin the literal prerelease, not moving `@beta` or unqualified packages, for this investigation's reproducible pairing. — [Server registry](https://registry.npmjs.org/@orpc/server); [Query registry](https://registry.npmjs.org/@orpc/tanstack-query)
- The supplied getting-started page is now v2-oriented: it installs `@beta`, uses `RPCLink({ origin, url: '/rpc' })`, and references the v1 migration page. It must not be combined with old v1 tutorials or pretrained snippets. — [Getting started](https://orpc.dev/docs/getting-started); [v1 migration](https://orpc.dev/docs/migrations/from-v1)
- Code-first client typing uses `RouterClient<typeof router>` plus `createORPCClient(link)`, with a type-only server import; contract-first uses `oc`, `implement(contract)` and `RouterContractClient`. Neither requires client code generation. A server-only caller uses `call` or `createRouterClient`, bypassing HTTP but retaining procedure validation/middleware. — [Getting started](https://orpc.dev/docs/getting-started); [Contract-first](https://orpc.dev/docs/contract-first); [Server clients](https://orpc.dev/docs/client/server-side)
- `.input` executes runtime Standard Schema validation; an inferred handler result is compile-time typing, **not runtime output validation**. Explicit `.output` schemas validate results and supply schemas for public documentation; an unsupported schema converter falls back to Standard JSON Schema or an empty schema, not invented response structure. — [Procedures](https://orpc.dev/docs/procedure); [Standard Schema conversion](https://orpc.dev/docs/integrations/standard-schema); [Specification](https://orpc.dev/docs/openapi/specification)
- Query utilities produce native TanStack options/keys, not replacement React state management. Released beta.43 forwards query/infinite/live/streamed `signal` into procedure calls; streamed results accumulate chunks, live results replace the latest value, and `maxChunks` can bound accumulated history. Homarr's catalog `@tanstack/react-query 5.101.2` is above the documented minimum numerically, but its resolved query-core pairing was not installed/verified here. — [Released utilities](https://unpkg.com/@orpc/tanstack-query@2.0.0-beta.43/dist/index.mjs); [Query guide](https://orpc.dev/docs/integrations/tanstack-query); [Catalog](../../package.json)
- Query invalidation, optimistic updates, retries, session-scoped cache reset, hydration and forbidden-data clearing remain chosen application policies. SSR hydration of rich values needs an appropriate serializer; infinitely open live/streamed prefetches need explicit server cancellation and client reopening. — [Query guide](https://orpc.dev/docs/integrations/tanstack-query); [Existing provider](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx)
- v2 RPC serialization round-trips Date, bigint, Map, Set, undefined and non-finite numbers; root byte streams and async iterators have dedicated transports, while Blob/File are unsupported inside iterator events. `RegExp` is no longer built in. This is not tRPC SuperJSON's wire format. — [Serializer](https://orpc.dev/docs/rpc/serializer); [Released serializers](https://unpkg.com/@orpc/client@2.0.0-beta.43/dist/shared/client.DpkGsZt-.mjs); [Migration](https://orpc.dev/docs/migrations/from-v1)
- REST/OpenAPI serialization is deliberately one-way: Date becomes ISO text, bigint text, Set/Map arrays; native client values need validation/coercion/custom handling. A typed `OpenAPILink` alone is not proof of rich-type round-trip parity. — [OpenAPI serializer](https://orpc.dev/docs/openapi/serializer)
- v1 and v2 RPC/OpenAPI-link clients are wire-incompatible; `@orpc/openapi-client` moved into `@orpc/openapi`, Query packages consolidated, and `url` split from `origin`. Old `.prefix/.tag/.$route` builder methods are removed; `.route` requires an explicit extension. — [Migration](https://orpc.dev/docs/migrations/from-v1); [Exact exports](https://registry.npmjs.org/@orpc/openapi/2.0.0-beta.43)
- v2 errors have code/message/data, not a `status` field; HTTP statuses belong to handler `errorStatusMap`. `.errors` gives typed error data, but Homarr's flattened Zod/domain errors need deliberate remapping. Duplicate router/procedure middleware now runs twice unless deduplicated explicitly. — [Error guide](https://orpc.dev/docs/error-handling); [Migration](https://orpc.dev/docs/migrations/from-v1); [Existing formatter](../../packages/api/src/trpc.ts)

### Inferences

- oRPC code-first is a plausible internal TypeScript surface; contract-first/explicit output schemas are stronger boundaries for independently consumed public APIs. This is a maintainability recommendation, not evidence that every Homarr procedure should become public. — [Contracts](https://orpc.dev/docs/contract-first); [Generator filtering](https://orpc.dev/docs/openapi/specification)
- The Zod peer conflict applies to the **optional converter package**, not a demonstrated inability of Homarr's schemas to validate through Standard Schema. Resolve converter/version compatibility deliberately; do not claim an untested upgrade is harmless or empty JSON schemas are acceptable public documentation. — [Exact Zod manifest](https://registry.npmjs.org/@orpc/zod/2.0.0-beta.43); [Fallback behavior](https://orpc.dev/docs/integrations/standard-schema)
- The tRPC bridge could reduce initial procedure rewriting but does not preserve tRPC transport clients or Homarr's error formatter. Keep the existing tRPC endpoint during an incremental experiment if compatibility matters; bridge success is not full migration parity. — [Bridge](https://orpc.dev/docs/integrations/trpc); [Released bridge](https://unpkg.com/@orpc/trpc@2.0.0-beta.43/dist/index.mjs); [Existing provider](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx)

### Gaps

- No compiler, lockfile-resolution, Zod upgrade, bridge, Query hydration or browser compatibility test was performed. Exact API existence is verified; feature-equivalent behavior across Homarr's complete router is not.

## 2. How does Fetch mount on Nitro v3, and where do cancellation, realtime and security stop being automatic?

### Takeaway

Nitro v3 can host released beta.43 Fetch handlers directly: no Elysia instance or separate listener is required. HTTP streaming is documented, while WebSocket hosting, per-transport identity, lifecycle and every authorization rule still need explicit application integration. — [Nitro entry](https://nitro.build/docs/server-entry); [Released Fetch handler](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/adapters/fetch/index.mjs); [WebSocket adapters](https://orpc.dev/docs/adapters/websocket)

### Cited Findings

- Mandatory v3 means the `nitro` package, not v2 `nitropack`. Prior release evidence identifies `nitro@3.0.260903-beta` versus moving nightly/main, H3 v2, opt-in filesystem scanning and removed auto-imports; exact Nitro runtime behavior must be pinned separately from exact oRPC beta.43. — [Nitro migration](https://nitro.build/docs/migration); [Released Nitro manifest](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/package.json); [Prior version findings](../Homarr%20Nitro%20migration%20experiment/nitro-runtime.md)
- `RPCHandler` is imported from `@orpc/server/fetch`; `OpenAPIHandler` from `@orpc/openapi/fetch`. Both accept the router and use the same released Fetch adapter machinery; `.handle(request, { prefix, context })` returns a discriminated `{ matched: true, response: Response }` or `{ matched: false }`. — [Exact server declaration](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/adapters/fetch/index.d.mts); [Exact OpenAPI adapter](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/adapters/fetch/index.mjs)
- Mount shape: register explicit Nitro `/rpc/**` and chosen REST-prefix routes; their `defineHandler` reads `event.req`, passes it unchanged to the chosen handler with the same prefix, supplies request-derived context, and returns its Response when matched. Return an API 404 for unmatched calls within an owned API prefix. This composes documented H3 v2 mounting with Nitro route registration, not a tested turnkey Nitro plugin. — [oRPC H3 adapter](https://orpc.dev/docs/adapters/h3); [Nitro routing](https://nitro.build/docs/routing); [Fetch adapter](https://orpc.dev/docs/adapters/fetch-api)
- Alternative mount: `server.ts` exports `{ async fetch(request) { ... } }`, invokes RPC/REST handlers by their prefixes, and returns matched Responses. Return `undefined` only for paths intended for Nitro's renderer; do not turn all unmatched page requests into an API 404. — [Nitro entry/fallthrough](https://nitro.build/docs/server-entry); [Fetch match contract](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/adapters/fetch/index.d.mts)
- Nitro's server entry is a **fallback catch-all**, not global middleware: more specific Nitro routes win. Context/auth setup solely in that entry cannot secure separately registered Nitro routes; global concerns belong in outer middleware/hooks with procedure-level permissions retained. — [Nitro lifecycle warning](https://nitro.build/docs/server-entry)
- Keep Nitro responsible for listening/build/deployment: standalone oRPC examples call Node/Bun servers, and standalone Elysia examples use `.listen()`, but those are not instructions to start a second listener inside Nitro. Nitro's Elysia example exports `app.compile()`. — [Fetch examples](https://orpc.dev/docs/adapters/fetch-api); [Nitro framework entries](https://nitro.build/docs/server-entry)
- Do not eagerly consume the request body before oRPC handles it. Official Elysia integration explicitly sets `parse: 'none'` because oRPC reads the raw Request; this matters for multipart/binary/stream inputs too. — [Elysia adapter](https://orpc.dev/docs/adapters/elysia)
- Released Fetch link places `options.signal` into fetch init; released standard handler passes `request.signal` into the procedure. That establishes the forwarding seam, **not** that every Nitro preset, proxy or upstream service cancels work correctly. — [Exact Fetch transport](https://unpkg.com/@orpc/client@2.0.0-beta.43/dist/adapters/fetch/index.mjs); [Exact standard handler](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/shared/server.B1ecixZJ.mjs)
- `asyncIteratorObject(schema)` supplies typed, validated streamed events; Fetch output is SSE, client cancellation uses AbortSignal or iterator `.return()`, and cleanup belongs in a generator `finally` with signal-aware upstream work. Event IDs support resumption **if the application can replay**; they do not create a durable event log. — [Server streaming](https://orpc.dev/docs/async-iterator-object); [Client streaming](https://orpc.dev/docs/client/async-iterator-object); [Serializer framing](https://orpc.dev/docs/rpc/serializer)
- SSE completion includes oRPC-specific signaling; plain EventSource does not recognize it and may reconnect. This is not tRPC's existing EventSource/WS protocol, nor automatically the Assistant's AI SDK UI-message stream. Fetch HTTP compatibility does not imply those clients can remain unchanged. — [SSE warning](https://orpc.dev/docs/async-iterator-object); [Existing client links](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx); [Assistant route](../../apps/nextjs/src/app/api/assistant/chat/route.ts)
- Released Fetch adapters expose event-stream settings under `toFetchResponse.eventStream`; docs specify initial header-flush comments and a 15-second keep-alive default, unlike old v1 flat options/5-second default. Byte streams are root-level passthrough; File/Blob require appropriate runtime globals and, cross-origin, exposed `Content-Disposition`/`Standard-Server` headers. — [Fetch settings](https://orpc.dev/docs/adapters/fetch-api); [Runtime requirements](https://orpc.dev/docs/requirements); [Migration](https://orpc.dev/docs/migrations/from-v1)
- WebSockets are a separate adapter: `/websocket` exposes `RPCHandler`; `/crossws` exposes **`experimental_RPCHandler`**, not the ordinary name. Released CrossWS handler needs both `.message(peer, message, options)` and `.close(peer)`; Nitro must own upgrades/hooks. Per-call request context is not the initial upgrade request, so capture/validate upgrade identity explicitly where appropriate. — [Exact CrossWS exports/types](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/adapters/crossws/index.d.mts); [Released lifecycle](https://unpkg.com/@orpc/server@2.0.0-beta.43/dist/adapters/crossws/index.mjs); [Adapter context warning](https://orpc.dev/docs/adapters/websocket); [Nitro WebSockets](https://nitro.build/docs/websocket)
- WebSocket client reconnect is available but defaults disabled; this does not establish Homarr heartbeat/reconnect notifications, session expiry/revocation, bounded queues or graceful-shutdown parity. Those are existing application behaviors to preserve. — [Reconnect guide](https://orpc.dev/docs/adapters/websocket); [Existing WS server](../../apps/websocket/src/main.ts); [Beszel subscription](../../packages/api/src/router/widgets/beszel.ts)
- Optional `@orpc/publisher@beta.43` exists, but its Redis adapter peers on `redis >=6.0.0`, whereas Homarr uses `ioredis 5.11.1`. v1's IORedis adapter was replaced; adopting the helper is a separate dependency/state decision, not a prerequisite for forwarding existing Redis pub/sub into an async generator. — [Exact publisher manifest](https://registry.npmjs.org/@orpc/publisher/2.0.0-beta.43); [Migration](https://orpc.dev/docs/migrations/from-v1); [Catalog](../../package.json)
- Typed context and middleware can carry session/API key, db, forwarded URL, device and onboarding claims; they do not implement Homarr authentication. Preserve cookie/API-key precedence for internal RPC, API-key-only REST and Bearer/ApiKey-only MCP, including public-board permissions and secret-decryption ordering. — [oRPC context](https://orpc.dev/docs/context); [Existing context](../../packages/api/src/trpc.ts); [REST identity](../../apps/nextjs/src/app/api/%5B...trpc%5D/route.ts); [MCP identity](../../apps/nextjs/src/app/api/mcp/_handler.ts)
- MCP names/descriptions, eager capability selection, schema transformations, confirmations, prompts/resources, safe errors and OAuth discovery/PKCE are separate from HTTP routing and OpenAPI. Existing extractor inspects tRPC metadata/internals and dispatches through its caller; replacing the router requires a curated replacement adapter, not automatic REST-to-tool exposure. — [Existing extractor](../../packages/api/src/mcp-tools.ts); [MCP protocol](../../apps/nextjs/src/app/api/mcp/_protocol.ts); [OAuth authorize](../../apps/nextjs/src/app/api/mcp/oauth/authorize/route.ts)

### Inferences

- Prefer direct Nitro Fetch routes as the simplest evaluation baseline. Keep binary/media, Assistant and MCP endpoints on their existing protocol-oriented seams unless a separate migration is justified; oRPC need not own every HTTP response merely because it owns procedures. — [Nitro entry](https://nitro.build/docs/server-entry); [Current capability inventory](../Homarr%20Nitro%20migration%20experiment/api-auth-migration.md)
- Preserve existing DB/schema/IDs, encryption keys, credentials/providers, board data and jobs; introducing a contract transport neither requires nor proves a data conversion. Keep existing domain/authorization services as the authority behind old and new adapters. — [Migration preservation boundaries](../Homarr%20Nitro%20migration%20experiment/api-auth-migration.md)

### Gaps

- No validated beta.43/Nitro-v3 integration matrix or deployed stream/upgrade test was found in the inspected primary material. Abort forwarding is source-verified; client disconnect propagation, proxy buffering, upload ceilings, replay/backpressure and authenticated WS cleanup still require later feature-parity evidence.

## 3. Which OpenAPI generator owns the public contract, and does Elysia add decision-relevant value?

### Takeaway

Nitro metadata OpenAPI and oRPC schema OpenAPI are different generators; nesting a router does not merge/discover its procedures automatically. If oRPC owns contracts, Elysia/Eden adds no demonstrated inner-procedure type-safety benefit; evaluate Elysia only for independently valuable HTTP routes/plugins/ergonomics, not as an assumed RAM or typing winner. — [Nitro OpenAPI](https://nitro.build/docs/openapi); [Exact Nitro generator](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/src/runtime/internal/routes/openapi.ts); [oRPC generator](https://orpc.dev/docs/openapi/specification); [Eden overview](https://elysiajs.com/eden/overview)

### Cited Findings

- Nitro enables experimental `experimental.openAPI`, statically extracts `defineRouteMeta({ openAPI: ... })`, infers path parameters and generates OpenAPI **3.1.0**. Bodies, responses, security and reusable components need explicit metadata; arbitrary handler code does not yield validated input/output schemas. — [Nitro OpenAPI](https://nitro.build/docs/openapi)
- Released Nitro generator iterates `handlersMeta`, normalizes Nitro route patterns and uses their metadata. It does not walk an oRPC router, Elysia's registry or nested wildcard business procedures; registering `/rpc/**` is not sufficient to document all procedures behind it. — [Released Nitro source](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/src/runtime/internal/routes/openapi.ts)
- Nitro's default dev endpoints are `/_openapi.json`, `/_scalar`, `/_swagger`; production defaults off, with `runtime` or `prerender` opt-ins and an explicit access-control warning. Enabling these endpoints does not enable or configure oRPC's generator. — [Nitro OpenAPI options](https://nitro.build/docs/openapi)
- oRPC's `OpenAPIHandler` runs procedures as REST-style routes; **`OpenAPIGenerator` separately** walks procedure contracts asynchronously and converts input/output/error schemas. Handler existence alone is not a served JSON specification or UI. — [Released handler](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/adapters/fetch/index.mjs); [Released generator](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/index.mjs)
- Exact beta.43 API: `new OpenAPIGenerator({ converters })`, then `generate(router, { version, base: { info, servers, components }, filter })`. Defaults to **3.2.0**; generates older 3.1/3.0 documents through downgrading. Choose a common 3.1 target deliberately if merging with Nitro; never just relabel a 3.2 document as 3.1. `QUERY` operations cannot downgrade below 3.2. — [Released declarations](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/index.d.mts); [Released conversion](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/index.mjs); [Version caveat](https://orpc.dev/docs/openapi/specification)
- Routing metadata is `os.meta(openapi({ method, path, prefix, tags, ... }))`, not native builder `.route/.prefix` by default. Without overrides, nested `planet.create` becomes `POST /planet/create`; v2 prefixes apply to **all** procedures. RPC transport routing is distinct from these REST paths. — [OpenAPI routing](https://orpc.dev/docs/openapi/routing); [v1 migration](https://orpc.dev/docs/migrations/from-v1)
- The handler's mount prefix and generator's server/base paths must agree: do not silently produce `/api/api/...` or document unmounted URLs. `base.servers` can state the actual external API base, and metadata determines procedure paths. This is an integration consistency requirement inferred from the documented independent controls. — [Fetch prefix](https://orpc.dev/docs/adapters/fetch-api); [Generator base](https://orpc.dev/docs/openapi/specification)
- Serving option A: provide the generated document to a Nitro Response route and point an independently configured UI at it. Option B: released `OpenAPIReferenceHandlerPlugin({ spec, allow, ... })` serves a static/dynamic supplied document and guards UI/JSON with `allow`; the plugin does not generate the document implicitly. — [Exact plugin declaration](https://unpkg.com/@orpc/openapi@2.0.0-beta.43/dist/plugins/index.d.mts); [Reference guide](https://orpc.dev/docs/plugins/openapi-reference); [Nitro handlers](https://nitro.build/docs/routing)
- `generate` supports a procedure filter, but filtering documentation does not by itself prevent calling a mounted procedure. Apply the same intentional public selection to the REST handler, and preserve documented statuses/error encoders/security requirements. A security object documents authentication; it does not execute it. — [Generator filtering/error schemas](https://orpc.dev/docs/openapi/specification); [Handler](https://orpc.dev/docs/openapi/handler); [Homarr curated public router](../../packages/api/src/open-api.ts)
- Elysia has its own `@elysia/openapi` generator, UI at `/openapi` and JSON at `/openapi/json`; Standard Schema conversion can need `mapJsonSchema`. This is a third documentation authority, not automatic merging with Nitro or oRPC. — [Elysia OpenAPI plugin](https://elysiajs.com/plugins/openapi)
- Eden derives its typed client from the exported **Elysia app type**. Official oRPC/Elysia mounting declares a wildcard Request-to-Response handler with body parsing disabled; it does not reify every oRPC input/output contract as a native Elysia route. Eden therefore cannot be assumed to infer the mounted inner procedure contracts. — [Eden](https://elysiajs.com/eden/overview); [oRPC Elysia adapter](https://orpc.dev/docs/adapters/elysia)
- Elysia can add native validated routes, its middleware/plugin conventions and an Eden client **for those Elysia routes**, and Nitro explicitly supports its compiled Fetch app. Those are possible independent benefits; they are not stronger oRPC validation, an oRPC protocol replacement, or evidence of compatibility for native WS/Bun-specific plugins. — [Eden](https://elysiajs.com/eden/overview); [Nitro Elysia entry](https://nitro.build/docs/server-entry); [Fetch mounting](https://elysiajs.com/patterns/mount)

### Inferences

- Proposed simplest public-spec ownership: curate an oRPC public REST router/contract with explicit schemas, generate one document, add any separately retained HTTP operations intentionally, and serve that document from one chosen endpoint. Disable/confine competing Nitro/Elysia public docs rather than presenting an incomplete wildcard-generated spec as complete. — [oRPC filtering](https://orpc.dev/docs/openapi/specification); [Nitro generator boundary](https://github.com/nitrojs/nitro/blob/v3.0.260903-beta/src/runtime/internal/routes/openapi.ts)
- If merging is necessary, establish a common OpenAPI version, external base/prefix, unique path+method and operationId ownership, component-name/$ref collision handling, consistent errors/security and public/internal filters. Explicit merge/validation is application work; no automatic cross-generator merge was established by these sources. — [oRPC document/version controls](https://orpc.dev/docs/openapi/specification); [Nitro metadata/components](https://nitro.build/docs/openapi)
- Recommendation for evaluation, **not an architecture decision**: mandatory pinned Nitro v3 + aligned oRPC beta.43 Fetch handlers is sufficient for the proposed contract layer. Make Elysia opt-in only after naming a benefit outside oRPC-owned procedures; otherwise it duplicates HTTP dispatch/context/schema responsibilities while Eden remains redundant for that surface. — [Fetch API](https://orpc.dev/docs/adapters/fetch-api); [Nitro entry](https://nitro.build/docs/server-entry); [Elysia wildcard integration](https://orpc.dev/docs/adapters/elysia)
- Keep runtime migration and tRPC-to-oRPC migration separable. For a future authorized experiment, preserve existing contracts initially, select a bounded procedure set, then evaluate type inference/public spec/auth/errors/serialization/abort/realtime parity before expanding. The beta Zod peer conflict and unsupported tRPC formatter are concrete gates, not reasons to promise a wholesale rewrite. — [Bridge limitations](https://orpc.dev/docs/integrations/trpc); [Exact Zod peer](https://registry.npmjs.org/@orpc/zod/2.0.0-beta.43); [Existing boundaries](../Homarr%20Nitro%20migration%20experiment/api-auth-migration.md)
- No RAM winner follows from framework names, minified client size, package counts or Fetch compatibility. Nitro still has an outer runtime/router and Homarr keeps stateful integrations/DB/jobs/Redis/native resources; process RSS includes more than JS heap or bundle bytes.
