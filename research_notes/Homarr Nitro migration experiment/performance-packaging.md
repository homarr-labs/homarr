## 2. How should RAM, CPU, idle/load/soak and cold/warm latency be measured?

### Takeaway

Use total cgroup accounting as the primary small-container footprint, with process RSS/PSS and runtime heap as separate explanatory measurements. Pre-register independent runs, cache states, workload and measurement windows; repeated pages against one warm server do not establish cold startup, memory reliability or sustained-load p99.

### Cited Findings

- Cgroup v2 `memory.current` is total memory charged to the cgroup and descendants; `memory.stat` explains anon/file/kernel and other components. `memory.peak` is a lifetime or same-file-descriptor-reset peak depending on kernel support. `memory.events` exposes limit/reclaim/OOM counters; swap is separate in `memory.swap.current`. — [Linux cgroup v2 memory controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory).
- Linux `docker stats` CLI subtracts cache (`inactive_file` on cgroup v2), whereas the Engine stats API exposes the raw usage and cache separately. Therefore an unqualified `docker stats` screenshot is not the same metric as total cgroup memory. — [Docker stats reference](https://docs.docker.com/reference/cli/docker/container/stats/).
- `cpu.stat` reports cumulative `usage_usec`, `user_usec`, `system_usec` and controller-specific throttling counters. CPU limits express bandwidth, not hardware frequency. — [Linux cgroup v2 CPU controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cpu).
- Node `process.memoryUsage()` distinguishes RSS from V8 heap, external allocation and ArrayBuffer allocation; ArrayBuffers are included in external, so adding them double-counts. Worker RSS is process-wide, while other fields are thread-specific. The docs warn glibc fragmentation can raise RSS without heap growth. — [Node process memory documentation](https://nodejs.org/api/process.html#processmemoryusage). The fetched page described Node 26; verify against the pinned Node 24 documentation before implementing instrumentation.
- Bun documents `bun:jsc` heap statistics and its `node:v8` compatibility surface reports JSC, not a V8 heap; ignored flags and untracked counters can exist. Cross-runtime heap numbers must retain runtime-specific names and semantics. — [Bun 1.4.2 benchmarking docs](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/project/benchmarking.mdx); [Bun 1.4.2 compatibility docs](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/runtime/nodejs-compat.mdx).
- Docker warns that repeated new collector processes are relatively expensive. The existing runtime harness executes shell/awk/redis-cli inside the measured cgroup, adding small process/CPU/memory disturbances. — [Docker runtime collection guidance](https://docs.docker.com/engine/containers/runmetrics/); [runtime collector:145-185](../../scripts/benchmarks/docker-runtime.mts).
- Constant-rate load and latency measured from intended arrival time can expose coordinated omission: a client that waits for each response before issuing the next request can hide stalls. wrk2 documents this, its approximately millisecond timing granularity and calibration requirement; it is an example, not a mandated dependency. — [wrk2 primary README](https://github.com/giltene/wrk2#readme).
- The current `startToReadyMs` starts before network creation and includes creating/connecting a benchmark proxy container; readiness polls once per second. Settling occurs with browser pages still open, hence includes subscriptions/polling and is not a no-client idle phase. — [runtime harness:166-178,683-755,1383-1419](../../scripts/benchmarks/docker-runtime.mts).

### Inferences

**Proposed reproducible protocol, not measured results or acceptance budgets:**

1. **Freeze a run contract before collection.** Record source snapshot/fingerprint and lockfile; baseline/candidate image platform digests; package/runtime/engine versions; Linux kernel and cgroup mode; native CPU architecture/model/core allocation; RAM/swap limits; CPU governor/VM allocation; Docker/BuildKit/storage driver; disk/volume mount and filesystem; all runtime flags and sanitized env; DB driver and fixture hash; Redis configuration; network fixtures; browser/version/viewport; TLS, keep-alive, HTTP version and compression policy. Never compare native ARM to emulated x86 or silently mix machines. Existing provenance covers much of this but needs limits/flags/fixture details. — [runtime provenance](../../scripts/benchmarks/docker-runtime.mts); [Docker multi-platform guide](https://docs.docker.com/build/building/multi-platform/).
2. **Independent replicas and balanced order.** Use fresh containers/cgroups and isolated appdata copies per replica, rotating or randomizing cell order within hardware blocks. Keep base images pre-pulled for server-start measurements; measure first pull separately. Pre-register replication counts, warmup/load/soak durations and load rates before observing results; raw run IDs remain the unit for RAM/startup comparisons. Proposed small pilot: five independent replicas per cell, expand if noise/uncertainty is substantial. This is a design choice, not a claim of statistical sufficiency. Do not discard outliers without a predefined invalid-run reason. — [existing balanced-pair approach and limits](../../scripts/benchmarks/benchmark-pair-lib.mts).
3. **Two startup cases.** (a) Clean persistent fixture requiring migrations; (b) already-migrated durable data. Time Docker start request, process entry, listening, HTTP ready, WebSocket subscription round-trip, first authenticated board/widget settlement and first completed task separately. Exclude harness network/proxy creation from app-start timing. A TCP accept or static HTML shell alone is not capability readiness. Report each cold first request separately from startup overhead and later warm requests. — [migration sequence](../../scripts/run.sh); [instrumentation readiness](../../apps/nextjs/src/instrumentation-node.ts); [existing board outcome gates](../../scripts/benchmarks/docker-runtime-lib.mts).
4. **Distinct phase windows.** After capability readiness: no-client idle with schedulers still enabled; one-board/subscription steady idle; identical warmup; fixed offered-rate load at representative rates; saturation sweep as a separate capacity diagnostic; sustained mixed-workload soak; post-load recovery. Cover several cycles of relevant cache expiry, polling, cron and Redis persistence. Existing ten-minute settle is a useful short stability diagnostic, not evidence of long-term leak absence. Soak duration and fixture sizes need operator agreement. — [existing settle constants](../../scripts/benchmarks/docker-runtime-lib.mts); [Redis persistence](../../packages/redis/redis.conf).
5. **Collect every phase, preferably from outside the app cgroup.** Raw timestamped `memory.current`, `memory.peak` when available, full `memory.stat`, `memory.events`, `memory.swap.current`, `cpu.stat`, `cpu.max`, and `io.stat`; per-process PID/executable/command/RSS/PSS; process and FD/socket counts; Redis allocator info; low-frequency app heap observations if later instrumentation is authorized. Record unavailable PSS/heap as null, not zero. `anon + file` is not necessarily total memory; fields within `memory.stat` can overlap, so do not sum all fields. Do not sum RSS across processes as a substitute for cgroup accounting. — [kernel accounting](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html); [current collector](../../scripts/benchmarks/docker-runtime.mts).
6. **Report memory with time and meaning.** Per-run idle median/range; phase p95/max and cgroup lifetime peak; anon/file/kernel explanations; post-load recovery; soak trend in bytes/hour with workload/cache cardinality; OOM/reclaim/throttling and failures. Thirty-second samples can miss short peaks, so retain kernel peak and document sampling cadence. A temporal p95 memory level is not a p95 across independent deployments. RSS/heap growth alone does not establish a leak. Do not force GC, clear caches or reclaim pages in the primary production run; isolate such diagnostics. — [kernel peak/accounting](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#memory); [existing forced-GC diagnostic](../../scripts/benchmarks/request-handler-memory.mts).
7. **Normalize CPU explicitly.** `CPU core-seconds = delta usage_usec / 1e6`; average cores used divides that by elapsed seconds. Report CPU seconds per correctly completed operation at the same offered load, along with completed/error/time-out counts and throttling deltas. Preserve user/system split and end-to-end throughput; do not compare unlabeled percentages with different CPU quotas. Include external required services for deployment totals. — [CPU controller definitions](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html#cpu).
8. **Tail latency from actual work.** Use an external generator with a recorded arrival schedule and enough headroom; preserve intended-arrival and actual-send timing, queues/dropped arrivals, status/body checks, timeouts and failures. Report p50/p95/p99, counts and histograms per route/workload/cache state per independent run. Measure TTFB and complete body separately. For streams record first meaningful event/chunk, inter-chunk delay, full completion and cancellation; for subscriptions record connect/auth/first frame and update-delivery latency. Do not mix stream-open duration with ordinary request latency. — [coordinated omission rationale](https://github.com/giltene/wrk2#readme); [existing complete-stream outcome checks](../../scripts/benchmarks/docker-runtime-lib.mts).
9. **Uncertainty and attribution.** Keep success latency and failed/timed-out counts side by side; do not let fast errors win. Choose sufficient requests/independent runs for the desired percentile precision; twenty page samples cannot establish a stable p99. Publish per-run quantiles and uncertainty rather than averaging p99 values into a fictitious pooled p99. Preserve raw samples/histograms and state quantile algorithm. Build, memory, API, browser and DX are separate outcomes, not one invented score. — [existing sample summary](../../scripts/benchmarks/dev-benchmark-lib.mts); [pair limitations](../../scripts/benchmarks/benchmark-pair-lib.mts).

### Gaps

- User/operator decisions remain: resource budget, acceptable latency/error tradeoffs, representative board/integration/cache cardinalities and traffic rates, duration/precision requirements, constrained-hardware tier and architecture weighting. No numeric RAM target or winning runtime follows from these sources.
- Existing harness needs extensions for independent replicas, external service totals, closed-client idle, scheduled sustained load, process heap, FD/socket/IO/OOM/swap observations and reliable p99. Existing short settling slope is descriptive, not proof of a memory leak or its absence.

## 3. What constitutes a fair H3/Hono/Elysia + Node/Bun matrix?

### Takeaway

Separate the framework effect from runtime, packaging, topology and frontend rendering changes. Use a common Nitro-managed Fetch server boundary for the primary six-cell experiment; platform-native framework listeners belong in a separately labeled optimization experiment and cannot inherit published performance claims.

### Cited Findings

- Current Nitro documentation demonstrates H3, Hono and compiled Elysia `server.ts` entries and a default object implementing `fetch(Request)`. Node production output is described as standalone `.output`; the Bun preset adds Bun-specific optimizations. These docs were retrieved through Context7 but are not a pinned installed Nitro version in this experiment. — [Nitro server entry](https://nitro.build/docs/server-entry); [Hono example](https://nitro.build/examples/hono); [Node runtime](https://nitro.build/deploy/runtimes/node); [Bun runtime](https://nitro.build/deploy/runtimes/bun).
- Elysia's own documentation distinguishes portability from optimization; Bun-native routing/WebSockets/file handling and Node adapter optimizations are platform-specific. A compiled Elysia Fetch entry under Nitro need not exercise the same native listener fast paths. — [Elysia compiler documentation](https://github.com/elysiajs/documentation/blob/main/docs/internal/jit-compiler.md); [Elysia adapter documentation](https://github.com/elysiajs/documentation/blob/main/docs/blog/elysia-20.md); [Nitro server entry](https://nitro.build/docs/server-entry).
- The baseline currently uses `better-sqlite3`; replacing that with `bun:sqlite`, in-memory persistence or a different ORM adapter is an additional variable, not a free runtime substitution. — [SQLite driver](../../packages/core/src/infrastructure/db/drivers/sqlite.ts); [Docker native binding](../../Dockerfile).

### Inferences

**Proposed tiers:**

| Tier | Cells | Purpose and interpretation |
| --- | --- | --- |
| Shipping baseline | Current Next + Node 24.18.0, existing nginx/internal Redis and capabilities | User-visible whole-system reference. Current app dependencies and flags stay intact. |
| Primary capability-equivalent matrix | Nitro + H3 / Hono / Elysia on Node 24.18.0; same three on Bun 1.4.2, **only where capability gates pass** | Pin identical frontend assets, Nitro/core logic/fixture/DB/cache/topology within the matrix. Pin framework and adapter versions. Use corresponding production preset and record generated output. A failed cell is unsupported/incomplete, not a performance loser or zero score. |
| Runtime isolation subexperiment | Same Node-preset output on Node and Bun, if supported | Helps separate execution-runtime differences from Bun-preset packaging/optimization changes. Native dependencies still must pass. |
| Packaging/topology ablations | Same selected matrix cell, internal vs external Redis; nginx retained vs compatible integrated ingress; optional split frontend/backend | Attribute service removal/output changes separately. Report both app-only and full deployment footprints. Default deliverable remains one small container; splitting is optional, not required and not GitHub Pages. |
| Native optimization diagnostics | Hono/Elysia/H3 standalone runtime adapters/listeners, or a driver substitution | Separate experiment only; not the Nitro-managed product result. Record disabled/effective fast paths and capability differences. |

This design follows the distinct entry/preset/adapter behavior in [Nitro docs](https://nitro.build/docs/server-entry) and [Elysia platform-specific docs](https://github.com/elysiajs/documentation/blob/main/docs/internal/jit-compiler.md); compatibility remains to be demonstrated, not assumed.

Require correctness before timing. - Keep browser/UI/widget functionality identical; include useful board data, not only mounted placeholders. A headless/API-only microbenchmark is a diagnostic tier, not a whole-app migration win. - Match data-driver semantics, DB journal/synchronous/connection settings, transaction contention, Redis persistence/pubsub/TTL, cache key cardinality and hit ratio, timers, batch sizes, streaming cancellation/backpressure, TLS/HTTP/keep-alive/compression, logs/telemetry, validation/auth middleware and payload sizes. Record each instead of assuming defaults are equal. Optional PostgreSQL should be a separate persistence block with its external resource usage shown. — [SQLite baseline](../../packages/core/src/infrastructure/db/drivers/sqlite.ts); [Redis baseline](../../packages/redis/redis.conf); [runtime flags](../../scripts/run.sh).
- Distinguish **process cold**, server cache cold/warm, DB/page cache, Redis state, browser HTTP cache, service-worker/query persistence, build cache and dependency store. ## 4. How should image footprint and native/multiarch packaging be compared?

### Takeaway

Measure per-platform compressed distribution bytes, unpacked image/layer footprint and runtime/persistent growth separately. A standalone JS bundle is not a complete Homarr runtime: native bindings, CLI/migrations, certificates, privilege handling and durable storage still matter.

### Cited Findings

- Nitro documents deployable standalone `.output`, production public asset serving and native/non-bundleable dependencies remaining external. `noExternals` is not evidence native bindings disappear. Public gzip/Brotli artifacts are optional and can trade stored bytes/build work for lower browser transfer. — [Nitro Node deployment](https://nitro.build/deploy/runtimes/node); [Nitro config](https://nitro.build/config); [Nitro public assets](https://nitro.build/docs/assets), retrieved via Context7.
- Next baseline already ships traced production dependencies rather than the entire install; assembly copies compiled output, `.next/static` and `public`. Any comparison against an imaginary full `node_modules` baseline exaggerates migration savings. — [Dockerfile:48-49](../../Dockerfile); [assemble-standalone.mjs](../../apps/nextjs/scripts/assemble-standalone.mjs); [standalone-artifact.mjs](../../apps/nextjs/scripts/standalone-artifact.mjs).
- OCI per-platform manifests reference layer/config descriptors with byte sizes and media types, including compressed layer types. A multiarch index is not one platform's download; Docker selects the architecture-specific manifest. — [OCI manifest specification](https://github.com/opencontainers/image-spec/blob/main/manifest.md); [Docker multi-platform structure](https://docs.docker.com/build/building/multi-platform/).
- Docker disk reporting distinguishes virtual image size from shared/unique local storage. Existing build/runtime scripts call `docker image inspect` and label `Size` as `localUncompressedBytes`; they do **not** measure registry compressed transfer. — [Docker system df reference](https://docs.docker.com/reference/cli/docker/system/df/); [docker-build.mts:263-344](../../scripts/benchmarks/docker-build.mts); [docker-runtime.mts:1526-1534](../../scripts/benchmarks/docker-runtime.mts).
- Current release builds have separate `linux/amd64` and `linux/arm64` jobs, with ARM on `ubuntu-24.04-arm`, and publish a combined manifest. Docker warns QEMU compilation/compression can be much slower than native builders. — [release workflow](../../.github/workflows/deployment-docker-image.yml); [Docker multi-platform strategies](https://docs.docker.com/build/building/multi-platform/).
- Bun 1.4.2 documents x64/ARM64 musl binaries and Node-API implementation supporting most existing Node-API extensions, not all arbitrary native modules. A generic Node-API claim does not validate Homarr's exact binding set. — [Bun installation docs](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/installation.mdx); [Bun Node-API docs](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/runtime/node-api.mdx).
- Root install trusts `bcrypt`, `better-sqlite3`, `sharp`, `ssh2`, tree-sitter-related packages and esbuild scripts. Trust is installation permission, not proof every package is in the traced runtime. Current Next externalizes dockerode, isomorphic-dompurify, jsdom and better-sqlite3; the CLI also has explicit externals. — [root manifest](../../package.json); [Next config:42-46](../../apps/nextjs/next.config.ts); [CLI manifest](../../packages/cli/package.json).

### Inferences

**Proposed footprint report per architecture/runtime/topology:**

- **Distribution:** architecture-specific manifest digest, compression/media type and sum of unique layer descriptor sizes; list config/manifest overhead separately. Report full first-download and incremental update bytes separately, using known already-present layer digests; do not sum amd64+arm64 index contents as one user's download. Tar/gzip of `.output` is only an app artifact metric, not OCI image bytes. — [OCI layer structure](https://github.com/opencontainers/image-spec/blob/main/manifest.md); [Docker platform selection](https://docs.docker.com/build/building/multi-platform/).
- **Unpacked:** local image virtual bytes, shared/unique store bytes and layer attribution; optionally logical merged-rootfs bytes, allocated disk bytes and file count. Keep these labels distinct: overwritten/deleted layer contents, filesystem allocation and store sharing make them different. Include runtime binaries/system libs, native external packages, app server, frontend/public/precompressed assets, CLI/migrations and other auxiliaries. Existing inspect results can seed this, not replace compressed measurement. — [Docker disk definitions](https://docs.docker.com/reference/cli/docker/system/df/); [baseline image contents](../../Dockerfile).
- **Growth:** writable container cache/logs and `/appdata` DB/Redis/uploads/certificates before/after workloads, plus first startup/migration peak. Durable data should remain in volumes with existing compatibility/ownership guarantees, not baked into an image or dropped for size. — [volume/startup contract](../../Dockerfile); [entrypoint ownership](../../scripts/entrypoint.sh); [Redis persistence](../../packages/redis/redis.conf).
- **Build/DX footprint:** dependency install, app compile, dependency tracing/output assembly, image export/compression and full Docker build wall time/peak separately. Preserve separate cold-store/cold-builder/warm-source-change cases and remote-cache policy; a completely cached Docker no-op is not compiler speed. Extend existing Next-specific parser rather than declaring Nitro builds ineligible because no Next marker appears. — [build harness](../../scripts/benchmarks/docker-build.mts); [baseline assembly](../../apps/nextjs/scripts/assemble-standalone.mjs).
- **Native compatibility gate:** inventory only final traced/output native bindings and shared-library requirements, recording runtime ABI, architecture and musl/glibc. Verify load plus real DB/auth/image/SSH operations on native amd64/arm64 in a later execution phase. Do not copy an amd64 binding into arm64 output, assume a Node binding works in Bun, or swap persistence drivers silently. Alpine versus glibc images belong in separate packaging blocks; no assumption either has lower total memory. — [native binding copy/build prerequisites](../../Dockerfile); [Bun Node-API limits](https://github.com/oven-sh/bun/blob/bun-v1.4.2/docs/runtime/node-api.mdx).
- **Minimal image tradeoff:** keep build compilers/package-manager/dev dependencies outside final layers, but preserve runtime CA trust, native libs, migrations/CLI, `_FILE`, privilege drop and signal lifecycle. Removing shell/nginx/Redis or compiling a single executable might change troubleshooting, cross-platform assets, compatibility and update behavior; benchmark only after parity is verified. Bun-only app packaging might still need Node for current migration/CLI helpers unless separately migrated—report both binaries if both ship. — [Dockerfile](../../Dockerfile); [run.sh](../../scripts/run.sh); [entrypoint.sh](../../scripts/entrypoint.sh); [CLI build](../../packages/cli/package.json).

### Gaps

- No output/layer/native-binding inventory was produced by running builds, and no registry manifest/image was measured. No compressed or unpacked size winner is known.
- Bun's exact compatibility with this checkout's `better-sqlite3 12.11.1`, other traced native modules and Linux CPU feature tiers needs validation; the docs do not establish it. Distinct ARM/x64 musl binaries are available, but that is not proof all application features work.
- Optional split frontend/backend may duplicate runtime/base-layer and operational overhead or improve independent updates; no measured net saving is available. Keep one small-container default and aggregate split-system costs.

## 5. How should browser performance, DX and published benchmarks be interpreted?

### Takeaway

Measure the same useful dashboard and developer workflow end to end, not a response string, readiness smoke or dev-server banner. Published router/runtime rankings are hypotheses for choosing experiments, not evidence of Homarr RAM, image size, browser responsiveness or sustained-load performance.

### Cited Findings

- Current runtime measurements already record FCP/LCP, navigation TTFB, long tasks, layout shifts, decoded script bytes, resource transfer sums, optional Chromium heap, board/implementation/data settlement and Spotlight feedback/readiness. Login soft navigation is separated from fresh authenticated-document LCP; the main document's transfer is not added to the resource transfer sum. The JS filter only includes resources with `initiatorType === "script"`, so a complete JS-delivery accounting needs resource/content-type reconciliation and inline code. — [docker-runtime.mts:430-605,1090-1189](../../scripts/benchmarks/docker-runtime.mts).
- W3C Resource Timing defines encoded versus decoded body size; cache/cross-origin/service-worker behavior and finite timing buffers affect exposed data. `transferSize` is a browser API metric, not exact packet/registry bytes; the current editor's draft uses a fixed overhead rather than exposing precise headers. — [Resource Timing editor's draft](https://w3c.github.io/resource-timing/), work in progress, consulted 2026-10-10.
- Vite documentation explicitly says TypeScript transpilation does not typecheck; warmup/pretransformation can shift first-request work into server startup. Current Next config separately disables build-time type errors and the app has `tsc --noEmit`; root typecheck is separate. Thus removing typecheck is not a fair Vite speed benefit. — [Vite features](https://github.com/vitejs/vite/blob/main/docs/guide/features.md); [Vite performance](https://github.com/vitejs/vite/blob/main/docs/guide/performance.md); [Next config](../../apps/nextjs/next.config.ts); [app scripts](../../apps/nextjs/package.json); [root scripts](../../package.json).
- Current dev command starts only Next via Node, with tasks/WebSocket production imports aliased away in development; full-capability dev topology requires explicitly starting services. Comparing that to a Nitro dev server that runs everything would confound DX memory/startup. — [app scripts](../../apps/nextjs/package.json); [Next dev aliases](../../apps/nextjs/next.config.ts); [architecture reference](../../.agents/skills/codebase-context/references/architecture.md).
- Hono's official benchmark page publishes router/handle-event cases and runtime-specific examples, including historical Deno versions and a lookup-route command. These are not Homarr capability-equivalent app/DB/auth/browser tests and do not establish Homarr RAM. — [Hono benchmarks](https://hono.dev/docs/concepts/benchmarks).
- Elysia's compiler docs cite platform-specific native optimizations and a TechEmpower plaintext ranking; its Node adapter blog links another framework benchmark. Those claims have their own workload, runtime and adapter, not necessarily Nitro's Fetch boundary. — [Elysia compiler docs](https://github.com/elysiajs/documentation/blob/main/docs/internal/jit-compiler.md); [Elysia adapter blog](https://github.com/elysiajs/documentation/blob/main/docs/blog/elysia-12.md).

### Inferences

**Proposed browser protocol:** same board/integration fixture, browser build, viewport, host and network/CPU profile; capability checks before timing; separate cold browser HTTP/query/service-worker state, cache-warm reload and SPA navigation. Measure document plus JS/CSS/fonts/images/API transfer using browser-reported encoded/decoded sizes and a declared observation boundary; distinguish first useful board from delayed feature chunks. Capture build chunk manifests/attribution and JS execution/long-task traces separately from downloaded bytes. Register timing-buffer handling; cross-origin zeros are unknown, not zero payload. — [existing browser collection](../../scripts/benchmarks/docker-runtime.mts); [Resource Timing limitations](https://w3c.github.io/resource-timing/).

Record navigation-to-useful-board/widget data, first interaction-to-painted-feedback and complete result, menu/search/modals/edit-save workflows, subscription frame delivery and errors. LCP/FCP alone cannot prove readiness. Raw scripted interaction durations are not field INP; obtain correctly defined Event Timing/INP observations in a later instrumentation phase if needed. Compare current SSR/RSC versus Vite SPA as whole UX systems; do not substitute “hydrated” for a meaningful shared capability marker or let an empty shell win. — [existing readiness and interaction gates](../../scripts/benchmarks/docker-runtime.mts); [pair scope/limits](../../scripts/benchmarks/benchmark-pair-lib.mts).

**Proposed DX protocol:**

- Hold dependency install and auxiliary service startup outside primary dev-server timing; report them separately. Match full dev topology and aggregate its memory. Record cold dependency/prebundle/build caches versus warm restart independently; timestamp process spawn → listening → first useful authenticated board. Include prewarming work in the appropriate phase instead of hiding it. — [current dev topology](../../apps/nextjs/next.config.ts); [Vite warmup docs](https://github.com/vitejs/vite/blob/main/docs/guide/performance.md).
- For HMR, use equivalent tiny frontend component text/style changes, a shared package change and a server handler change. Record file-write completion → visible painted update or verified new API result; state preserved versus full reload/restart, failures, dev process CPU/RAM and watch cardinality. Do not equate terminal “updated” to a usable UI. Perform future file mutations only in disposable benchmark snapshots, not concurrent researchers' source. Existing `dev-board.mts` can supply browser gates, not HMR editing/timing. — [dev-board harness](../../scripts/benchmarks/dev-board.mts); [build snapshot precedent](../../scripts/benchmarks/docker-build.mts).
- Measure lint/typecheck separately for cold uncached and warm incremental runs, same TypeScript version, strictness, included packages and generated route/API types. Record command, cache-hit status, graph scope, success/errors, wall time and process-tree peak. A Turbo cache hit is cache retrieval, not typecheck execution; generated-type preparation belongs in clean-check workflow timing. Also report cold/warm production compilation/image build independently. — [root scripts/toolchain](../../package.json); [app typecheck](../../apps/nextjs/package.json); [Vite transpile-only docs](https://github.com/vitejs/vite/blob/main/docs/guide/features.md).
- Qualitative DX rubric: code/debug/source-map clarity, route/schema inference, library/tool compatibility, restart/HMR correctness, ability to run one dev command, native install/release complexity and reproducibility. Keep human judgments separate from measured timing rather than inventing a DX score. — [existing command separation](../../package.json); [runtime/native packaging constraints](../../Dockerfile).

**Publication rules:** label external statements as “framework-author claim” with version/runtime/adapter/hardware/workload/sample methodology; archive the linked benchmark commit before reproducing it. Do not carry historical Deno/Workers or native Bun plaintext rankings into Nitro-on-Node/Bun Homarr. Only promote a result to a Homarr comparison after capability parity, provenance and independent-run checks. Missing data stays unavailable. A single winning microbenchmark cannot decide architecture. — [Hono primary benchmark scope](https://hono.dev/docs/concepts/benchmarks); [Elysia optimization scope](https://github.com/elysiajs/documentation/blob/main/docs/internal/jit-compiler.md); [existing claim limits](../../scripts/benchmarks/benchmark-pair-lib.mts).

### Gaps

- **Explicitly unmeasured:** Homarr Node/Bun/H3/Hono/Elysia RAM, natural heap, load CPU, independent cold/warm p50/p95/p99, saturation/errors, multi-hour soak/recovery, migration/startup timing, compressed OCI/updated image bytes, unpacked layer attribution, browser chunk/transfer/execution/interactive regressions, Vite startup/HMR and matched typecheck. No numerical winner or reduction target can be supplied.
- Required future decisions: product resource/latency/browser budgets and unacceptable capability/data-loss regressions; frontend rendering/topology; runtime/version support and architecture tiers; representative production workload. Research establishes a protocol and known blind spots, not approval to remove services, change persistence or ship a migration.
