# Homarr persistence, cache, tasks and WebSocket replacements

Research for [AJN-489](https://linear.app/ajnart/issue/AJN-489/map-persistence-cache-and-background-replacements), owned by Thomas. Read-only investigation; no Linear edits, migration, installation, prototype, measurements or tests. Local baseline: `66e2199f9cd1e4026249c3763413988bab8664c4`, inspected 2026-10-10. Repository links below are relative to this note and refer to the shared checkout. Upstream links use inspected commit hashes or exact published package versions where possible.

## 1. What exactly does the current checkout persist, coordinate and stream?

### Takeaway

Homarr already embeds the task and WebSocket applications in its HTTP process; the production runtime is **Node**, not Bun. Redis is more than disposable caching: it contains restart-persistent snapshots, integration sessions, temporary security state, atomic concurrency controls, invalidation generations, log history and pub/sub.

### Cited findings

#### Database and durable application data

- Runtime database engines are SQLite through `better-sqlite3` and external PostgreSQL through `pg.Pool`, both wrapped directly by Drizzle. MySQL/MariaDB are explicitly rejected; changing driver configuration does not convert existing data. — [SQLite factory](../../packages/core/src/infrastructure/db/drivers/sqlite.ts), [PostgreSQL factory](../../packages/core/src/infrastructure/db/drivers/postgresql.ts), [environment validation](../../packages/core/src/infrastructure/db/env.ts).
- Relational data includes users, accounts, sessions, API keys, groups and permissions, boards/layouts/sections/items, applications, integrations and encrypted secrets, media, icons/repositories, settings, onboarding, assistant threads/messages/configuration, cron configuration, trusted hostnames and custom-widget definitions/secrets. Media bytes are stored in a database BLOB, not merely filesystem pointers. SQLite and PostgreSQL have separate schemas. — [schema exports](../../packages/db/schema/index.ts), [SQLite schema](../../packages/db/schema/sqlite.ts#L180), [PostgreSQL schema](../../packages/db/schema/postgresql.ts).
- SQLite transaction callbacks are synchronous; PostgreSQL callbacks are asynchronous. Many multi-table mutations rely on these transactions. A concrete multi-user correctness boundary is gutter-root creation: PostgreSQL locks the board row with `FOR UPDATE`; SQLite uses an `immediate` transaction before reading roots and inserting missing ones. Replacing either with independent KV reads/writes would lose that boundary. — [transaction dispatcher](../../packages/db/transactions.ts), [transaction collection helpers](../../packages/db/collection.ts), [board mutation](../../packages/api/src/router/board.ts#L2776).
- Startup runs dialect-specific Drizzle SQL migrations, then seed and custom data migrations, before launching the application; migration failure aborts startup. Migrations can explicitly be disabled. Nitro task naming is not a replacement for this migration history or custom conversion logic. — [SQLite migrator](../../packages/db/migrations/sqlite/migrate.ts), [PostgreSQL migrator](../../packages/db/migrations/postgresql/migrate.ts), [custom migrations](../../packages/db/migrations/custom/index.ts), [production launcher](../../scripts/run.sh#L48).
- Production mounts `/appdata` and configures SQLite at `/appdata/db/db.sqlite`; trusted-certificate files and Redis dumps also live under this volume. The image ships the native `better_sqlite3.node` binding and migration bundles. — [Dockerfile](../../Dockerfile), [entrypoint](../../scripts/entrypoint.sh#L18).
- SQLite backup export opens the database read-only, requests `wal_checkpoint(TRUNCATE)`, uses `VACUUM INTO`, and creates a ZIP containing the database and version/encryption metadata. Import validates the archive, migrates a temporary database, re-encrypts secrets when necessary, replaces the database file and exits the application to trigger restart. PostgreSQL uses native backup tooling instead. The ZIP does **not** include Redis. — [export implementation](../../apps/nextjs/src/app/api/backup/export/route.ts), [import implementation](../../apps/nextjs/src/app/api/backup/import/route.ts), [backup contract](../../apps/docs/docs/management/backup.mdx).

#### Tasks and live transport

- Exactly three jobs are registered: weekly analytics (hidden, no manual/custom interval, run-on-start), weekly icon repository synchronization (run-on-start, relational transaction updates), and minute ping. Startup also deletes SQL login sessions whose auth providers are no longer enabled. Jobs have DB-backed enable flags and editable cron expressions, runtime start/stop/manual trigger, startup hooks and success/error status hooks. — [registry](../../packages/cron-jobs/src/index.ts), [analytics](../../packages/cron-jobs/src/jobs/analytics.ts), [icons](../../packages/cron-jobs/src/jobs/icons-updater.ts), [ping](../../packages/cron-jobs/src/jobs/ping.ts), [session cleanup](../../apps/tasks/src/on-start/session-cleanup.ts), [manager](../../packages/cron-jobs/src/job-manager.ts), [group lifecycle](../../packages/cron-jobs-core/src/group.ts).
- Existing Croner callbacks launch `catchingCallbackAsync()` with `void`; the inspected scheduling code supplies no explicit distributed lock or overlap protection and no persisted execution queue. Do not claim existing exactly-once/catch-up/retry guarantees. — [creator](../../packages/cron-jobs-core/src/creator.ts#L87), [interval changes](../../packages/cron-jobs/src/job-manager.ts#L35).
- `apps/nextjs` instrumentation imports both runtimes; tasks start asynchronously and failure exits the process, while WebSocket listener readiness is awaited. **Although the architecture reference says Bun, authoritative production code launches `node apps/nextjs/server.js`; Docker pins Node 24.18.0 and Bun 1.4.2 as a build/package tool.** The container additionally runs nginx and optional Redis. — [instrumentation](../../apps/nextjs/src/instrumentation-node.ts), [launcher](../../scripts/run.sh#L97), [Dockerfile](../../Dockerfile), [reference with stale runtime wording](../../.agents/skills/codebase-context/references/architecture.md#L23).
- Current WebSocket transport is tRPC over `ws` on port 3001: parses the session cookie, loads SQL session, creates authorized tRPC context, sends 30-second heartbeat with 5-second pong deadline, broadcasts reconnect on SIGTERM and closes the listener. — [WebSocket runtime](../../apps/websocket/src/main.ts).
- Current subscription procedures are cron status, permission-filtered logs, admin Docker log streams and integration-authorized Beszel realtime metrics. Docker/Beszel are direct upstream streams, not Redis-derived data; Beszel has bounded event queue and AbortController cleanup. Board client cache invalidation is separate from these subscription procedures. — [cron router](../../packages/api/src/router/cron-jobs.ts), [log router](../../packages/api/src/router/log.ts), [Docker stream](../../packages/api/src/router/docker/docker-router.ts#L185), [Beszel stream](../../packages/api/src/router/widgets/beszel.ts#L198), [board updater](../../packages/boards/src/updater.ts).

### Inferences

- A Redis-removal design must classify state by required lifetime. Disposable response caches can cold-start; statistics, latest task state, log/sample history and encrypted session/image/preview mappings currently have restart survival through Redis and must be deliberately converted or preserved. The SQL backup excluding Redis does not make those runtime capabilities nonexistent. — Evidence: duty table, [Redis persistence](../../packages/redis/redis.conf), [application restart loop](../../scripts/run.sh).
- One process eliminates inter-process messaging, **not** concurrency among users or asynchronous requests. CAS, one-time claims, credential-aware invalidation and late-write fencing remain necessary. — Evidence: [preview CAS](../../packages/api/src/router/custom-widget/preview-sessions.ts), [claims](../../packages/api/src/router/custom-widget/configuration-requests.ts), [response lock fencing](../../packages/redis/src/lib/channel.ts#L181), [board transaction](../../packages/api/src/router/board.ts#L2776).

### Gaps

- No execution or measurements were performed. File-level search cannot establish whether external deployments or dynamically loaded code use every exported primitive; the apparently unconsumed ping/queue paths need product confirmation before deletion.
- No proven task drain/recovery contract was found in Homarr's task entrypoint. Abrupt interruption can leave latest status `running`; preserving history and repairing restart state need an explicit policy, not a parity assumption.

## 2. What do current Nitro APIs actually provide, and what version/maturity caveats matter?

### Takeaway

Nitro can host SQL connectors, KV backends, function/HTTP caching, cron-triggered operations and same-listener WebSockets. These are abstractions and runtime integration, not replacement relational engines or automatic equivalents for Redis's atomic coordination; the latest released Nitro v3 is beta and differs materially from its current documentation/source.

### Cited findings

#### Version ledger

- Registry snapshots on the research date: `nitro` latest **3.0.260903-beta**, release git head `0509fb904ec87a0962187af13893b20cfdf2d34f`; `nitropack` latest **2.13.4**. V3 release depends on db0 `^0.4.1`, unstorage `^2.0.0-alpha.10`, ocache `^0.3.0`, CrossWS `^0.4.12`, H3 `^2.0.1-rc.31`; V2 instead depends on db0 `^0.3.4`, unstorage `^1.17.5`, CrossWS `^0.3.5` and H3 `^1.15.11`. These are not interchangeable API generations. — [Nitro registry](https://registry.npmjs.org/nitro), [nitropack registry](https://registry.npmjs.org/nitropack), [released package manifest](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/package.json).
- Current Nitro main was inspected at `cef5305050325a36601ff118b9651d43a0f9ba58`; db0 main at `be03a5173df0eef15df286f0f296195ed7a0fc56`; unstorage main at `aba7648bc6313b776310b05af7b2cd4db87ae463`; CrossWS main at `f93e98e0938f81685b4a373b9a6878ee2f95eb3c`. Main docs/source can contain unreleased functionality even when `package.json` version is unchanged. Critical differences below were checked against release source/package artifacts. — [Nitro source](https://github.com/nitrojs/nitro/tree/cef5305050325a36601ff118b9651d43a0f9ba58), [db0 source](https://github.com/unjs/db0/tree/be03a5173df0eef15df286f0f296195ed7a0fc56), [unstorage source](https://github.com/unjs/unstorage/tree/aba7648bc6313b776310b05af7b2cd4db87ae463), [CrossWS source](https://github.com/h3js/crossws/tree/f93e98e0938f81685b4a373b9a6878ee2f95eb3c).
- Context7 `/nitrojs/nitro` was consulted for database/tasks/WebSocket APIs; its snippets reference main. Direct primary source was needed to distinguish released behavior. Public paths `/guide/database`, `/guide/tasks`, `/guide/storage` returned 404; source docs were used instead. — [database source docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.database.md), [tasks source docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.tasks.md), [storage source docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/8.storage.md).

#### SQL: abstraction, not engine replacement

- `experimental.database` enables `useDatabase(name)` from `nitro/database`: lazily constructed/cached db0 connection, parameter-bound tagged `sql`, raw `exec`, and prepared statements. Default is file-backed SQLite `.data/db.sqlite`. Named connections select real drivers; documented connectors include Node SQLite, better-sqlite3, Bun SQLite, libSQL variants, PostgreSQL, MySQL, PGlite, Neon, PlanetScale and Cloudflare D1/Hyperdrive. Third-party driver packages still have to exist; Nitro may prompt/install missing dependencies during build. Database support is explicitly experimental; db0 calls itself early-stage. — [Nitro database docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.database.md), [connection cache](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/database.ts), [db0 maturity](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/README.md).
- `sqlite` aliases Node's built-in SQLite; source uses synchronous `DatabaseSync` even though the db0 facade returns promises. Bun must explicitly select `bun`/`bun-sqlite`, whose implementation imports `bun:sqlite`; its default filename is `.data/db.bun.sqlite`. Set the **existing absolute path** instead of relying on defaults. Node and Bun driver file/schema/transaction behavior must not be assumed identical from the runtime-agnostic facade. db0 SQLite docs also mention `.sqlite3` for better-sqlite3; the inspected Node source uses `.sqlite`, reinforcing explicit path selection. — [Node connector](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/connectors/node-sqlite.ts), [Bun connector](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/connectors/bun-sqlite.ts), [SQLite driver docs](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/2.connectors/sqlite.md).
- External PostgreSQL is supported, but db0's published PostgreSQL connector uses a single lazy **`pg.Client`**, not Homarr's `pg.Pool`. It rewrites db0 `?` parameters to `$n`. SQL dialect differences and PostgreSQL-specific operations still exist; unsupported `?` JSON operators require function equivalents. — [published connector](https://unpkg.com/db0@0.4.1/dist/connectors/postgresql.mjs), [PostgreSQL docs](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/2.connectors/postgresql.md), [Homarr pooled driver](../../packages/core/src/infrastructure/db/drivers/postgresql.ts).
- db0's core API has capabilities metadata and `dispose()`/async disposal, but no callback transaction or migration/backup manager in the inspected interface. Drizzle integration does provide BEGIN/COMMIT/ROLLBACK and nested savepoints. **It targets Drizzle v1/RC**, unlike Homarr's `0.45.2`; it changes relational configuration to `defineRelations`/`relations` and has join-column collision/streaming limitations. Published `db0@0.4.1` integration imports v1 `SQLiteAsyncDatabase` APIs, confirming this is not merely an unreleased documentation warning. — [core interface](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/types.ts), [integration docs](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/3.integrations/drizzle.md), [published SQLite integration](https://unpkg.com/db0@0.4.1/dist/_chunks/sqlite.mjs), [Homarr versions](../../package.json).
- Reviewed db0 Drizzle transaction implementations share the same connection/session and issue asynchronous BEGIN/body/COMMIT without an evident per-transaction mutex or checked-out connection. The PostgreSQL connector is single-client. This is **evidence of a multi-request interleaving risk**, not proof of isolated concurrent transactions or a measured bug. Preserve direct Drizzle drivers until concurrency semantics are settled. — [SQLite transaction source](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/integrations/drizzle/sqlite/_session.ts), [PostgreSQL transaction source](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/integrations/drizzle/postgres/_session.ts), [published SQLite implementation](https://unpkg.com/db0@0.4.1/dist/_chunks/sqlite.mjs).
- Nitro's inspected `useDatabase` module stores instances but registers no disposal hook itself. db0 connector disposal can close SQLite/client resources; the application must establish when connections stop accepting work and are disposed. Nitro does not generate Homarr's migrations or guarantee backup/restore compatibility. — [Nitro database runtime](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/database.ts), [db0 interface](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/src/types.ts), [Drizzle migration guidance](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/3.integrations/drizzle.md).

#### KV and caching

- **Released v3:** `useStorage()` from `nitro/storage`, `storage`/`devStorage` configuration. **Current main:** `useKV()` from `nitro/kv`, `kv` configuration and `$development.kv`; older names are deprecated aliases. API covers get/set/remove/list/meta/raw values/mounting, not a relational model. Default root memory loses data at restart. Persistent mounts may use filesystem, Redis or other unstorage drivers. — [release storage docs](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/docs/1.docs/8.storage.md), [main storage docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/8.storage.md).
- Published unstorage 2 alpha memory driver is a plain Map plus per-key TTL timers, without a capacity bound. Filesystem driver persists files and optionally uses atomic writes, but its `setItem` ignores TTL options; watch is filesystem notification, not Redis pub/sub or a durable message queue. A persistent filesystem mount is not evidence of fsync, multi-key transaction, CAS or expiry parity. — [published memory driver](https://unpkg.com/unstorage@2.0.0-alpha.10/dist/drivers/memory.mjs), [published filesystem driver](https://unpkg.com/unstorage@2.0.0-alpha.10/dist/drivers/fs.mjs).
- Unstorage Redis driver uses ioredis, supports URL/host/TLS/auth/database options, cluster settings, default/per-write **seconds** TTL and batch access. It exposes ordinary KV get/set/remove, not Homarr's NX token locks, Lua fenced writes, atomic counter/CAS, lists and subscription semantics through the generic API. An underlying ioredis instance can be accessed, but doing so retains the Redis dependency and driver-specific code. Redis persistence still depends on the Redis server configuration. — [Redis driver docs](https://github.com/unjs/unstorage/blob/aba7648bc6313b776310b05af7b2cd4db87ae463/docs/2.drivers/redis.md), [driver implementation](https://github.com/unjs/unstorage/blob/aba7648bc6313b776310b05af7b2cd4db87ae463/src/drivers/redis.ts).
- Nitro v3 cache is powered by **ocache**, not merely the older Nitro v2 cache implementation. `defineCachedFunction` supports keying, integrity/validation, explicit invalidation/expiry and single-flight resolution per function instance/key; `defineCachedHandler` exposes a plain handler rather than those invalidation methods. SWR is opt-in, `maxAge` defaults to one second, and SWR without `staleMaxAge` has unlimited stale retention/no storage TTL. Function cache JSON serialization needs explicit transforms for non-JSON shapes. — [released cache docs](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/docs/1.docs/7.cache.md), [published ocache implementation](https://unpkg.com/ocache@0.3.0/dist/index.mjs).
- **Released v3 cache default is unstorage root memory, not automatically a bounded LRU.** A custom bounded ocache storage can be supplied. **Current main only** adds explicit cache `memory`/`fs`/`kv` drivers with default memory LRU at 10,000 entries/100 MB and configurable `maxSize`/`maxBytes`; fs does not remove expired files automatically. Do not report these new configuration defaults as released beta behavior. — [release runtime](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/cache.ts), [main cache docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/7.cache.md), [published ocache memory storage](https://unpkg.com/ocache@0.3.0/dist/index.mjs).
- HTTP cache wrappers intentionally sanitize request headers/query/cookies unless allowed into the key. Main/release docs require explicit `varies`, query/cookie/authorization allowances and honor private/no-store responses. Generic whole-route caching across authorized users is unsafe without reproducing the existing permission/credential/identity boundaries. Redis-backed cache storage does **not** make ocache's local pending Map a distributed refresh lock. — [released cache policy](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/docs/1.docs/7.cache.md), [ocache pending Map](https://unpkg.com/ocache@0.3.0/dist/index.mjs), [Homarr identity](../../packages/request-handler/src/lib/integration-request-handler.ts).

#### Tasks and shutdown

- `experimental.tasks` enables named `defineTask`/`runTask`, filesystem/config registration and cron-to-task mappings. Node/Bun persistent-server presets use Croner; provider presets may use platform cron. API is explicitly experimental. `waitUntil` is optional runtime context, not durable storage. — [main task docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.tasks.md).
- Documented concurrency is one in-flight run per task name per instance; different payloads are coalesced into the first result, not queued. Source running map is local. **Implementation caveat:** both inspected release/main check that map before awaiting lazy handler resolution, then set it afterward without a second check; two first calls can pass the guard while loading. Treat documented deduplication as insufficient evidence for a hard overlap guarantee at this boundary. — [main docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.tasks.md), [released task runtime](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/task.ts), [main task runtime](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/runtime/internal/task.ts).
- Inspected tasks have no durable queue, missed-run recovery, retry history, cross-instance lock, payload-scoped idempotency, runtime DB-configured schedule mutation or built-in Homarr status publisher. Main registers `close` to stop cron handles; released beta runtime does **not**. Source also constructs scheduledTime payload once at schedule-runner startup, whereas main docs describe current timestamp; avoid treating it as an authoritative per-run time. — [release implementation](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/task.ts), [main implementation](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/runtime/internal/task.ts), [main docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.tasks.md).
- Nitro wraps srvx server close so SIGINT/SIGTERM/explicit close await Nitro `close` hooks, once. This provides a lifecycle attachment point, not persisted task execution or automatic cancellation/drain of arbitrary upstream work. `useDatabase` itself does not hook it. — [released shutdown hook wrapper](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/shutdown.ts), [database runtime](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/database.ts).

#### WebSockets and live streams

- V3 uses `features.websocket: true` and `defineWebSocketHandler`; CrossWS powers Node and native Bun adapters on the HTTP listener. Upgrade hooks can authenticate/attach context; peer APIs send/subscribe/unsubscribe/publish/close. Peer publication is namespace-scoped and excludes the publishing peer. These are transport primitives, not tRPC wire compatibility, role middleware, latest-value replay or historical delivery. — [released WebSocket docs](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/docs/1.docs/50.websocket.md), [Node runtime](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/presets/node/runtime/node-server.ts), [Bun runtime](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/presets/bun/runtime/bun.ts).
- Published **CrossWS 0.4.15** has optional sync adapters for Redis, PostgreSQL LISTEN/NOTIFY, Node cluster IPC and BroadcastChannel. Redis accepts caller-supplied ioredis/node-redis and duplicates a subscriber; PostgreSQL requires a dedicated client rather than a rotating Pool. This disproves a blanket claim that current CrossWS cannot relay across processes, but does not provide durable replay. Nitro's inspected preset code constructs adapters with only the hook resolver, so do not assume a storage Redis mount automatically enables CrossWS sync. — [published sync implementation](https://unpkg.com/crossws@0.4.15/dist/sync.mjs), [Redis sync source](https://github.com/h3js/crossws/blob/f93e98e0938f81685b4a373b9a6878ee2f95eb3c/src/sync/redis.ts), [Nitro adapter construction](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/presets/node/runtime/node-server.ts).
- H3 SSE provides one-way HTTP streams with close callbacks, event IDs and retry hints, suitable in principle for logs/status/Beszel outputs. Automatic browser reconnection does not by itself replay missed records; application state/history remains necessary. — [Nitro SSE docs](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/50.websocket.md#server-sent-events-sse).

### Inferences

- Safest SQL approach is retaining Homarr's existing Drizzle/schema/migrators on the existing engines while changing only hosting. A runtime migration does not require db0; adopting it now adds ORM-version and transaction-isolation work without removing the relational engine. — Evidence: [Homarr drivers](../../packages/core/src/infrastructure/db/drivers/index.ts), [db0 integration constraints](https://github.com/unjs/db0/blob/be03a5173df0eef15df286f0f296195ed7a0fc56/docs/3.integrations/drizzle.md).
- KV-driver portability should be limited to plain cache/blob metadata until atomic and lifetime requirements are separately modeled. `getItem` then `setItem` cannot implement a security CAS or NX lease across awaited operations. — Evidence: [KV API](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/docs/1.docs/8.storage.md), [current preview CAS](../../packages/api/src/router/custom-widget/preview-sessions.ts).

### Gaps

- No driver or replacement was executed. Native addon packaging on the target image, Node/Bun cancellation/backpressure behavior, transaction interleaving, restore compatibility and actual throughput remain unvalidated; promise-shaped APIs do not prove nonblocking execution.
- CrossWS sync availability is confirmed for 0.4.15, not every version allowed by Nitro's `^0.4.12`. A fixed lockfile/version is required. No first-class Nitro sync configuration was verified.
- No backup manager, migration ledger, distributed task coordinator or atomic KV CAS was found in the inspected Nitro surfaces. This is a bounded source finding, not a claim that no third-party ecosystem solution exists.

## 3. Which topology is feasible, what can safely disappear, and what path preserves capabilities?

### Takeaway

Feasible conservative target: one **Node 24.18** Nitro server in one container, the existing SQLite file on `/appdata` or external PostgreSQL, embedded job manager, same-listener live transport, and Redis retained initially. A strict Redis-free single-process target is plausible only with explicit durable-state conversion and application-owned atomic concurrency/invalidation services; no Nitro-only parity is established.

### Cited findings

### Inferences

#### Safe simplification sequence

1. **Pin the target release and runtime before API design.** Use Node first: production already runs Node and ships its native SQLite binding. Preserve `/appdata/db/db.sqlite`, schema/migration ledger, encryption material, media BLOBs and external PostgreSQL/Redis configuration. Replacing SQL/KV APIs and choosing Bun are separate decisions. — Evidence: [production launcher](../../scripts/run.sh), [Dockerfile](../../Dockerfile), [version ledger](https://registry.npmjs.org/nitro).
2. **Consolidate listeners and lifecycle, not data semantics.** Nitro can serve HTTP and upgraded connections on one listener. Remove `apps/websocket`'s separate port/listener only after preserving tRPC protocol/context/heartbeat/reconnect or explicitly converting all clients to a replacement protocol. Tasks are already embedded, so this is not a measured multi-process reduction. nginx can potentially disappear if its forwarding/static/header/timeout behavior is replicated; that full HTTP audit is outside this note. — Evidence: [current instrumentation](../../apps/nextjs/src/instrumentation-node.ts), [ws implementation](../../apps/websocket/src/main.ts), [Nitro Node listener](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/presets/node/runtime/node-server.ts).
3. **Keep Croner and DB-backed JobManager initially.** Put migration readiness before accepting writes; start session cleanup and run-on-start hooks with current failure semantics. Add lifecycle ownership for stopping timers, aborting/draining upstream work and disposing database/Redis connections. Retain durable latest execution history but repair stale `running` after restart. Nitro task wrappers may simplify invocation, but do not remove runtime schedule management or add execution durability. — Evidence: [launcher migration barrier](../../scripts/run.sh#L48), [group startup](../../packages/cron-jobs-core/src/group.ts), [status publication](../../packages/cron-job-status/src/publisher.ts), [Nitro shutdown hook](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/shutdown.ts).
4. **Preserve Redis first, then classify and convert deliberately.** Plain cache accesses can adopt unstorage selectively. Preserve raw ioredis for atomic locks/CAS/rate/claim operations and existing SuperJSON envelopes. For an eventual strict singleton, convert statistics/history/security mappings into SQLite or PostgreSQL tables with expiry and bounded retention, preserve remaining TTLs/revisions/encrypted values and verify conversion before removing Redis. Avoid migrating expiring locks as active ownership: quiesce owners, reconcile state, and establish a fresh startup epoch. This is a proposed conversion plan, not a performed migration. — Evidence: [atomic Redis operations](../../packages/redis/src/lib/channel.ts), [security state](../../packages/api/src/router/custom-widget/preview-sessions.ts), [current persistence](../../packages/redis/redis.conf).
5. **Only then remove the Redis daemon and its supervisor branch.** Replace cross-process pub/sub with a local bus and persistent replay reads; keep bounded caches/queues, same-process keyed guards, atomically updated preview revisions/claims and rate/concurrency rules. Choose explicit restart policy for counters and active leases: application-only restarts currently retain their Redis state. A process restart resetting security windows would be a behavior change, not free equivalence. — Evidence: [launcher restarts only application](../../scripts/run.sh#L100), [limiter semantics](../../packages/custom-widgets/src/server/request-limits.ts), [log history contract](../../packages/api/src/router/log.ts).

#### What the topology can remove

- **Without replacing persistence:** separate WebSocket listener/port and task application packaging boundaries can disappear into Nitro; the relational engine, migration logic and Redis semantics can stay unchanged. This targets simpler lifecycle/transport ownership, not an asserted performance win. — Evidence: [already embedded runtimes](../../apps/nextjs/src/instrumentation-node.ts), [Nitro listener/tasks](https://github.com/nitrojs/nitro/blob/cef5305050325a36601ff118b9651d43a0f9ba58/src/presets/node/runtime/node-server.ts).
- **After explicit single-process state conversion:** internal Redis and its process supervision are removable in principle. Local buses/guards are valid only when HTTP, timers, streams and operational writes really share one instance. One container with Node cluster/workers is **not** this condition; rolling replicas/external writers require shared coordination again. SQLite still handles user concurrency transactionally; persistent caches still need invalidation/epoch guarantees. — Evidence: [current SQL locking](../../packages/api/src/router/board.ts#L2776), [Redis coordination](../../packages/redis/src/lib/channel.ts), [Nitro per-instance task map](https://github.com/nitrojs/nitro/blob/0509fb904ec87a0962187af13893b20cfdf2d34f/src/runtime/internal/task.ts).
- **External service path remains valid:** external PostgreSQL and Redis can be retained for existing deployments. db0 PostgreSQL is a different client lifecycle/pooling choice; unstorage Redis covers KV but raw commands remain for current atomic behavior. CrossWS 0.4.15 can relay through Redis or dedicated PostgreSQL LISTEN/NOTIFY, but wiring it into Nitro and replay/error semantics are additional work. — Evidence: [db0 client](https://unpkg.com/db0@0.4.1/dist/connectors/postgresql.mjs), [unstorage Redis](https://github.com/unjs/unstorage/blob/aba7648bc6313b776310b05af7b2cd4db87ae463/src/drivers/redis.ts), [CrossWS sync](https://unpkg.com/crossws@0.4.15/dist/sync.mjs).

### Gaps / decisions required

- **Hard gaps before parity claims:** db0/Drizzle v1 compatibility and concurrent transaction isolation; scheduler runtime mutation and hard overlap exclusion; crash/restart conversion of Redis state; owner-fenced security controls; stream protocol/client compatibility; shutdown drain/disposal; released-beta cache bounds; backup/restore and encrypted-value conversion. No experiments were authorized or performed.
- Decide whether strict singleton is a supported deployment contract or merely the default. Preserving external PostgreSQL alone does not make process-local invalidation/rate limits correct across replicas. If multi-instance behavior must remain supported, retain a shared coordinator or design transactional database equivalents before deleting Redis.
- Decide which Redis-derived values can explicitly be cold-started versus must survive restart. Under the assigned preserve-capabilities constraint, do not silently discard statistics, histories, preview/configuration requests or issued image mappings.
- Avoid selecting PGlite/libSQL/cloud-provider engines solely because listed connectors exist: data conversion, SQL features, migration journals, backup and target-runtime behavior were not verified here.
- Recommended next architecture decision: **Node Nitro hosting with existing Drizzle + embedded Croner/JobManager + Redis retained**, then a separately scoped, contract-led Redis elimination. Research establishes feasibility and gaps, not permission to migrate or a measured justification for a full engine/runtime rewrite.
