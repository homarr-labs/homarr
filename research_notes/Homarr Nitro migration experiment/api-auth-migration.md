## 1. What Next.js/tRPC coupling and capabilities must survive?

### Takeaway

Homarr has substantial reusable domain and infrastructure code, but Next-specific request context, authentication cookies, rendering/hydration, navigation, and localization permeate shared packages. Removing Next.js does not require simultaneously removing tRPC; removing both at once would also replace the authorization, serialization, subscription, and MCP dispatch boundaries described below. [API context](../../packages/api/src/trpc.ts), [RSC context](../../packages/api/src/rsc-context.ts), [client provider](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx), [MCP dispatcher](../../packages/api/src/mcp-tools.ts).

#### Authentication, sessions, permissions and API keys

- Installed auth is `next-auth` **5.0.0-beta.32** with `@auth/core` **0.41.3**; Next is **16.3.6**, tRPC **11.18.0**, and catalog Vite **8.1.4**. Auth uses a custom Drizzle adapter over Homarr's existing users/accounts/sessions tables. Provider-scoped email lookup prevents accidental cross-provider identity merging, with an explicit dangerous credentials-linking option. [dependency catalog](../../package.json), [adapter](../../packages/auth/adapter.ts), [identity schema](../../packages/db/schema/sqlite.ts).
- Credentials use lowercased username plus `provider='credentials'`, comparing existing bcrypt hashes. LDAP service-binds, searches the configured user attributes/filter, rejects ambiguous results and invalid email, binds as the user to verify the password, loads external groups, and creates/reuses a provider-scoped local user. Preserve stored hashes, provider identity and user IDs, not only successful login screens. [credentials authorization](../../packages/auth/providers/credentials/authorization/basic-authorization.ts), [bcrypt helpers](../../packages/auth/security.ts), [LDAP authorization](../../packages/auth/providers/credentials/authorization/ldap-authorization.ts).
- **Critical nonstandard behavior:** although Auth.js Credentials normally supports JWT sessions, Homarr manually creates database sessions and sets `homarr.session-token` (or configured prefix) in the sign-in callback, runs `session.strategy='database'`, and overrides JWT encode/decode to return the session cookie/null. Cookie writes call `next/headers`. This is a custom compatibility mechanism to port or deliberately replace, not a stock adapter configuration that can be copied unchanged. [auth configuration, lines 27–128](../../packages/auth/configuration.ts), [session helpers](../../packages/auth/session.ts), [Auth.js credentials reference](https://authjs.dev/reference/core/providers/credentials).
- OIDC supports issuer/client/token-auth method/scope customization, reverse-proxy callback URL construction, profile-name extraction, strict verified-email checks for credential linking, optionally forcing userinfo, a FusionAuth token-response workaround, and custom trusted-certificate fetch. Login events synchronize external groups unless configured for local management, retain the everyone group, update user name/image and write the theme cookie. [OIDC provider](../../packages/auth/providers/oidc/oidc-provider.ts), [email verification](../../packages/auth/providers/oidc/verified-email.ts), [events](../../packages/auth/events.ts), [redirect handling](../../packages/auth/redirect.ts).
- Auth route inspects the provider in the URL, conditionally enables secure cookies and rewrites the request origin from forwarded headers. Main auth access is NextAuth wrapped in React request cache; the browser exports `signIn`, `signOut`, `useSession` and `SessionProvider` from `next-auth/react`. Logout/session-refresh behavior and proxy URL trust need replacement adapters too. [auth route](../../apps/nextjs/src/app/api/auth/%5B...nextauth%5D/route.ts), [server auth](../../packages/auth/next.ts), [client auth](../../packages/auth/client.ts).
- Permissions are deeper than login/admin checks: board ownership, user/group grants, public access and global overrides compose view/modify/full; denied board access deliberately becomes NOT_FOUND to avoid existence disclosure. Integration use/interact/full are separate. Native query access can be inherited from a visible board, including public boards, whereas arbitrary integration requests require full integration access. Permission expansion is recomputed from DB groups for sessions/API keys. [board permission constructor](../../packages/auth/permissions/board-permissions.ts), [board denial semantics](../../packages/api/src/router/board/board-access.ts), [integration permissions](../../packages/auth/permissions/integration-permissions.ts), [query access](../../packages/auth/permissions/integration-query-permissions.ts), [session permissions](../../packages/auth/callbacks.ts).
- API keys are `<id>.<token>`, bcrypt-validated against a stored key and converted to the creator's current permission-bearing session. **Authentication differs by transport:** tRPC tries `ApiKey`, then cookie session; REST explicitly uses only `ApiKey`, never ambient cookie sessions, with wildcard CORS/preflight; MCP accepts `ApiKey` or Bearer with the same key format and no browser-cookie fallback. Preserve these distinctions rather than applying one generic cookie middleware to all routes. [key validation](../../packages/auth/api-key/get-api-key-session.ts), [tRPC HTTP route](../../apps/nextjs/src/app/api/trpc/%5Btrpc%5D/route.ts), [REST route](../../apps/nextjs/src/app/api/%5B...trpc%5D/route.ts), [MCP authentication](../../apps/nextjs/src/app/api/mcp/_handler.ts).

#### Integration APIs and public behavior

- Most integration behavior is already server-package-owned: `createIntegrationAsync` lazily loads concrete clients, typed integration interfaces describe capabilities, and trusted-certificate-aware HTTP/WebSocket clients perform upstream operations. Native widget middleware checks integration kinds/access before decrypting secrets. Integration business code need not be reimplemented merely because the HTTP router changes. [factory](../../packages/integrations/src/base/creator.ts), [base integration](../../packages/integrations/src/base/integration.ts), [native middleware](../../packages/api/src/middlewares/integration.ts), [package manifest](../../packages/integrations/package.json).
- Public boards can grant native integration **read** access via board visibility without handing out credentials/full access. Anonymous app visibility is restricted to apps/bookmarks on public boards; authenticated users can see individual apps through this access helper, while administrative list surfaces have their own permission requirements. Blanket `requireSession` on every widget read would regress public dashboards. [integration query permissions](../../packages/auth/permissions/integration-query-permissions.ts), [app access control](../../packages/api/src/router/app/app-access-control.ts), [public API documentation](https://homarr.dev/docs/management/api).
- `POST /api/integrations/request`, tRPC `integration.request`, and MCP `integration_request` share the generic proxy contract: exactly one ID/name/kind selector; all methods require full access; DELETE additionally requires confirmation; path cannot escape saved origin/path prefix; stored authentication wins; decrypt only after authorization; trusted certificate/hostname checking; response-secret redaction; no retries, redirects or caching, including GET. The documented ceilings are 10 KiB body, 16 KiB headers, 1 MiB response and 15 seconds. Homarr HTTP 200 may still describe an upstream failure in `ok/status/data`. [request procedure](../../packages/api/src/router/integration/integration-request.ts), [connection authorization](../../packages/api/src/router/integration/integration-http.ts), [public contract](https://homarr.dev/docs/management/api#call-any-integration-api-endpoint).
- iCal and TrueNAS are intentionally excluded from the generic HTTP tool, not removed from native Homarr integrations. qBittorrent native operations support API-key **or** username/password credentials and discover version before choosing v5 stop/start versus legacy pause/resume. Generic qBittorrent authentication declares only API-key Bearer mode; public Homarr docs require qBittorrent 5.2+ for that mode. UniFi generic HTTP authentication is adapter-owned and documented as requiring HTTPS and the actual controller port. [integration definitions](../../packages/definitions/src/integration.ts), [qBittorrent implementation](../../packages/integrations/src/download-client/qbittorrent/qbittorrent-integration.ts), [Homarr public documentation](https://homarr.dev/docs/management/api#call-any-integration-api-endpoint).
- Independent upstream verification: qBittorrent's official WebUI API documentation specifies `/api/v2/...`, method-sensitive GET/POST, login with an SID cookie, matching Origin/Referer host and port, and business failures that may use HTTP 200. It supports the need to retain service-aware adapters rather than replacing all integration auth with generic browser Bearer fetch. Its retrieved v5.0+ page does **not** establish the newer API-key 5.2 contract; see gaps. [official qBittorrent API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-%28qBittorrent-5.0%29).

### Gaps

- This is an architectural/source inventory, not demonstrated parity across every integration deployment/provider version. No live private integration was contacted and no login, upload/restore, subscription or MCP exchange was executed.
- `getSessionFromTokenAsync` returns a found session with its expiry but does not itself reject expired rows. It is used for WS auth; migration must resolve expiry enforcement/revocation policy explicitly rather than treating this helper as a complete secure session validator. [session helper](../../packages/auth/session.ts), [WS consumer](../../apps/websocket/src/main.ts).
- Retrieved public Homarr API prose says same-origin requests can use a session cookie, but the REST implementation explicitly excludes cookie auth. Treat that wording as applicable to the tRPC/browser surface, not as a reason to broaden REST authentication during migration. [public prose](https://homarr.dev/docs/management/api#authentication-and-browser-access), [REST source](../../apps/nextjs/src/app/api/%5B...trpc%5D/route.ts).
- Backup import's examined re-encryption function handles `integrationSecret`; durable schema also contains Assistant and Custom Widget encrypted material. Full-key-conversion coverage and safe restore/restart behavior require a dedicated review before any format/key change; do not claim current backup conversion proves those families survive a new key. [import function](../../apps/nextjs/src/app/api/backup/import/route.ts), [encrypted schema families](../../packages/db/schema/sqlite.ts).
- Upstream API-key behavior for qBittorrent 5.2 and full UniFi compatibility were not independently verified beyond Homarr's implementation/public contract. TrueNAS official API URL `https://api.truenas.com/v25.04/` returned an empty object listing, so it was not used as proof of protocol details; the exclusion claim above is specifically Homarr's current implementation. ## 2. How do Nitro/H3 typed fetch/OpenAPI, Hono RPC and Elysia Eden compare?

### Takeaway

Nitro is a server build/runtime layer that can host H3, tRPC, Hono or Elysia; these are not mutually exclusive deployment alternatives. For this monorepo, keeping tRPC preserves the most existing type/behavior contracts initially; Hono RPC or Eden offers replacement server-inferred TypeScript contracts, whereas a schema-generated OpenAPI client is useful for framework-independent public HTTP contracts but does not supply authorization, MCP semantics or existing subscriptions. [Nitro framework integration](https://nitro.build/raw/blog/v3-beta.md), [official Nitro+tRPC example](https://nitro.build/raw/examples/vite-trpc.md), [Hono RPC](https://hono.dev/docs/guides/rpc), [Eden](https://elysiajs.com/eden/treaty/websocket.html), [OpenAPI client](https://openapi-ts.dev/openapi-fetch/).

### Cited Findings

| Option | Verified contract/type behavior | Validation and realtime implications |
| --- | --- | --- |
| Nitro v3 + H3 | Native Vite plugin builds frontend/backend into `.output`; route handlers use web Request/Response. Current documented `serverFetch` returns a Response and makes internal requests through Nitro without a network round-trip. Handler/config typing is not evidence of an end-to-end browser RPC client with inferred validated request bodies. [Vite integration](https://nitro.build/raw/docs/vite.md), [server utilities](https://nitro.build/raw/docs/utils.md), [TypeScript](https://nitro.build/raw/docs/typescript.md) | H3 supports runtime Standard Schema validation for body/query/params and explicitly warns that TypeScript generics are not validation. CrossWS hooks/upgrade context, pub/sub and SSE are primitives, not tRPC protocol compatibility. [validation](https://h3.dev/examples/validate-data), [Nitro WebSockets/SSE](https://nitro.build/raw/docs/websocket.md) |
| Nitro OpenAPI + generated client | Experimental OpenAPI 3.1 extraction reads explicit `defineRouteMeta` metadata; path params are inferred, but bodies/responses/security need an accurate schema contract. `openapi-typescript` plus `openapi-fetch` supplies method/path/request/response types from generated `paths`. It is a fetch client, not a runtime access-control layer. [Nitro OpenAPI](https://nitro.build/raw/docs/openapi.md), [openapi-fetch](https://openapi-ts.dev/openapi-fetch/) | Runtime Zod/H3 validation must still run on the server. Define multipart/binary/stream contracts separately and add Query adapters/cache policies. OpenAPI security objects document requirements; they do not execute Homarr permission logic or recreate MCP metadata. [H3 validation](https://h3.dev/examples/validate-data), [current authorization](../../packages/api/src/trpc.ts), [MCP metadata](../../packages/api/src/mcp-tools.ts) |
| Hono RPC | `hc<typeof routes>` infers validator input and `c.json` output/status types without schema code generation; routes must preserve chained inference. Global error middleware is not inferred automatically without `ApplyGlobalResponse`; monorepo strictness, matching Hono versions, large type-graph IDE cost and splitting/precompiling clients are documented caveats. [Hono RPC](https://hono.dev/docs/guides/rpc) | Zod/Standard Schema validators can reuse existing schemas; Zod OpenAPI is a separate extended integration. RPC WebSocket helper opens a browser WebSocket rather than preserving Homarr tRPC subscriptions. Query lifecycle, serialization, cancellation and application event validation still require design. [Zod OpenAPI](https://hono.dev/examples/zod-openapi), [WS helper](https://hono.dev/docs/helpers/websocket), [current links](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx) |
| Elysia + Eden Treaty | Eden infers from an exported Elysia application type; routes carry runtime schema and status contracts. Elysia supports Standard Schema (including Zod), so adopting it does not inherently require rewriting every schema to TypeBox. It also supports Node through `@elysia/node`, not only Bun. [Elysia overview](https://github.com/elysiajs/documentation/blob/main/docs/at-glance.md), [Node adapter](https://elysiajs.com/integrations/node.html) | Eden offers typed `.subscribe()` WebSocket endpoints with body/response schemas. Elysia OpenAPI is a plugin and Standard Schema conversion can require `mapJsonSchema` (`z.toJSONSchema` for Zod 4); output types/documentation do not replace runtime auth or server-side authorization. [Eden WS](https://elysiajs.com/eden/treaty/websocket.html), [OpenAPI](https://elysiajs.com/patterns/openapi.md) |
| Retain tRPC under Nitro | Nitro has an official Vite+tRPC example using `fetchRequestHandler` and exporting `AppRouter`. Homarr already uses that fetch adapter, keeping transport migration narrower than procedure/client rewriting. [Nitro example](https://nitro.build/raw/examples/vite-trpc.md), [existing HTTP route](../../apps/nextjs/src/app/api/trpc/%5Btrpc%5D/route.ts) | Existing SuperJSON, input transforms, middleware, procedure metadata and callers remain usable after Next-specific context/auth adapters are separated. HTTP SSE/WS still need deliberate hosting and lifecycle wiring. [tRPC setup](../../packages/api/src/trpc.ts), [client transport](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx), [WS host](../../apps/websocket/src/main.ts) |

- **Version qualification:** current Nitro documentation explicitly describes a v3 public beta, renaming `nitropack` to `nitro`, H3 v2, removing auto-imports, opt-in server scanning and changes to presets/utilities. v2 documentation describes generated server-route types and generated tsconfig instead. The v3 evidence retrieved here does not establish v2-style `$fetch` route inference or a validated browser request contract in v3. Select/pin a version before using snippets or estimating migration work. [v3 beta announcement](https://nitro.build/raw/blog/v3-beta.md), [migration guide](https://nitro.build/raw/docs/migration.md), [v2 TypeScript guide](https://v2.nitro.build/guide/typescript).
- Vite provides low-level SSR support but describes it as intended for library/framework authors; it is not a replacement App Router by itself. Nitro has an RSC example using the **experimental** Vite RSC plugin, custom navigation, action serialization and streamed hydration. This establishes feasibility, not drop-in compatibility with Next routing, metadata, next-intl or Homarr's request cache. [Vite SSR guide](https://vite.dev/guide/ssr.html), [Nitro RSC example](https://nitro.build/raw/examples/vite-rsc.md).
- Auth.js Core `Auth(request, config)` accepts a standard Request and returns a Response, providing a plausible framework-neutral OIDC/auth seam. It still defaults credentials to JWT-oriented behavior and database strategy uses a cookie containing a sessionToken. Homarr's explicit manual session/cookie customization remains work even if Core is retained. [Auth.js Core](https://authjs.dev/reference/core), [Credentials](https://authjs.dev/reference/core/providers/credentials), [Homarr configuration](../../packages/auth/configuration.ts).
- Existing OpenAPI is already curated: optional auth is patched for selected public reads; the generator's root-refinement omission is repaired for user preferences; integration examples avoid mutually exclusive selectors; only an explicitly selected eager router is exposed. Existing MCP likewise has its own filtering, schemas, names/descriptions and safe caller dispatch. Neither metadata set is mechanically equivalent to generated REST routes. [OpenAPI corrections](../../packages/api/src/open-api.ts), [MCP extraction](../../packages/api/src/mcp-tools.ts), [MCP route](../../apps/nextjs/src/app/api/mcp/_handler.ts).

### Inferences

- Decision separation: choose (1) frontend rendering/router, (2) server packager/runtime, (3) application transport/type contract, and (4) auth integration independently. Vite+Nitro+tRPC is a valid staged architecture; Vite+Nitro+Hono is also viable if Hono inference is desired. There is no evidence that choosing Nitro requires giving up RPC or domain packages. [Nitro integrations](https://nitro.build/raw/blog/v3-beta.md), [tRPC example](https://nitro.build/raw/examples/vite-trpc.md).
- For a no-codegen internal TS API, Hono/Eden infer more directly from validated handlers than an unqualified assertion of “Nitro typed fetch.” For a public/multilanguage contract, curated OpenAPI is more independent from server implementation. Neither removes the need to normalize errors, Date/Map/binary serialization, cache invalidations, retry rules or stream events that tRPC currently supplies. [Hono RPC](https://hono.dev/docs/guides/rpc), [Eden example](https://github.com/elysiajs/documentation/blob/main/docs/index.md), [OpenAPI client](https://openapi-ts.dev/openapi-fetch/), [existing client behavior](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx).
- Do not export every route as an MCP tool from OpenAPI. Keep an intentional capability catalog with stable names, bounded schemas, descriptions/confirmation policies, query-versus-mutation semantics, secret exclusions and the same authorization-enforcing service dispatcher. The current metadata/extractor is a precise baseline for that design. [tool extractor](../../packages/api/src/mcp-tools.ts), [integration tool policy](../../packages/api/src/router/integration/integration-request.ts), [protocol registration](../../apps/nextjs/src/app/api/mcp/_protocol.ts).

### Gaps

- No selected Nitro version, verified native-addon bundling, Hono/Elysia client performance measurement, CrossWS+tRPC bridge, or complete inference comparison was executed. Do not use framework bundle-size/performance marketing as a Homarr container-size or memory estimate.
- Context7 indexed different moving documentation/source branches; direct current Nitro docs superseded older snippets where names/options differed. A future implementation should use the chosen release's exact docs/types and validate Node adapter subscription/stream behavior, not assume all deployment presets have parity. [Nitro migration](https://nitro.build/raw/docs/migration.md), [CrossWS adapter caveats](https://nitro.build/raw/docs/websocket.md), [Elysia Node](https://elysiajs.com/integrations/node.html).
- Auth.js Core provides a standard handler but the inspected primary docs do not provide a ready-made Nitro integration preserving Homarr's credentials/database-session hack. Treat that integration as security-sensitive implementation work; retaining Auth.js versus changing authentication libraries remains a human architecture decision. [Auth.js Core](https://authjs.dev/reference/core), [Homarr manual session handling](../../packages/auth/configuration.ts).

## 3. What safe seams support incremental replacement without losing data or capabilities?

### Takeaway

The safest sequence is to isolate request/auth/domain adapters, mount the existing tRPC/public REST/MCP/streaming surface on the new server, and move UI routes incrementally before changing API contracts. Keep the existing Node/Drizzle/Redis/certificate/data-volume behavior and a single external origin; frontend/backend can be internally split without requiring multiple user-deployed containers or static-only hosting. [existing runtime](../../Dockerfile), [nginx routing](../../nginx.conf), [Nitro Vite output](https://nitro.build/raw/docs/vite.md), [tRPC fetch seam](https://nitro.build/raw/examples/vite-trpc.md).

### Inferences

1. **Extract adapter seams first, without changing the external API.** Split Next-only `headers/cookies/auth`, React request memoization, userAgent and revalidation from explicit context/domain functions. Expose safe client/server entrypoints so Vite cannot accidentally include DB, env secrets, Node clients or Next-only utilities. This is particularly important because `@homarr/common/server` and `@homarr/auth` currently combine reusable helpers with framework-dependent imports. [RSC context](../../packages/api/src/rsc-context.ts), [common exports](../../packages/common/src/server.ts), [auth exports](../../packages/auth/index.ts), [shared SSR cookie import](../../packages/api/src/shared.ts).
2. **Strangle HTTP routes before procedures.** Mount existing tRPC fetch routes and curated REST/MCP adapters in Nitro, retaining stable paths, auth rules, schemas and SuperJSON. Standard web Response routes (health/images/MCP/Assistant) are safer initial moves than a wholesale router rewrite, once their auth and Next-specific route parameters are adapted. Keep the old backend for unmoved routes during rollout behind one reverse proxy; two internal processes can still be one container. [Nitro+tRPC](https://nitro.build/raw/examples/vite-trpc.md), [existing route handlers](../../apps/nextjs/src/app/api), [nginx](../../nginx.conf).
3. **Move the frontend while keeping `clientApi` initially.** Replace App Router-specific layout/navigation/bootstrap/hydration per route. A CSR route loader can replace an RSC call while reusing React/Mantine/widget/forms, Query policies and tRPC hooks; selecting SSR/RSC instead requires an explicit new framework integration. Removing RSC cannot expose server-only data/functions to the browser. [client API](../../packages/api/src/client.ts), [provider policies](../../apps/nextjs/src/app/%5Blocale%5D/_client-providers/trpc.tsx), [Vite SSR](https://vite.dev/guide/ssr.html), [Nitro experimental RSC](https://nitro.build/raw/examples/vite-rsc.md).
4. **If replacing tRPC, do it bounded-context-by-bounded-context after authorization extraction.** Define transport-independent services that accept identity/db/context and enforce the existing permission rules, then have old tRPC and new H3/Hono/Elysia routes call those services. Use one authoritative Zod input/normalization source and explicitly preserve error/serialization/output contracts. Maintain a separately curated MCP capability catalog and REST compatibility adapter rather than reverse-generating security policy from OpenAPI. [procedure middleware](../../packages/api/src/trpc.ts), [board helper](../../packages/api/src/router/board/board-access.ts), [MCP dispatch](../../packages/api/src/mcp-tools.ts), [OpenAPI corrections](../../packages/api/src/open-api.ts).
5. **Keep stateful services and Node until separately justified.** Nitro's database/storage/task primitives are optional facilities, not a reason to convert Drizzle or replace Homarr cron/Redis. A same-origin deployment with one backend authority avoids cross-origin cookie/CORS changes and duplicate schedulers. Optional split frontend/backend should preserve forwarded URL trust and persistent mounts, with explicit lifecycle/readiness ownership. Static frontend files are fine; GitHub Pages/static-only operation cannot preserve this backend feature set. [Nitro optional primitives](https://nitro.build/raw/blog/v3-beta.md), [existing lifecycle](../../scripts/run.sh), [embedded services](../../apps/nextjs/src/instrumentation-node.ts), [backup/LDAP/server APIs](../../apps/nextjs/src/app/api).

### Gaps

- Required decision: whether SSR/RSC behavior itself must be preserved or equivalent client-rendered behavior is acceptable. This changes page/bootstrap/localization/metadata/hydration work materially; Vite+Nitro alone does not decide it. [current RSC layout](../../apps/nextjs/src/app/%5Blocale%5D/layout.tsx), [Vite SSR scope](https://vite.dev/guide/ssr.html).
- Required parity gates, not run during research: credentials/LDAP/OIDC behind HTTP and TLS proxies; provider-linking denial and group changes; expired/revoked sessions; API keys and anonymous boards; REST cookie rejection/CORS; multi-integration partial failures; qBittorrent/UniFi/trusted CA/native TrueNAS; multipart/media/SVG/ETag; large backup with same/different key; all four subscription flows; stream abort/approval continuation; MCP tool/schema/resource/OAuth compatibility; Custom Widget public reads/actions/preview/configuration/Workshop and durable data restoration. Source evidence above identifies contracts; it does not replace deployment verification.
- No evidence supports a promised smaller image/RSS, faster boot, faster widget loading or full capability parity yet. Native-addon tracing, migration-file/assets inclusion, tool catalogs that eagerly import code, and preserving Redis/nginx/jobs may dominate production cost irrespective of the chosen HTTP framework. [current Docker packaging](../../Dockerfile), [eager MCP composition](../../packages/api/src/mcp.ts), [Next external packages](../../apps/nextjs/next.config.ts).
