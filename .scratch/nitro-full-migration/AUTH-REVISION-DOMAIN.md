Global permissions are the actual `groupPermission` rows joined through actual `groupMember` rows, expanded with `getPermissionsWithChildren` (`packages/auth/callbacks.ts:10–21`, `nitro/sql-authority/snapshots.ts:116–143`). There is no separate user-global-permission table, and the reader does not invent Everyone membership. Actual sign-in writers establish that membership.

User/group/resource cascades can change access. User deletion also sets board/media/custom-widget creators NULL and cascades other user-owned records; it is not merely deleting a login row. Do not reconstruct these cascades in application code or change FK actions for generation convenience.

`packages/auth/security.ts` uses bcrypt hash/compare; existing password and API-key hash bytes must not be regenerated during revision adoption. Verification tokens are a separate identifier/token/expiry table, not an admitted API-key or opaque-session generation. Preserve original dates, account tokens, serialized preferences/options and all encrypted fields.

### 2.2 Current native read/lease facts

`PolicyIdentity` (`packages/auth/nitro/policy/identity.ts:3–10`) has userId/groupIds/expanded permissions only. Foundation `Principal` (`packages/contracts/src/request.ts:1–3`) instead requires subject/sessionRevision. API `BackendPrincipal` (`packages/api/src/nitro/context.ts:9–16`) needs real SessionUser profile fields. None supplies the other's missing fields by shape equivalence.

`packages/auth/nitro/sql-authority/{contracts,snapshots,authority,lifetime}.ts` owns credential admission and leases, not durable generation:

- Opaque witness: exact token/user/provider/expiry and conservative host deadline. API-key witness: exact ID/hash/user/provider, **no stored expiry**. Raw witness is private.
- `credentialSnapshotStatement` selects one bounded joined credential/user/membership/global-permission statement with observed DB clock; decoder validates complete rows and expands actual permissions. It does not select a revision or full profile.
- `authority.ts:250–274` uses existing main-runtime bounded SQLite transaction or PG bounded transaction for that one statement. The issuer repository separately uses PG `boundedSnapshotAsync`; do not mislabel the authority reader as already using that multi-statement snapshot API.
- API-key admission verifies bcrypt outside SQL, then rereads exact stored credential witness before lease creation (`authority.ts:625–639`). A future revision must be in that verified/reread evidence, not attached afterward from a second unrelated read.
- `assertCurrentAsync` rereads and compares exact credential witness plus sorted identity. Same-token expiry change currently makes an old opaque witness unequal. Membership/global-grant changes are noticed when rechecked; remove/reinsert restoring identical values is an ABA invisible to equality alone.
- The owned token fence/active lease registry and close/release promises are genuine in-process lifecycle machinery, but neither WeakMap membership nor a fence is durable Auth revision. Existing API-key revocation through this reader is rejected with `COMMIT_AUTHORITY_JOIN_REQUIRED`; a prepared DELETE statement is not an enabled key-revocation capability.
- `SqlAuthorityReadLease` has identity/credentialType/validity/lifetime/assertCurrentAsync/releaseAsync, **no revision/profile**. Real user colorScheme exists and is selected/validated by `production-sessions/repository.ts` and native session-result decoding; that does not make it part of the request lease.

No conversion from requestId, token, userId, expiry, a random per-request value, current-grant hash, local counter or an asserted receipt can fill foundation sessionRevision. A nonsecret revision describes a domain observation; it is never bearer authorization.

### 2.3 Existing runtime epoch is not this domain

`packages/db/runtime-catalog.ts` describes four infrastructure tables (`homarr_runtime_meta/state/history_stream/history_entry`), catalog version `homarr.runtime.sql.v1`, meta ID1 epoch and ID2 NULL mutex. `homarr-runtime:uninitialized:v1` is the initialization sentinel, not an installation UUID. `runtime-state.ts` initializes a persisted infrastructure epoch; state/history backings reject changed epochs. P3 copy reset clears these tables and privately creates a fresh epoch, leaving domain rows untouched.

That epoch is not credential or actor authority generation. Reusing SQL backing infrastructure is a possible future implementation choice **only with an explicitly reviewed Auth-owned key/namespace, value schema, lifecycle and same-transaction writer protocol**. No Auth state key currently exists in the inspected producers. `createRuntimeStateSqlBacking.mutateAsync` starts its own bounded transaction; calling it after a credential transaction would not atomically advance Auth evidence with credential DML. Its increment operation also requires positive TTL, so a durable, non-expiring Auth allocator cannot simply adopt that operation unchanged. No second pool, generic executor or KV-as-auth substitute is proposed.

## 4. Three semantic choices — recommendations are not selected policy

Candidate names below describe roles only, **not existing fields, keys, tables or accepted exports**. Each uses a durable Auth-owned domain incarnation plus domain-owned monotonically advanced evidence, selected alongside actual credentials. Do not call a row's default constant “current”.

| Choice                                                            | What sessionRevision would identify for opaque sessions AND API keys                                                                                                                                                                                                         | Advantages                                                                                                                                                                              | Costs/limits                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **C — credential incarnation/generation**                         | Exact admitted credential's durable incarnation and selected credential generation. API key has its own key incarnation, never a synthetic session row. Same-token renewal can retain incarnation and either retain or advance generation according to the renewal decision. | Narrowest writer set; individual key/session replacement/removal has precise identity; avoids retiring every actor session for a harmless profile update.                               | Does not represent changed memberships/global/resource grants. Need separate genuine grant currentness/cache transition and locked mutation authority. Renewing expiry still invalidates today's exact witness even if the durable credential identity stays stable.                                                           |
| **A — actor authority generation**                                | Actor's durable incarnation and generation for the explicitly selected authority scope; all admitted sessions/keys of that actor may share it. Credential authentication/witness remains independently mandatory.                                                            | Actor-global permission refresh has one durable observation shared across credential types.                                                                                             | Does not distinguish two credentials or same-actor credential replacement unless policy deliberately invalidates all of them. Grant replacement/deletion needs complete affected-actor protocol or an explicitly coarse shared authority generation. No credential cache partition can be inferred from the actor value alone. |
| **C+A — separately named credential and actor-global components** | Versioned nonsecret composition of admitted credential incarnation/generation and actor authority incarnation/generation, without token/key locator/hash. Only the defined components form the foundation string.                                                            | Clear distinction between credential replacement and authority change; catches durable ABA in both; can inform separate cache transition owners without pretending to be boardRevision. | More writer/migration work. One string alone still cannot enforce currentness, expiry, SQL locks, resource ACL or browser retirement. Including all resource/content changes would make this a much larger and noisier domain.                                                                                                 |

**Corrected technical recommendation for Oracle:** propose only genuine credential-lifetime identity for the foundation string. `packages/contracts/src/request.ts:1–3` requires an opaque string, and `apps/backend/src/server/application.ts:88–115` neither decodes it nor requires combined authority. C+A is a conditional extension only if a demonstrable consumer requirement later justifies it; it is not favored or required now. Preserve the original same-token expiry-renewal workflow, web password changes retaining sessions and keys, and both CLI password commands deleting sessions only. Internal renewal evidence is a technical revalidation concern, not a logout choice. The retained option tables are inventory, not selected policy or a user-question gate; permission/resource/Query/UI/privacy/preview obligations remain independent and undiminished.

## 6. Candidate source-only atomic rules after policy selection

### 6.1 SQL-backed identity and numeric representation

Two concrete storage shapes remain candidates: additive generation/incarnation columns on existing credential/user rows plus an Auth-owned durable allocator/domain record; or Auth-owned sidecar records keyed privately to existing row identities, with explicit FK/tombstone/non-reuse rules. Columns avoid another credential lookup but do not by themselves prevent deletion/recreation ABA. Sidecars leave credential rows untouched but add a model/conservation/restore requirement. Neither is chosen here.

Infrastructure state storage is a third implementation location, **not a fourth semantic choice**: only an approved Auth-owned non-expiring value/allocator and fixed in-transaction statements could make it durable domain state. Generic state mutation followed by credential DML on another transaction is insufficient; P3 currently clears runtime state. Do not claim existing infrastructure keys implement the domain or change runtime epoch semantics.

SQLite INTEGER and PG BIGINT have signed 64-bit storage limits; an Auth nonnegative sequence using that representation must reject exhaustion before increment, not wrap/round/reinitialize. Exact existing precedent is `runtime-history/validation.ts`: maximum `9223372036854775807n`, canonical decimal text parsing with BigInt, `nextSequence` rejects overflow; history statements CAST sequences AS TEXT for read and AS BIGINT for bound writes. PG runtime history schema uses bigint mode, SQLite history schema exposes integer. Auth cannot blindly reuse driver JS-number results beyond safe integer.

If choosing 64-bit sequence evidence, fixed reads should return canonical decimal text, validate exactly with BigInt/range and keep Principal serialization a versioned nonsecret string. If choosing JS-number counters, their exact bound is Number.MAX_SAFE_INTEGER, **not** SQL's 64-bit ceiling. Existing date/row/deadline validators use finite/safe numbers for their own roles; they neither validate a future revision nor grant arbitrary Auth numeric limits. SQLite/PG date mappings and existing snapshot limits stay unchanged. No production budgets/defaults or field-length constraints have been invented.

### 6.2 Same-transaction writer rules

1. Capture genuine main runtime, owned operation/lifetime/finite deadline, credential logging suppression and chosen Auth domain incarnation before read/write admission. Host logging/config/readiness is still original01's separate prerequisite. Do not acquire a generation via SQL before logging protection is real.
2. Fixed domain writer acquires its domain/actor/credential anchors in one reviewed order, revalidates original witness plus selected durable generation/incarnation, applies original DML and advances/allocates required evidence **in the same native transaction**, checks exact affected rows, and returns detached evidence only after settlement. No generic callback accepts a claimed revision as authority.
3. SQLite reuses existing bounded synchronous BEGIN IMMEDIATE; no bcrypt/provider await or asynchronous callback inside it. PG reuses same checked-out main-pool native transaction. Ordinary bounded PG uses plain BEGIN; snapshot PG uses REPEATABLE READ READ ONLY. Snapshot coherence is not locked mutation authority or proof of fresh READ COMMITTED after acquiring a writer mutex.
4. Actual PG fixed Auth establishment admission verifies READ COMMITTED and owns native SHARE ROW EXCLUSIVE locks over `user`, `account`, `group`, `groupMember` (`transaction-gate.ts:341–365`). Existing statements additionally lock existing user/account/session rows and ordered group parents. This is narrower than a universal writer protocol: `apiKey`, `groupPermission` and future domain anchors are not magically protected by those four table locks. Ordinary callbacks cannot issue arbitrary control/table-lock SQL. Any indispensable new fixed native lock admission requires its own precise runtime/gate allocation, not a widened generic executor.
5. Actor-global updates need a reviewed affected-actor rule. Per-actor bumps require stable full old/new affected membership enumeration, canonical sorted actor locks and protected group parents/absence predicates; do not lock group then opportunistically acquire user locks in conflict with existing user→group order. Alternative coarse domain/global authority advance avoids unbounded fan-out but changes invalidation semantics and contention. Return this as a smaller protocol/design phase if affected rows cannot be safely bounded; no silent subset update/truncation.
6. Use existing actual parent locks in `runtime-authority/locks.ts`: user FOR UPDATE; groups ordered by ID with maximumRows+1 FOR UPDATE. They protect only what participating writers serialize. FK key-share, locking existing child rows, or CAS on a revision alone does not protect an initially empty membership/grant predicate.
7. Native callback failure, decoder failure, exceeded bounds, missing generation, cancellation, overflow or loss of backing fails closed. Successful no-op versus change effects follow chosen semantics, not guessed SQL row counts. All participants must see the same domain; one old enabled writer means no activation, including online CLI/admin/adapter/background/cascade writers.
8. Publish owner closing/revocation fences before reentry, stop new claims synchronously, await admissions/leases/SQL/native work before resource retirement. Preserve A/B single-owner/logout/drain behavior. COMMIT-dispatched ambiguity remains unresolved even if response/invalidation fails; preserve `TransactionCommitAmbiguousError` and private primary/cleanup failures, quarantine/reconcile, never retry automatically or declare rollback.

Native writer generation atomicity does not supply the separately required authorization-through-COMMIT. SQL generation is evidence, not authorization; source grants/credential validity/pinned config and locks still need the separately allocated join.

### 6.3 Missing state, adoption, restart and ABA

- **Normal restart:** read persisted Auth domain incarnation/allocator/row evidence; never reseed counters or issue a new principal from local startup randomness. New in-process leases/cache lifetimes are fine, but cannot impersonate durable Auth evidence.
- **Initial adoption/backfill candidate:** under genuine maintenance with incompatible writers stopped/drained, transactionally allocate evidence for all existing users/sessions/keys without changing their IDs/tokens/hash/expiry/profile/accounts/grants. Rows with invalid/missing evidence cannot yet produce a new foundation principal. This is withheld new capability, not authorized deletion/logout of the old deployment.
- **Lazy candidate:** a separately owned transactional initializer verifies the existing credential/actor and unique domain state under locks, allocates absent evidence once, and selects it in the same transaction. Concurrent initializers cannot default to the same reused value. It must distinguish genuinely never-enrolled rows from accidentally lost state; silent missing-state recreation after activation permits ABA. The read-only request projection cannot become this hidden writer.
- **Loss/partial upgrade:** missing/malformed/retired domain backing, skipped writer migration, unsupported schema or allocator exhaustion denies new principals; no default generation=0/1, userId fallback or hash of raw state. Credential rows remain preserved for repair under an explicit lease. A completed schema append without complete writer/adoption protocol is not readiness.
- **Delete/recreate:** deleting a session/key/user row must not reset its identity counter when the same token/ID/user ID is later inserted. A nondeletable domain allocator with never-reused allocations, durable tombstones, or explicitly unique stored incarnations is required. The domain allocator and retention rules need actual SQL ownership; they cannot be a WeakMap.
- **Restore/reset:** replacing a SQL image can rewind both counters and credentials. A counter stored only inside that image cannot prove non-reuse across arbitrary rollback. A controlled adoption must retire old resources and establish a fresh **Auth-owned SQL-backed incarnation**, with reviewed fresh allocation/recovery fencing outside the replaceable image where needed, before new admission. A UUID-backed candidate offers collision-resistant namespace separation, not a deterministic never-reuse proof; an exact guarantee needs an authoritative nonrollbackable allocation/fence protocol. Neither is implemented. Never copy `homarr_runtime_meta.epoch` or an imported revision as new Auth authority.
- **Critical bearer distinction:** fresh Auth incarnation invalidates old leases/revision receipts, but does **not** invalidate an old raw cookie token or API-key token restored byte-for-byte into a valid row. The existing transport carries no prior Auth incarnation for comparison. Restoring an already revoked credential can therefore authenticate anew unless a reviewed surviving revocation record/restore policy rejects it. Do not claim epoch rotation alone prevents credential resurrection. Preserving still-valid credentials and blocking revoked restored credentials requires authoritative reconciliation beyond the replaced image; this is an activation stop, not permission to rotate/delete all tokens.
- Existing target `prepareLegacyBackupAsync` intentionally removes sessions/verification tokens/setup claim for migration logout; API keys/passwords/accounts remain. This separately established migration behavior is not permission to add forced logout to ordinary forward schema adoption/restart or key rotation to restore. Explicit old49 API-preparation compatibility is already recorded unresolved in CONTRACTS; do not fabricate schema/reset support. Failed restore recovery must retain attempted-domain fencing and await retirement, never reopen an old image under a reused generation.
