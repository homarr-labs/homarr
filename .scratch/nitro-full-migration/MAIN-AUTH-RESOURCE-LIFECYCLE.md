## 3. Owner states, promises and underlying-task identities

Use source-local discriminated owner state, not DB phase alone: `constructing`, `configured`, `initializing`, `ready`, `closing`, and terminal `closed` or `close-failed`. Internal primary failure is retained separately from cleanup outcomes. An initialization/construction failure permanently closes admission even when cleanup succeeds. No transition back to configured/ready or new construction after failure/closing is permitted.

The following private slots have distinct roles:

| Slot                             | Meaning and required publication                                                                                                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Full runtime, proxy, helper      | The actual acquired handles, retained at the boundaries in section 2. No replacement/second acquisition.                                                                                                                                   |
| `initializationTask`             | A deferred `Promise<void>` registering the one real helper-ready invocation before invoking it. It mirrors the actual helper return's settlement, not public ready cleanup. Never an abort/deadline race.                                  |
| `helperInitialization`           | The actual promise returned by private helper ready when invocation returns; associate it with the prepublished task. If invocation synchronously throws, settle that same task as rejected. Source return type is `void                   | Promise<void>`through`RuntimeContribution`; resolve void only after the actual call returns. |
| `readyPromise`                   | A different deferred shared promise for callers. It awaits initializationTask, checks closing/currentness, and on initialization failure awaits owner cleanup before rejecting. Close must **never await this wrapper**.                   |
| `closingPromise`                 | One deferred shared owner-close promise. Store it and state `closing` before aborting, calling helper/handles, invoking any callback or entering the cleanup worker. All reentrant/repeated close calls return this exact promise.         |
| Partial-construction close slots | One deferred task each for directly closing retained proxy/runtime when no helper exists. Publish each identity/attempt bit before invoking its real close method. They cannot coexist with helper-delegated cleanup for the same handles. |
| Active operation tasks           | Deferred identities registering underlying guarded proxy/admission calls before those calls begin. They mirror underlying completion; caller wrapper/cleanup continuations are not drain tasks.                                            |

Only the owner exposes lifecycle entry points. Publish shared promises by explicit deferred assignment before work, not `slot ??= selfCall()` or an async IIFE whose body runs first. Install fulfillment/rejection observation on each registered task before the corresponding external/helper/native call. Record a started task before any signal hookup can synchronously reenter. Keep its identity registered until the **underlying invocation** settles, then record its result, remove that identity, and settle its deferred gate; public failure handling runs only afterward. Keep the shared promise slot after removal for idempotence, rather than deleting it and allowing another attempt.

All ordering below is a required static sequence, not a tested race guarantee. Direct native access by an outside consumer would bypass it and is expressly not admitted.

## 4. Ready: publish before invocation, cleanup without self-wait

1. Check the owner fence first. During closing/terminal state reject unavailable without starting anything. During initialization return the existing readyPromise; after successful readiness return its shared promise only while current. After failure return the retained failed result, never retry helper ready.
2. For the first configured call, create and store initializationTask and readyPromise, register their settlement handlers, and set `initializing` **before** composing/observing the app signal or invoking any helper work. The supplied app signal is captured once; subsequent calls cannot replace the first initialization lifetime or create a second task.
3. Initialize an invocation marker as registered/not-started. Combine the owner lifetime with that captured app lifetime only after publication. Recheck closing/aborted state after any signal setup. If close/abort occurred before helper invocation, record not-started cancellation and reject/settle initializationTask without calling helper ready. This releases the close worker's pending registration; it must not leave a task waiting forever for work deliberately skipped.
4. If still permitted, mark invoked and call the private helper contribution's actual ready once. Retain its returned promise in helperInitialization immediately on return and wire its settlement to the registered task. A synchronous throw follows the same rejected-task path. Reentrant close during the call sees the owner closingPromise and the already registered initializationTask, even before helperInitialization can be assigned.
5. On actual underlying settlement, record success/failure and remove the active initialization identity before resolving/rejecting its gate. The raw helper's initialization has now settled, including any awaited opening-failure cleanup. An abort event alone never takes this step.
6. On success, check owner closing/abort state and genuine helper `assertCurrent`/runtime ready gate before publishing owner `ready`. If close won, do not reopen or fulfill readiness; wait the shared close and reject sanitized unavailable. If the final currentness check fails, retain that primary failure and perform the same failure cleanup path. No credential operation follows an owner-state label alone.
7. On initialization failure, retain the actual rejection internally, invoke the owned dispose entry point (or reuse its already published promise), await cleanup settlement, then reject readyPromise with sanitized initialization failure. Preserve primary and cleanup errors internally even if cleanup rejects. **The close worker waits initializationTask, not readyPromise**, so this failure path cannot wait on itself.

The real helper's initialization already serializes its actual open/migrations/seed/readiness sequence. The owner does not repeat those methods or call helper ready a second time. On close during opening/migration it requests owner-lifetime abort, but still waits the raw task to settle. Only then may native close occur; the existing DB rejection for close-during-opening/migration is not used as a cleanup strategy.

## 5. Close and failed-construction cleanup

### Publication and drain

On the first dispose call, create/store closingPromise and change state to closing synchronously, before owner lifetime abort, signal listeners, helper calls or native reentry. Disable every new ready/read/admission/constructor-binding operation at this same fence. Then start one cleanup worker; repeated/reentrant calls only retrieve its published promise. Abort is a request to stop, not successful drain.

The worker awaits any registered actual initialization task to settlement, recording its rejection without skipping later cleanup. It also awaits all already registered underlying guarded operation tasks. No new task can enter after the fence. It does not await readyPromise, application readiness, its own close promise, request cleanup wrappers or a caller result that itself awaits owner dispose. No owner dispose is offered to request contexts or awaited from inside its own tracked native operation. No Promise.race, timeout, clock callback or deadline substitutes for settlement.

### Exactly one cleanup route per acquired obligation

- **Helper returned:** after actual initialization/operation settlement, invoke its private closeAsync exactly once behind an owner-published delegated-cleanup task. Observe and retain that task's actual completion. The helper again awaits its stored initialization, which is already settled; no self-wait. Its real body attempts proxy close, catches that failure, attempts runtime close and then aggregates. Delegate these obligations to that existing body; do not call proxy/runtime close separately afterward, even if the helper rejects. Retained handles remain identity/failure-accounting evidence, not permission for a duplicate fallback native close.
- **Helper never returned:** actual initialization was never invoked. Close every retained proxy (if any), then retained runtime (if any), through the prepublished per-handle tasks. Catch each failure and continue to the next obligation; await each real completion. Runtime phase is configured at actual construction, not opening/migrating. This covers runtime-validation throw, proxy construction/validation throw and later helper-construction throw before return.
- **Helper returned but guarded result construction failed:** retain the construction primary error, publish owner closing state/promise, and take the helper-delegated route above. Await it before rejecting the async constructor. Do not return a partially built owner or claim cleanup succeeded merely because construction failed.
- **Constructor threw before any returned handle:** retain the construction error, record that no runtime/proxy handle was acquired, and reject after the empty cleanup obligation set is settled. Do not report a physically closed native runtime that never existed.

The owner's direct partial-construction route and helper delegation are mutually exclusive and fixed from the retained helper slot before cleanup. A task rejection never clears its attempted bit or permits retry/reacquisition. An unexpected cleanup exception is retained, remaining obligations are still attempted, and terminal failure is truthful; it does not silently select another route.

### Opening-failure/native-close details

The DB open failure path already awaits closeConnection before its open promise rejects (`runtime.ts:173–176`). Awaiting actual initialization includes that cleanup. Later helper runtime close fulfills the remaining runtime-lifetime obligation; if connection has been cleared it does not close the same native connection again. Migration failures do not automatically close the runtime; helper disposal does so after their settlement. If open's own cleanup rejects, retain the actual error returned by DB; do not claim to recover an earlier primary error hidden by the unchanged DB implementation. All available owner/helper primary and cleanup errors are retained, without inventing unavailable provenance.

During the final real runtime close, the native bounded-lifetime abort can reenter owner dispose before DB assigns its inner closing slot. The prepublished owner/delegation promise blocks another helper/native invocation, so this reentry returns the same owner promise. This proof requires that no raw helper/native close escapes. Native close's actual rejection is terminal cleanup failure, not grounds to repeat close or claim physical retirement.

## 6. Failure accounting and truthful terminal state

Retain private `unknown` primary errors and per-task cleanup outcomes; when both exist, keep an internal aggregate containing the primary and actual cleanup rejection(s), including the helper's own aggregate. Do not replace the primary with cleanup, discard a cleanup error, flatten it into a success flag or attach sensitive causes to outward exceptions. Public errors/status use fixed codes such as construction-failed, initialization-failed, cleanup-failed or unavailable, with no raw cause, credential, config, SQL, path or callback-produced text. No raw-error logging/reporting hook is introduced.

Owner status distinguishes admission failure, cleanup settlement and native retirement. `didClose` means the actually acquired cleanup obligations fulfilled and the retained runtime, if acquired, reached actual `closed`; it is never set at abort/close invocation. Record whether a runtime was acquired so empty construction cleanup cannot be mistaken for a native close. A normally constructed owner reaches closed only after successful cleanup; a cleanup rejection or a runtime not actually closed reaches close-failed with didClose false and permanently closed admission. Initialization-failed plus successful cleanup is still failed initialization, not successful ready. Repeated dispose returns the exact original fulfilled/rejected closingPromise and cannot improve the stored outcome by retry.

With helper delegation, rely only on its real guaranteed attempts/settlement and actual runtime phase; do not invent per-resource native success details unavailable from its aggregate. The real proxy close sets its bit without separate native work; a fulfilled delegated close plus real runtime closed supports the source-level all-obligations-completed status. A rejected delegated close is failed cleanup even if runtime.phase is closed. These statuses describe source-level observed completion, not a physical drain test.

Application dispose catches contribution failures and continues. Therefore its fulfillment cannot override owner close-failed or constitute successful physical main/Auth disposal. Preserve a separately reviewable sanitized owner outcome; the private error ledger stays with the owner. Future whole-host result handling is a separate composition allocation, not an application rewrite here.
