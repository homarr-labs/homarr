## Why two files are insufficient

1. `runtime.ts` 102–105 independently constructs a generic helper; native 323–338 already constructs and retains the real helper/runtime/proxy. A consume-owner path must remove that second construction, not call both.
2. Native result 352–369 exposes guarded admission/proxy reads but no engine/phase/SQL-readiness facet. Native `runAsync` 293–299 is admitted only after ready by `registerOperation`/`assertCurrent` 78–117. No pre-ready schema accessor is present.
3. Current host registry/resources require a caller schema before persistence starts (`runtime.ts` 59, 98–105), and RPC checks actual admitted schema identity afterward (`126`, retained B5 public-rpc 121–123). A trusted native consume path must instead obtain that actual schema from the ready owner's admitted callback. It must not import a schema singleton, cast caller schema to identity, or manufacture a pre-ready schema handle.
4. Retained `assembly.ts` 23–27 requires `MainPersistenceRuntime`, which includes public open/schema/content migration/close methods (`contracts.ts` 28–34), though assembly uses engine/phase/SQL readiness and the separate contribution lifecycle. Its validation 39–47 also requires phase `configured`. Feeding it the narrow ready-owner bundle would fail both its static shape and configured-phase check. Adding fake migration callbacks or exposing the full retained runtime is not an acceptable two-file workaround.
5. Retained assembly disposal 187–200 uses an async-IIFE assignment; the requested host-level prepublication should be explicit before invoking delegated disposal, rather than relying on native coalescing alone.

**Indispensable third file:** `apps/backend/src/server/runtime-composition/assembly.ts` — narrow the required host persistence runtime to admission plus real SQL readiness; validate the ready owner without treating readiness as just a phase label; prepublish host disposal before delegated work. **No fourth file is indispensable for this candidate:** existing `AdmissionRuntime`/`MainPersistenceRuntime` types can supply a `Pick`, and existing proxy compatibility can use a genuine whole-owner disposal alias as specified below. If that close contract is not accepted, do not invent a stub: pause and separately allocate narrow read-only proxy signatures in `public-settings.ts` and `public-culture.ts` rather than weakening `ProxySettingsReader` or silently widening this plan.

The host runtime facet is exactly **`Pick<MainPersistenceRuntime<NativeDatabase, NativeSchema>, "engine" | "phase" | "runAsync" | "checkReadinessAsync">`**. This preserves typed genuine admitted resources and real readiness units without exposing the full runtime, native client, open/migrate/content maintenance or separate close capability. The proxy close alias is required only because current `ProxySettingsReader` includes close (`contracts.ts` 47–51), while retained B5 consumers use only its reads; it conveys actual disposal, not pretend proxy-only cleanup.

`takeForPublicHost()` must check owner state and claim only an unclaimed configured owner, publish the claim synchronously and reject duplicate/closing claims. No shared borrowed-owner mode, optional ownership flag or factory/owner union is proposed. The named method and host factory contract explicitly transfer lifetime responsibility; merely passing an arbitrary externally owned resource object must not trigger hidden disposal. External calls to the original native `dispose` remain the same closing operation and cannot bypass currentness/drain. Transfer is a lifetime contract, not authentication, epoch or principal authority.

## Exact construction and lifecycle order

Proposed consume-owner construction is asynchronous because actual schema is available only after guarded native readiness. Use one host-building path; do not introduce interchangeable schema/factory/owner modes.

1. Capture/validate the supplied host configuration and validate required source producer inputs without allocating a generic helper. Validate its persistence configuration against the native owner's pinned configuration. If validation fails before a successful transfer, the caller retains its owner and cleanup obligation.
2. Explicitly claim via `takeForPublicHost()`. Put **all post-claim work** inside construction failure handling. From this point the consuming host factory owns disposal, including failed construction. A failed duplicate/closing claim must not dispose another host's owner.
3. Call that bundle's real `ready(startSignal)`. Opening, migrations, fresh seed checks and readiness remain the existing native/helper sequence, not separately callable host operations. `startSignal` is an explicit trusted construction lifetime input, not a replacement durable epoch or permission lease. Preserve native first-readiness signal/lifetime semantics; later host ready calls cannot silently replace that signal.
4. Enter that bundle's guarded `runtime.runAsync` and use the callback's **actual schema** to construct `backend.resources(schema)` and the exact two-leaf registry. Build settings/culture/RPC with the same bundle, captured schema identity and existing concrete consumer factories. Do not return or retain the admitted database; only the source schema/resource definitions and completed host graph may outlive the callback. The existing scope remains responsible for database revocation/settlement, whose native completeness is still unproved.
5. Inside this construction use the supplied settings factory with each admitted schema, preserving equality to the captured actual schema (`runtime.ts` 110–113). Pass that same captured schema to RPC; pass the owner guards/admission/proxy reads unchanged to settings, culture and RPC (`106–133`). Any retained input schema supplied for proven legacy callers must be checked against actual schema, never substituted for it.
6. Assemble only after owner readiness and actual-schema binding, using the narrowed third-file contract. Assembly must accept genuine ready supplied ownership and still perform actual guarded readiness SQL in its existing readiness/health paths, rather than requiring callers to advertise `configured`. Prepared application construction is not production listener mounting. No route is a deferred success stub or placeholder consumer.
7. Native `runAsync` performs its post-operation currentness check before construction returns. Abort/currentness/consumer/assembly failure after transfer must await the **same owner's `dispose()`**, including if native readiness already initiated it. Preserve the original construction failure unchanged if cleanup succeeds; if cleanup fails, preserve both in ordered `AggregateError` with original cause. Do not swallow cleanup error, log raw failures, automatically retry, or claim successful construction. Independently owned allocations inside missing consumer factories need their real contracts; owner cleanup alone does not invent cleanup for them.
8. On successful return, the host owns transferred lifetime. Its contribution start invokes the same native ready function and guard, with abort checks around the cached result and real SQL readiness. Dispose must publish the host closing promise before invoking delegated application disposal, keep native coalescing/abort/drain, await physical work requested by the existing implementation, and report closed only after successful native disposal/closed-state verification. If actual application disposal/drain semantics are required, that caller is a separate source/lifecycle hold, not an assumed guarantee.

Native already publishes `closing` before abort/cleanup (181–192), tracks operations before invoking them (89–104), and waits observed initialization/operation settlement before helper close (154–169). The adapter must use those exact closures rather than duplicate counters or a second lifetime framework. There is no deadline race, retry or separate host-owned pool in this proposal.

## Existing generic prepared interface: compatibility cannot be invented

The exact source-backed existing inputs are `runtime.ts` 57–95: explicit host configuration and caller schema; `MainPersistenceFactories`; settings store/schema-resource factory; backend source procedures/contribution/metadata/schema resources/setup resources/context factory; culture factories/cookie codec/key/options/clock; rendering and error reporting. These are **declared caller inputs, not identified actual caller sites**. None of the three authorized current bodies establishes an external caller that requires preserving the existing synchronous generic constructor.

Do not infer either that callers exist or that none exist. Before changing the existing constructor's signature/return shape, the coordinator must identify its actual caller scope. If genuine prepared callers need preservation, retain their public API as a thin wrapper around the same construction logic with explicit ownership, and allocate that compatibility only after those callers are known. Do not preemptively add a factory-versus-owner option union, separate resource graph, exported alternative mode or unreviewed async breaking change. No source barrel export, manifest, compose or production entry edit is included here. Consequently this candidate's consumer/lifetime design is concrete, but release of its function-signature allocation is also held pending caller identification and oracle review.
