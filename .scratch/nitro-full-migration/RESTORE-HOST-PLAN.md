## Proposed whole-app maintenance protocol

One active backend and one exclusively owned data directory. The host must first provide a real cross-process ownership mechanism and restart supervisor; an in-memory restore flag or a state lease alone cannot exclude another backend. All current **and later** producers register before activation with owner identity, captured runtime generation, admission fence, actual stop/drain/close outcomes and dependency ordering. Registration after the gate closes is refused. An unknown producer, bypassing SQL connection or unregistered credential client keeps restore held.

1. **Authorize and ingest without live mutation.** Actual current admin or source-equivalent valid no-users/setup-start claim; respect demo mutation policy and origin/CSRF. Authorize before `readBackupUploadAsync`. Preserve existing bounds (ZIP 256 MiB, multipart 257 MiB, DB 512 MiB, aggregate 514 MiB, metadata 1 MiB, key entry 1,024 bytes); add reviewed concurrent ingress/copy admission limits, not a claim that per-request limits bound all memory. Any inspection is copied/sensitive SQL-only evidence, never apply permission.
2. **Confirm a concrete attempt.** #112's missing server-owned attempt record binds one generated attempt ID to current identity/claim and authority revision, captured runtime generation, exact immutable archive/candidate identity, target engine/schema/key reference and selected board. Confirmation is one-shot with expiry/currentness checks, not a browser boolean. Proposed concrete operations are confirm-and-reserve, read-safe-status and reconcile-an-existing-attempt; no caller SQL/path or success-returning work callback. Competing confirmations reject, and lost replies reuse the attempt ID for status, never a second apply. Journal stores no credential/key material. Binding internal digests does not authenticate unauthenticated CBC/archive provenance.
3. **Transfer accepted work to the supervisor.** Persist accepted attempt ownership before reporting “accepted”, not “restored”. Finish/cancel the ingress/control response before waiting for all application requests: a restore handler must not call `Application.dispose()` or DB `closeAsync()` while its own request/admission is among the awaited work. Supervised work has a separate bounded ownership lifetime. Progress/status is minimal and authority-gated; a request disconnect does not authorize an unsupervised retry or destruction of retained recovery state.
4. **Fence immediately, then settle in dependency order.** Reject new ordinary HTTP/RPC/SSR/body/provider/job/cache/history/credential admissions; fence captured generations and private output before waiting. Initiate scheduler, provider, stream and cache stops concurrently where independent, but retain backing/SQL/transport resources until their dependants settle. No new work after observed maintenance/currentness loss. Already admitted rollback/finalization/unsubscription gets only its resource-owned cleanup path, never a broad business-write exception.
5. **Drain the actual owners.** Await ingress readers and outgoing body source cancellation/release; private SSE/history snapshot/live queues and pending sink writes; jobs/manual effects/configuration reads/status finalization; request-handler coalesced/late operations, renewals and state/generation/fanout work; logs/sample append/trim/publication; integration execution, credential exchanges, testing/shared transport and SDK/socket/DNS/pool settlement. Producer completions must not repopulate state or deliver private bytes after the fence. Domain stops do not close injected DB/transport resources. Preserve collected cleanup failures, and do not turn a deadline-rejected promise into a settled native operation. A stuck provider/reader/cleanup holds maintenance; do not close SQL underneath it.
6. **Only then use DB-only maintenance.** Drain all admitted SQL acquisition/statements/transactions, unset configured facades/readers after their users settle and take/validate the owned consistent old recovery snapshot. Keep only explicitly owned maintenance/authority reads available through copied preparation and the final real identity/claim/currentness check; then `closeAsync` every resource that can address the live DB before replacement. Never call close inside its own admitted callback. Resource close failure means “not closed”; readiness must stay fenced. Future P epoch checks are a second guard against retained handles, not proof that missed producers were drained.

Foundation's current `closeApplication` is terminal and refuses recreation. Prefer supervised process replacement to pretending the same disposed application can resume. Its accepted standalone Bun signal shutdown ordering does not establish pre-drain for arbitrary programmatic close. COMPOSITION must join explicit maintenance initiation to producer fences and independently checked resource outcomes; neither a Nitro close hook nor a resolved `Application.dispose` alone authorizes file replacement. A narrowly isolated supervisor status/recovery path must never retain an ordinary DB lease or offer private content while maintenance is active.
