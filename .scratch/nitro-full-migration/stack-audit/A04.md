## Exact mixed-barrel fixes (proposed, not edits)

1. **Root type/runtime split:** `package.json:7-10` routes both main/types and `.` to `index.ts`. Its `Session` export/NextAuth augmentation shares a module with `next/headers`, `configuration.ts` → `@homarr/db` + `env.ts`, and `security.ts` → bcrypt. Move browser-facing session/provider capability contracts to an explicit type-only public entrypoint; retain backend entrypoints for factories/crypto. `nitro/context-types.ts` is already a pure type leaf used by `packages/api/src/nitro/context.ts:1`; it is only SessionUser, not a complete Session replacement. Genuine `import type` is erased—this audit does **not** allege it executes bcrypt—yet its type graph remains NextAuth-coupled. Example browser consumer: Next `_client-providers/session.tsx:7`.
2. **Do not broaden `/shared`:** `shared.ts` → `permissions/index.ts` → board/integration calculators currently uses only type imports of NextAuth Session; there is no DB/env runtime edge there. Preserve that separation while removing the Next-specific type. `integration-provider.tsx` is pure React projection and cannot grant server authority.
3. **Server barrel stays server:** `server.ts:1-11` combines SQL queries/callbacks and `providers/check-provider.ts` → `env.ts`. `integrations-with-permissions.ts:3` captures ambient db. Inject owned persistence/configuration at backend composition; expose separate public DTOs for provider names/local-management modes/permission booleans. A type import of this barrel (e.g. Next board `_query-snapshot.ts:10`, Nitro `-onboard-transitions/resources.ts:1`) is not a runtime SQL import, but still needs independent frontend contract closure.
4. **API-key constant split:** `api-key/index.ts` combines a safe literal with verifier → bcrypt → `server.ts` → DB/env. `packages/api/src/open-api.ts:4` imports the constant from that mixed public entrypoint. Offer a constant-only public subpath/contract; verifier remains backend-owned. `constants.ts` is not currently independently exported in package.json.
5. **Policy split:** `nitro/policy/index.ts:1-5` exports pure identity/resource decisions together with `crypto.ts:1-2` (Buffer/node:crypto) and `secrets.ts:1` (Buffer/secret execution). A runtime import of a pure symbol from this barrel creates a server graph unless safely separated; tree-shaking is not a boundary contract. Existing observed consumers are backend Nitro router sources, not proof of a browser leak. Publish pure decisions/contracts separately from server codec/secret execution; preserve the actual algorithms.
6. **Other backend-only mixed entries:** `nitro/verifiers/index.ts:1-21` includes ldapts plus bcrypt; `nitro/session-primitives/index.ts:1` combines cookie types and node:crypto. Do not use these runtime entries for browser contracts. `nitro/sql-authority/index.ts` → persistence/bcrypt and `nitro/critical-writers/index.ts` → both native DB engines remain backend-only and are **not currently public package exports**; their existence is not a registered production dependency.
7. **New frontend inferred-type edges (static only):** `apps/nitro/src/features/identity/client.ts:3-11` type-imports backend context and procedure factories; its user/API-key factory edges reach `packages/api/src/nitro/routers/{user,api-keys}.ts:4` → `@homarr/auth/security` → bcrypt. `packages/api/src/nitro/assembly/client.ts:3-5` type-imports `createExpansionApiAssembly` from `assembly/index.ts`, whose runtime imports include `routers/integration-operations.ts` → `@homarr/auth/nitro/policy` → node:crypto/Buffer. These are type-graph coupling paths, **not evidence that erased type imports execute server code in a browser**. The frontend needs an explicit public client contract boundary rather than substituting runtime backend barrels. `apps/nitro/src/features/auth/contracts.ts` itself has standalone interfaces/types with no observed imports; preserve that isolated seam. API/frontend graph closure remains A03/A02-owned, not an A04 relocation/edit allocation.
