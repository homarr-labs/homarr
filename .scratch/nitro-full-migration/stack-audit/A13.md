## Dependency boundary

Whole-text scans found **zero direct Next.js, next-intl, tRPC, Redis, `@homarr/api`, `@homarr/auth`, `@homarr/db`, `~/` or application-module imports** in this package. Strings describing `@homarr/widgets` in the component catalog are not actual widget-adapter imports. `scripts/check-architecture.mjs:6–11,73–82` refers to old Next management and widget paths for static checks, not runtime imports. Do not interpret this direct-import result as proof that all cross-package consumers or transitive exports are migrated.

- `src/core`: shared Zod v4 schema/normalization/import/credential-redaction/catalog/assistant-lifecycle logic. `request-schema.ts` imports the real HTTP integration-kind catalog from `@homarr/definitions/integration`; do not substitute a permissive string enum. `component-discovery.ts` imports Mantine namespaces for generation/discovery, so it is not a server-authority entrypoint.
- `src/jsx`: Acorn/Acorn-JSX analyzer and bounded interpreter, React emitter/sanitizer, actual Mantine component wrappers. Browser-compatible does not mean hook-free: runtime components acquire input and runtime contexts and Query-backed request components. Keep analyzer-specific exports distinct from UI/runtime barrels; never pull `/server` into the browser.
- `src/runtime`: already uses TanStack React Query, not tRPC. `CustomWidgetRuntimePort` is the real integration seam; context/messages/components are supplied by the host. No replacement interpreter, fetch singleton, fake Query result, session or grant provider is needed.
- `src/workbench`: message/callback-driven React/Mantine/CodeMirror UI and editor validators. `CustomWidgetWorkbenchPort` describes preview/query/simulation/live-action/journal acquisition but does not implement it. Contextual management/navigation, persisted forms, integration selection and preview execution are outside this package.
- `src/server`: reusable Node/Undici domain services, never browser modules. DNS/TLS/crypto/zlib, encrypted preview secrets, TTL/CAS, limiter ownership and HTTP effects require genuine backend composition. No ambient Redis adapter exists here. Keep services package-owned and compose through the already prepared resource contracts rather than relocate or rewrite them into a frontend app.

## Contracts that must survive unchanged

### Validation, interpreter and trust

`core/custom-jsx-schema.ts:19–55,76–101,193–204,234–314` owns `homarr-custom-widget-v2`, Unicode authoring normalization, the 50,000-character template limit, strict definition/create/update/import rules, line-array exclusivity and separate stricter preview parameter validation. Saved definitions remain repairable; do not apply preview-only strictness indiscriminately to old stored records. `request-schema.ts` preserves maximum 8/default sources, 64 requests, strict HTTP/integration union, named option/param references, header reservations, manual actions, DELETE full permission/confirmation, and invalidation query targeting. Options retain 64-entry limits, defaults, bounds, static/dynamic choices and normalization versus validation distinctions.

Preserve `jsx/{analyzer*,policy,safe-language-policy,regex-policy,interpreter*,collection-methods,string-methods,jsx-emitter,safe-properties,safe-bindings,bindings}.ts*` together. The parser/interpreter is real restricted AST execution, not JavaScript evaluation or placeholder rendering. Keep operation/depth/collection/render/string budgets, own-property access, prototype/reflective denial, safe callable registration, callback slots, regex restrictions, blocked tags/props/styles/URLs and diagnostics. Runtime wrappers retain denied components, scoped control names, no escaping portals/modal pickers, safe links, button types, bind/reset lifetimes and conflict diagnostics. Missing component exports remain diagnostics, not silent support.

`core/component-{catalog,registry}.ts` consume the single generated catalog. Preserve its bytes/schema/version and icon list; do not generate a competing catalog or broaden safety to make missing components render. Authoring prompt/resource versions and assistant continuation, follow-up/source-change, template digest/evidence and sequential-mutation gates are part of parity, not optional documentation. Their turn-local guidance is not storage authority.

### Runtime and public data

`runtime/types.ts:31–60,79–102` keeps item and preview identities, cancellation signal for queries, confirmed actions, target invalidation, genuine confirmation/notifications, edit mode and published per-request status. `sub-fetch.tsx:43–102` keys data by item/preview scope, request, serialized params and cache version; retains retries, bounded polling, disabled queries, identity-bound manual triggers and nonpublication of repeated manual-card results. `actions.tsx` preserves local action result publication, simulation labeling, DELETE/declared confirmation, pending toggles with rollback and server/result-declared invalidation. `refresh-button.tsx` distinguishes a named request from `parent`/`*` refresh.

`custom-jsx-renderer.tsx` preserves per-instance input registration, type conflicts, cleanup/reconciliation, scalar reset semantics, budget/render errors, boundary reset keys and isolated layout. Browser request capabilities are credential-free presentation metadata, **never current authority**. Keep backend board/integration/current-user checks for every dispatch; do not let preview IDs, `previewLiveActions`, `minimumBoardPermission`, edit-mode booleans or UI confirmations authorize an item request. `core/import.ts:180–192` strips local integration bindings from portable export; definition-security validates/redacts credentials and unsafe prototype keys. HTTP response redaction occurs before result publication. Never send encrypted preview secrets or connection/TLS resources to UI. `workbench/parseRequestManifest`'s tolerant editor fallback and malformed capability filtering are UI behavior, not acceptable execution validation.

### Preview, configuration and execution

`server/preview-sessions.ts` preserves 10-minute absolute expiry, owner-not-found concealment, revision CAS with up to eight attempts, encrypted secrets, journal limit 50, independently stored evidence and remaining-TTL propagation. Template/source/secret/live-action mutations advance revision; template revisions require full preview validation and unchanged-template rejection. `preview-session-evidence.ts:18–24` accepts 2xx query evidence and simulated-or-2xx action evidence keyed by **revision/kind/request**. Persistence must consume final-revision evidence and original definition fingerprint/rebinding checks from the existing prepared handlers, not this service alone. No new live execution may be enabled because simulation succeeded.

`server/request-limits.ts` needs atomic category rates plus owner-specific concurrency (user/item 4, definition 8, lease 60 seconds), late-release isolation, partial-acquisition rollback and fail-closed store errors. Local Maps are existing optional single-process implementations, **not production fallback adapters**. Preview CAS/evidence ownership, limiter admission/release, configuration-token claim/apply and authority-to-COMMIT effects require transactional/coordination owners; plain Nitro KV cannot emulate CAS. Only bounded response cache replacement is a KV candidate after reviewed TTL/key/epoch/in-flight retirement semantics; no such implementation is supplied here.

`network-policy.ts`, `auth.ts`, `request-executor.ts`, `request-dispatcher-lifecycle.ts`, `request-manifest.ts`, `response.ts` preserve same origin/path prefix, all-address DNS validation/pinning, scope restrictions and metadata/reserved-address denial; actual certificate/hostname trust; delayed connection derivation; header/query/body auth; exact declared params; 10 KiB request, 1 MiB response and JSON/decompression budgets; three redirects only for unauthenticated queries; 10-second hops/45-second total deadline; one-second bounded dispatcher close/destroy; redacted logs/results and successful-response-only cache/in-flight/epoch invalidation. A generic fetch bridge cannot substitute for these protections.

`core/source-setup.ts` and `workbench/source-setup.tsx` preserve suggested/confirmed URLs, scope, integration kind/id, configured-secret indicators and source-authentication identity. UI readiness deliberately does not require every optional credential; keep backend validation distinct. The frozen source preparation also requires the shared serialized configuration store, ten-minute token expiry, owner/source-auth snapshot, secure GET/POST completion route, binding-change secret deletion and explicit-secret precedence. The package alone does not implement that token lifecycle; no permissive request/grant crossover is acceptable.
