## Import and rendering graph

1. `next.config.mjs` wraps static Next export with `fumadocs-mdx/next`; trailing slashes and unoptimized images are explicit. `package.json` invokes Next for dev/build/type generation; `tsconfig.json` retains Next plugin/generated types and `@/`/`@site/` aliases. These are actual old-stack dependencies, not replacement implementations.
2. Root `src/app/layout.tsx` renders React HTML, metadata/viewport, Next Script sequencing, runtime configuration, Fumadocs provider, independent Kapa launcher/script and client analytics. `Provider` uses `fumadocs-ui/provider/next`, lazy search, and system/light/dark theme. Route groups use Fumadocs HomeLayout or DocsLayout; docs sidebar behavior uses the framework adapter, tree, relative-link and sidebar primitives.
3. `src/lib/source.ts` uses Fumadocs MDX macros, Zod frontmatter schemas and loader to compile docs/blog, infer titles, transform navigation, enumerate static routes, generate processed Markdown and LLM corpora. MDX imports local React metadata modules and components; many imports use `from "."`, so preserve extension resolution and neighboring `index.ts[x]`. `src/types.ts` exposes ReactNode-bearing descriptions/configuration; these are not plain JSON catalogs.
4. Docs/blog/API pages await Next params, call `notFound`, enumerate static params, generate metadata, and render compiled MDX/TOC/breadcrumbs/neighbor links. Link/image/navigation/script replacements require explicit behavior, not a rename. No docs `loading.tsx`, `error.tsx`, middleware, server-action directive, Redis or tRPC runtime import was found in the owned source scan. Workshop's React error boundary and loading components are separate features.
5. `api/search/route.ts` exports Fumadocs **`staticGET`**, not a request-time search service. `search.tsx` uses the matching Orama `staticClient`; the generated index includes docs and API pages, processed metadata and only real HTML anchor destinations. It does **not** currently index blog posts despite README wording about searching project news.
6. `src/lib/openapi.ts` reads the generated public OpenAPI document, narrowly normalizes recursive unconstrained JSON for Scalar, and builds tag-grouped operation pages. `openapi-page.tsx` is client-side Fumadocs/Scalar. Markdown uses the same schema; preserve authentication, parameters, bodies, responses, explicit request sending, instance URL and reverse-proxy paths. JSON payload contents were not audited.
7. Workshop browser routes and the static 404 fallback call `@homarr/workshop/backend` through cached `WorkshopBackend` instances, with shared schema validation and runtime URL overrides. This is the Workshop/PocketBase client abstraction, not the proposed Homarr Nitro backend. `useWorkshop.ts` includes auth refresh/GitHub OAuth, listing/sorts/filters, reconciled voting, submissions/screenshots, reporting, deletion and comment CRUD. Preserve moderation/account/detail UI and authority on the existing backend; no provider operation was invoked.
8. Direct shared-package edges are `@homarr/definitions`/integration/doc slugs, `@homarr/ui/widget-icons`, `@homarr/custom-widgets/{core,workbench,catalog,catalog-example}` and `@homarr/workshop/{backend,schema}` plus its root. The docs mascot imports `tools/motion-reel/three/{lab-types,logo-rig}`. These cross-partition paths are dependencies to coordinate, not inspected/accepted active implementations.
9. No direct `@homarr/translation` or `next-intl` import was found. Docs declares English HTML, English search, local English editor messages and next-themes color mode; translation contributors are fetched from static public JSON. Shared workbench/UI translation coupling must be reconciled by their owning audits rather than inferred from docs-only scans. No direct `@homarr/{api,auth,db,core,redis}` dependency appears in this source scan; no unconditional main-backend migration is justified by these docs consumers.

## Preservation and blockers

- Keep every content filename, historical blog, typed catalog entry, metadata title/order, screenshot/SVG, subtitle and public schema/catalog/contributor asset at its existing path. No hashes, catalogs or asset contents are copied into these reports. Generated payloads need their existing generation provenance maintained; no freshness claim follows from metadata-only classification.
- All proposed docs replacement targets are **unassigned**. The safe preservation target is the same `apps/docs/<relative path>`; this report does not assign docs to `apps/nitro` or `apps/backend`, nor inspect active replacement code outside A15. No actual docs replacement fact was established.
- A main-app-only removal can keep the docs workspace/build isolated and preserve stable shared browser/schema exports. Global deletion of Next/Fumadocs or root catalog entries cannot be justified while this separate site still requires them. Shared workbench/icon/schema changes must keep the docs consumer's browser/build-time graph working and must not pull Nitro bootstrap/SQL/Redis into it.
- Scope approval, complete docs feature mapping, build-time MDX/server-only equivalent, static host/Workshop routing agreement, generated OpenAPI/custom-widget catalog regeneration, and future explicit validation are blockers to including docs in whole-repository removal. No production join is cleared by this inventory.
