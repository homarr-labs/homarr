## Verified legacy production chain

1. `Dockerfile:13–19` installs from the root manifest/lock and workspace manifests, then copies the checkout. Its actual build command at **31** explicitly selects `@homarr/nextjs...` and `@homarr/cli`; it does not call the now-Nitro root `build` script. A Next compiler cache is mounted at **28**.
2. `Dockerfile:42–53` packages the bundled product CLI, native SQLite binding, migrations, and **`apps/nextjs/.output/standalone`**. It also copies the Redis config and nginx template. The runtime includes Redis/nginx and exposes **7575**.
3. `scripts/run.sh:31–62` rejects MySQL, creates writable volume directories, and runs the dialect migration bundle with failure abort. It then generates a fresh auth secret (**64–65**), starts nginx (**75–82**), chooses internal/external Redis (**84–91**), and launches **`node apps/nextjs/server.js`** (**93–111**) with a one-second restart loop. Termination traps cover migration, Next, nginx, and Redis.
4. `nginx.conf:7–26` binds 7575, sends `/websockets` to **3001**, and everything else to **3000**, retaining Host and forwarding headers and a 256 MiB body limit. **The reviewed launcher never starts the 3001 websocket service.** A successful HTTP launch does not establish working live delivery.
5. `scripts/entrypoint.sh:18–34` prepares/chowns volume, Redis, Next cache, and nginx paths; **38–49** implements `_FILE` secret inputs; **51–55** drops privileges before exec.

The root-manifest snapshot (`build/dev/start → @homarr/nitro`, with `--no-env-file`) and `.run/dev.run.xml` / `.vscode/launch.json` root commands may already choose the new app during local development. **`paseo.json:12` bypasses that root script and explicitly launches `@homarr/nextjs`**. Root commands cannot fix Docker's explicit filter/output/launch chain.

## Exact required cutover changes

### Production build, packaging, lifecycle, and asset serving

- Replace **Dockerfile's explicit Next build filter, Next cache mount, standalone COPY, and `scripts/run.sh` launch/restart target together**. Build the approved backend artifact and frontend client assets (and the SSR server artifact if the target uses SSR), then copy every required runtime dependency, asset, public file, migration and CLI artifact into a documented production layout. Exact package/output names must come from the missing cutover specification/new-app owner, not this audit. An existing `@homarr/nitro` root script is only a snapshot.
- A production frontend build must be served by the **same application listener** as health, RPC, REST, auth, MCP/discovery, media, uploads, and live delivery. Route APIs/streams before any frontend fallback; missing API/asset paths must not become HTML. Preserve hashed-asset caching, correct MIME types, deep links and public/PWA/localization assets. The existence of these target implementations is not verified in this scope.
- Remove the required internal/external Redis process/config/env/volume coupling once new state/jobs are implemented. Preserve existing `/appdata` data; audit does not authorize deleting Redis or any user data. Choose either a direct app listener on 7575 or a retained single-upstream nginx proxy; eliminate the separate 3001 assumption and obsolete forwarding/cache paths. Preserve IPv6 behavior, trusted forwarding semantics, streaming/upgrade behavior and upload limits intentionally.
- Update entrypoint writable-directory ownership to real backend/media/cache paths, retaining PUID/PGID, `_FILE` and exec behavior. Retain startup migration ordering/failure abort, MySQL rejection, native SQLite binding resolution, durable session-secret lifecycle, graceful termination and cleanup of in-process jobs/streams. Do not carry a fresh-per-start auth-secret strategy into sessions that require restart continuity.
- `.github/actions/extract-build-artifact/action.yaml:33–53` currently **boots** the product image, copies the nginx template, archives `/app`, and replaces native SQLite binaries at two hardcoded locations for Debian. Update extraction/validation to the new runtime layout and actual binding resolution. Prefer extracting immutable build artifacts without starting product migrations/background services. Keep amd64/arm64 and glibc/musl handling; `.github/actions/prebuilt-debian` and `deployments/prebuilt-debian` are native-binding support, not inherently Next-dependent.

### CI and generated artifacts

- `.github/workflows/ci.yml:95,118–121` restores Next caches and explicitly rebuilds Next for the Custom Widget bundle gate. Replace the product compiler cache/build target and rewrite `scripts/check-custom-widget-bundle.mjs`: it reads Next SSR chunks, loadable manifests, module IDs and `/_next` asset paths. Keep the lazy-runtime/browser-byte budget against the new frontend build manifest, not a renamed Next directory. **Do not remove docs' separate Next build/cache merely because the product migrates.**
- `tooling/github/setup/action.yml:55–71` distinguishes product Next and documentation caches. Retarget only the product half. `turbo.json:33–40` already includes `.output/**`, but not `dist/**`; set outputs from the approved backend/frontend layout, preserve dependency ordering and platform hashing. No target command or cache was exercised.
- `scripts/check-openapi-schema.mts:4–9,42–43` imports the old API generator, emits a 3000-base document, compares the docs schema, and force-exits because the import graph owns background handles. Replace it with a side-effect-free projection of the new public API contracts and approved origin semantics. Update `.github/workflows/docs-update-openapi.yml` and `validate-docs.yml:7,54–58`; the latter still invokes a Next catch-all route spec. Update `database.yml:47` affected-path classification for new backend/frontend startup/onboarding/backup paths. Release/preview workflows both use the root Docker build and therefore inherit its legacy path.

### Developer CLI, config, E2E, and measurements

- `paseo.json:12` must select the approved new dev entry and allocated port; keep docs independent. `.run` and `.vscode` mostly call root scripts: reconcile them with the root-manifest owner, rather than inventing a second launcher. `development/development.docker-compose.yml` / root `docker:dev:up` still provision Redis; retain optional PostgreSQL while replacing required Redis setup. Update stale setup statements in `AGENTS.md` and `tools/homarr-dev/README.md:18` only after the runnable contract is agreed.
- `tools/homarr-dev/internal/run/{build,prepare}.go` builds the root Docker context. Its Docker launcher, port parser and UI assume **7575** and mount `/appdata`; preserving the external listener/volume contract avoids needless CLI churn. The production bundled `homarr` CLI/native binding remains a separate packaging obligation. Do not confuse developer CLI with product CLI, or execute the tool during this audit.
- Preserve readiness/liveness contracts consumed by `e2e/shared/create-homarr-container.ts:38` and `e2e/health-checks.spec.ts`. Replace the Redis-specific health case/helper with evidence for the new required runtime dependencies, without adding speculative tests in this audit. `e2e/shared/{e2e-db,seed-admin-user}.ts` directly use old DB/auth internals; migrate fixture setup to the approved persistence/auth contracts. `e2e/mysql-conversion.spec.ts:61–64` explicitly verifies `/api/user-medias/<id>` response bytes/content type after two boots: preserve migration/media compatibility or make the intended break explicit.

Add the actual new generated-output exclusions and separate browser/server typing where required. `.oxlintrc.json:35` applies the widget-barrel guard only to `apps/nextjs`; extend/retarget it so the new frontend does not silently lose the architecture constraint. `.dockerignore` / `.gitignore` contain obsolete Next/tasks/websocket artifacts and must describe the new output layout while continuing to exclude secrets and runtime data.
- Benchmarks are **not stack-neutral**: `docker-build-lib.mts:14,54`, `board-static-graph.mts:114–126`, `benchmark-pair-lib.mts:250–251`, and `docker-build.mts` require Next cache/source/compile timing. Introduce explicit legacy/target measurement adapters or revise the schema/gates; neither stripping failures nor reporting absent Redis as zero establishes equivalent work.
- `patches/trpc-to-openapi.patch` changes Zod coercion handling in the old adapter. Remove its registration/payload only when the dependency owner proves no retained consumer needs it. Other vendor patches, converter frozen fixtures, showreel assets and historical changelog entries are not automatic cutover deletion candidates. `tools/v2-showreel/src/scenes/front-door.ts:424` depicts tRPC in presentation material, not production execution.

Observed production-consumer paths are `/api/health/ready`, `/api/health/live`, `/api/trpc/*`, `/websockets`, and `/api/user-medias/<id>`, plus board/init/login/navigation. Showreel REST examples are illustrative, and upstream fixture-provider `/api/*` paths are not Homarr route registrations. Inventory does not establish a complete endpoint surface. Then verify they share one listener, preserve auth/origin/error/stream behavior and work from the actual packaged image, not only the root dev command. **No execution-based claims were made here.**
