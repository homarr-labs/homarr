# Authority → native COMMIT binding — proposed narrow join

Planning only. G3 is accepted by both reviews and committed as `c009cba62` (current `CONTRACTS.md`); older pending-review wording in persistence/media handoffs is historical. `MEDIA-ATOMIC-PLAN.md`'s upload group plus optional icons and exact-URL paired deletion semantics are Oracle-accepted. **Neither acceptance supplies real current authority through COMMIT. Both media mutations remain absent.** This plan proposes that missing join, not a new auth engine, SQL implementation, Stage P release or #113 completion.

## 1. Actual source facts and the gap

- Frozen `auth/nitro/policy/identity.ts` snapshots server-derived identity/expanded permissions; `requireAuthenticated`, `requireGlobalPermission`, `enforceMutationMode` and `authorizeSetup` are pure decisions. `resources.ts` consumes principal-filtered grant evidence. None owns session verification, durable revocation, a transaction lock, a revision counter or native COMMIT. Cookie/token/expiry helpers in `session-primitives/index.ts` likewise establish no reader/lifetime authority. Existing API read leases (`assertCurrentAsync`/`releaseAsync`, including board/media/integration preparation) are consumer contracts, not such producers.
- `auth/callbacks.ts:10–21` reads **distinct group permissions joined to actual `groupMember` rows for the user**, then invokes actual `getPermissionsWithChildren`. There is no independent user-global grant table or automatic everyone-name union here. Everyone membership is established by source sign-in effects, not inferred by the reader. The existing expansion gives admin → media-full-all → media-upload/media-view-all; media deletion must not invent a separate admin bypass.
- `router/medias/media-router.ts:55–126` and the frozen native helpers require media-upload for upload; delete requires authentication, then missing → NOT_FOUND `Media not found`, then owner **or** expanded media-full-all, otherwise FORBIDDEN `You don't have permission to delete this media`. Null creator is not the actor and needs full-all. Demo read-only mutation denial precedes authentication/input in the outer legacy/native procedure; preserve `prepareMediaUploadAsync`'s separate defensive ordering and denial-before-body-read. Setup claims cannot authorize media.
- Existing SQL authority rows are `user` (ID/provider/profile/password), `session` (session_token PK, user_id FK, expires), `apiKey` (ID PK, stored hash, user_id FK), `groupMember` (group_id/user_id compound PK), `group` (ID PK/name), `groupPermission` (group_id/permission). User deletion cascades sessions/keys/memberships and sets media creator to NULL; group deletion cascades memberships/grants. SQLite expiry is timestamp_ms integer, PG expiry is timestamp; preserve those physical representations. There is **no** persisted principal/session/grant revision to copy into a new contract.
- `auth/session.ts:21–54` looks up a token and current user/group permissions but does **not** explicitly reject expired rows. `configuration.ts` separately configures database sessions/maxAge; API-key authentication verifies a stored hash asynchronously and builds a session-shaped result without a session row. These paths are not interchangeable evidence for a new reader. **Q16 remains unanswered:** Auth.js Core OIDC plus explicit SQL-session establishment/reader/renewal/revocation is proposed, not selected. Do not silently choose expiration semantics, turn display expiry into API-key validity, use JWT claims, or revive unsupported Core Credentials/database behavior.

### Exact accepted G surface

`packages/db/runtime.ts:270–306` exposes `boundedTransactionSync<T>(operation, callback: (db: HomarrDatabase) => T): T` for SQLite and `boundedTransactionAsync<T>(operation, callback: (db: HomarrDatabasePostgresql) => Promise<T>): Promise<T>` for PG. `BoundedTransactionOperation` is exactly `{ signal: AbortSignal; lifetime: AbortSignal; deadlineAt: number }`. Runtime additionally supplies its own bounded lifetime, admission/drain, quarantine and maintenance/close invalidation.

`transaction-gate.ts:160–249` uses SQLite BEGIN IMMEDIATE, synchronous guarded execution, failure capture, scope revocation, then `gate.check()` immediately before setting dispatched and native `client.run("COMMIT")`. PG `:252–395` checks out one existing-pool client, owns BEGIN/statements, revokes/drains scope/native tail, rejects recorded failures even if caught, then `gate.check()` immediately before dispatched/`client.query("COMMIT")`. Checks cover signals and finite wall/monotonic deadline, **not actor/grant/session/demo facts**. An AbortSignal with no genuine revocation producer is only cancellation. Awaiting a policy SELECT or `assertCurrentAsync()` immediately before returning from the callback still leaves a gap and supplies no SQL lock across G's drain/COMMIT.

## 2. Recommended binding: locked source facts, not a last boolean callback

Ask Oracle to accept a **media-specific locked-authority protocol**. A genuine AUTH reader first admits the request; DB then reacquires/verifies the necessary authority on the same transaction as the accepted media SQL. Locks remain owned by the native transaction, including G's scope revoke/drain and actual COMMIT. No raw session/client escapes and no generic caller-provided DB authorization callback is proposed. Successful preliminary policy is not a permission to eagerly write outside this locked interval.

The admission carries only server-private authenticating-credential provenance, actor ID and the source facts the reader actually verified, plus owned lifetime/bounds/release. Names below describe **candidate roles, not accepted exports**; credential locators/witnesses are private to AUTH/DB, not public BackendPrincipal/DTO fields. SessionUser and PolicyIdentity remain unchanged. The future real reader, not API input or guessed counters, must originate any currentness/revision information. No new durable version/schema is necessary for the row-lock proposal.

### SQLite

After all asynchronous preparation, enter the accepted bounded **synchronous** BEGIN IMMEDIATE transaction. On that admitted connection synchronously reread the actor, the exact authenticated credential evidence, memberships and group grants; expand with the existing pure definition algorithm and enforce the exact media decision/demo mode **before the first media write**. Use actual synchronous get/all/run forms; never async callbacks, `.execute()` promises, asynchronous session init/renewal, hash verification, provider/body I/O or another connection. G3 refusal/failure capture is retained, not caught to authorize COMMIT.

The immediate write transaction excludes competing SQL writes, including deletes, new memberships/grants and credential changes, through root COMMIT. A prior read snapshot/admission does not: authority must be read inside this transaction. Any asynchronous credential verification is completed beforehand against a private exact stored witness (e.g. API-key hash/user ID), then checked for equality under the write transaction; a changed/absent witness rejects, never trusts the earlier verification or silently verifies a different key. SQLite does not require or support PG FOR SHARE syntax.

### PostgreSQL: concrete source anchors and missing writer protocol

Use the accepted checked-out bounded transaction with **fresh statement reads** (the current plain BEGIN uses the normal connection isolation setting; the producer must establish/verify suitable READ COMMITTED semantics or stop, not assume an earlier repeatable snapshot is current). Parameter-bound locks use existing IDs; no fabricated sentinel row/role/advisory-lock key:

1. Lock actual actor `user` by ID **FOR UPDATE**; absence rejects. This conservative per-actor mutex blocks actor deletion and is the required parent anchor for that actor's membership/credential writers, including insertion into an empty membership set. It changes scheduling, not grants. For operations touching multiple users, acquire actor/target user IDs in one canonical sorted order, not caller-first order.
2. Resolve/recheck the exact authenticated credential under the actor lock: SQL-session row by the verified locator/user ID **FOR SHARE**, or the actual API-key row/hash/user ID **FOR SHARE** only for a separately accepted real API-key reader. Reject absent/remapped/replaced evidence. These locks block credential update/delete. Creation, renewal, sign-out/revocation, replacement and account-establishment writers must take the same parent user FOR UPDATE **before** child writes; an ordinary Drizzle/Auth.js adapter is not automatically compliant. No raw token/hash is logged or returned.
3. Read the actor's complete membership IDs after the user lock. Lock those `group` parents **FOR SHARE in sorted ID order**, then reread the joined group-permission facts and expand them with actual `getPermissionsWithChildren`. Membership writers must lock the affected user(s) FOR UPDATE before changing any member row, and protect referenced group parents; group-grant insert/update/delete/replacement writers must lock the target group **FOR UPDATE** before any grant change. Group deletion must hold that parent FOR UPDATE through its cascades. Explicit parent-lock protocol protects **absent/new grant and membership rows**, not only selected rows; FK checks/key-share alone do not protect a predicate set. Changed/disappeared parents invalidate the attempted evidence before media writes. Grant writers never acquire user locks after holding group locks; multi-target writers need the same canonical lock order or a separately reviewed deadlock-safe plan.
4. Using these current locked facts, check authentication/actor identity, source media-upload or owner/full-all decision and demo admission. Then perform the already accepted media SQL unit, not a separate transaction. Delete locks/reconfirms exact media ID/creator FOR UPDATE and uses the accepted null-safe CAS; this protects creator changes including another user's deletion/SET NULL. Upload's chosen local repository FOR SHARE and delete's exact-URL cleanup remain as in MEDIA-ATOMIC-PLAN. Keep all locks through G's drain and root COMMIT.

**Every enabled new authority writer must participate**, regardless of endpoint: user delete/provider/account changes, session create/renew/revoke/expiry cleanup, API-key replace/delete/create, local membership add/remove, permission saves, group delete/cascades, LDAP/OIDC group reconciliation and everyone-membership effects, first-user/setup/registration paths and restore/admin/background writers. `auth/events.ts`'s synchronizations are database membership changes; do not poll providers while holding SQL locks. They must be applied through the same writer admission. Current unmounted legacy/native factory bodies are source oracles, **not compliant current writers**; do not activate their bare context.db writes and count them as bound. A direct/raw enabled writer, second authority store or unreviewed adapter breaks the proof: leave media absent until it joins or remains unmounted. Restore/resource replacement uses accepted maintenance abort/drain, not row locks on an abandoned connection.

Row locks establish serialization with durable revocation: a revocation/grant writer that wins first is visible to the locked read and prevents unauthorized writes; a media operation that wins and remains valid commits before the conflicting revocation can change those facts. Merely beginning a revocation HTTP request is not itself a committed revocation. No new immediate-revocation-intent policy is assumed. If the chosen real AUTH service promises earlier invalidation, it must drive its owned lifetime synchronously at G's dispatch boundary as well; a timer/polling cache alone cannot prove that promise.

### Time, non-SQL mode and the actual dispatcher

SQL locks do not stop time or changes in a separate authority/config store. Once Q16's genuine reader accepts a session-expiry rule, it must supply the **actual verified** validity bound; DB reconfirms the same relevant row/bound under locks. Construct G's `deadlineAt` **before gate entry** as the minimum of the owned operation deadline and that accepted authority validity deadline. Existing G captures deadlineAt on creation: do not mutate it later, assume a timer will run during synchronous SQLite, or extend it from a stale cookie/display expiry. Renewal/replacement races reject stale credential evidence or require a newly admitted operation, never automatic replay of a mutation. API keys have no persisted expiry here; do not invent one from `createSessionAsync`'s display timestamp. Clock conversion/drift and expiration behavior remain reader acceptance obligations, not an incidental new policy in this plan.

For demo mode, source DEMO_MODE/DEMO_READ_ONLY is immutable runtime configuration, not a SQL permission. COMPOSITION must pin that real mode for the operation's runtime admission; if a future configuration replacement is possible, it must abort and drain the old owned lifetime **before** replacing it. Do not add demo fields to user/session rows or accept client flags. Host close/maintenance/restore storage identity must retain G's runtime lifetime and drain semantics. Thus the dispatch proof is **locks over revalidated SQL facts + authentic credential/validity bound + pinned mode/owned lifetime + G's native check**, not signal alone.

For these fully bound media operations the preferred proposal needs **no change to G3 or ordinary defaults**: transaction locks survive callback completion, and G already checks the effective deadline/lifetimes at actual native dispatch with no intervening JS await. Native queue/socket dispatch and post-dispatch uncertainty retain G's stated limits; this is not a hard-real-time database-server commit-time expiry guarantee.

If the eventual genuine reader cannot express its validity with these held facts/deadline/pinned lifetime, **HOLD**, do not install a generic `authorizeAsync` callback. The smallest possible additive proposal would be a DB-private, nonforgeable **media-operation-bound dispatch permit** produced only after locked revalidation, with a synchronous, non-I/O assertion placed inside the actual root dispatcher after failure/drain checks and adjacent to the existing gate check. It must bind actor/credential, transaction/resource ownership, exact upload/delete plan and real authority lifetime; caller booleans, async assertion, detached check or guessed revision are forbidden. That would require separate Oracle contract review, DB-owner allocation and native race evidence before any gate change; no such interface is accepted or needed by assertion alone now. Ordinary transactions/copy paths and omitted options must stay unchanged.

## 3. Preparation, source errors and whole atomic unit

AUTH/host preflight authenticates the actual request, enforces source demo/access precedence and fences input admission **before multipart consumption**. `prepareMediaUploadAsync` then validates the group and buffers original bytes/IDs in input order, rechecking around awaits. MD5/mapMediaToIcon preparation is outside SQL; icon IDs follow the accepted conditional repository branch. No new upload-count/total-size policy is chosen. Delete performs the existing narrow ID/creator read and `assertMediaDeletionAuthorized` before its private plan; this preserves missing/non-owner errors but is not its COMMIT authority.

The locked transaction recomputes the same necessary decision; source policy uses current expanded grants, not a manually duplicated inheritance matrix or an added role. The DB/domain join must make the existing media deletion predicate usable synchronously on locked evidence without importing API application internals into DB: a precisely reviewed pure predicate/helper seam or fixed source-derived requirement (`media-upload`; authenticated owner OR media-full-all against reconfirmed creator), not an arbitrary user callback. AUTH owns credential/grant facts; the media domain owns source error/projection mapping. No stale permission array becomes trusted merely because its user ID matches.

Pre-write absence/denial retains source authentication/permission/media errors. Authority/lock/native failure is not mapped to occupied/missing/success or swallowed; caught scoped decoder/execution failures poison bounded COMMIT as accepted G3 proves. Placement is preflight → outside-SQL preparation → same-transaction lock/revalidation → accepted media/repository/icon queries → completion/drain → native gate/COMMIT. Additional SQL checks at the end are harmless only while protected facts remain locked; an awaited final check without those locks is insufficient.

The atomic unit remains the already accepted **entire invocation's media group + optional corresponding icon group**, or **one exact media + all exact-URL icon mappings across repositories**. It is not one transaction per file or a media-only fallback after a selected icon branch fails. Preserve IDs, bytes, source creator/null semantics, no-local-repository behavior, affected-row expectations and URL/CSS/serialized references exactly; do not duplicate/redesign the SQL plan here. New local-icon/sync writers also require the domain admission and transaction-time reference/CAS protocol from MEDIA-ATOMIC-PLAN; an authority lock cannot prevent stale sync reinsertion. Legacy sync stays unmounted.

All PG work remains on one checked-out client; lock timeout/deadlock/abort/constraint/decoder failure before dispatch causes whole-unit rollback, awaited settlement and owner cleanup, **no automatic retry**. SQLite never awaits inside its transaction. After dispatch G may return `TransactionCommitAmbiguousError` even after a successful native COMMIT followed by cleanup failure. Preserve that classification, primary/cleanup causes privately and quarantine/evict unusable resources; do not turn it into an ordinary authorization denial or guaranteed rollback. Confirmed durability is not erased by failed response/invalidation. Reconciliation of exact generated rows/mappings is separately owned and never reissues writes automatically.

## 4. No-users/setup boundary is separate, not an anonymous media bypass

Source `onboarding-claim.ts:62–75` checks users **first** and permits claim-only access only with no users and a valid stored `serverSetting` key `__onboarding_claim` (hash, expiresAt, timing-safe match). `identity.ts:101–110` and native procedure also allow authenticated expanded admin; a required step still uses actual onboarding/fallback normalization. Preserve expired/missing claim, users-present denial, source clock and error order; no new bootstrap role. Read-only accepted setup-read factories do not make a setup mutation atomic.

SQLite BEGIN IMMEDIATE can protect users-empty, claim/current-step reads and the corresponding first-user write synchronously. **PG row locks cannot protect an empty user table, a missing claim row or missing onboarding row.** Future setup/registration writers need a separately reviewed predicate protocol. A concrete schema-preserving candidate is native transaction-held table locking of existing `user`, `serverSetting` and `onboarding` in a fixed order using SHARE ROW EXCLUSIVE for the setup mutation, before users-first reads; it serializes contenders and conflicts with authority-changing DML even when the sets are empty. Re-read claim and step under that admission, retain claim expiry through actual dispatch, and include every new user-creation/claim/step writer. No arbitrary sentinel/epoch/table may be invented.

That candidate is **not executable through today's bounded callback**: `transaction-gate.ts:94–149` admits SELECT/WITH/INSERT/UPDATE/DELETE and its managed savepoint forms, not arbitrary LOCK TABLE. Any fixed setup-lock acquisition would need a separate DB-private owner/Oracle allocation at the native transaction boundary, not a widened public SQL-control escape or generic auth callback. No setup implementation/gate edit is proposed for media. Do not hide this absence predicate HOLD behind an ordinary session/user row lock.
