## 2. Recommend one candidate: credential columns plus one enduring allocator

Recommend **two additive evidence columns on each existing `session` and `apiKey` row, and one small Auth-owned singleton table**. Reuse the main-runtime native transaction machinery, current credential selectors/FKs, fixed statement generators and exact sequence/text validation pattern. Do not introduce a generic state resource, second pool/framework, separate actor table, per-user generation or credential sidecar population.

The names below are prospective design names, not existing schema/exports or allocated file destinations:

| Prospective storage                            | Columns / role                                                                         | Conservation and constraints                                                                                                                                                                                                                                |
| ---------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing `session`                             | Add `auth_lifetime_sequence`, `auth_write_sequence`.                                   | Preserve `session_token`, `user_id`, `expires`, PK/index/FK actions. Both new fields nullable only to represent explicit pre-adoption state, never an admitted credential. No default generation.                                                           |
| Existing `apiKey`                              | Add the same two fields.                                                               | Preserve ID, original stored bcrypt hash, user FK; no session surrogate, expiry, hash regeneration or token rotation.                                                                                                                                       |
| New Auth-owned `homarr_auth_credential_domain` | Singleton `id = 1`; `namespace`; `head_sequence`; `phase` in `initializing` / `ready`. | No user/credential/runtime FK. Enduring allocator survives all credential/owner deletions and P3 infrastructure reset. Namespace immutable during ordinary operation; head never decreases. Phase is durable adoption readiness, not request authorization. |

Use one global allocation sequence for both lifetime creation and private credential writes. Creating a credential assigns a newly allocated value to both fields. A real same-lifetime expiry write allocates a new value only for `auth_write_sequence`. This needs only one allocator and makes both committed lifetime and write evidence non-reused within the uninterrupted domain. Unrelated head advancement is not a global logout or grant revision. The deliberate cost is serializing credential writers on one bounded mutex; permission/resource/profile-only writes are not enrolled in that bottleneck. No sequence-pool optimization is needed for the first producer.

The enduring singleton is necessary because storing a counter solely on a deletable credential row allows delete/reinsert to reset it. Its single-row lock also supplies absent-row serialization for participating credential writers. It has no bearer revocation history: adding this domain model is a real new conservation obligation, not a claim that the original40 already includes it.

**Brief alternatives:** a credential sidecar adds joins, duplicate row ownership and cascade/adoption state without helping the two existing credential tables; a user incarnation/global-authority model is not required by the actual foundation consumer; runtime-state keys are cleared by P3 and their public mutation opens a separate bounded transaction. Making state keys permanent/atomic would expand accepted infrastructure lifecycle, TTL and reset contracts. Reject those for this minimal candidate. Preserve `homarr.runtime.sql.v1` and its four-table meaning.

### 2.1 Minimal real owner binding, without a new actor model

Actual SQLite `schema/sqlite.ts:38–46,102–114` and PostgreSQL `schema/postgresql.ts:56–64,120–132` give both credential families a non-null user FK with **ON DELETE CASCADE**. Deleting a user therefore removes its credentials in the same initiating database transaction. Recreating that user ID cannot preserve those deleted rows; newly inserted credentials receive new allocator values. This proves the credential-lifetime owner boundary under participating native writers without adding a user-incarnation column/table.

Owner reassignment on a credential is replacement: allocate a new lifetime/write pair atomically with its actual FK-changing DML. A provider-binding change on a surviving user must replace affected credential lifetime evidence in the same native unit, because A selects user provider. Two provider changes restoring equal values must not restore old receipts. This is a conditional writer obligation, not a new provider-change endpoint. Profile/name/preferences/password-only updates do not change this binding. Account link/unlink/token refresh does not automatically replace the ordinary selected credential.

This argument depends on preserved FK enforcement and participating writers. Disabling cascades, restoring/reinserting original evidence, changing user/provider behind the protocol or replacing the whole image falls outside it. It does not establish actor-global permission identity, property-change ABA or grant authorization.

## 3. Concrete encoding, validation and guarantee boundary

### 3.1 SQL and private representations

- Recommend SQLite **INTEGER** and PostgreSQL **BIGINT** for all three sequence fields, range `0..9223372036854775807` for the singleton head, `1..9223372036854775807` for admitted credential fields. Each credential must satisfy `lifetime <= write <= head` in a coherent selection.
- On SQLite, constraints must reject non-integer storage classes, not merely numeric-looking values. On both engines require either both credential fields NULL or both positive/in-range with `write >= lifetime`. The singleton PK/check permits only ID1; namespace and phase are non-null and validated. No credential FK to runtime infrastructure or auto-resetting sequence/default is proposed.
- Fixed reads return sequences with **CAST AS TEXT**, never driver JS-number mappings. Validate exact decimal text, length at most19, no sign/space/leading zero/exponent, then BigInt and the explicit range. Only allocator head may be `"0"`; no admitted credential may be 0. Bind writes/CAS through canonical decimal strings cast to the integer SQL type, preserving exact values beyond `Number.MAX_SAFE_INTEGER`.
- Grounding: `runtime-history/validation.ts:3,28–48` already bounds signed64, parses canonical decimal with BigInt and rejects exhaustion; `runtime-history/statements.ts:32–35,58–59` uses text reads and integer casts. Reuse that small pattern. Its current errors/names are history-specific; do not widen a history API or import its epoch as Auth evidence. A narrowly factored shared numeric primitive would require a later exact allocation only if actually worthwhile.

Recommend a lowercase canonical UUIDv4 namespace persisted **once at explicitly owned fresh initialization/first adoption**, using the existing `node:crypto` randomUUID pattern already used by runtime-state/copied reset, not request randomness. Validate its exact representation on every fixed selection. No startup replacement of a present namespace and no infrastructure-epoch reuse. This is collision-resistant namespace allocation, not a deterministic all-history nonrollback guarantee; restore fencing remains §9.

### 3.2 Public and private identity must be different

Recommend public nonsecret string grammar `homarr.auth.credential.v1:<namespace>:<kind>:<lifetime>`, with kind `session` or `api-key` and canonical positive lifetime text. This is a proposed serialization, not an accepted export or implemented decoder. Foundation consumers treat it as opaque. The admitted subject stays the real user ID. No token/hash/user ID, mutable expiry, head, permissions or request ID is encoded.

Private credential evidence carries namespace, lifetime and write sequence **alongside the original exact witness**: session token/user/provider/expiry/deadline, or key ID/hash/user/provider. The head is validated as an upper bound but is **not** part of credential equality: another credential's allocation must not invalidate this lifetime/lease. Domain phase must be ready; its change or namespace loss rejects the observation. Never expose raw witnesses, bcrypt hashes, repository operations or an authorizing receipt through this public string.

Global committed allocations are monotonically distinct in an uninterrupted domain. A rolled-back allocation may be reused only because no usable receipt/result was published. Native settlement precedes evidence publication. COMMIT ambiguity is not rollback; no automatic retry/reallocation is allowed. At the maximum, any operation needing allocation fails before its original DML; no wrap, rounding, sequence restart or silent namespace replacement. Deletion/revocation needs no new allocation and can still remove a credential at exhaustion.

**Where the guarantee ends:** participating writers and an intact, unrewound allocator prevent ordinary deletion/recreation and mutable-write ABA. Arbitrary DBA bypass, lost domain state, imports of old evidence, allocator rewind or whole-image replacement cannot be certified by these SQL fields. Random UUID separation supplies conditional collision resistance, not surviving revoked-bearer rejection or deterministic nonrollback authority.

New values enter credential DML in the **same** native transaction; no callback supplied string or detached state mutation substitutes for this.

## 5. Ordered locks and absence protection, not generic SQL authority

### 5.1 Recommend one common credential-writer mutex

SQLite keeps the existing synchronous **BEGIN IMMEDIATE** transaction (`transaction-gate.ts:207`): singleton check/CAS, original DML and returned evidence execute synchronously. No provider/bcrypt await or asynchronous callback is inserted. Cancellation/finite deadlines and native quarantine/settlement remain intact.

PostgreSQL keeps the existing owned main-pool transaction and **plain BEGIN** (`transaction-gate.ts:254`), with fixed credential admission verifying READ COMMITTED. Recommend this acquisition order for every participating credential writer:

1. Lock/validate the existing ready Auth singleton **FOR UPDATE before any user/Auth table or row lock**. Its one-row mutex serializes allocation and credential identity predicates, even when no credential/destination row exists. Missing singleton fails; normal writers never initialize it.
2. For the existing fixed session mutation entrypoint, retain the native `user → account → group → groupMember` SHARE ROW EXCLUSIVE table-lock order and original isolation/timeout checks (`transaction-gate.ts:341–365`), **after** that singleton lock. The current wrapper routes establish, renew and revoke through the same establishment admission (`438–454`); none loses its original preamble here. Later separately allocated key/bulk fixed operations take their actually required locks after the singleton, without inventing an existing key-table lock.
3. Lock affected existing users in canonical ID order, before account/credential row witnesses and before the existing ordered group parents. Reuse `runtime-authority/locks.ts` user FOR UPDATE and ordered group helpers; keep original account and credential exact-match locks/preconditions. A remap involving two users locks both canonically. Domain serialization supplies missing-user/credential predicate protection only against participating credential/owner writers.
4. Check original name/email/provider selections, account link absence, credential/destination absence and evidence under the held locks; then perform allocator CAS/original DML. Every enabled credential/owner-binding writer uses the same mutex first. PK/unique/FK failures still abort; do not turn a collision into replacement or pick a different user silently.

This requires a **specific fixed native preamble amendment** in `transaction-gate.ts`/`runtime.ts`, not merely adding a callback lock after today's establishment table locks. Otherwise an owner deletion could hold the singleton and wait for a user table lock while establishment holds that table lock and waits for the singleton. The preamble must use actual native client-owned SQL/timeout checks before handing out the scoped database; no generic callback may issue transaction-control or table-lock SQL. Preserve generic bounded/snapshot behavior and existing ordinary BEGIN semantics.

No `apiKey` table lock is claimed to exist. The proposed singleton mutex plus genuine user/credential row witnesses supplies key insertion/remap/delete absence protection **only** if all enabled participating writers obey it. No guessed FK key-share, existing-child lock or numeric CAS covers nonparticipating key writes. Such writers stay disabled/held. The original four table locks also do not protect `groupPermission` or establish authority-through-COMMIT; any necessary overlapping authority-writer lock-order review remains a separate genuine join, not a lease to enlist every group/resource path here.

Read-only REPEATABLE READ snapshots remain read-only (`transaction-gate.ts:255`), not this mutation mode. No second pool, advisory-lock framework, generic SQL executor or increment-after-DML transaction is proposed.

## 7. Fresh initialization, preserved-data adoption and missing-state behavior

**Recommend explicit drained-maintenance backfill, not lazy request adoption.** Compatible writers and admission remain stopped; original data is never reseeded or logged out. Fresh initialization follows the same explicit readiness protocol after the schema exists, with no seed behavior invented for PostgreSQL (current `runtime.ts:223–230` fresh initializer is SQLite-only).

1. Authenticate the approved whole-target schema/ledger and enter genuine same-runtime maintenance with incompatible processes/CLI/background writers stopped and active work drained. Ensure credential SQL logging is suppressed before any selector/backfill read. The present generic runtime readiness probe does not imply Auth-domain readiness.
2. At an explicitly verified first adoption/fresh domain, insert exactly one `initializing` singleton with a newly persisted namespace and head0, atomically under maintenance. Head0 means an empty allocator, **not** default credential evidence. Already present initializing state can resume only with an authoritative retained adoption scope and intact monotonic head; missing ready state after activation is loss, not first adoption.
3. Backfill original sessions then keys in deterministic fixed bounded batches. Under the same native singleton lock, select a bounded set with both evidence fields NULL, validate original rows/FKs, allocate a distinct value for each and CAS-update only the two added fields. Preserve every original token/hash/ID/user/provider/expiry/date/account/permission/serialized/encrypted value. No global-grant or profile write is required.
4. Each batch commits original evidence enrollment plus head advancement; admission stays unavailable while phase is initializing. On cancellation/error, keep committed head/assignments and phase; resume remaining NULL pairs, never reassign enrolled lifetimes or reset head. A partial pair, invalid assigned values, duplicates or head below assigned evidence is corruption and stops repair/adoption, not a fallback default. Fixed checks must include cross-family allocation consistency; use streamed/bounded validation rather than silently truncated samples.
5. After all rows are validated/enrolled and no missing/malformed assignment remains, CAS phase to ready in the fixed native unit under maintenance. Fresh empty databases can complete with head0 and no credentials; subsequent creation allocates positive values. Reopen Auth admission only after separate writer/lifecycle/host approvals, not from schema migration or phase alone.

Batch count/deadline limits reuse the owner's reviewed bounded-operation machinery; this report sets no guessed production budgets. Conditional later provider-remap operations must cover all affected credentials atomically or stop, not reuse adoption's admission-off batching for a live partial remap.

Lazy initialization would add writes to a read projection and make absent state difficult to distinguish from loss; reject it for this first candidate. A single enormous backfill transaction would unnecessarily block large preserved datasets; durable initializing phase plus bounded maintenance batches is the minimal resumable alternative. No new actor enrollment is necessary because credential FKs/lifetimes provide §2.1's owner boundary.

On normal restart retain namespace, head, phase and credential sequences. Do not mint a fresh namespace or reset head on process start. After activation, unsupported schema, initializing/missing/malformed domain, NULL/invalid evidence or exhausted required allocation fails the new Auth capability closed while preserving original rows for separately authorized repair. No ordinary forward logout, key rotation, forced credential deletion or hidden read-path write is authorized.

## 9. Restore boundary and honest unresolved authority

This candidate protects ordinary durable evidence in an intact nonrollback domain; it cannot prevent restored old bearer bytes authenticating again. A fresh namespace retires old revision receipts/leases but current opaque cookie and API-key transports carry no previous namespace. Byte-restoring a revoked token/hash into a valid row can authenticate anew even after fresh allocation. A head stored in that same replaced image is not surviving revocation/nonrollback authority.

Before applicable restore/recovery activation, a separately owned design must provide authoritative revocation/adoption reconciliation **outside the replaced image**, retire/drain old resources, fence attempted replacements and recovery, and establish which conserved credentials are demonstrably still unrevoked. Collision-resistant UUIDs alone do not supply that proof. Keep restore/Auth admission held at that boundary; do not propose blanket token/key rotation/deletion or infer ordinary forward logout from existing migration-session logout. A failed replacement must not reopen an old image under reused accepted evidence.

This is not a blocker for reviewing/implementing an unmounted ordinary durable producer under later exact leases. It is an explicit limit, not permission to activate an incomplete restore-capable host. Main-runtime/logging/admission and physical lifecycle remain original owners' separate joins.
