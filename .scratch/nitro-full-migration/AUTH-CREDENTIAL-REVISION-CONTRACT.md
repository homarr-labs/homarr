## 2. Proposed meaning: actual credential lifetime

An authenticated foundation revision would identify the durable lifetime of the **actual admitted credential and its owner binding**, within an Auth-owned non-reuse domain. Opaque sessions and API keys are separate credential kinds: a key has its own identity, never a fabricated session row or expiry. The proposed owner binding must distinguish deletion/recreation of an owner even when its stored user ID is reused; it does not imply an actor-global permission generation or choose an owner-incarnation field.

The public value is a nonsecret opaque string. Only a genuine credential admission backed by selected durable evidence may produce it. Possessing, echoing or parsing it cannot authenticate a bearer, authorize a host/request, establish a grant, prolong expiry or confer mutation authority. `subject` remains the actual admitted user ID, not an invented credential identifier.

No substitution from requestId, raw token, token/hash digest, userId, expiry, per-request randomness, current-grant hash, process-local counter, WeakMap receipt, preview configuration revision, Query partition or `homarr_runtime_meta.epoch` is valid. A future durable allocator's design is unselected; this prohibition on synthetic request evidence does not select or rule out any properly reviewed persistent allocator.

The string's conceptual identity is lifetime evidence, **not** a claim that all current witness fields or permissions are unchanged. Private exact credential evidence and separately selected identity remain necessary. Equality of public lifetime values is not sufficient lease currentness. Different values alone do not prove physical cancellation or grant revocation.

### 3.1 Renewal: stable lifetime versus internal revalidation

**Technical recommendation only, not a storage or policy implementation:** keep the public credential-lifetime identity stable across the existing same-token renewal. An expiry extension continues the same bearer/owner, not a new login. Advancing that public identity for every due renewal would conflate lease witness freshness with credential replacement without a demonstrated foundation consumer requirement.

A currently compares token/user/provider/**exact expiry**; an old lease becomes unequal after a successful expiry change (`snapshots.ts:145–170`, `authority.ts:304–319`). Preserve this rejection and its captured host deadline. Stable lifetime must not make an old lease gain the renewed validity window. A genuine post-renewal selection must validate the new exact witness before producing a usable new lease; no in-place deadline extension by caller assertion.

Internal mutable evidence may need advancement with the expiry DML to distinguish intervening writes/ABA that exact value equality cannot detect. Alternatively a later design might prove an equivalent exact, non-reused internal witness protocol. That choice needs actual atomic/CAS/read proof; it is unselected here. If advanced, private renewal evidence and public lifetime identity are distinct roles, not permission to change tokens, log users out or ignore exact expiry. No-op renewal cannot invent a committed evidence advance.

## 5. Non-reuse, representation and missing-state design still open

- **ABA:** deleted/reinserted session/key rows and deleted/recreated owners must not reuse lifetime evidence even when all original bytes match. A concrete durable allocator/incarnation/tombstone protocol and atomic writer coverage must supply this, not row-value hashes or local counters. No choice among storage shapes or allocator types is made.
- **Finite exhaustion:** whichever domain is selected must have an exact finite bound or a separately justified non-reuse model. Exhaustion fails before mutation/allocation; never wrap, round, reset or silently start a new namespace. SQL signed64, JavaScript safe-number and opaque-incarnation candidates have different proof obligations; none is the selected Auth field.
- **Canonical representation:** later storage/read/serialization rules must be exact across SQLite/PostgreSQL and process restarts, reject malformed/ambiguous/noncanonical representations, and keep numeric evidence out of lossy driver conversions. No chosen BigInt column, delimiters/version prefix, default or field length is specified here. Original dates/hashes/serialized values keep their current representation.
- **Normal restart:** retain durable lifetime/non-reuse facts. Startup randomness or a restarted counter cannot impersonate persisted identity. New local leases/cache lifetimes do not change credential identity or force logout.
- **Missing state:** after activation, missing/malformed/retired evidence fails new principal production; never fall back to 0/1, user ID or a hidden lazy recreate. Keep original credential rows for explicitly owned repair. Failing new capability is not authorization to delete credentials or alter the old deployment.
- **Initial adoption:** backfill under drained maintenance versus a separately owned transactional lazy initializer remains a future design choice. It must distinguish never-enrolled rows from lost active evidence, serialize concurrent allocation and preserve every existing token/hash/user/account/date/grant. A read-only request projection cannot secretly become the initializer.
