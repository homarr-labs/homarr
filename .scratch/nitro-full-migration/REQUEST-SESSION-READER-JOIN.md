## Header/cookie policy, with actual source differences

Existing constant is `API_KEY_HEADER_NAME = "ApiKey"` (`packages/auth/api-key/constants.ts:1`); existing public `@homarr/auth/api-key` exposes it. There is no located named `HeaderApiKey` selector/helper to invent. Use the real header access `request.headers.get(API_KEY_HEADER_NAME)`. Do not invoke legacy `getSessionFromApiKeyAsync`: it uses another database/session path and logs key/user/request information (`api-key/get-api-key-session.ts:22–76`), not this genuine reader's registry.

Legacy browser RPC source explicitly does key-first, then cookie (`apps/nextjs/src/app/api/trpc/[trpc]/route.ts:34–42`). REST is explicitly API-key-only (`app/api/[...trpc]/route.ts:16,27–36`); REST/MCP are outside this proposal and must not inherit browser-cookie fallback.

| Request credential condition                                                        | Required proposed behavior                                                      |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Header absent                                                                       | Read the genuine session cookie and call the same reader's opaque admission     |
| Header present and malformed                                                        | Reject before API-key SQL; no anonymous conversion or cookie fallback           |
| Header present while explicit policy disabled                                       | Reject before SQL; no fallback, even with a valid cookie                        |
| Well-formed header, approved reader returns authenticated                           | Use that exact API-key lease; ignore cookie as an authority selector            |
| Well-formed header, approved reader **fulfills** with anonymous                     | Only then perform genuine cookie admission; never manufacture an identity       |
| Reader rejects, bcrypt/native read fails, deadline/lifetime expires, request aborts | Reject; do not catch as anonymous, retry or fall back                           |
| Cookie absent or genuine opaque reader fulfills anonymous                           | Anonymous only if request/shared lifetime and finite deadline are still current |
| Duplicate/malformed cookie or cookie reader failure                                 | Reject; no permissive parser or anonymous fallback                              |

Important intentional narrowing: `authority.ts:621–624` currently returns anonymous for a malformed key. The new adapter must distinguish absent header from present empty/invalid header, require exactly the existing two nonempty dot-separated parts, and throw existing `SqlAuthorityError("INVALID_OPERATION")` before delegation. Do not silently normalize/trim or invent a new token format. Reader errors remain errors. This rejects malformed-header fallback rather than claiming byte-equivalence to the older permissive browser selector.

Approved API-key admission already selects a real stored hash, calls `comparePasswordsAsync`, checks lifetime/deadline, rereads and matches the actual credential witness, then registers the genuine lease (`authority.ts:613–640`). A well-formed missing/nonmatching/changed key can yield its real anonymous result. This is not a new fake validation implementation. API keys have `no-stored-api-key-expiry`, not a fabricated session expiry; request deadline/lifetime still bounds them.

Cookie selection reuses `readSingleCookie(request, name)` in `production-sessions/origin.ts:23–35` and `sessionTokenCookieName(prefix)` in already public `session-primitives/index.ts:20`. The former rejects duplicate cookies and URI decode errors. It is Auth-private: the new leaf may expose this **one existing named parser** alongside the getter if Backend needs it; do not deep-import it across packages or export the origin/CSRF guard/secrets. This exact parser re-export is included in the proposed new leaf inventory, not a new parser. The cookie prefix/secure-origin policy must come from the same real pinned issuer configuration, not a new default or request-forwarded header. No mutation CSRF gate is invented for arbitrary API-key read clients.
