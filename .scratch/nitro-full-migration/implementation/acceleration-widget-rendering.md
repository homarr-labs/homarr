# Widget rendering acceleration handoff

## Outcome and limits

Source implementation is confined to `apps/nitro/src/features/widgets-runtime/` and this handoff. Nothing is mounted. No runtime, browser, lint, typecheck, build, test, format, installation, listener, SQL, provider, credential, container, Git, or nested-agent operation was performed. Source-only inspection does not establish runtime correctness or production admission. Q16/Q17/Q18 remain held, including source grant quirks.

The existing `@homarr/widgets/manifest` and its underlying registry remain the only kind, definition, option, and component catalog. All 69 kinds are discoverable through those exports. This is not a claim that 69 kinds render natively. `support.ts` is an import-compatibility admission set, not another widget registry: it contains no definitions, defaults, icons, component loaders, or business algorithms.

## Implemented source

- `transport.ts`: browser-only, same-origin cookie transport using the already-declared oRPC Fetch RPCLink. `WidgetRpcClient` derives inputs and outputs directly from the frozen `createWidgetProcedures` factory, under its real `widget` namespace. No tRPC transport, principal manufacture, credentials, backend changes, wire renaming, JSON coercion, or Date conversion.
- `native-client.ts`: 95 explicit query/mutation/subscription adapters matching the frozen Widget factory. These are transport bindings, not 95 mounted handlers or 95 rendered widgets. Query utilities currently cover the source usages for stats, DNS, smart home, downloads, indexers, requests, notifications, Custom API data, and secrets. The stats imperative refresh calls the native client directly.
- `hooks.ts`: ordinary React Query data/loading/error/refetch state, inherited source cache defaults and widget polling policies, caller query options, exact-input cache updates/cancellation/invalidation, and an authority cache-scope suffix. Forbidden/unauthorized responses throw even when stale data exists. Mutations never automatically retry and abort on unmount or client/authority change. Aborting an already-dispatched mutation is not proof that a server-side effect was rolled back. Beszel subscription hooks consume the real oRPC iterator, honor `skipToken`, abort and close on cleanup, suppress callbacks after cancellation, and do not reconnect automatically.
- `host.tsx`: original manifest resource loading, card shell and title badge, definition-driven integration requirements and advanced-view admission, edit-mode inert content, item/board/dimensions/scale/state/runtime references, source default reduction, typed option-schema parsing, source option-patch merging, scoped recovery/refresh/status/polling actions. The caller must supply the actual source-derived option schema, not a permissive record schema. Compact/advanced changes do not change the host identity. Callers should retain the source portal-owned runtime/state references across layout changes.
- `error.tsx`: source domain error descriptions/icons and definition error overrides, native oRPC permission handling, retry, and a logs link only when current host admission supplies log-view access. No raw upstream error or secret text is rendered.
- `actions.tsx`: existing definition context actions, labels, icons, hidden/disabled/color flags and handlers. It does not infer grants, add mutation authority, or implement an editor.
- `source-adapters.ts`: an uninstalled Vite resolver restricted to importers within the existing widgets source directory. It redirects the source client hooks, query-cache permission check, and query-key helper to the native lane. It also redirects the original weather renderer import to `views/weather.tsx`. It does not rewrite the catalog or mutate legacy source. No global alias, route, config, provider, manifest, or API registry was changed.
- `views/weather.tsx`: a native weather query assembled with the real existing compact and advanced weather views, preserving options, dimensions, disabled-weather/loading states, details, forecast, units, charts and accessibility. No copied weather calculations or fake data.

### Live ownership versus recovery evidence

- Before the fix, render-time `record` created a zero-count entry in the same map used by `ownedQuery`. Ordinary child cleanup reduced the count but retained membership. When a clock weather corner disappeared, an identical weather query still active in another widget consequently matched the clock's refresh/status/error predicates.
- `ownedQuery` now requires a positive registration count. Render-time recording writes only to the separate `recoveryKeys` map and cannot grant live ownership. Both `refresh` and `getDataStatus`, including its error and fetching flags, use only the positive-count predicate. No registration means no query-derived status or refresh ownership, irrespective of cache activity elsewhere.
- Registration acquires a count on an entry captured by that cleanup closure. Cleanup runs once, ignores a replaced entry, decrements only its own acquisition, and deletes the last live entry. With two local registrations for one key, releasing one leaves the other live; releasing the last removes ownership. Repeating an old cleanup cannot decrement a newly acquired entry after remount.
- A normal last-child cleanup also removes that key's recovery record. Thus the clock shrink in the supplied scenario leaves neither live nor retry ownership of the other widget's weather query. Key replacement releases the previous key through the existing hook effect dependencies; registering the next key restores its own live and recovery entries. Polling effect replay and remount reacquire registrations without changing query identity.
- A failed renderer boundary is deliberately different: its committed failed state retains the recovery records when its children are cleaned up, while live entries are still released. Render-time records also retain keys from a failed initial render whose registration effect never committed. Retry therefore does not require positive live counts, and retained failure records never feed ordinary refresh or status.
- Retry captures a fixed set of recovery hashes before awaiting cancellation and reset. Both operations use that same set rather than a changing live predicate. The recovery record clears only after both operations resolve; a rejected reset leaves it available for another retry. The boundary permits only one pending reset through the resulting state commit, checks its lifetime before starting the deferred reset, and ignores completion after unmount or replacement of that reset. A subsequent renderer failure records a fresh recovery attempt.
- Shared-cache behavior remains intentional: normal child cleanup does not cancel or reset the identical query still used by another widget. Explicit failed-renderer recovery can affect a shared query actually recorded by that renderer; it does not create per-widget query IDs or change cache semantics. Cancellation remains a client/query lifecycle operation, not proof of remote rollback or cancellation-proven suspense behavior.

These are source-derived lifecycle traces, not executed reproductions or verified end-to-end results. The user prohibited commands, checks, lint, typecheck, tests, builds, formatting, installs, browser/runtime operations, network access, Git, and nested agents for this fix; none were performed. React Query is already declared at `5.101.2`. Given the previously explicit Context7 quota failure, this fix used only installed `@tanstack/react-query/src/useBaseQuery.ts` and `@tanstack/query-core/src/queryClient.ts` to inspect pre-commit throwing, predicate-based cancellation, and reset/refetch behavior; it made no further documentation network requests or quota workarounds.
