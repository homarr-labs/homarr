# Synthetic auth bootstrap — memory to ready existing file

## Verdict

**Source-feasible through an existing public native snapshot API; not executable under the current child allocation, not runtime-proven, and not authenticated application completion.** A separately authorized genuinely new memory runtime can perform canonical empty adoption and export its actual SQLite contents. MAIN can then open that new synthetic file as `mode:existing`, without file first adoption or invented metadata. No DB/Core/Auth guard change or native FD attestation is needed for this alternative. Existing populated-installation adoption remains held.

No commands, hashes, checks, compilation, evaluation, SQL execution, data/config/environment/secret reads, materialization, Engine/container/service calls, or nested agents. Historical acceptance and native-memory results are coordinator premises, not reproduced evidence.

## Domain carry and epoch/reset conventions

Canonical empty adoption creates a real UUID namespace, native INTEGER head zero, and then phase `ready` after validating the session/API-key families (`runtime-auth-credential/statements.ts:172–188,330–355`). Export copies that stored domain and the actual migration ledger/catalog; it does not recreate them from the returned adoption DTO. Physical SQLite layout need not be byte-identical after VACUUM; stored values/representations are the conservation target.

The issuer reads exactly one ready domain, valid namespace, native head storage and signed64 TEXT sequence, including for its no-cookie session observation (`auth/nitro/sql-authority/snapshots.ts:147–205,354–380`). Session mutation reads/uses the stored domain and canonical allocator (`db/runtime-auth-session/statements.ts:166–207,408–448`; `runtime-auth-credential/statements.ts:164–169`). Those predicates do not tie the stored namespace to an original memory handle, runtime-meta epoch, or adoption-owner WeakMap. Consequently a genuinely copied ready domain qualifies at this source boundary after normal K/reopen checks and fresh issuer construction. No production/restart proof follows without an authorized run.

**Epoch correction:** `initializeRuntimeStateEpochAsync`, `runtime-state.ts:271–303`, only mints on the uninitialized sentinel. A direct snapshot after the memory epoch retains that UUID; normal MAIN reopen returns it. MAIN has a new local connection/owner lifetime, **not automatically a new stored epoch**. Do not advertise new-epoch proof or update meta manually.

If a distinct stored epoch is required, the existing **copy-engine** path can supply it, but its whole contract must be used:

- `createSqliteCopyEngine` is public (`db/package.json:18`). Its byte input checks SQLite header and 100-byte–512-MiB size, writes an owned exclusive/no-follow 0600 temporary copy, and requires compatibility → schema migration → content migration → reset → seal (`copied-sqlite.ts:146–175,258–350`). It consumes bytes; it does not export the live memory runtime itself.
- `resetRuntimeAsync:305–344` resets exactly `homarr_runtime_history_entry`, `homarr_runtime_history_stream`, `homarr_runtime_state`, and `homarr_runtime_meta`; it reinstalls id1 with a new UUID and id2 NULL. It does **not** reset `homarr_auth_credential_domain`, its phase/head/namespace, the migration ledger, or business credentials. `runtime-catalog.ts:35–40` confirms the four-table set. Runtime-referrer/temporary-object/catalog checks remain mandatory.
- `sealAsync:202–227` refuses a missing owned reset, verifies empty runtime state/history and reset meta, performs native VACUUM, closes, and returns bounded bytes. Those bytes can later be written unchanged to the one final synthetic file using the separately authorized exclusive/no-follow 0600 write/sync/close transaction. Dispose the engine's temporary copy through its own API; do not skip reset just to retain the source epoch.
- MAIN then reads that reset UUID; it still does not mint another one. The domain remains source-ready. This is more I/O and conversion than direct snapshot, not the minimal route unless the distinct epoch is required.

The concrete distinct-epoch composition is native runtime snapshot to a separately owned staging path → bounded unchanged-byte read of that new output → `createCopyAsync` → `assertCompatibleAsync` → `migrateSchemaAsync` → `migrateContentAsync` → `resetRuntimeAsync` → `sealAsync` → exclusive final-file materialization and physical disposal of owned staging/copy resources. Compatibility takes source dialect/version/export time, not adoption evidence; any supplied version/time must come from the actual selected source/export, never an old accepted envelope or fabricated native-ready receipt. These additional staging/read/write/cleanup obligations require their own explicit allocation. No existing API performs this entire composition automatically.

Neither route is backup apply. `api/src/backup-runtime/index.ts:156–166` also deletes sessions, verification tokens and onboarding claim before mandatory reset/seal. `backup-runtime/nitro-join/contracts.ts:48` and `service.ts:26` explicitly retain `applyReady:false`. Do not use backup preparation as a ready application installer, clear its hold, or invent an apply operation. Copy-engine reset obligations attach to that conversion/seal route; direct runtime snapshot is a separate existing export contract, not a hidden reset bypass.

## Remaining auth/application blocker and readiness correction

A ready empty domain does not supply a login account, password, API key or session. Canonical credentials account construction and setup completion remain a separate join: `api/src/nitro/routers/onboard.ts:24–35` holds both transitions; `onboard-transitions.ts:18–47` has an empty implemented-path array and builders without handlers. Their genuine claim/no-users/current-step/atomic plan producer must be approved before synthetic account creation. Do not hand-insert principals/passwords/groups, use demo identities, or bypass setup to manufacture a successful login.

Also correct the prior completion plan's suggested readiness probe: **`getProductionSessionRequestReader(issuer).admitOpaqueSessionAsync(null, bounds)` is not a domain check.** `sql-persistence.ts:1064–1089,1127–1138` delegates to `sql-authority/authority.ts:1219–1222`, which returns anonymous immediately when no token exists. The actual no-cookie issuer observation is `observeSessionForIssuerAsync(null)` internally (`authority.ts:842–861,678–710`), reached by the genuine session HTTP flow (`production-sessions/service.ts:410–415`), and it uses the ready-domain decoder. It is not a new public readiness method. Use authorized real session HTTP execution/conservation observations, not a fabricated startup Request, a guessed public issuer getter, or null-reader admission as proof. MAIN's returned object has no public `productionSessionIssuer` getter (`native-main-persistence.ts:1243–1270`).

**Decision:** reuse public `snapshotSqliteAsync` for the minimal source-ready file candidate; use the complete existing copy engine only if a distinct stored epoch is part of the accepted contract. No native first-file-adoption implementation is needed for this synthetic route. New consumer/source/compiler/finite initialization and filesystem settlement allocation, then genuine setup/account production and separate MAIN execution evidence, remain required. Real installation adoption, backup apply, production installer reuse and full-app acceptance remain out of scope.
