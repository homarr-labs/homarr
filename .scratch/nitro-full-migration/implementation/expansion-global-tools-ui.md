## Provider order and session contract

The only order remains `contracts/providers.ts`: settings → session → locale → theme → direction → query → jotai → modals → notifications → spotlight → assistant. The bridge supplies contributions to that composer; it does not rebuild the chain. Theme/direction adapters are exported but intentionally not installed through an unsupported contribution slot.

`app/session-transition.ts` remains the sole transition authority. Chrome consumes `useSessionTransition(queryClient)` without creating a store or listener registry. Peer mutation owners must continue using capture/current/invalidate/run transition APIs; disabled chrome is not an authorization boundary. A failed transition remains blocked according to the existing API, never treated as success by this feature.

1. Root owner must resolve the dependency graph before mounting source providers, rather than cross-importing Next.js implementation files. Passing a component does not prove its transitive graph is SSR-safe.
2. Allocate real notification/Jotai/modal/spotlight resources within the request/application owner, bind real methods before creating frozen adapters, and reuse the resulting component identities. Never invoke the factory on each render, share resources between SSR requests, or bind the notifications default global store.
3. Server and first client render must use matching snapshot, source values, provider graph, slot tree and React ID prefix. Provider identities must remain stable within each application lifetime; server and client resources are separately allocated. Source resource hydration and teardown belong to the request/client owner, not this presentation directory. No session/user data is serialized here.
4. Root must keep exactly one theme provider, direction provider, modal renderer and notification surface. The modal frame bridge is an alternative source-renderer integration, not an extra renderer atop `@homarr/modals`. The source does not currently export its frame state; that mount edge remains held.
5. Source modal close callbacks run in the source owner, including close-all top-to-bottom ordering. Closing frames must remain supplied until `exitModal`; hidden retained frames may not capture focus or close the current frame. Initial SSR overlays remain closed until client activation. Source lifecycle wiring has not been claimed as mounted parity.
6. No CSS/global-script entrypoint changes or browser listeners were introduced here. Supply a request-appropriate theme and root selector; forced scheme intentionally does not claim user preference persistence or auto-scheme support.

## P2 fix lineage: retained modal close-all exit completion

This record was relocated from `implementation/expansion-global-tools-ui.md` to `scratch/implementation/expansion-global-tools-ui.md` with a patch move; all preceding source/dependency/validation evidence is retained as historical EXPANSION35 evidence. The only code change for this follow-up is `apps/nitro/src/features/global-tools/source-modal.tsx` and its private typed lifecycle hook. No other provider, chrome, slot, style, source host, API, schema, manifest, route or entrypoint was changed.

Failure sequence supplied for independent review: open keep-mounted A, open B, let A's hide transition finish, then close all. A's `opened` remains false during the phase change to closing. Previously the adapter discarded A's earlier native exit completion because A was still logically open, then waited forever for another transition that could not start.

The hook records committed visibility as visible/exiting/exited, distinct from source open/closing phase. A committed true-to-false visibility edge marks an exit pending, including its native delay. Only Mantine's native completion advances an actual pending exit to exited. That completion is retained even when the source phase is still open. When an already-exited hidden frame later becomes closing, a committed effect calls the real `exitModal(id)` once, without restarting an animation or scheduling a fabricated completion. Never-opened closing frames also have no pending transition to wait for.

Native callbacks use the latest committed source phase, ID and removal callback, not the phase captured when the hide animation started. Returning visibility cancels pending completion bookkeeping; subsequent hide starts a fresh pending exit. Finalization is latched before calling the source removal function. Repeated callbacks/effect replay cannot finalize the same closing episode twice. Effect cleanup disarms callbacks after unmount without issuing a second source removal or resetting the finalization latch. There is no per-app global state, timer, listener, registry, local frame removal or synthetic transition callback.

Design is preserved: the existing mount activation, opened expression, native duration/delay/easing, overlay, inspector presentation, focus trap/return-focus, scroll lock, Escape/outside-close interception and keep-mounted rendering remain unchanged. `SourceModalFrame` and `SourceModalHostProps` contracts are unchanged. Mantine still dispatches supplied `transitionProps` lifecycle callbacks itself; this fix does not wrap, replay or replace them.

Dependency verification: Nitro already declares React 19.2.7 and Mantine core/hooks 9.6.0. Context7 remains explicitly quota-blocked from the recorded lookup; this follow-up used current official [Mantine Transition](https://mantine.dev/llms/core-transition.md), [React useRef](https://react.dev/reference/react/useRef) and [React useEffect](https://react.dev/reference/react/useEffect) documentation plus installed 9.6 `Transition/use-transition`, `ModalBaseContent`, `ModalBase`, `Modal` and `use-isomorphic-effect` source/declarations. Installed code confirms transitions react to changes in mounted/opened, native completion can capture an earlier callback, reopening cancels native work, and zero-duration completion still invokes native callbacks. No library was added.

### Independent rereview handoff

Review the single bug-fix lineage against these sequences, without treating static reasoning as runtime verification:

- A hidden and already exited before close-all: remove A exactly once through the source callback; B retains its visible exit animation.
- Close-all while A's hide is delayed/in flight: retain A until actual native completion, then remove using the current closing phase.
- A returns visible before its prior exit completes: ignore obsolete completion while visible, retain content, and wait for the next actual hide completion.
- Native double completion, unstable callback identity and Strict Mode setup/cleanup replay: at most one source removal per closing episode.
- Source removes a frame or the host unmounts before completion: cleanup disarms removal; no callback resurrects or removes a replacement frame.
- Initially hidden/never-opened closing frame and zero-duration/reduced-motion exits: no invented timer or wait for a nonexistent transition.

All original source-provider export, actual source-host removal, mount/resource graph, request/client isolation, SSR hydration and privacy holds remain unchanged.
