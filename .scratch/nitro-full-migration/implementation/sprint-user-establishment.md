## Source conservation

- Demo read-only mutation enforcement precedes source authorization and handler effects. `initUser` retains admin bypass of claim/no-user access, but not of the required `user` step. `register` stays public rather than authenticated/claim-only. `create` requires authentication and admin before checking credentials enablement. Every credentials-disabled error remains `FORBIDDEN` / `Credentials provider is disabled` through the existing frozen helper.
- The first-user/no-user predicate belongs to the source onboarding middleware: `users.findFirst({ columns: { id: true } })`, followed by stored claim validity only when no user exists. No count heuristic, counterfeit admin, role inference, or new prerequisite is added in the handler. Existing accepted setup-read resources contain the actual predicate, stored claim read/hash/expiry verifier and normalized step read; they still need a real context/admission producer.
- Username conflicts use the original full `users.findFirst` with both name and provider equality, optional ignored-user handling, and `CONFLICT` / `Username already taken`. These three leaves pass `credentials` and no ignored ID. Name normalization remains in the original schemas, not a new helper.
- `userInitSchema` retains its confirmation refinement and optional-email behavior. Registration retains the original intersection, including its confirmation refinement and required invite ID/token strings. Create deliberately reuses the existing shape-only intersection conversion. That conversion does not copy the left object's object-level password-confirmation refinement; this source behavior is not corrected. `groupIds` remains required with no default even though the metadata does not enumerate it. Email null is not silently accepted where the source only accepts optional/empty/string email. All metadata text is unchanged.
- Initialization ordering is credentials gate → username lookup → maximum group position → password hash → user ID → group ID → row preparation → LDAP-or-OIDC next-step selection → transaction. Maximum position retains `result[0]?.value ?? 1`, so an empty group table yields position `2` for the new group. LDAP is tested before OIDC with original short-circuiting.
- Initialization transaction order remains user insert → credentials-admin group insert with owner and position → `admin` permission insert → group membership insert → unconditional onboarding update `{ previousStep: user, step: group | setup }`. It does not add a current-step SQL predicate, no-user recheck, group conflict handling, claim removal, or seeded everyone group. Source atomicity does not itself establish claim/empty-set evidence validity through COMMIT; that authority binding remains held.
- Registration selects only invite ID/expiration using both ID and token equality. Expiry remains strict `expirationDate < now`, so equality is not changed to expired. Missing invites short-circuit the clock read. There is no transaction-time expiry recheck. Username checking precedes hashing and ID generation. The registration row omits email and provider, preserving database defaults.
- Registration inserts the user before deleting the exact captured invite predicate inside the same native transaction. PostgreSQL checks `rowCount ?? 0`; SQLite checks `changes`. Zero deletion throws `FORBIDDEN` / `Invalid invite` inside the transaction so the preceding user insert must roll back. There is no retry, alternate invite lookup, fake consumed state, or successful partial registration.
- Create awaits its user insert before optionally inserting the exact supplied membership list, with no deduplication, group lookup, local-membership policy, role filtering or added transaction. A later membership failure can leave the inserted user, exactly as source. No automatic admin/everyone membership is added.
- All three source leaves return undefined and perform no login, session insert, sign-in event, session/token/claim cookie issuance, color-scheme cookie write, or session refresh. The everyone's-group membership and color-scheme cookie effects are in the separate source sign-in event, not these bodies. They are not relocated or silently simulated here. No JWT engine choice is made.

## Precise real-producer holds

1. **Authenticated context:** host must supply the actual accepted principal/session authority for the admin leaf and the init admin bypass. Pure password verification and accepted policy helpers are not a credentials session issuer. Q16 remains unanswered; no session-service producer is approved, bound, or replaced by a successful callback in this lane.
2. **Setup/no-user authority:** `context.setup` must come from the real admitted stored claim/no-user/step reader with the source cookie token and actual clock. The existing public setup-read factory can be reused without edits. Its pre-handler read is not proof that claim, step, or empty-set authority remains current at first-user COMMIT. A reviewed producer that preserves the existing source access distinction while owning that lifetime is still required; this lane adds no new authority policy or fake empty-set success.
3. **Native writer/schema:** `nativeDatabase(db)` must resolve to that exact admitted database authority, not another database, synthetic transaction object, or caller-controlled handle. Its discriminant and schema must match the actual native driver. The supplied read schema, native transaction schema, and captured invite predicate must reference the same physical tables. The contract is unmounted and not an approved physical binding.
4. **Atomic COMMIT/rollback:** the native writer must own initialization's five writes and registration's two writes through real commit, return only after completion, propagate rollback/commit failure, and retain request/resource admission until settlement. Registration's zero-row deletion must roll back its insert. There is no generic host executor or workaround for unsafe async SQLite callbacks. Create must retain its intentionally separate writes rather than being strengthened into an all-or-nothing transaction.
5. **Domain producers:** ID generation must be the original CUID producer; provider configuration must reflect the real enabled credentials/LDAP/OIDC state, not supplied permission assertions; clock must be real source-equivalent wall time. Database defaults, group foreign keys/uniqueness and native affected-row results remain physical schema authority. No success fixtures, duplicate-handling policy, seeding, migration or readiness policy are supplied.
6. **Login/session continuation:** if a later caller requests automatic login or everyone/cookie effects, it must use the actual separate approved sign-in/session producer and its original event ordering. This draft exposes no such producer, and the canonical source leaves do not require one to manufacture their void response. Account establishment is not evidence of a working credentials-login/session stack.
