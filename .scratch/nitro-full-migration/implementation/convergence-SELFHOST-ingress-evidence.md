# SELFHOST ingress: pinned API/source evidence

## Decision and scope

**Source-supported narrow ingress seam; runtime acceptance remains unproved.** Apply admission in `apps/backend/server/entry.ts` immediately before `nitro.fetch`, not in `src/server/host.ts`, an SSR fallback, or ordinary Nitro middleware. Validate the available original Host against the captured canonical public authority **before** changing the request URL. Keep one srvx/Bun listener and the existing Nitro dispatch. Direct public HTTP needs no URL replacement when its native URL already matches the capture. Captured public HTTPS over a preserved-Host HTTP proxy needs an origin-adjusted URL view: current SSR and authentication consume `request.url.origin`.

This is a read-only source investigation except for this new report. No application/configuration execution, shell commands, imports, dependency changes, server runs, SQL, secrets, environment reads, tests, or nested agents were performed. The concurrently revised SELFHOST plan was not read. Context7 was not retried because the coordinator supplied its exhausted-quota constraint; official public documentation and version-tagged upstream source were fetched instead. No production PASS is asserted.

## Bounded call chain: owner, conversion, static dispatch, SSR

1. `apps/backend/nitro.config.ts:5-10` selects the Bun preset but explicitly replaces the **build entry** with `./server/entry.ts` and sets `serverDir` to `./server`. This is distinct from Nitro's `serverEntry` catch-all handler option. `apps/nitro/vite.config.ts:98-115` loads this backend config; `:121-126` supplies the SSR build input.
2. Pinned Nitro resolves `options.entry` (`node_modules/nitro/dist/_chunks/nitro.mjs:217-234`). Its Vite bundler uses that input and writes `index.mjs` (`node_modules/nitro/dist/vite.mjs:13-27`); its standalone Rolldown builder does likewise (`node_modules/nitro/dist/_build/rolldown.mjs:9-15,45-54`). The default Bun preset has its own `serve` call (`node_modules/nitro/dist/presets/bun/runtime/bun.mjs:16-37`), but that preset entry must not be imported in addition to the explicit root entry.
3. The actual root entry loads capture, obtains Nitro, creates one `serve({ protocol: "http", trustProxy: false, manual: true, ... })`, and forwards every accepted request to `nitro.fetch` (`apps/backend/server/entry.ts:7-25`). It starts that listener at `:37`; shutdown remains at `:43-53`.
4. `srvx/bun` exports its Bun adapter (`node_modules/srvx/package.json:21-24`). The adapter enriches the **original native Request**, then calls the configured fetch chain (`node_modules/srvx/dist/adapters/bun.mjs:34-53`). It forwards Bun options, but overwrites `fetch` with its own adapter callback (`:55-68`); `serve()` calls `Bun.serve` once (`:71-74`). `wrapFetch` does not buffer or clone the request (`node_modules/srvx/dist/_chunks/_plugins.mjs:2-10`); response conversion also does not read the response body (`node_modules/srvx/dist/_chunks/_utils2.mjs:56-59`).
5. `useNitroApp` creates the generated app and initializes plugins (`node_modules/nitro/dist/runtime/internal/app.mjs:8-17`). Generated app code initializes `req.context.nitro`, then calls `h3App.fetch(req)` **with the same input**, not `new Request` or `toRequest` (`node_modules/nitro/dist/_build/common.mjs:5805-5810`). H3Core creates an H3Event from that request (`node_modules/nitro/node_modules/h3/dist/cache.mjs:370-396`). The event retains `req`, shares its context, and reads `req._url` if present, otherwise `req.url` (`node_modules/nitro/node_modules/h3/dist/response.mjs:95-106`). Its runtime and waitUntil access delegate to that request (`:111-115`).
6. Routing generation puts static handling first among global middleware when `serveStatic` is enabled (`node_modules/nitro/dist/_chunks/nitro3.mjs:57-64`); generated app middleware ordering is route rules, global middleware, then routed middleware (`node_modules/nitro/dist/_build/common.mjs:5820-5832`). Static handling can terminate GET/HEAD before application/SSR (`node_modules/nitro/dist/runtime/internal/static.mjs:4-34,38-66`). Therefore an SSR/host-only Host check would leave static assets outside admission. A root-entry check before Nitro covers the complete dispatch path.
7. Nitro's Vite integration discovers the SSR service and installs its SSR renderer (`node_modules/nitro/dist/vite.mjs:310-326`); `node_modules/nitro/dist/runtime/internal/vite/ssr-renderer.mjs:1-6` forwards `req` through `fetchViteEnv`. `node_modules/nitro/dist/runtime/vite.mjs:1-8` calls H3 `toRequest(input, init)`. Installed `toRequest` returns an existing Request unchanged when there is no init (`node_modules/nitro/node_modules/h3/dist/cache.mjs:204-210`). Relative-string conversion instead synthesizes **HTTP** using a supplied Host or `localhost`; it is not a public-HTTPS transport metadata solution.
8. `apps/nitro/src/entry-server.tsx:10-16` passes the Request to `fetchApplication`; `apps/backend/src/server/host.ts:12-47` lazily composes/readies the application and forwards it. Application cancellation combines `request.signal` with lifetime cancellation (`apps/backend/src/server/application.ts:36-38`). Do not create a separate application/native persistence owner to canonicalize ingress.

No `apps/backend/.output/server` directory was available. This proves the installed generator/source chain, **not** inspection or successful execution of the concrete isolated generated artifact. Artifact import/owner/static proofs remain required.

## Host representation: what Bun 1.4.2 actually makes available

Pinned public upstream source supplies the missing evidence; Fetch Headers alone is not assumed to expose raw multiplicity:

- [Bun 1.4.2 HttpParser.h](https://github.com/oven-sh/bun/blob/bun-v1.4.2/packages/bun-uws/src/HttpParser.h): `HttpRequest::getHeader` returns the first matching field (`:273-287`); iteration starts at `headers + 1` and visits stored fields (`:230-265`). Header parsing stores each field and advances the slot (`:1040-1069`), with no duplicate-Host collapse in that loop. SP/HTAB at field-value edges are stripped (`:1048-1056`). Missing Host enforcement is conditional on HTTP version/options, with upgrade/CONNECT exemptions (`:1266-1276`); an empty Host is explicitly different from an absent field.
- [Bun 1.4.2 Request.rs](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/webcore/Request.rs): native Request header materialization calls `HeadersRef::create_from_uws` (`:239-256`). URL construction independently consults `req.header("host")` and canonicalizes the assembled URL (`:861-948`); `request_target_path` extracts a path from absolute-form request targets (`:804-828`). This is **not** a raw authority proof. Invalid/missing Host can leave a bare path; URL canonicalization can erase case/default-port distinctions. Absolute-form target authority is not retained as a separate public field for the application.
- [Bun 1.4.2 bindings.cpp](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/jsc/bindings/bindings.cpp#L2544-L2568): `WebCore__FetchHeaders__createFromUWS` iterates all retained native fields and calls `map.add` for known names (`:2552-2565`).
- [Bun 1.4.2 HTTPHeaderMap.cpp](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/jsc/bindings/webcore/HTTPHeaderMap.cpp): `HTTPHeaderMap::add(HTTPHeaderName, const String&)` combines repeated names with `", "`, except Cookie/Set-Cookie. There is no Host-specific first/last-wins branch. Thus retained repeated Host lines become a comma-bearing available `headers.get("host")` value. Rejecting commas also rejects a single comma-bearing Host; distinguishing those two wire forms is unnecessary for fail-closed admission.
- Bun's public [Headers.getAll reference](https://bun.com/reference/globals/Headers/getAll) supports only Set-Cookie; `getAll("host")` is not a raw-header workaround. Installed typings say the same (`node_modules/bun-types/fetch.d.ts:51-68`). Counting `Headers.entries()`, `Headers.count`, or `toJSON()` cannot recover wire multiplicity.

**Result:** there is version-tagged source support for a comma-rejecting guard on native Bun HTTP/1 ingress, including identical duplicates and empty duplicate values. This is not a live-wire assertion. Raw-socket verification on the actual Bun 1.4.2 binary/generated artifact remains an Oracle gate. If duplicates disappear before this point in the actual runtime/proxy, a Fetch-level check cannot recover them; require upstream rejection or another explicitly reviewed ingress API rather than claiming complete admission.

### Native context/options do not expose a better raw Host API here

`request.runtime.bun` contains only `{ server }`; `request.ip` is a getter that closes over the original native Request and calls `server.requestIP(original)` (`node_modules/srvx/dist/adapters/bun.mjs:35-50`; `node_modules/srvx/dist/_chunks/types.d.mts:528-532,563-589`). No raw header list, request target, socket object, or separate raw Host is attached. `server.requestIP` reports address/family/port, not HTTP headers (`node_modules/srvx/dist/_chunks/types.d.mts:50-62`; [Bun Server reference](https://bun.com/reference/bun/Server)).

The public [Bun 1.4.2 serve options](https://github.com/oven-sh/bun/blob/bun-v1.4.2/packages/bun-types/serve.d.ts#L742-L900) do not declare a raw-header callback, duplicate-Host policy switch, or public-origin URL override. srvx permits Bun-specific options (`node_modules/srvx/dist/_chunks/types.d.mts:35-45,423-427`), but its index signature is not proof that an invented option exists. Node's `rawHeaders`/`joinDuplicateHeaders` and Bun's internal `onNodeHTTPRequest` are not the public srvx/Bun fetch API. Switching adapters or adding a second Node listener is not needed or authorized by this evidence.

## Minimum fixed-authority admission contract

This is a proposed contract from the source evidence, not product implementation:

1. Capture one canonical credential-free HTTP(S) public **origin** at startup, with `basePath === ""`. Keep listener bind address/port separate. Public HTTP may use a LAN authority; captured public HTTPS assumes a deployment-controlled TLS proxy preserving that authority in Host. Do not infer public authority from a wildcard/loopback bind address.
2. On the original Request, read Host **before** any URL/header rewrite. Reject absent/empty Host, commas, visible control bytes including DEL, whitespace inside the available value, and anything not exactly the captured URL's canonical `.host`. Exact comparison naturally rejects userinfo, slash/backslash/query/fragment tricks, trailing dots, alternate numeric host forms, Unicode/percent spellings, port mismatch, leading-zero ports, and noncanonical case. Header-name casing remains case-insensitive. Do not lowercase/trim a hostile available value into acceptance. Wire-edge OWS was already removed by Bun and cannot be retrospectively inspected.
3. Use a canonical capture where `new URL(capture).origin === capture`. Canonical authority excludes explicit default ports; therefore `Host: example.test:443` is rejected for `https://example.test`, and `Host: example.test:8443` is required for `https://example.test:8443`. This deliberately narrow policy matches existing auth's exact Host checks. If case-insensitive/default-port aliases are desired, they need a separately explicit policy, not silent URL normalization.
4. Only after Host succeeds, parse the native URL defensively. Reject unparsable/credential-bearing/fragment-bearing URLs and an unexpected parsed authority. Compare its authority under the **native transport scheme** to a URL built from the already validated Host; HTTP and HTTPS have different default-port normalization. A parsed `request.url.host` alone is insufficient because it already lost distinctions and says nothing about missing/duplicated Host. If admission must additionally reject conflicting absolute-form target authority, this Bun fetch API does not expose that original authority: allocate that requirement to a proven upstream parser, not an imaginary field.
5. Keep `trustProxy: false`. Strip `Forwarded` and every case-insensitive `x-forwarded-*` field before Nitro or application code sees them. Do not remove or replace `Origin`, `Sec-Fetch-Site`, Cookie, Authorization, content headers, or request cancellation. In the pinned adapter `trustProxy: false` only prevents the proxy middleware from running; it **does not delete** forwarding fields (`node_modules/srvx/dist/_chunks/_trust-proxy.mjs:53-60`).
6. For direct matching public HTTP, forward the same native Request after header sanitization; no URL reconstruction is necessary. For captured public HTTPS over HTTP, preserve pathname/query but set scheme/authority exclusively from capture. Never use Forwarded/X-Forwarded values, listener URL, or request-target authority as the public origin. Set authority/port explicitly when changing scheme; do not retain a stale HTTP/default/listener port. Do not resolve a pathname beginning `//` as a relative URL against capture; replace origin components on the parsed URL or concatenate a fixed captured origin with its pathname/search without allowing authority resolution.
7. Forward to the existing `nitro.fetch`; return its Response/Promise without text/JSON/arrayBuffer reads. Preserve request context, cancellation, body stream ownership and transport-derived address. No early application composition, separate static dispatcher, new native server, or synthetic `runtime: { name: "bun" }`.

The existing startup schema still requires loopback HTTP and equates public origin to listener (`apps/backend/src/server/startup-configuration.ts:15,279-300,384-391`). `captureHostConfiguration` already accepts HTTP(S) origins and empty base paths but does not itself demand textual canonical equality (`apps/backend/src/server/runtime-composition/configuration.ts:5-26`). These are source constraints the coordinator's revision must address; this report does not modify them. The guest locale handler still has a loopback-only guard (`apps/backend/src/server/runtime-composition/public-culture.ts:138-146`). Keeping Origin/Sec-Fetch-Site is necessary but does not remove that separate restriction.

## URL-view choices; no assumed clone API or ghost transport metadata

### Existing helper: `requestWithURL` from `nitro/h3`

Installed H3 exports **`requestWithURL(req: ServerRequest, url: string): ServerRequest`**, described as a lightweight URL proxy without `new Request` allocation (`node_modules/nitro/node_modules/h3/dist/index.d.mts:193-198`; [official H3 request utilities](https://h3.dev/utils/request#requestwithurlreq-url)). The implementation is `node_modules/nitro/node_modules/h3/dist/cache.mjs:181-197`:

- Overrides `url`, masks `_url` so H3 cannot reuse a stale parsed transport URL, and delegates other properties to the original Request.
- Binds body-reading methods to the original Request; leaves `bodyUsed` live rather than caching it; does not read, tee, buffer or construct a body.
- Reads original signal/body/runtime/context/waitUntil/ip through the target. The srvx ip getter still closes over the true original native Request. Context writes forward to the target.
- Public import is available through the already declared Nitro dependency. No bare-H3/deep import or newly invented helper is necessary.

**Prefer this existing helper if the narrow downstream contract only needs Fetch behavior, `ip`, context and waitUntil.** It is not the original object's identity. Native operations such as `server.requestIP(proxy)`, `server.timeout(proxy)` or `server.upgrade(proxy)` are not established as accepting a JS Proxy; retain/pass the actual original Request for those operations and allocate explicit runtime checks if they are needed. Cached proxy property reads also are not a guarantee that future external replacement of target properties remains observable. Do not promise transparent native transport identity.

### Original-object URL override when native identity must remain intact

The pinned srvx trust-proxy implementation already adjusts Bun's original Request with `Object.defineProperty(request, "url", { value: url.href, enumerable: true, configurable: true })` (`node_modules/srvx/dist/_chunks/_trust-proxy.mjs:68-79`). A fixed captured-origin override **after** Host validation can follow that existing descriptor pattern without enabling proxy trust, allocating another Request, or copying transport metadata. This keeps native identity and the original streaming/cancellation/context properties. Do it before Nitro/H3 parses a URL, and prevent stale `_url` if present; native Bun adapter does not populate `_url`, but H3 explicitly honors it.

This is the smaller alternative if native identity is a hard requirement. It uses a source-supported srvx pattern, not a new transport wrapper. The native internal URL and overridden JS view can differ, so later `new Request(original)`/Auth.js conversions must be included in runtime validation; descriptor support and effective URL use on the actual generated entry are not proven by this report.

### Reconstruction/clone fallback: not required for the source-supported paths

There is **no `cloneRequest` export** in the installed Nitro/H3 2.0.2/srvx sources searched. Do not put that name in an implementation plan as a pinned available API. Native `Request.clone()` tees the body; `new Request(url, original)`/spreading a Request is not evidence that arbitrary srvx properties survive. If a physical replacement becomes necessary, explicitly use the original unconsumed stream as `body` only for body-permitting methods, the original method/headers/signal, and `duplex: "half"` for a streamed body; do not call `.clone()` or read bytes merely to rewrite an origin. An explicit `new Request` does not automatically preserve srvx `context`, `waitUntil`, `ip` or original transport identity. Carry a proven original-request reference for native operations instead of making the replacement pretend to own a Bun transport. This higher-complexity fallback remains unapproved/unexecuted here.

## Why a Host-only/relative SSR solution is not enough

- SSR is not fully origin-relative today: `apps/nitro/src/ssr/render.tsx:23,64-68` derives bootstrap `routing.origin` and `document.websiteUrl` from `context.request.url`. An unchanged HTTP-backend URL behind public HTTPS publishes the wrong origin even when Host is correct.
- Auth admission requires URL origin to match configured external origin (`apps/backend/src/server/runtime-composition/auth.ts:529-537`); issuer checks URL origin and exact Host (`packages/auth/nitro/production-sessions/origin.ts:66-77`). Both currently allow missing Host in these inner checks, so neither replaces stricter ingress admission.
- Existing issuer `coreRequest` strips only four forwarding fields and creates a new Request after its own checks (`packages/auth/nitro/production-sessions/origin.ts:139-145`). It is auth-local, too late for static/SSR, and does not strip the entire `x-forwarded-*` namespace. Do not reuse it as global ingress.
- H3's relative `toRequest` defaults to HTTP and possibly localhost (`node_modules/nitro/node_modules/h3/dist/cache.mjs:204-210,294-295`); it cannot infer the captured external HTTPS origin or enforce original Host presence.
- Existing common utilities were checked: `packages/common/package.json:14-29`; `packages/common/src/server.ts:1-5`; `packages/common/src/url.ts`; `packages/common/src/request.ts`. `extractBaseUrlFromHeaders` trusts X-Forwarded-Proto/Host and even picks HTTPS from a comma-list (`url.ts:11-26`); `ipAddressFromHeaders` trusts X-Forwarded-For (`request.ts:13-15`). Neither is admissible. Safe navigation URL helpers (`url.ts:59-100`) validate link destinations, not listener authority/multiplicity/transport. No common raw-ingress or clone helper was found.

- [H3 request utilities](https://h3.dev/utils/request): existing URL proxy and `toRequest`; installed H3 2.0.2 implementation/types and `bun.lock` bind the API finding.

**Coordinator-ready conclusion:** original Host validation plus forwarding-header removal at the custom root ingress is source-feasible without a new listener/dependency/body buffer. Native direct HTTP can stay unchanged; HTTPS needs a captured-origin URL view. Existing H3 URL proxy is available when native identity is not demanded; the pinned srvx same-object URL descriptor pattern is the narrower identity-preserving alternative. There is no supported `cloneRequest` assumption or raw Bun header API to lean on. Runtime wire/proxy/artifact/stream proofs remain open; do not promote this evidence to production acceptance.
