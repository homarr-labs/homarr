Source-only candidate, frozen on return for independent review. Owns only new `packages/api/src/backup-runtime/nitro-join/` and this handoff. No host mounting, restore acceptance, target-50 proof, authenticated read/write/restart or #111/#112/#125 completion.

## Actual join

`createNitroBackupService(config)` constructs the existing `createSqliteBackupDependencies` directly with explicit temporary-directory/migration-folder/key/authorization configuration. It takes no live database, environment, SQL executor, reset callback, caller-selected epoch or controller-result callback. `@homarr/db` is already an API runtime dependency and its copy-engine factory is already publicly exported. Frozen backup contracts/parser/crypto/inventory/inspection/controller, original restore/export flow, five-transform entrypoint and STAGE-P-RESTORE-HANDSHAKE were read; mutable P2/copied-engine source was not read or modified.

- `inspectAsync(bytes, options)` delegates to actual frozen `inspectLegacyBackupAsync`: authorization, parser, isolated copy, compatibility, schema migration, references, original five content transforms, inspection and copy cleanup. It returns inspection only.
- `inspectUploadAsync(request, options)` and `prepareUploadSourceAsync(request, options)` additionally authorize their exact operation before the existing bounded multipart reader, then perform the corresponding frozen inspection/preparation. Both request and explicitly supplied cancellation signals are preserved. Frozen operations authorize again after ingress; ingress authority never becomes apply authority.
- `prepareSourceAsync(bytes, options)` delegates unchanged to `prepareLegacyBackupAsync`. Exact order remains compatibility/catalog checks before schema writes → SQL migration → references/source ciphertext validation and rekey → five original content transforms → target ciphertext/reference validation → selected-board validation → copy-only migration logout (session/verification token/obsolete claim) → seal and original reopened verification → disposal. Board selection never filters durable content. No reset is appended after sealing.
- Returned `SourcePreparation` exposes only `toJSON()` review metadata with `applyReady: false`; exact service-local object identity owns its private sealed source snapshot. There is no bytes accessor, transferable ID, RPC capability or export of the prepared database. Retention admission counts concurrent reservations. `discard` and successful service close zero the retained byte array; late preparation after cancellation/close is rejected and zeroed.
- `inspectExportSnapshotAsync({ dialect, bytes, metadata }, signal)` accepts explicit server-only snapshot bytes, creates an actual isolated copy, checks compatibility, existing integrity/domain references and all six target-key ciphertext columns through original crypto, and returns existing inventory inspection. It does not migrate, transform, logout, clear rows, seal or distribute the export copy. Older snapshots missing current domain tables may reject; this is current-schema export inspection, not an upgrade pipeline. Input bytes are never modified. `downloadReady: false` is unconditional.
- `exportAsync(signal)` authorizes `export`, then rejects `export-sanitization-unavailable` before any snapshot capture/download/live DB operation. There is no fake ZIP, fixture reconstruction, unsafe raw fallback or key-carriage decision.
- `applyAsync(preparation)` verifies live service-local retention and rejects `runtime-reset-unavailable` without reset, native replacement, authority consumption or restart.

## Lifetime and privacy

Explicit positive safe-integer active-operation and retained-preparation bounds are mandatory. New work rejects while closing/closed or at admission capacity. Request cancellation composes with constructor-owned lifetime and close cancellation. Actual awaited operations remain tracked until their frozen engine disposal settles; close aborts admission, awaits all settlements, then zeros retained snapshots even when draining fails. A copy cleanup failure permanently fences admission and causes close to reject rather than reporting completed cleanup. No timeout is treated as completed cleanup. This owns only this service's source preparations, not the DB runtime, incoming request bodies, alternate connections, providers or whole-app writers. The caller must await `closeAsync` when the parent lifetime aborts; merely aborting the parent rejects work but does not release retained preparations.

Configuration, keys, snapshot inputs and preparation objects stay server-only. No bytes, plaintext, ciphertext, arbitrary underlying error, SQL or keys are returned/logged by this join. Ordinary returned inspection retains source names/IDs/counts and is still sensitive and principal-authorized. Existing parser/engine intermediate buffers are not claimed securely erased by the adapter. Uploaded-body reads use the frozen reader and are not forcibly interrupted halfway through its pending read; shutdown honestly waits for that work.

## Exact held joins

The frozen `BackupEngine` still has only create-copy, compatibility, schema migration and content migration operations. Its `CopiedDatabase` permits original controller SQL but this join adds no SQL statements or runtime-table knowledge. An accepted DB-owned isolated reset must enforce copy ownership and phase internally and be invoked **after target validation/logout, before seal**, then verify exact catalog/ledger and reopened output. A generic callback, fresh UUID, post-seal rewrite or deletion of live rows cannot satisfy that gap. This wave intentionally defines no proposed reset signature or boolean claiming target readiness.

Export needs a separately accepted isolated-copy exclusion operation preserving exact schema/meta/ledger while dropping private runtime authority/history/status, plus snapshot capture/concurrency ownership, archive serialization and approved sensitive-download/key-distribution policy. Raw live snapshots and prepared restore bytes are not an export fallback. The explicit export inspection uses frozen copy validation and makes no candidate50 catalog claim; final source49/target50 journal/schema gates remain DB-owner and producer/consumer acceptance work.

Whole-runtime maintenance remains missing: principal-bound one-shot authority, denial of new writers, all-enabled connection/provider/job/append/fanout/cache/security drain, bounded acquisition/native COMMIT settlement, recovery snapshot identity, exclusive SQLite file/WAL/SHM replacement, interrupted recovery, resource epoch rebinding, supervision and genuine authenticated readiness/read/write/restart. Service-local admission/drain is not that contract. DB-only maintenance is not called or advertised as whole-runtime closure.
