## Teardown, restart and acknowledged outcomes

Single-instance/self-hosted ordering: fence incoming/manual admissions and schedules; abort/dispose HTTP/SSE request scopes and await their real cleanup; stop/drain jobs **while status SQL lifetime remains live for finish(error)**; stop Widget handlers/Stats and close the full Integration binding owner plus owned HTTP/ping/Analytics transports; dispose status consumers; drain generation/fanout/history/state users; only then close or maintain/rebind SQL and erase copied codec material. Preserve cleanup failures; abort and `close()` requests are not settlement acknowledgements. H must join prepublication failures and late acquisitions too.

On ordinary restart, adopt the existing epoch/data; use a genuinely new status owner ID, repair only another owner's interrupted running record to idle/error while retaining original run ID/start time, and keep terminal statuses and SQL histories. Create fresh disposable caches/listeners; do not clear history, reuse an old owner ID, reset revisions or replay previous triggers/provider writes. Concurrent deployments require separate scheduler ownership: the current repair logic is not an HA election lease.

Integration form receipts remain under the separate acknowledged-outcome allocation, not this lane. Its provider-lifetime receipt does **not** survive owner/process destruction. Main-host retention must keep actual acknowledged result IDs and stage ownership until reconciliation, with read-only recovery; unresolved dispatched outcomes cannot be turned into failure/retry permission. No existing generic durable receipt/replay primitive was established. Process-loss recovery requires a separately reviewed minimal SQL-owned operation identity/reconciliation contract if demanded; keep uncertainty visible until then. Never replay arbitrary completion callbacks, provider controls or ambiguous COMMIT writes to reconstruct a receipt.
