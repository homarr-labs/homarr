## Five source dispositions

1. **Custom re-admission without resurrection.** An invalid admission is permanently retired. Replacement requires a mounted field, authenticated observed session, current real static source and a different source/binding/session/mount association. An identical retired candidate cannot re-admit on ordinary renders. `isCurrentOwner` captures the published record and checks its exact installation/mount/binding/source/session; `onChange` uses that captured record's path. Local upload wrappers bind dispatch/currentness/reconciliation to the same record, delegating to the unchanged genuine resource hook. A stale old file-picker callback cannot follow the helper's latest observation into a replacement admission. Resolved upload IDs remain genuine results; no after-write stale error relabels them unknown, and no old unknown/held upload is automatically reset or resent.
2. **Repository own-update acknowledgement.** The wrapper reads the actual pre-row through the latest committed form's `getValues`, requiring the selected ID/index and serialized expectation. It invokes the original six setters and `form.validate()` synchronously. It then requires the same active source and ID/index, exact controlled field values, and unchanged other fields. Only the actual matching post-row updates `origin.fields`, before React's row observer; returned validation errors remain unchanged. Invalid provider URL therefore leaves the selected dialog usable for correction/Confirm and owned new-row Cancel removal. External reorder/removal/replacement or mount/binding/session loss retires the record instead of being acknowledged as an own update. No validator/schema was duplicated.
3. **Known B cannot close over reverted A.** The clean shortcut is idle-only, with no held intent and actual ready data/clean form. Known outcomes use real `AppForm.submit()` even when its dirty flag is false. Captured A after known B/read failure is recorded; read-only reconciliation of B cannot acknowledge A. The held intent blocks later clean baseline adoption from overwriting A. A later explicit A can write once against the real successful current B read; the original known B is not resent. Unknown remains read-only retry plus false.
4. **Settled B is not authority over adopted C.** A settled receipt carries its actual form-baseline association. Its read-only branch requires that association and the submitted values, and acknowledgement additionally requires the fresh actual read to match those values. Independent clean C adoption creates a new association/current-data witness without rebinding B's historical receipt. Restoring B in C's form therefore enters a genuinely new write validated against C, not obsolete `prior.read`, and never acknowledges B while the read still shows C. Values already matching actual current data use a genuine matching read rather than an unnecessary mutation or unconditional success.
5. **Pending upload cannot be skipped by Parent Save.** The actual icon resource is published in the committed host observation before baseline-adoption decisions. Its existing `upload.isPending` includes upload-cache settlement. Imperative save rejects pending/unpublished resources before registering an operation, before its shortcut/submission path, and after awaits before true. Actual AppForm pending remains intact. The parent handoff/owner registration-before-static-retirement, final checks and false→app-tab behavior were not changed.

Actual AppForm acknowledgement still uses its existing submitted-value dirty logic, preserving edits made during an await. Remaining dirty edits prevent true/adoption. Baseline association stays fixed throughout an operation. Own post-baseline advancement requires matching actual read data, completed AppForm acknowledgement, no held intent and a genuinely clean form; an unrelated later baseline cannot acquire the old receipt's scope. Original input/source/known `void` result and unknown/read-error behavior remain separate. Notifications and mismatch handling recheck operation ownership after awaits.
