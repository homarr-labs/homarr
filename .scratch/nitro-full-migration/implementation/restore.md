# Current Homarr backup preparation

## Outcome and authority

Unmounted source-preserving preparation is implemented in `packages/api/src/backup-runtime/`. It accepts the actual old `db.sqlite` + `metadata.json` ZIP and the older optional `encryption-key.txt`, not a new-format-only fixture. No production DB resource, HTTP route, app registration, manifest, migration, schema or current installation was changed. No live replacement, recovery, new-app authorized read/write or supervised restart was performed. **This is not whole-product/current-backup end-to-end compatibility acceptance, nor completion of #111/#112.**

Accepted inputs are the source archive structure, current physical schema and codecs, Q11 direct Drizzle/drivers, Q12 copied data and Q15 migration logout. The JOIN-WAVE dispatch additionally accepts persistence r3's exact copied-engine/runtime boundary following independent reviewer `ses_ed8ccf548ffeCYQTH2YqrMZPgq`, superseding older HOLD labels in the frozen handoffs. ## Actual functions

- `parseLegacyArchive(bytes)`: store/deflate ZIP central/local consistency, unique names, non-overlap, CRC, root entries, path safety, SQLite signature, metadata/dialect/key checks. Inflation has `maxOutputLength`, so forged small declared lengths cannot bypass allocation limits. No archive paths are extracted to disk. Unknown safe entries are ignored after aggregate size accounting. ZIP64, multi-disk, encrypted ZIP and unsupported compression are rejected; the current source exporter needs none of them.
- `readBackupUploadAsync(request)`: streamed actual/declared multipart limit, duplicate/missing-file rejection and compressed-file bound. Host authorization must run before this ingress helper. It is not a route or an authorization decision.
- `inspectLegacyBackupAsync(bytes, dependencies, options)`: injected authorization, copied resource, authoritative compatibility/schema/content hooks, integrity/reference checks, all 40 family counts, board IDs/names and source-compatible home-board priority. Returned metadata is projected without encryption material. Inspection neither validates the encryption key nor grants restore authority.
- `prepareLegacyBackupAsync(bytes, dependencies, { trustedSourceKey?, selectedBoardId?, signal? })`: same copied path; all six ciphertext columns validated/rekeyed in a synchronous transaction before content conversion; target-key ciphertext validated again afterward; reference validation; explicit source/target keys, no environment fallback. Invalid selected board IDs reject. Board choice changes only the returned destination, never filters/drops boards or remaps IDs. Source sessions, verification tokens and `serverSetting.__onboarding_claim` are removed on the copy. A sealed SQLite snapshot is retained server-side in `PreparedLegacyBackup`; its JSON projection returns only inspection, not bytes/keys/ciphertext/plaintext.
- `sourceModels` and `encryptedFields`: explicit current-schema physical inventory, not a second schema or ORM.
- `createSqliteBackupDependencies(config)`: direct accepted DB copy-engine composition with caller-supplied authorization, key and primitive file configuration; no live database or environment-derived resource access.

`ParsedLegacyArchive.withServerContents` and `PreparedLegacyBackup.withServerSnapshot` are trusted server-only callback seams, not RPC/browser DTOs or authorization capabilities. Never register them as public procedures or log input archives/configuration. Their private fields and JSON projections prevent accidental ordinary JSON key/database delivery; this does not make a source archive sanitized. Preparation errors have fixed typed codes and never retain arbitrary SQL/crypto/adapter errors as public messages/causes. Cleanup failure rejects rather than returning a successful prepared result.

## Bounds and key behavior

Preserved limits: ZIP 256 MiB; multipart 257 MiB; SQLite 512 MiB; aggregate declared archive contents 514 MiB; metadata 1 MiB; key entry 1,024 bytes. Both header consistency and decompression output are checked. These are per-operation bounds, not a proof of concurrent ingress/memory scheduling. Authorization, cancellation and copied-resource lifecycle are injected; decompression/SQL/crypto currently execute synchronously and cannot interrupt halfway through a single operation. The host must own workload/concurrency limits.

Metadata `encryptionKey` and legacy key-file values are private. Conflicting archive keys reject; a trusted supplied key conflicting with an embedded key rejects. A source key is required for **any** non-null encrypted field, including Assistant-only, v2-only, legacy-only and widget-only content; zero integration rows do not bypass this gate. Same-key imports still decrypt/validate all ciphertext, unlike the old early return. Null Assistant fields remain null. Crypto updates only ciphertext columns, retaining timestamps, keys, IDs and all other raw SQL values. AES-256-CBC `hexCiphertext.hexIV` matches `packages/common/src/encryption.ts`; its environment-initializing public server aggregate is deliberately not imported. No plaintext goes into SQL parameters or returned inspection.

Important inherited limitation: CBC/source metadata are unauthenticated. Padding and strict UTF-8 validation reject the known wrong-key regressions, but cannot cryptographically prove that every arbitrary key is wrong when an archive has no independently trustworthy key/integrity evidence. Embedded/supplied key conflict is deterministic; manual source-key trust and any authenticated archive-provenance/key confirmation belong to the accepted policy join. Do not advertise authenticated archive integrity or universal wrong-key detection from CBC. Policy/crypto helpers are independently accepted, but real authority/key-provenance consumption remains an unmounted join. Conversion here retains the actual existing ciphertext format and explicit source key validation; no old environment-initializing codec entrypoint is imported.

## Exact consumed engine and outstanding maintenance join

`BackupEngine` currently requires:

1. `createCopyAsync(bytes, signal)` returning an exclusively owned, isolated, restricted SQLite resource; never open the installation or derive paths from ambient environment. DB owner supplies no-follow/unique temporary ownership, safe source opening, schema-object policy and cleanup.
2. `assertCompatibleAsync(metadata, copy, signal)` verifying the authoritative dialect/version/migration ledger and supported upgrade window before writes. `homarrVersion: "unknown"` is a real source-export outcome; metadata alone cannot identify migration support. Unknown/future ledgers must not be silently treated as current.
3. `migrateSchemaAsync(copy, signal)` applying packaged real Drizzle SQLite migrations without seed; `migrateContentAsync(copy, signal)` applying the five real custom transformations with explicit resources. Restore must validate/rekey every source ciphertext before any content transformation can delete/rearrange old secret rows.
4. `CopiedDatabase.all/iterate/run`, synchronous `transaction(() => undefined)` with real rollback/immediate exclusion, `sealAsync()` closing/checkpointing a standalone consistent image without missing WAL data, and idempotent `disposeAsync()` disposing every resource/owned temporary artifact. Sealing/disposal must never replace a live file. These operations are now provided by the accepted actual copy engine; supplemental synthetic input fixtures remain current-schema-only.

The accepted `createSqliteCopyEngine` now supplies the required split migration ordering and copied-resource/compatibility/sealing bridge and is consumed here. Ordinary `createPersistenceRuntime` exposes separate schema/content operations plus startup `migrateAsync`, tracked admissions/transactions and DB-only maintenance/snapshot/close. This restore lane does not configure or consume the live runtime/facade, and does not modify persistence-owned files or import the old global DB. Acceptance of DB resources is not acceptance of whole-app maintenance.

No `apply`/`MaintenanceCoordinator` shim or success-returning no-op exists. Required accepted C-MAINTENANCE revisions are: exclusive principal-bound acquire/confirm with one-shot/ambiguous-attempt handling; rejection of new writers; bounded job/refresh/HTTP/SSE/upstream drain; every independent DB connection closed; cache/security epochs fenced; recovery snapshot captured and durably identified; exclusive verified replacement with WAL/SHM handling owned by persistence; interrupted apply recovery; supervised restart; real DB/auth/service readiness; migration logout/claim outcome; and bounded release/failure semantics. The current DB-only `maintenanceAsync` does not establish those whole-runtime properties. Prepared snapshots/inspection are not maintenance leases. A new authorized runtime read/write/restart test must close the gate before claiming restoration into Nitro.

Consistent live source-export service, concurrent export ownership, sensitive-download/key-carriage policy, SQL-WASM/journal packaging, browser preview/restore panel and SQLite→PostgreSQL conversion are not implemented/mounted in this preparation lane. PostgreSQL source ZIP export remains unsupported; preparation yields SQLite only and does not claim cross-engine restoration. COMPOSITION now declares the API entrypoint and API test dependencies described above; runtime code uses the existing `@homarr/db`, `superjson` and Bun/Node facilities.
