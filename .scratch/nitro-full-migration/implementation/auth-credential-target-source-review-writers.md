## Journal, lock, snapshot and marker conclusions

**Timestamp progress is not authenticated target identity.** SQLite0015:654–667 and Pg0017:57–67 select only the latest row and gate on a Number-converted timestamp. They select hash but do not compare it to accepted expected history. They do not inspect full ordered prefix/snapshot lineage or require exact target count. The initial last-row value remains constant throughout each migration loop. Generic0009:10–24 rereads configured filesystem data and hashes that data; it cannot self-authenticate a supported target. H102–106 requires module-owned whole-history pins, ledger-object-first shape validation, exact dates and fixed original runtime anchors; these visible bodies are not that validator.

**Two different TOCTOU boundaries remain.** Filesystem exists→read and journal→SQL reads are visible at0009:7–15; trusted immutable host inputs are still required by H104. On both engines latest ledger read precedes transaction establishment (0015:652–657;0017:54–60). No inside-lock reread is visible, so the read cannot be represented as a lock-protected coherent migration snapshot. This identifies an absent synchronization bridge, not a tested concurrent duplicate-migration outcome. Schema/table creation also precedes the migration envelope; do not claim the entire operation rolls back its bootstrap objects.

**Migration transaction is not maintenance or read-snapshot authority.** SQLite migration's plain BEGIN and Bun transaction's default deferred do not supply H167/Dsg81's fixed synchronous BEGIN IMMEDIATE mutation protocol. Pg no-config BEGIN does not itself verify READ COMMITTED; its generic FOR strength/OF/nowait/skip-locked SQL builder0017:288–306 does not mean a ledger/domain mutex was acquired. No selected body implements fixed read-only REPEATABLE READ snapshot admission, drained maintenance, compatible-writer exclusion, singleton-first/user-before-ordered-group locking or through-COMMIT authority. H159–169/C57–63's genuine main-runtime/transaction-gate ownership remains UNREAD.

**Marker/append/ledger source-order candidate only.** If a future authenticated append contains the fixed pending-marker DML among its migration SQL chunks, sync SQLite0015:661–667 and Pg0017:63–67 place that chunk before that migration's ledger insert within their visible migration envelope. This is the narrow JS prerequisite suggested by H143–149, not proof that such an append exists, statements are transaction-safe, native DDL/marker/ledger commits atomically, or the actual product selects these sessions. No SQL asset was read here. Native client behavior, physical constraints and genuine same-resource completion remain separately required. No after-migration INSERT, callback attestation or caller firstAdoption flag may substitute.

**Target epoch/allocator/CAS has no producer in these seven bodies.** A query builder can format caller-supplied WHERE/RETURNING, but does not supply an owned Auth namespace/head/phase CAS, canonical decimal validation, exhaustion/one-row effect checks or exact original credential witness. C19 forbids runtime epoch/request/local-counter substitutes; Dsg43–60 and H135/167/174–178 require private fixed native text/BigInt allocation and atomic evidence/original DML. This tranche finds none of that producer here and does not infer absence elsewhere. Main14 and schema/custom9 joins are not duplicated. Hook/report delivery or a queued continuation cannot create genuine producer ownership or native settlement.
