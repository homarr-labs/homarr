### P1 #1: observe execution before natural await / user continuations

Pinned Drizzle 0.45.2 `query-promise.js` implements `then` as `this.execute().then(...)`, while `catch`/`finally` forward through `this.then(...)`. Binding these inherited methods to the raw builder bypassed the guarded `execute` call; an await rejection handler or user `catch` could consume a decoder failure before the formerly tracked derived promise settled.

When `onFailure` is opted in, **only methods whose function identity is exactly the installed `QueryPromise.prototype.then`, `.catch` or `.finally`** execute with the existing guarded builder as their receiver. No class/prototype, client or pool is mutated. The library's own continuation implementation now calls its guarded `this.execute()` exactly once: the full underlying execution promise is wrapped/tracked and its rejection recorded **before** the library attaches caller handlers. This is source-grounded continuation dispatch, not an execution-method-name heuristic, separate SQL execution or eager assimilation of a lazy builder. Direct execution remains observed as before. Nested scopes inherit the opt-in and preserve the same parent-active/revocation checks; private/reflection/argument-composition protections remain unchanged.

Ordinary scopes without `onFailure` keep the raw bound receiver and existing wrapper semantics. Count builders are not misclassified as QueryPromise continuations; count/composition behavior and successful scalar count remain exercised. Default `settleAsync()` still only drains and never gains a new failure policy. G's existing finite first-failure recorder and native/scoped drain check prevent root COMMIT even if the caller catches/handles the original rejection or it has already settled.

### P1 #2: synchronous-only SQLite library executions, not just callback results

Core scope adds the approved **optional** `synchronousExecutions?: boolean`, set true only by the bounded SQLite gate. Immediately after an actual guarded library invocation, a returned native Promise is given a rejection consumer and synchronously refused with `TypeError("Bounded SQLite library execution must be synchronous")`; `observe` records that refusal immediately. Even if the callback catches it and returns no promise, the root failure check rolls back before COMMIT. In the pinned Bun implementation, INSERT and mapper work occur synchronously inside the async `.execute()` before it returns its Promise; the immediate refusal therefore rolls back the already-executed SQL. No microtask/clock-wait trick is used.

This check is at library invocation, not generic `wrap`/metadata traversal: lazy builders and `.run`, `.all`, `.get`, synchronous relational execution and SQL/count composition remain legal when they actually return synchronously. No method is forbidden just because its name is `execute`; no ordinary asynchronous facade/body changes policy. Nested scopes inherit the option. Returned callback promises still reject as before, and retained continuations remain revoked. The rejected async mapper promise is consumed internally without an unhandled rejection; the synchronous refusal is the immediate failure that poisons the root. G's accepted cleanup classification continues to retain primary/cleanup causes and quarantine unusable resources.

### P1 #2: cleanup errors cannot replace durability classification

The private gate retains a discriminated success/failure outcome and separately bounded cleanup-error list until **all** cleanup attempts finish. Rollback, SQLite busy-timeout restoration/native close, and PostgreSQL end/listener removal/release errors are collected rather than thrown over the primary failure. Multiple causes use `AggregateError`; the original execution/native/abort cause is retained. The final decision is centralized: **if COMMIT was dispatched and any primary or cleanup failure exists, return `TransactionCommitAmbiguousError` (`TRANSACTION_COMMIT_AMBIGUOUS`) with the complete cause**, including a physically successful commit followed only by restoration or release failure. No retry or false rollback claim follows. A fully successful path preserves its callback return value.

On unusable-resource cleanup failure, the private gate calls its owner quarantine callback synchronously, before subsequent admission/release. `PersistenceRuntime` keeps a sticky quarantine reason, enters `failed` unless already closing/closed, and aborts its bounded lifetime. `requireReady` refuses all subsequent admissions; already queued maintenance checks quarantine before touching the resource and cannot reset it to ready. SQLite attempts native close after all rollback/restoration attempts. PostgreSQL attempts awaited native end for uncertain checkout cleanup, then evicted release; a failed release triggers quarantine/end and a final bookkeeping eviction attempt, with that attempt's error also retained. This is cleanup of the same owned resource, not a mutation retry or replacement pool. Healthy ordinary phases/signatures are unchanged; this does not retroactively repair or claim universal cancellation of already admitted ordinary work.

### Native ownership and actual dispatch guard

- **PostgreSQL:** explicitly acquire one client from the existing pool, handle setup/BEGIN/callback/COMMIT/ROLLBACK/release in resource-owned cleanup, and construct the pinned Drizzle `NodePgSession`/`NodePgTransaction` on a **private per-checkout proxy**. The checked-out client remains owned across every await.
- The proxy serializes native statement dispatch. There is no caller-visible metadata exception: guarded database/select/subquery `_`, session, statement and raw-client reads still reject, and private property descriptors remain hidden. Resolution asserts the same scope/parent lifetime, substitutes only identities registered in that scope, and recursively copies array/plain-data-record containers so selection fields containing guarded count aliases also resolve. ## Runtime and transaction ports

`packages/db/runtime.ts` exports `createPersistenceRuntime(config)`:

- SQLite: `{ engine: "sqlite", path, mode: "fresh" | "existing", migrationsFolder?, logger? }`. No environment fallback. Fresh file creation is exclusive and mode 0600; existing mode requires a regular file and never creates a missing DB. `:memory:` requires fresh mode. Default SQLite selection belongs to explicit host configuration, not import-time environment discovery.
- PostgreSQL: `{ engine: "postgresql", connection: PoolConfig, migrationsFolder?, logger? }`. Requires an explicit connection string or host/database/user; caller supplies credentials/TLS/pool bounds. A pg pool opens only during `openAsync`; the host must supply complete options rather than rely on pg's ambient connection fallback behavior.
- `openAsync()` transitions configured → opening → open; PostgreSQL verifies `SELECT 1`. Failure closes its created connection and rejects.
- `migrateSchemaAsync()` transitions open → migrating → schema-ready. Existing SQLite must have a nonempty, exact ordered prefix of the packaged migration hashes/timestamps; unknown, changed, future or incomplete identities reject before migration writes. PostgreSQL reads its pinned `drizzle.__drizzle_migrations` ledger and applies the same prefix check when present; existing `public.user` content without a supported ledger rejects. That PostgreSQL preflight is typechecked but not exercised against a new real instance in this lane. Both engines use their pinned real Drizzle migrators. SQL assets/journals are not regenerated.
- `migrateContentAsync({ initializeFreshAsync? })` transitions schema-ready → migrating → ready and runs the five existing transformations. Optional initialization is accepted only for explicitly fresh SQLite; no startup/restore reseeding is inferred. Failed migration/content leaves failed readiness, requiring explicit close. `migrateAsync(options)` composes the two steps for ordinary startup, not backup crypto preparation.
- `checkReadinessAsync()` returns `{ engine, phase, ready }` and checks `SELECT 1` only when ready. It does not initialize or migrate resources. The phase getter reports lifecycle state.
- `withDatabaseAsync(callback)` supplies the revocable discriminated `{ engine, database, schema }` handle, with real SQLite versus PostgreSQL schema/driver types and no raw client access. `runAsync(callback)` is the narrow legacy-query compatibility bridge with a SQLite-shaped type; its PostgreSQL cast does not make SQLite-only methods portable. Both admit work only while ready, revoke on callback completion and drain started asynchronous operations before releasing admission.
- `transactionSync(callback, behavior = "deferred")` is SQLite-only, supports explicit immediate/exclusive behavior, nested savepoints and synchronous rollback. Async functions reject before invocation; promise-returning callbacks roll back and their transaction/query-builder handles are revoked. Do not perform network awaits or retain handles across callbacks. Direct `database.transaction` receives the same guard.
- `transactionAsync(callback)` is PostgreSQL-only and uses Drizzle's checked-out pool-client transaction across awaits. The prior isolated SQL proof demonstrated same-session continuity, rollback and lock exclusion; this adaptation has not rerun the real PostgreSQL product/migration matrix.
- `maintenanceAsync(callback)` rejects new admissions, drains tracked callbacks, supplies the owned discriminated handle and restores readiness after the callback unless closing. Concurrent close waits for maintenance and then drains/terminates this resource. It is **DB-only** maintenance, not a whole-app lease or authorization decision. Calling close from inside an admitted callback is invalid because it waits for that callback.
- `snapshotSqliteAsync(destination)` uses a private temporary directory and `VACUUM INTO` consistent SQLite image, publishes with exclusive-copy/no-overwrite semantics, mode 0600, fsyncs the output and cleans only its owned temporary output. It cannot target the source path, does not replace a live database and does not implement PostgreSQL backups. Caller owns the successful destination and its sensitive lifecycle. A post-publication/fsync failure may leave the destination and must be reconciled rather than blindly retried.
- `closeAsync()` is idempotent, rejects close during open/migrate, fences new admissions and drains active work before closing Bun SQLite or ending the pool. Raw internal errors retain driver causes; sanitize them at the authorized API boundary, never serialize/log SQL parameters or credentials as public errors.

`packages/core/src/infrastructure/db/drivers/*` now require explicit connection options and logger configuration; neither importing the factories nor schema mapping creates a DB or imports DB env. `createDb(schema, options)`, `createSqliteDb(config, options)` and `createPostgresDb(config, options)` are changed signature candidates. Lower-level factories return owned `$client` resources; their caller must close them. Runtime factory callers should prefer the tracked ports.

The SQLite `Changes` return type is intentionally adapted from the actual Bun statement result: installed Drizzle Bun declarations advertise `void`, but the implementation returns `{ changes, lastInsertRowid }`. A real `.run().changes === 1` regression protects existing affected-row comparisons. SQLite media mapping remains the existing BLOB → Buffer Drizzle column implementation, not a new serialization format.

One measured source-preservation PRAGMA is required: installed better-sqlite3 is built with `SQLITE_DEFAULT_FOREIGN_KEYS=1`; fresh native probes returned 1 for it and 0 for Bun.
