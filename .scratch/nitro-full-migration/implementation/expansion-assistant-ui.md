## Generation and physical-settlement stop line

The native factory's 19 leaves do **not** contain a generation stream procedure. Legacy generation depends on the existing AI SDK/assistant-ui runtime, server provider/tool execution, approvals, Workshop per-user token/quota, current owner checks, signed generation-access metadata and provider cancellation. None is copied, proxied or fabricated here.

`AssistantGenerationBinding` is an unbound **consumer interface**, not a ready producer or protocol implementation. Pass `kind: held` until a separately reviewed actual native generation transport exists. Its source-shaped request carries the durable thread `id`, selected `modelId`, reasoning, original branch messages and browser pathname/time-zone hints. Hints are never authentication or board authority. Global tool contracts, approvals, execution and continuation must remain with the real runtime owners.

For a future available binding, `start` must synchronously return a genuinely owned handle before dispatch, or throw only before dispatch. `messages` must supply actual full assistant UIMessage snapshots with stable IDs, original parts and server metadata. `settled` must represent physical provider/tool/body shutdown, not reader cancellation or an already-resolved promise. The owner must retain its run through component unmount, authority revocation, restore/drain and rejected settlement. This interface alone proves none of those obligations.

The consumer tracks the acquired iterator, initiates its actual `return()` on cancellation and awaits that cleanup **and** `settled`. Cancellation before acquisition is retained and applied when the iterator arrives. A cancellation notification only interrupts waiting on `next()`; it is not a settlement acknowledgement. Missing/rejected/nonterminal iterator cleanup and rejected/unknown physical settlement remain busy/held. Pending cleanup or settlement stays awaited without a timeout. Stop can preserve the last received partial response; it never creates a synthetic completion or generation token. Final snapshots are serialized in observed parent order, then owner-checked durable `getThread` readback reconciles the UI. Missing snapshots stay visible as unconfirmed and block further generation; mutation failure is not automatically replayed. Unmount/revocation aborts local write/read lifetimes and masks late rendering/cache delivery. Client abort is not asserted to roll back already-dispatched server SQL.

The drawer blocks close/escape/backdrop dismissal during local work. Actual cross-surface sharing, a global generation admission mutex, awaited host disposal and all native server resource/authority-to-COMMIT bindings remain missing joins, not claims satisfied by a React cleanup or callback.

## Bounded four-finding correction return

- **Iterator cancellation:** explicit acquired-iterator ownership and awaited `return()` replace implicit stream-loop cleanup. A stalled `next()` cannot prevent initiating cleanup; it still cannot prove physical shutdown. Unknown cleanup/settlement retains the operation and drawer hold.
- **Ambiguous user append:** the original user ID, parent and snapshot are retained before dispatch. Draft clearing requires a supported owned-thread row with that same ID, parent, user role, parts and complete parent chain. Missing/incomplete/mismatching readback preserves the snapshot, draft and admission hold. Recovery reads only; it never retries the append or allocates a replacement ID.
- **Ambiguous model update:** a synchronous attempted-model reference closes stale event-handler admission before dispatch. The hold clears only on matching owned-thread readback, using the source-returned model ID when available. Recovery cancels prior thread queries and issues a fresh direct `getThread`, not merely `getRuntimeOptions`; an old model or failed read does not establish a terminal mutation outcome.
- **Stale thread deletion:** each row completion checks its mounted lifetime and current deletion identity. The parent uses a functional current-selection comparison, so deleting A after selecting B cannot clear B; an unmounted row cannot invoke its old deletion callback.

Corrections are limited to `conversation.ts`, `chat.tsx`, `thread-list.tsx` and this handoff. No native leaf, client contract, shared owner, rich renderer or integration HOLD was replaced. These source corrections are frozen for rereview, not validated execution or feature acceptance.

## Secret, owner and telemetry boundaries

No credential or header is loaded from storage into a form. Only source `apiKeyConfigured`/`customHeadersConfigured` flags are used. Newly entered secrets live in local form state and the single explicit call closure, are cleared on submission/destination change and disappear when the authenticated feature subtree unmounts. They are not placed in TanStack mutation variables, localStorage, URLs, notifications or logs. No secure-memory-erasure guarantee is made for JavaScript strings.

Private query keys require the genuine host-supplied current lifecycle scope plus actual principal user ID. Read functions combine query cancellation with that lifecycle signal; mutation access is checked before dispatch. An aborted/held authority masks children and clears feature queries. The host must never reuse a lifecycle scope across authority changes, must abort the old authority before replacement and must bind the real session-transition policy. The UI does not issue sessions, invent permission arrays or repair Q16.

Full stored message metadata is preserved for source persistence. Only allowlisted numeric usage/provider/model/timing/cost/context fields render. Generation access tokens, arbitrary metadata and raw provider errors are not printed or exported. The optional part renderer receives parts, not the message metadata. `getGenerationTelemetry` continues to perform the server's owned-thread/message lookup and user/thread/generation-bound token verification; the frontend does not infer or weaken that verification. Missing usage is absent/not reported, never a fabricated zero or inferred cost.

Pending input/approval tool states block new generation. There is no local approval executor, auto-approval policy, board mutation form, widget installation workflow or fabricated tool success. Completed unfamiliar parts can be shown only by the separately accepted renderer.
