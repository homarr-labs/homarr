## 3. Request association and native capacity: public versus version-bound

**Documented public hook:** `Agent.createConnection(options, callback)` accepts asynchronous completion (N-doc:230–267; N-TLS-doc:65–68; installed `@types/node/http.d.ts:1699–1702`). Return `undefined` and invoke the supplied callback with the verified target Duplex; returning the raw proxy stream would trigger premature native pool admission unless using an internal marker, which is forbidden. Both pinned Agents invoke this callback path (B-agent:284–308 / N-agent:447–471). This is source compatibility plus prior bounded feasibility, not new production evidence.

**Request-bearing hooks are source-bound, not documented public override guarantees.** Both ClientRequest constructors validate an Agent-like `addRequest` function and invoke it with the actual request. Both exported Agent prototypes implement `addRequest(req, options[, legacy port/localAddress])` and `createSocket(req, options, callback)`; these names are callable without native symbols. However, neither method is declared on installed Agent types or documented in the inspected pinned public HTTP API sections. Existing r3 `https-agent.ts:20–43` already structurally delegates `createSocket` to associate its synchronous invocation with `createConnection`. A future per-instance/subclass bridge at these ordinary property names is a **pinned source-coupled extension requiring explicit acceptance**, not a newly discovered stable public cancellation hook. No native prototype/global patch is proposed.

Request signal/queue consequences:

- Native `ClientRequest` consumes and **deletes** `signal` before `addRequest` (B-client:246–249,403 / N-client:271–274,406). `createConnection(options.signal)` cannot be assumed to contain caller cancellation. B-abort/N-abort call `stream.destroy(...)` dynamically; source supports a request-specific destroy bridge installed at admission, plus `request.destroyed` checks for already-aborted construction. An Agent-wide signal would be incorrect.
- Admission is earlier than creation and covers free-pool reuse as well as queued requests. Free-pool reuse does **not** call `createSocket`/`createConnection` (B-agent:229–246 / N-agent:378–399). `reuseSocket` is a documented public hook but cannot observe admission of new or queued requests by itself. r3's temporary request field must be captured synchronously into each transaction before any await, never reread by asynchronous continuations.
- Agents merge their options over request options, normalize servername, compute pool key, then choose reuse/create/queue. Per-request timeout is copied in `createSocket` (B-agent:219–240,265–279 / N-agent:368–392,427–442). Do not guess identity, port, pooling or timeout behavior from the raw input URL alone. `getName` is public; retaining native key computation avoids inventing a shared tunnel pool across different targets/trust options.
- Native `ClientRequest.destroy` before socket assignment marks `destroyed` and records the error but does not remove a queued request or necessarily emit immediate close (B-client:503–522 / N-client:510–524). Agent free handling shifts a queued request and calls `onSocket`; `onSocketNT` then handles its destroyed state. An event-only `close`/`socket` listener cannot provide prompt pending/queued cancellation. Actual native queues may retain cancelled entries until native assignment; do not splice `agent.requests` to hide this.
- Native `destroy()` iterates only free/active pools (B-agent:492–504 / N-agent:660–672), not pending connector transactions or queued requests. Native removal may schedule another `createSocket` from the queue (B-agent:405–447 / N-agent:578–611). A retirement fence must therefore cover both admission and reentrant creation. Error completion of that scheduled creation does not itself demonstrate removal/drain of all queued records.

**Capacity HOLD discovered from source:** native limits compare only `sockets`/`freeSockets` lengths and `totalSocketCount`; insertion and count increment occur in `oncreate`, **after** delayed completion (B-agent:239–250,284–299 / N-agent:391–403,447–455). No initial pending reservation is present in these paths. Thus a callback-only connector does not automatically preserve finite maxSockets/maxTotalSockets while several tunnels are pending. This is a structural accounting gap, not a newly observed over-limit run. Native tunneling has a similar delayed-pool path; existing behavior is not permission to broaden it or claim stronger bounds.

No inspected documented public hook reserves such capacity or removes a queued tombstone. Public `requests`/`sockets`/`freeSockets` are explicitly **do not modify** (N-doc:328–344,409–437). Incrementing native counters, inserting placeholder streams, changing configured limits or installing a new scheduler is not authorized. **Full P1 cannot be called ready until a separately accepted bounded reservation/queued-drain seam is returned, or this limitation receives explicit disposition.** Default SAMECA and source/failure-join planning do not depend on the D1 override answer.

## 4. Axios redirect/HTTP ownership boundary

Read installed Axios `lib/adapters/http.js:258–295,962–1139,1322–1335` and follow-redirects 1.16.0 `index.js:127–136,335–355`: the actual HTTP adapter builds native protocol Agents, uses native transport for maxRedirects=0, otherwise follow-redirects selects `options.agents[scheme]` and creates a new native request each hop. Outer abort destroys its current native request. A bridge must identify that **actual per-hop ClientRequest**, not Axios config/one signal per Agent or follow-redirects private `_currentRequest` state. HTTP↔HTTPS redirect switches to a different Agent; an HTTPS-only connector cannot claim ownership of its HTTP continuation. Header/auth stripping, streamed body replay, limit/error semantics and redirects remain actual adapter obligations, not new wrappers to implement in P0.

Native HTTP forward-proxy rewriting occurs in the ClientRequest constructor **before Agent.addRequest**, through private proxy config (B-client:110–147,389–403 / N-client:151–190). HTTP Agent connects to the proxy using only `proxyConnectionOptions` (B-agent:154–179 / N-agent:295–322). HTTPS Agent likewise supplies only host/port to initial proxy TLS (B-https:272–318 / N-https:362–409); target TLS options are distinct. No public custom-CA propagation hook was found for either native outer connection. Replacing only HTTPS createConnection does not solve HTTP forward TLS, source rewriting or pre-pool ownership. Whole production guard stays HELD, not a protocol/path whitelist or direct fallback.

Native CONNECT parsers accept status **200** (B-https:149–162 / N-https:249–262); accepted primitive/planning allows 2xx before target TLS. This status-policy difference is now explicit and needs source-preservation disposition before promotion; neither native code nor accepted plan is edited here. Delegate any future CONNECT parsing to actual Undici, never copy/rewrite the native parser.

## 5. Undici 7.29.1 initial-socket and handoff handshake

Installed provenance is `node_modules/undici/lib/core/connect.js`, recorded hash `67956a204fe3982edbf032dd44ff9c1c391daaa85c05e9750d245bdfb2b87fe0` in accepted feasibility evidence (not recomputed now). Its public `buildConnector` accepts a connector callback, but `types/connector.d.ts:33–34` declares **void** return. Source creates native TLS/TCP at lines 86–114, sets keepalive/timeout/listeners at 120–147, and returns the socket at 149. Callback is nulled before invocation on connect/secureConnect or error; no builder-local end/close terminal callback is installed. The return is a pinned implementation dependency, not a type-guaranteed API.

Critical additional source: `lib/dispatcher/client.js:372–399,465–527` ignores connector return, establishes HTTPContext only after callback and destroys through that context. With no HTTPContext, Client destruction completes through a queued microtask. Therefore **Client.destroy completion alone cannot establish initial socket physical close**, especially before callback. `lib/dispatcher/client-h1.js:821–871` owns the socket only once connected; detached upgrade at 530–564 clears Client context. `api/api-connect.js:51–83` removes its signal listener before delivering the socket; `core/util.js:786–805` removes only Undici-registered listeners, not arbitrary external close listeners. A separately attached physical owner can survive handoff; library context/signal ownership does not.

Future handshake requirements, not implementation:

1. Register request/generation/transaction and pending Client before dispatch. Pre-register a connector invocation record before calling buildConnector; queue any callback outcome until its returned-stream ownership is reconciled. Do not let a synchronous callback/reentrant cancel deliver or discard a stream before ownership exists.
2. On successful return, validate the real stream without pretending void is a socket type, attach independent error/end/close ownership, and immediately reconcile already-closed/cancelled/retired state. If callback and return expose distinct streams, own both; track all late deliveries. Keep one completion gate; callback throw is a retained failure, never a second callback attempt.
3. **Unresolved pre-return throw seam:** native connect can allocate a stream before builder keepalive/timeout/listener setup or user callback code throws. An exception before return may hide the initial stream from the wrapper, and Client has no context yet. A registered transaction with no stream is not proof of physical ownership. Current return-source inspection and primitive positives do not prove this cannot happen. Require an exact source-backed bounded capture/cleanup guarantee, or **HOLD**; no global TLS patch, private socket lookup, native symbol, replacement connector stack or rerun of primitives is authorized to conceal it.
4. Preserve independent abort and physical-close joins when Undici removes CONNECT cancellation wiring. Own detached stream before releasing Client; verify permitted CONNECT status before creating/owning target TLS. Early end/close before callback must terminally reject and join real closes, not wait for a successful handshake forever. A client destroy resolving after abort does not replace these joins.

Existing accepted feasibility remains three Bun and three Node primitive runs with actual streaming, trust negatives and handoff closure; its injected release failure happened **after close**. No new conclusion about synchronous throw, genuine destroy failure, arbitrary reentrant callback, finite capacity, queues or default-managed parity is inferred.

## 6. Essential failure-join correction: smallest proposed lease only

Read frozen `packages/core/src/infrastructure/http/ownership.ts:107–145` and `https-agent.ts:110–129`:

- `ownNodeAgent` registers native pool close promises, calls destroy, then starts independent connection joining/all-settled. If destroy throws, its catch rejects **before** calling `waitForConnectionsClosedAsync` or initiating that all-settled branch.
- `waitForConnectionsClosedAsync` itself throws recorded retirement failures **before** draining its tracked connection map. Merely calling it from a finally block would therefore still not join available physical closes.

**Minimal prospective correction is both files**, under a new explicit lease: retain destroy/wait failures, initiate every available independent physical join despite those failures, continue tracking late connections/connector completion, settle all available joins, aggregate honestly and never call `onReleased` on failure. A still-unclosed stream remains strongly owned/quarantined; watchdog expiry, rejected destroy or cleared cache cannot declare it closed. Repeated disposal stays the same Promise including failure. Source inspection identifies the missing branch; no accepted r3 bytes were edited or new failure test run. This correction does not confer queue/capacity or routing authority.
