## Serialization, identity, expiry and effects

The ordinary storage value is this JSON-compatible envelope:

```text
{ type: "homarr-serialized-cache", version: 1,
  logicalKey: string, value: string, expiresAtMs: number | null }
```

Each read validates unknown storage contents with a strict Zod schema: exact type/version, string key/value, and finite, nonnegative expiry no greater than `Number.MAX_SAFE_INTEGER`. The stored key must equal the requested logical key; payload UTF-8 bytes must not exceed the snapshot limit. Unknown versions, wrong fields/key, oversized payloads and expired records are misses after scoped cleanup. A driver-returned `Error` is thrown rather than misclassified as a corrupt entry eligible for deletion. A rejected cleanup propagates instead of being silently reported as successful removal.

- `null` from storage is missing. A valid envelope whose value is the string `"null"`, an empty string, or any SuperJSON serialization is a hit. The adapter never revives Dates, interprets embedded dates, parses the application string, changes Query keys or makes a security decision.
- Every JavaScript UTF-16 code unit in the logical key becomes four lowercase hex digits, grouped in at most 64-character path segments. A distinct non-hex `empty` segment represents the empty key. A terminal non-hex `value` leaf prevents a shorter key's file from colliding with a longer key's directory. Colons, slashes, backslashes, question marks, Unicode and lone surrogates retain exact identity; there is no lossy UTF-8 conversion, hash collision, normalization or trimming of the logical key. The full original key also remains in the envelope.
- An explicit **512 UTF-16-code-unit key bound** rejects rather than truncates larger keys. This is a candidate resource bound, not a new board identifier/fingerprint rule. The source family uses board ID plus a 64-character SHA-256 fingerprint; the producer join must confirm its accepted IDs fit the bound. Arbitrary filesystem path limits/base lengths are not certified by the bound.
- `ttlMs !== undefined` takes precedence even when zero or negative. Otherwise `ttlSeconds * 1000` is used. Selected nonfinite TTL is an error, never a no-TTL write. Selected nonpositive TTL removes the key without serializing/storing the supplied value. Positive TTL produces an absolute millisecond deadline immediately before the native write is dispatched; no rounding to seconds is applied. Excessively large nonfinite/out-of-range deadlines reject before the write.
- A write without TTL replaces the entire envelope with `expiresAtMs: null`; no previous logical expiry is retained. No native TTL option is sent. This avoids depending on FS's nonexistent expiry behavior or native timer range/rounding. Logical expiration is checked after the read completes, including slow native reads. Physical expiry is not claimed.
- The strict cache admits at most **100** actual/queued operations, at most 100 key lanes and at most 100 caller timers; payload writes are bounded at **512 KiB** and keys at 512 code units. There is no value memo, retained-key index, background janitor, driver enumeration, scan cursor, watch, scheduled cleanup, automatic retry or batching.
- Each read does at most one read and, if invalid/expired, one removal of that exact encoded key. Each write/remove performs one native mutation. Cleanup uses the same key lane as all owned get/set/remove operations, and holds it until the native cleanup settles. A newer rewrite through this owner cannot occur between reading an obsolete entry and removing it, even after a caller timeout. This is sole-owner ordering only, **not a security CAS or proof about all compatible/external writers**.

## Actual settlement and shutdown

Admission reserves a key lane and a pending slot until the underlying operation settles, not until the caller's timeout resolves. Rejected operations still release their lanes only after settlement. A queued operation whose local deadline already expired is skipped before native IO; if native IO already began, timeout does not cancel it, release its slot, unlock its key, or authorize a retry. A timed-out set/remove (or read with cleanup) may still finish; the caller's mutation disposition remains ambiguous. Drain establishes promise settlement, not successful commit/readback, and no retry is attempted.

`stopAsync` synchronously stops new admissions, awaits all accepted actual settlements (including queued operations and cleanup), then releases this instance's ownership slot. It has no misleading forced-success deadline. An indefinitely unsettled native call leaves shutdown unsettled and the mount claimed. The cache does not abort native IO, clear persisted values, dispose global/prefixed storage, mount/unmount anything, or dispose a foreign driver. The Nitro composition owner must join this stop **before** its own storage teardown. A subsequent owner may be constructed only after that join, against a still configured valid private mount.

Root 4.4.3 is not a substitute. Nothing was run or passed here.
2. **Mount/driver/deployment join:** a separate owner must configure the exact private mount and intentionally choose the driver. A private mount name does not prove its physical directory is disjoint from other mounted directories. No driver, location, deployment volume, filesystem permissions, durable directory, atomic-rename/power-loss behavior or memory capacity is accepted here. Explicit memory is process-local disposable acceleration, not persistent/shared state. Root fallback and Redis fallback are absent. No mounted-storage/appdata change is authorized by this report.
3. **Persistent unknown-orphan cleanup:** the candidate only removes entries encountered by owned reads. Expired files never read again, old fingerprints, preexisting unsupported files and memory entries never revisited are not enumerated or reclaimed. There is no total backing-capacity bound or physical three-day deletion guarantee. Installed FS `getKeys` recursively materializes results and does not offer a verified bounded pagination contract; slicing that array would not bound native work. Persistent cleanup needs a separately owned bounded enumeration/index/driver primitive and a sole-writer join or atomic conditional removal. This remains a release hold, not a fake scan guarantee.
4. **Native failure and cancellation proof:** installed FS `readFile`/`unlink` helpers use `catch(ignoreNotfound)`, which returns a non-not-found error object instead of necessarily rejecting. Reads returning `Error` are surfaced here, but unstorage `removeItem` ignores its driver's resolved return value; it can hide a returned unlink error. No full native remove-failure proof or error-repair shim is claimed. Missing write/remove methods and read-only/non-atomic FS configuration are rejected, but that is not execution evidence. Driver write/removal/timeout/shutdown/error/resource behavior requires a separately authorized native join; no IO, fault injection or live data was used.
5. **Sole-owner lifetime/writer join:** the factory gate is module-local, not a distributed lease. HMR/duplicated module copies, other `useStorage` users, external filesystem writers, concurrent processes and remounts are outside its ordering guarantee. Same-key stale cleanup is safe only for all writes through this single owner on the approved single-backend model. Native unstorage/FS atomic rename is not conditional removal or security CAS. A multi-writer design needs an actual conditional primitive or must disable read/remove cleanup.
6. **Board producer/transport join:** supply this real storage seam to the producer without importing backend runtime into the browser; preserve all generation, authorization, Query-key migration and late-restore rules. Producer-level removal after a separately decoded invalid/busted application snapshot is still unconditional and outside the adapter's read-and-cleanup critical section; its cross-request rewrite ordering/publication needs explicit review. A cache-local lane does not make that higher-level read/decide/remove sequence atomic. No consumer, transport, acceptance or cutover exists yet.
7. **Generation/publication/native SQL join:** generation/lease/state/security and response owner-conditional writes stay with their existing native contracts. No SQL-check-then-KV-write, fresh/stale multi-write, stale persistence, synchronization or invalidation fence is fabricated. Their producer/native failure joins and same-listener delivery remain separate and held.
8. **Composition shutdown join:** stop producer admissions, await their actual work and this cache owner's drain, then retire only the composition-owned storage resources. No server plugin/config/lifecycle/listener edit is made here. Process supervision cannot treat a local caller timeout or a forced process exit as evidence that native work settled.
