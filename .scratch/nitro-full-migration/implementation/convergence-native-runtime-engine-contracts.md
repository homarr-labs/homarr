## 1. Original START204: completed start operation, not queued work

Primary sources, at the reported Moby commit:

**Scope:** retain the actual original request's fully received/closed204 and task settlement. It establishes completed startup under the source/runtime association; it does not establish workload readiness, workload success, continued running, namespace closure, or universal durable daemon-state persistence. Checkpoint errors after SetRunning are logged rather than returned. A fast process may already be exited when204 reaches the caller.

Cancellation is specifically insufficient: the Engine's task creation/start uses `context.WithoutCancel(ctx)`. A lost/aborted/non204 response therefore remains ambiguous and must not be retried or treated as a daemon stop. Metadata cannot retrospectively settle it.

**Exclusive starter remains necessary.** `validateState` ordinarily produces304 for running state, but `containerStart` also has a locked `resetRestartManager && Running` early nil return. A concurrent external starter could make a204 association misleading. The coordinator's exclusive-writer lease is an external ownership assumption, not an inspect measurement or a property of HTTP204 alone.

## 5. Linux private PID init-exit closure — scoped derivation

Primary standard:

- https://man7.org/linux/man-pages/man7/pid_namespaces.7.html , DESCRIPTION, “The namespace init process”, “Nesting PID namespaces”, and “setns(2) and unshare(2) semantics” (Linux man-pages6.19). PID1 is the namespace init; its termination causes SIGKILL of namespace processes; later fork into that dead namespace fails ENOMEM. PID namespace membership is fixed at process creation; processes cannot move into ancestor PID namespaces.
- Matching numeric upstream kernel: https://raw.githubusercontent.com/gregkh/linux/v7.2.9/kernel/pid_namespace.c , `zap_pid_ns_processes`. It disables PID allocation, signals remaining tasks with SIGKILL, waits/reaps, then waits until other allocated PIDs are gone. Its explicit invariant is: **when the init process is reaped, all processes in that PID namespace are gone**. Signal dispatch alone is not this completed invariant.
- Upstream v7.2.9 exit ordering: https://github.com/gregkh/linux/blob/v7.2.9/kernel/exit.c#L640-L670 (`find_child_reaper`), https://github.com/gregkh/linux/blob/v7.2.9/kernel/exit.c#L741-L774 (`forget_original_parent`), and https://github.com/gregkh/linux/blob/v7.2.9/kernel/exit.c#L780-L821 (`exit_notify`). `find_child_reaper` calls zap when no live reaper thread remains; `exit_notify` performs this work before making the exiting task a reportable zombie and notifying its parent. Namespace teardown can wait; there is no claimed finite SIGKILL/reap theorem for arbitrary stuck kernel I/O.
- OCI runtime-spec v1.3.0 namespaces, lines21–46: https://github.com/opencontainers/runtime-spec/blob/v1.3.0/config-linux.md#L21-L46 . A namespace entry without path requires a new namespace; omission inherits the runtime namespace. This version is named in the reported runc commit's go.mod.
- Exact runc `specconv` maps OCI PID namespace to NEWPID; the exact namespace syscall mapping/CloneFlags uses CLONE_NEWPID only when no join path is specified: https://github.com/opencontainers/runc/blob/29dd3dc2b13b4123162e5fe132504bb4b15569f1/libcontainer/configs/namespaces_syscall.go#L11-L33 .
- Exact containerd `handleInitExit` in the task service cited above records init exit from its existing reaper, holds init-exit publication until running execs finish, and describes private-PID tasks as already reaped. This supports ordinary propagation of the Linux closure fact; it does not authorize adding an exec, bespoke reaper or another launcher.

**Permissible future conclusion:** `derived-owned-context-closure`, with `measuredProcessInventory:false`, after the reviewed private-PID/runtime association, actual original START settlement, complete successful wait body, same-id exited/Pid0 inspection and all owned starter/control/file-writer tasks closed. Caller stdout settlement, caller/owner exit and actual physical file-close facts remain independently necessary. Host-process ownership is not supplied by Linux container PID semantics.

This conclusion concerns tasks in the owned private namespace under the standard contract, not zero unrelated VM/macOS processes, zero kernel workers, all filesystem effects complete, arbitrary compromised runtimes or the absence of privileged external API clients. Even CapDrop/NNP cannot prove no external writer. Coordinator exclusivity must cover the entire attempt and publication interval and exclude exec/restart/second START/update/concurrent administrative automation; repeated inspections cannot enforce that lease.

Exact OrbStack patch/kernel-binary attestation remains unavailable. A reviewer can accept the standard Linux contract as the scoped basis for mandatory new-context observations; if policy instead demands exact patched-kernel verification, **HOLD for that concrete unavailable evidence**, not a fabricated hash or universal verification framework. Likewise `privatePidNamespaceMeasured:true` cannot honestly mean a measured live target before CREATE: its pre-release meaning must be explicitly accepted as a platform-contract binding with later target observations, or the receipt ordering is circular.
