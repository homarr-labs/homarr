### Exact resource recipe for the 11 queries

Use the schema object returned by the same main persistence admission, never runtime table imports from the environment-selecting `@homarr/db/schema` root.

- Settings: `serverSettings: schema.serverSettings`, `boards: schema.boards`, operators `{eq, and}`, `inArray`, and the existing `settingsCodec` from `@homarr/api/nitro/helpers/settings`.
- Preferences: tables `{users, boards, boardUserPermissions, boardGroupPermissions, groupMembers, searchEngines}` from that schema; operators `{eq, inArray, or}`. No DB select-validator dependency is needed for this smaller factory.
- Groups: tables `{groups, users, groupMembers}`; operators `{eq, and, like, not, max}`; genuine `createId`; `providers()` returning the issuer's actual enabled provider names and `oidcGroupsLocalManagement`, not credentials-enabled defaults.
- API-key listing: table `{apiKeys}`, operator `{eq}`. Do not expose its create/delete procedures merely because their bodies exist.
- Version: actual build version supplied by H; no fabricated string.

Direct operators can come from the already-declared `drizzle-orm` dependency in API composition. Preserve existing pure helpers and table references. Providers/createId remain required even when the selected group procedures do not invoke them; do not satisfy the full factory with throwing placeholders.

The next five identity queries (`user.getAll`, `user.selectable`, `user.search`, `user.getById`, `invite.getAll`) are also present, giving a possible 16-query identity tranche. Their factories additionally require genuine `selectUserSchema` / `selectInviteSchema`, provider configuration, ID generation and the source logger. `packages/db/validationSchemas.ts` currently imports the environment-selecting schema root. Reuse its exact `createSelectSchema` recipe with the admitted physical tables and existing byte-unit refinement through the proper DB owner; do not blindly import that root, cast a replacement validator or add a generic validator framework. API currently declares `drizzle-zod` only as a dev dependency; any new production use/export declaration belongs to the coordinator.

## Concrete request join required from A / H / P

1. **Same physical main owner:** `native-main-persistence.ts:352–375` currently returns only guarded `engine/phase/runAsync/checkReadinessAsync`. Auth issuer construction needs the existing full native runtime's bounded transaction and auth-session mutation facilities; `readResourceAuthorizationSnapshotAsync` also needs `boundedTransactionSync` / `boundedSnapshotAsync`. H/P must provide an owner-held construction join to that same runtime. Do not open a second persistence runtime, widen this facade with optional methods or recover an ambient database.
2. **A's real producer:** obtain the reader through `getProductionSessionRequestReader(actualIssuer)`; its two methods return genuine `SqlAuthorityAdmission`. A must retain the original lease privately and supply the current `BackendPrincipal` profile (`id`, effective permissions, `colorScheme`, source profile fields), the host `Principal` (`subject`, real `sessionRevision`), asynchronous currentness and awaited release. The reader identity alone lacks the required user profile/color scheme and durable host revision. Copying the host subject into a fabricated SessionUser is not admission.
3. **One request ownership path:** existing `RequestServices.resolvePrincipal` receives `{request, signal, requestId, onDispose}` before its first await; `application.ts:44–47,55–68` owns late-registration rejection and reverse awaited cleanup. Register a genuinely acquired lease immediately; if registration fails, release it before propagating failure. Reuse this path, not an additional cleanup manager. Keep private admission associated with the original Request through A's owner, not caller DTO matching.
4. **Credential selection:** A owns real API-key precedence / cookie selection from the pinned issuer configuration. Reader rejection, malformed supplied key, disabled-reader and upstream failure are not anonymous fallback. Only genuine fulfilled-anonymous results may follow A's approved fallback. Do not reimplement Auth in API composition.
5. **DB/context:** keep the full finite RPC operation and serialization inside the main `runAsync((database, schema) => ...)` callback. Validate the schema object is the one used to build the resources. Reuse `createSetupBackedContext(input, {database, schema, signal, assertCurrent}, {operators:{eq}, now})`. It supplies actual SQL claim/no-user/current-step checks and freezes the context; no new setup adapter is needed.
6. **Currentness is two distinct obligations:** the synchronous setup fence checks original request signal, active DB callback and main-owner currentness. A's lease must separately be checked asynchronously before native dispatch and after finite serialization, with the genuine profile/permissions read tied to that lease. Do not replace asynchronous credential/grant validity with a synchronous no-op `assertCurrent`. These read checks do not establish validity through COMMIT for writes.
7. **Effects/disposal:** forward the original host effect sink and disposal registration through the existing fenced context. Supply genuine device classification, configured base URL and selected demo state; do not reuse the public adapter's hardcoded anonymous/undefined-device/disabled-demo tuple. Preserve disposal availability for acquired cleanup even on abort; request signal must not silently drop an obligation.

`createAdmittedPublicRpc` is intentionally anonymous-only (`public-rpc.ts:116–118`) and buffers the response before releasing SQL admission. It is not the authenticated adapter. `createBackendFetchContribution` has no principal-currentness or persistence ownership checks and its `access` is public; mounting it directly is not a solution. H should join an authenticated-only finite handler with the real producer above while leaving public settings' exact allowlist intact. For shared `/rpc`, separate exact dispatch or one finite explicitly admitted combined handler is necessary: neither existing handler returns pass for unknown paths, so stacking catch-all handlers makes the later one unreachable. No anonymous full-router fallback.

Subscriptions cannot use the finite `arrayBuffer()` strategy: it would retain SQL indefinitely and buffer an unbounded stream. Do not select `widget.beszel.subscribeSystemStats`, `docker.subscribeLogs`, `cronJobs.subscribeToStatusUpdates` or `log.subscribe` until J/H's real streaming retention/currentness/cancellation/drain join exists.
