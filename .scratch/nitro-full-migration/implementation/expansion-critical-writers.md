## Concrete native SQL algorithms

### SQLite

The dialect entrypoint uses the frozen `PersistenceRuntime.boundedTransactionSync`; G3 owns actual synchronous `BEGIN IMMEDIATE`, failure capture, root COMMIT/rollback and quarantine. The callback rereads the existing user, complete membership IDs, referenced group parents and DISTINCT joined grant facts on that same admitted transaction. It invokes the existing definitions expansion function before the candidate admin decision and writes. Matching physical `sqliteSchema` is used throughout. Reads use synchronous `.get()`/`.all()`, mutations `.run()`; no promises, provider/hash work or nested transactions occur inside the callback. Immediate admission excludes competing SQL writes, including absent/new memberships/grants, until native settlement. No PostgreSQL lock syntax is used on SQLite.

### PostgreSQL

The dialect entrypoint uses frozen `PersistenceRuntime.boundedTransactionAsync`; G3 owns one checked-out existing-pool client, BEGIN, ordered statements, scoped drain, root COMMIT/rollback and cleanup. The callback first executes `SELECT current_setting('transaction_isolation')`: anything other than exactly `read committed` fails instead of assuming statement freshness or widening G3 to allow SET/transaction controls.

It locks the real actor/user parent `FOR UPDATE` before reading complete memberships. It discovers only the actual relevant existing groups, merges actor membership parents and target/matching parents, and acquires them sequentially in canonical sorted ID order. A permission-replacement/deletion target is `FOR UPDATE` **from its initial acquisition**; other parents are `FOR SHARE`. This avoids a share-to-update upgrade on the actor's own target group. No sentinel/advisory key or new table is introduced. Each implemented operation touches a single user; multi-user writers are not covered or given a caller-first locking shortcut.

After locking, the callback rereads the complete actor membership set, rejects differences or disappeared parents, rereads DISTINCT grants joined through actual membership rows, and invokes actual `getPermissionsWithChildren`. Reconciliation additionally checks discovered parent ID/name pairs against locked parents before deriving mutations from those locked names. Every mutation uses the same transaction database and physical `postgresqlSchema`. Grant replacement and group deletion retain the exclusive target parent through the root transaction, including G3 callback revocation/drain and native COMMIT. Membership effects hold the user parent and referenced shared group parents. Empty sets are not proven by locking only currently existing child rows: their protection requires the real compatible user/group parent writers, which remain an explicit missing join.

Names absent at discovery are not protected by a fabricated name-predicate lock. Source event behavior skips absent groups; it does not promise automatic membership in a concurrently created or newly renamed group. A discovered parent changing/disappearing during acquisition rejects the candidate, without retry. These source-selection details must not be reused to claim a setup/no-users/missing-claim predicate protocol.

Private SQL body functions do not expose a database/client lease or accept injected business callbacks. Native result, constraint, timeout/deadlock and mapper errors propagate to G3; there is no fallback, retry, swallowed failure or false confirmed rollback after dispatched COMMIT. No last async permission read is presented as an alternative to transaction-held locks.

## Typed lifecycle, not a writer seal

`createCriticalWriterCandidateRuntime(runtime)` is the sole barrel-exported factory. It exposes:

- `execution: { kind: "hold", remainingJoins }`, with no executable state.
- `admitCandidate(candidate, boundedOperation)`: immediately throws the actual execution HOLD before phase checks, operation reads or candidate snapshots. The retained snapshot/reservation body is unreachable and would represent a **candidate cancellation/settlement lifetime only**, not verified identity, input validation, compatible-writer participation or authorization.
- The unchanged prepared single-use admission's `executeAsync()`, `revoke(reason: unknown)` and idempotent awaited `releaseAsync()`; state reports `admitted | executing | settled | released` separately from `live | revoked` cancellation. No caller can obtain an admission through the held boundary.
- Idempotent `closeAsync()`: immediately closes admission, aborts the owned lifetime, releases every tracked candidate and waits for its execution promise to settle. It does not close the composition-owned persistence runtime.

The operation signal, original operation lifetime, candidate revocation and owner-close lifetime are combined for the existing G3 contract. Only the supplied finite **operation** deadline is retained; it is not an accepted credential-expiry bound. Release requests cancellation and waits for native settlement before dropping tracking. Drain observes execution rejection without replacing the independently returned execution failure. There are no timers, manually attached listeners, external release callbacks or assertion/revision APIs. Cancellation infrastructure is not proof of durable credential revocation or early revocation-intent semantics.

`admitCandidate()` synchronously throws `CriticalWriterExecutionHeldError` / `CRITICAL_WRITER_EXECUTION_HELD`, carrying the immutable exact remaining joins. Direct dialect entrypoints retain their own unconditional HOLD. Prepared lifecycle and SQL bodies remain unreachable; removing any HOLD alone is expressly not authorized activation.
