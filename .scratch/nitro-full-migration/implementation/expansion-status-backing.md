## Exact persistence and policy contract

- The only durable key is `runtime-job-status:record:v1:<name>`, containing plain JSON `{ revision, ownerId, runId, value }`. `value` retains exactly name, running/idle, lastExecutionTimestamp and success/error/null. A missing raw value is absent; serialized JSON `null`, invalid records and a mismatched job name reject rather than fabricate an empty record. Timestamps are retained strings, not parsed, normalized or regenerated by storage.
- The previous **original serialized string** is the CAS condition, including its whitespace/property ordering; it is never decoded/re-encoded for comparison. Missing uses exact null/NX. A non-null domain update is encoded and validated before any mutation, then written with `ttlMs: null`. SQL receives only serialized conditions/writes/read keys, never the policy callback. Immutable detached records prevent one callback/subscriber from mutating another's record.
- Revisions must be nonnegative safe integers. The first record has revision 1; every successful update increments once. A non-null update at `Number.MAX_SAFE_INTEGER` fails without mutation. Policy null remains no write/no notification/return null, including at the maximum revision.
- Only an explicit `applied: false` triggers recomputation, using the same-observation current raw value returned by STATE. Every attempt shares the initial absolute deadline and host/stop/deadline signal. Exhaustion rejects. Malformed responses, storage rejection, deadline, abort and an ambiguous dispatched commit are not retried. A successful CAS must return the exact newly stored bytes before local notification is admitted.
- The unchanged source runtime owns ownerId/runId and timestamps. Begin generates run identity and the start timestamp once outside the conflict loop, retaining previous execution result. Interrupted repair changes a different owner's running record to the current owner and idle/error while preserving its previous runId and start timestamp. Finish requires the exact current owner/run; an older run's finish racing a replacement or repair loses CAS and recomputes to policy null. No new repair/finish policy or run replay exists.
- There is no second latest-value mirror, history list, status table, Redis/global/ambient DB, provider, scheduler, permission authority or persisted pub/sub payload. Logical local notifications use `cron-job-status:<name>`; `pubSub:last:cron-job-status:<name>` is untouched.

## Subscription and disposal contract

The backing attaches its actual local listener synchronously before its registration promise resolves. The unchanged runtime then performs its initial snapshot reads, filters by allowed job name and increasing revision, and coalesces one latest pending record per allowed name while serializing actual asynchronous sink delivery. The backing additionally filters out-of-order/duplicate committed notifications by per-subscription revision. Pending mutation/snapshot operations reject excess admissions immediately; there is no replay/outage queue. Subscription admission is bounded, and all key/revision maps are bounded by the host-supplied actual job-name set.

Backing unsubscription removes the listener and revision map before resolving. A defensive synchronous ingress-listener failure deactivates that subscription and is retained for rejected unsubscription/backing disposal; it does not turn an already committed successful run into an error status or retry its mutation. The existing runtime owns async sink failure reporting and waits for registration, every individual initial snapshot read, unsubscription and in-flight delivery. The composed resource awaits both runtime and backing cleanup. Backing disposal aborts new/in-flight operations, removes its local listeners and awaits actual started state promises; it neither closes an injected DB nor uses a timeout result to claim native settlement.

## Genuine joins still held

1. **Physical STATE acceptance:** an accepted same-main-DB state adapter must supply exact atomic CAS, explicit missing-key snapshots, returned post-write values, epoch fencing, captured lifetime, G3 dispatch fencing, native rollback/release and real settlement. This implementation imports no active DB peer source and provides no memory/KV substitute or fake success callback. Adapter source preparation is not both-engine contention/abort/overflow/restart proof. No physical resource was constructed here.
2. **Host registration/export:** the host must pass its actual immutable server-owned job-name set and register these exact record keys with the physical state resource. The structural registration is storage admission, not authorization. The coordinator must review/declare a package subpath for the new local index; no package export or host composition is changed here. This consumer needs no new third-party or workspace dependency: its only imports are sibling status-runtime source/types and its own files; built-in JSON, Promise, AbortController/AbortSignal and timers are used. Current package dependencies, ES2024/Node compiler configuration and installed Node `timers.d.ts`/`web-globals/abortcontroller.d.ts` signatures for timer unref, AbortSignal.any and throwIfAborted were inspected, not installed or changed. No third-party API syntax is newly used.
3. **Run abort versus host lifetime:** current status methods have no per-run signal. This consumer deliberately uses an explicitly supplied **host/resource** lifetime, not an inferred run signal. A canceled run may still need to record idle/error using that live host resource. The jobs host must first stop admissions/schedules, abort job effects and await the actual jobs stop/drain promise (including finish), then dispose status and finally the physical backing/DB. Binding status to the run's already-aborted signal or aborting its host lifetime before finalization is not an accepted substitute. This lane cannot claim per-run native SQL cancellation, provider completion, physical jobs drain or full-maintenance safety.
4. **Real private live delivery:** notifications are same-instance/same-process only. Another process or another separately constructed status backing does not deliver writes here; genuine composition must share one consumer for producer and subscribers. The real authorized Nitro/SSE sink must revalidate access, implement abort-aware backpressure and native delivery cancellation, await disconnect disposal, and actually settle before maintenance. The wrapper checks host lifetime before and after awaiting the supplied actual sink, but does not pretend those checks cancel or drain an uncooperative sink. No HTTP listener, transport, authorizer or fake sink was created.
5. **Durability ambiguity:** cancellation/response failure after actual commit dispatch can leave a durable record without local delivery. It is surfaced, never automatically retried or erased; a later initial snapshot can observe committed state. Crash after commit/before notification is likewise not an exactly-once delivery guarantee. Retained revisions must not reset while old records/consumers survive; full restore requires the separately owned whole-runtime drain/epoch reset.
