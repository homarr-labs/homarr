## 4. Correct file-credential seam and controlled synthetic lifecycle

### Current incompatibility

`packages/db/runtime.ts:508–515` privately mints `freshCredentialOwner` only from an actually new empty native `:memory:` connection. `adoptAuthCredentialsAsync:679–782` explicitly refuses file-backed first adoption, closes admission/drains, uses native K checks plus bounded adoption units, and retains ambiguous-COMMIT quarantine. MAIN's current initialization ends with real epoch initialization, but `createAuthenticatedReadResourcesAsync` constructs the issuer without adoption. Startup's `absolutePath`/external protected-file rules exclude `:memory:`.

Consequently the configured file-auth host cannot get a genuine ready credential domain from its current fresh-start path. Even a request with no session must read a ready singleton (`sql-authority/snapshots.ts:190`); this can block metadata/Auth entry before credentials are submitted. `ready:true` from persistence and `/api/health`'s `public-foundation` scope are not credential readiness.

The correct eventual MAIN callsite is **inside the already tracked `createAuthenticatedReadResourcesAsync` construction, before issuer/request/controller creation**, using its private retained raw runtime, original owner lifetime/startup signal and explicitly admitted finite operation bounds/batch limit. Do not use the guarded public read runtime, copy engine, `runAsync` domain-row inserts or an external adoption callback. Publish/register actual initialization tasks before dispatch and await their underlying settlement before any Auth/SQL cleanup. A rejected/ambiguous adoption cannot fall back to public-only authentication.

An already-adopted existing file is a different seam: after genuine K/owner readiness, the existing issuer getter and `admitOpaqueSessionAsync(null, boundedOperation)` can check the stored ready domain through the real reader without fabricating a Request/principal or allocating credentials. It is a possible bounded readiness consumer, not first-adoption provenance or proof of safe restart. Existing ready-domain startup must not call first adoption and reinsert/remint a singleton; absent/initializing/invalid domains remain unavailable pending a separately designed recovery path.
