### Epoch and retention lifecycle

After SQL/content readiness but before starting consumers, an explicit backing initialization transaction locks meta row 1, creates a UUID only if it still has the migration sentinel, and returns the installed epoch. Concurrent initialization must converge on the stored winner. Every constructed SQL resource captures that epoch and checks it in its actual transaction/snapshot. Initialization is not an import-time side effect or a reseed.

Ordinary restart keeps that epoch, last-good/non-expiring state, sequence heads and **absolute remaining expiry** unchanged. Expired rows are logically missing before any physical cleanup. A bounded expiry sweep may delete only already-expired rows under the same state mutex; it must not refresh TTLs, scan indefinitely, or delete persistent values. Sweeper scheduling belongs to the host/domain allocation, not an import-started timer or an added cron job in this wave. Old in-flight owners are not reconstructed from persisted token strings; a surviving ordinary-restart lease may block a replacement only until its existing expiry.

Full restore is different: incoming runtime state/history/status is never adopted as live authority. Reset/clear and rebind the runtime epoch only inside whole-runtime maintenance, as detailed in section 8.

## 4. Native atomicity, locks, clock and deadline

### Mutations: one transaction, not a read/modify/write promise chain

1. Validate finite operation deadline, registered keys/stream, mutation size and TTL arithmetic; check the operation and backing lifetime signals. Do not generate tokens or run providers here.
2. Obtain tracked DB admission and native transaction ownership. **SQLite:** guarded `database.transaction(syncCallback, { behavior: 'immediate' })`; the callback performs no awaits. **PostgreSQL:** guarded `database.transaction(asyncCallback, config)` on the main pool; installed Drizzle checks out one client and keeps all statements on it. Never issue BEGIN/COMMIT on a pool database's independent `execute` calls.
3. PostgreSQL takes epoch row 1 `FOR SHARE`, verifies the captured epoch, then state mutex row 2 `FOR UPDATE`. Every state mutation uses this order. This deliberately serializes all multi-key state mutations for one backend, including NX on absent keys, without acquiring unbounded key/advisory locks. Histories instead lock epoch row 1 `FOR SHARE`, then exactly their `(epoch, kind, name)` header `FOR UPDATE`; a missing header is inserted with `ON CONFLICT DO NOTHING` before locking it. Do not use one history-global mutex. Restore changes epoch row 1 `FOR UPDATE`; no operation upgrades its shared epoch lock to an exclusive one. SQLite's native writer lock supplies the corresponding serialization across connections.
4. **After every queued lock has been obtained**, check abort/deadline and observe the backing clock inside the transaction. Proposed clock expressions: SQLite integer Unix milliseconds from `julianday('now')`; PostgreSQL floor Unix milliseconds from `clock_timestamp()`, **not** transaction-start `now()`. Verify finite/supported numeric range before using it. Deadlines are caller-host Unix milliseconds: check `Date.now()` separately; do not compare a remote SQL clock directly to a host deadline without an accepted skew contract. Database wall time governs expiry; host wall time plus monotonic elapsed budget governs local admission timeout. Backward wall-clock behavior is not silently changed to a monotonic TTL policy.
5. Read the union of conditions/written keys/requested reads in bounded parameter chunks under the same native state mutex. Effective value is null for missing rows or `expires_at_ms <= observedNow`. Test **all** exact raw-string/null conditions before any write. A failed condition returns `applied: false` with the requested snapshot from this observation and makes **no** writes, including no expiry cleanup.
6. Precompute/validate the entire ordered write list. Sets store exact strings and expiry `observedNow + ttlMs` or null; non-positive set TTL is effective deletion. Deletes are exact-key deletes. Increment proposes Redis's canonical decimal input (`0` or `-?[1-9][0-9]*`), checked with bigint against `-9223372036854775808..9223372036854775807`; reject plus signs, whitespace, leading zeros, negative zero, fractions and overflow. Missing/expired starts at 1, existing expiry is replaced by the supplied positive TTL, and output is canonical decimal text. These lexical cases must be confirmed in the native gate, not inferred from the memory fixture's `Number(...)` implementation. Invalid counters or non-finite/out-of-supported-range TTL arithmetic roll back **all** writes; never use JS `Number` to increment. Repeated writes to the same key apply in their supplied order.
7. Obtain requested post-write values at the same observation point in the same transaction and build `{ applied: true, now, values }`; explicitly include every requested key with null when missing. Await every PostgreSQL statement; do not rely on the revocation drain to complete detached SQL. Recheck signal/deadline and SQL-clock expiry of positive owner/generation conditions before committing. If a previously satisfied fence expires during the transaction, roll back rather than publish a late owned write; do not return a success with a refreshed obsolete owner. Ordinary write TTL remains relative to the transaction observation, not a stale client enqueue timestamp.
8. Commit only through the reviewed resource-owned final gate; release admission only after native completion/rollback/client release. A response lost after a committed transaction is ambiguous. No blind mutation retry or payload replay; the existing acquire path may perform only its bounded exact-token cleanup.

Singleton composition is **not** the atomicity proof: async callers overlap, pg uses multiple clients, and other SQLite connections can compete. Native writer/row locks and all-or-nothing transactions are the proof. The process's publication queues are not distributed locks.

### Read-only snapshots

`readAsync` uses one SELECT containing one materialized clock observation, the captured-epoch check, requested key rows and expiry predicates. It returns one consistent `{ now, values }` even for no keys, without cleanup writes, per-key autocommit reads, or lease renewal. Reads use a native statement snapshot; mutations remain serialized. History latest reads likewise use one indexed `ORDER BY sequence DESC LIMIT bound` snapshot with epoch validation. PostgreSQL multi-statement jobs read batches use one checked-out `REPEATABLE READ, READ ONLY` transaction; SQLite uses a synchronous read transaction. Do not request PostgreSQL READ ONLY while also taking `FOR UPDATE` locks.

### Required stop-line: actual commit dispatch is not yet an accepted deadline port

Installed `node_modules/drizzle-orm/node-postgres/session.js:180–194` awaits the application callback and then dispatches COMMIT itself. Frozen `packages/db/runtime.ts:257–269` revokes/drains between that callback and the driver's commit. Neither interface accepts a commit-time abort/deadline guard. Bun's `session.js:31–38` delegates commit to the native synchronous transaction wrapper. Consequently a callback-final check alone is **not** evidence that cancellation in the subsequent PostgreSQL scheduling gap prevents COMMIT, nor that native I/O always finishes within 500 ms.

Oracle must approve a **small additive resource-owned bounded execution mechanism** before state/history writes are implemented: it must check both operation/backing lifetime and remaining budget immediately before actual driver COMMIT dispatch, keep checkout/BEGIN/locks/statements/rollback/release tracked, and expose only the concrete operations in section 5. A private guard on the checked-out pg client's query dispatch is a candidate; no raw client or session is supplied to domain adapters. No guessed pg `AbortSignal` query option, pool-wide BEGIN, automatic transaction retry or separate connection/pool is permitted. This requires an explicit future release of the minimal persistence owner seam; it is not permission to edit frozen r3 now or alter the restore worker's current port.

Queued checkout must be cancellable in result ownership: a client acquired after cancellation is released without BEGIN, and the pending acquisition remains tracked until settled. PostgreSQL lock/statement budgets must use reviewed transaction-local timeouts recomputed from the **remaining** budget, with checks after each wait; do not reset a full 500 ms on every statement or claim SQL timeouts cancel pool checkout. SQLite must not block the event loop in an unbounded native busy wait: propose explicitly reviewed, temporarily scoped `busy_timeout = 0` through guarded SQL before BEGIN/through COMMIT, restoring the previous value synchronously afterward, and surfacing contention as unavailability rather than late queued writes. This is not a new default PRAGMA. Validate these details with real contention before accepting them.

The enforceable promise is no commit dispatched after observed abort/deadline, and rollback for cancellation before that gate. A commit already dispatched can have an ambiguous outcome if cancellation/transport failure occurs during native commit. Hard real-time cancellation/durability during native commit is not available merely because a timer rejects the caller; Oracle must explicitly reconcile this unavoidable outcome with the accepted timeout contract. **Do not implement a weaker adapter and label it compliant.**

## 5. Concrete DB resources and dependency direction

Proposed entrypoints are server-only and constructed with the main runtime, captured epoch, backing lifetime and explicit admission limits. They return fully detached rows/strings, not retained builders.

Local structural primitive types mirror the accepted string/condition/write/snapshot union; the consuming state owner checks compatibility. No DB import of `@homarr/redis`, request-handler or API, and no generation/provider policy inside DB.
- `createRuntimeHistorySqlStore(...)`: `appendTrimAsync({ kind, name }, payload, maxEntries, operation) -> { sequence: string, payload: string }`; `readNewestAsync(stream, maxEntries, operation) -> readonly string[]`; `clearAsync(stream, operation) -> void`. Operations carry signal plus a concrete bounded SQL budget; the logs adapter derives that budget from an explicitly supplied host limit because `HistoryOperation` currently lacks `deadlineAt`. The store does not implement authorization or a new generic pub/sub service.
- `createRuntimeJobsSqlPort(...)`: implements the existing `dialect`, `queryAsync(statement)` and `executeTransactionAsync(statements)` shapes. Add a proposed **concrete batched** `querySnapshotAsync(statements) -> readonly rowSets[]` for a consistent analytics/icon read, rather than a callback that can escape a transaction. This additive jobs interface requires owner review before changing consumers.
- Job status uses state CAS plus a jobs/status-owned wrapper, not a DB-held policy callback. Read/decode the proposed record key, call the existing pure update function, check/increment its safe numeric revision, encode JSON, and CAS the exact previous serialized value/NX using state mutation. On conflict recompute from the new record within an explicitly bounded operation; null from the policy remains no mutation/return null. Domain code retains ownerId/runId repair/finish rules and timestamp generation. Invalid/overflowed revisions fail without mutation. SQL can supply the CAS; it cannot move run ownership or reauthorization into a generic storage callback.

**Pinned/library access:** `@homarr/db` already declares Drizzle, pg, SuperJSON and Bun types; Core declares Drizzle/pg/SuperJSON; redis declares DB/Core/SuperJSON; jobs declares DB/Core/state/status. No new library or install is proposed. Use existing Drizzle 0.45.2 SQL chunks/bound parameters. PostgreSQL guarded `.execute(SQL)` returns `.rows`/`.rowCount`; decode unknown values explicitly. Never read `$client`, `session`, `_` or statements to bind SQL.

The jobs port needs a reviewed positional-statement compiler: bind `?`/`$n` values into Drizzle SQL chunks, preserving the exact dialect, repeated numbered parameters and quoted literals/identifiers; validate counts and supported statement grammar. Reject unsupported/multiple statements and malformed placeholders. Do not use a blind regex replacement, interpolate values into `sql.raw`, or silently execute SQL with unbound placeholders. `sql.raw` is restricted to known trusted syntax fragments from the existing jobs builder, never client input. This remains a jobs-internal port, not an API procedure.

## 6. History retention, publication and private delivery

- Under the epoch/header lock, read/increment the head, insert the payload, and delete only entries beyond `ORDER BY sequence DESC LIMIT maxEntries` for that stream. Append and trim commit together. Newest reads do not create/trim rows; clear is namespace-local and leaves sequence head intact. SQL errors roll back header and entries. No timestamp sorting, list-in-JSON CAS, TTL, retention reset on restart, or background global-history truncation.
- Logs owner implements `LogHistoryBacking` over the concrete store and **one bounded per-stream append/commit/publication queue** shared by all in-process log producers. Advance local live ingress only after a successful commit, in that queue's append order; listeners register before history reads. This queue coordinates publication, not SQL atomicity. It must have explicit admission/byte budgets and reject/cancel overflow, not retain an outage replay queue. A SQL append failure publishes nothing. A crash after commit/before publication leaves a retained entry for future history but does not promise exactly-once live delivery.
- Only that logs adapter may publish log append results; do not expose an independent physical log writer that bypasses its queue. Native SQL supports competing connections' retention/sequence atomicity, but the accepted local listener contract does **not** deliver another process's writes. Cross-process fanout/outbox is not silently added. If multiple active publishing processes become a requirement, stop for a separate transport allocation rather than claiming the singleton removes connection races.
- Sample push/clear use the same physical store. Sample `publishAsync` is live-only raw SuperJSON; do not persist a latest snapshot or publish timestamped history by default. Preserve publish-before-push for the legacy explicit combination, not an invented atomic publish+history transaction.
- Log/samples/status subscription registration, queues, parse/authorization and cleanup stay with their domain owners. Keep existing 5,000-log and 100/15-sample **entry** bounds. Log/sample strings currently have no accepted total byte ceiling; require explicit host/#124-approved maximum payload bytes, queued bytes, pending SQL admissions and SQL operation duration before mounting. ## 7. Jobs read/write join and its allocation hold

Keep `cron_job_configuration`, `serverSetting`, icon/repository and existing session/account models unchanged. Configuration upsert remains the existing single `INSERT ... ON CONFLICT ... RETURNING`, preserving defaults and patch-only updates. Analytics settings continue exact serialized-value CAS with the existing maximum five attempts, preserving unrelated decoded fields through the domain's SuperJSON codec. Provider-session cleanup remains parameterized, authorized source SQL; this plan does not enable or choose any provider.

`executeTransactionAsync` executes the entire bounded icon statement batch in one native transaction and returns every native affected-row count in order, including the first deletion count expected by `applySyncAsync`. Failure in any statement rolls back everything. No provider/download/checksum/network work occurs under a DB lock. The physical port does not repair icon planning policy or run the scheduler.

The current `collectSnapshotAsync` and `readRepositoriesAsync` issue multiple `queryAsync` calls via `Promise.all`. Implementing each call correctly does **not** make that group a shared snapshot. After reallocation, jobs owner assembles their existing SQL into `querySnapshotAsync` batches, then performs its existing decoding/count/default policy outside the transaction. PostgreSQL uses one repeatable-read checked-out client, SQLite one synchronous snapshot; never simulate it with an ambient async-local raw DB provider.

Status JSON is persisted before local notification. Register status listeners before the existing status runtime's initial snapshot reads. Use live-only `cron-job-status:<name>` notification and revision filtering/coalescing already in the status runtime; do not add a second persisted latest record or a history list. `repairInterruptedAsync` after ordinary restart preserves the timestamp and previous run information while marking the old owner's running record idle/error; a late old-run finish must fail its CAS/policy check.

Jobs SQL/status methods currently do not carry the per-run signal. A constructor-bound host lifetime can fence maintenance, but cannot honestly promise per-run SQL cancellation. Do not infer a missing signal. Any additive per-run operation-budget/resource join is a later jobs-owner interface decision; status-finalization after run abort may intentionally need host rather than run lifetime. All started native SQL still has to settle before resource close.

**Original jobs owner is ICON-ONLY now.** Do not assign edits to `packages/cron-jobs/src/sql.ts`, its scheduler/status adapter or the active `jobs/runtime-bodies.ts` while that work is in progress. DB may prepare its separately allocated physical jobs port after gate approval; jobs/status consumption is sequential after ICON freezes and a new exclusive assignment is accepted.
