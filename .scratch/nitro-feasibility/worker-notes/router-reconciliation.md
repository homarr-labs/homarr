# Narrow shared-router reconciliation handoff

## Changed behavior

- Existing exports remain `RouterContext`, `createAppRouter`, and `AppRouter`. No shared interface or feature export changes are required.
- Both board callbacks now use internal `reconcileBoard(router, committedBoard?): Promise<void>`, rather than treating invalidation promise resolution as success. `onCommitted(board)` additionally requires a reconciled revision at least as new as the supplied commit, for the same board.
- Reconciliation captures the active board match/location and starts a new QueryClient-local epoch, then awaits **`router.invalidate({ sync: true })`**. It accepts only the same active board/location, no loading/pending matches, successful/non-not-found route matches, a settled/non-invalid board match with an increased `fetchCount`, and a schema-valid snapshot for the requested board **produced during this epoch**. Superseding reconciliation/navigation, failure/denial/not-found, aborted/unresolved work, missing data and old successful loader data reject with a fixed safe error.
- The board loader validates the existing `BoardSnapshot` boundary and board ID, records its invocation epoch only after successful completion, and refuses aborted or superseded results. Witnesses live in WeakMaps, outside Router context/dehydrated snapshots; no private record/session data is stored there. An invalidation that merely reuses a prior success cannot satisfy the witness.
- Loader and callback failures expose only `Board access could not be confirmed`; raw transport/schema errors, prior board payloads and private labels are never rendered by the new recovery view. Authorization itself remains in the producer/server policy, not duplicated here.
- Board route has explicit **error and not-found components** using the same safe `BoardRecovery` surface. It retains the registered `boardSlots.Session`, current client/QueryClient/router, a public-board link and a retry button. It renders no previous label/layout/widget/editor/capabilities. The public link is never disabled by the mask or retry state.
- Recovery `onSessionChanged()` uses the same guarded reconciliation and resets a React error boundary only after success, if `reset` is actually callable. This check accommodates the released Router's SSR error path, which passes `reset: undefined` despite the nominal prop signature.
- Transition arbitration/completion is exclusively owned by the access module's `runSessionTransition(queryClient: QueryClient, operation: () => Promise<void>): Promise<void>`, imported from `src/features/session/session-transition.ts`. Recovery Retry wraps its entire cancel/clear/reconcile/reset flow in this runner, just as SessionControls wraps its outer mutation flow. The runner synchronously masks before work, permits only one active operation per QueryClient, rejects overlaps without queuing or executing their work, unmasks only on success, and keeps failure masked while releasing the slot for another retry. Recovery has no separate begin/complete calls. Public navigation and SessionControls Refresh access/select/logout remain reachable.
- Router callbacks remain guarded reconciliation only; they are deliberately **not** wrapped in the runner, because SessionControls already owns the outer mutation operation and nested runner acquisition would reject. Error/not-found component mounting never clears a transition. Successful Recovery Retry may restore content only through the common access-owned runner's successful settlement.
- Successful recovery from an error route is possible because the released invalidation implementation resets error/not-found matches to pending and reruns their loaders. Normal browser public navigation may retain the existing session mask until the user confirms access through the visible session controls; this intentionally does not clear a mask solely because navigation succeeded.
