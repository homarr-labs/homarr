# English translation catalog audit

Scope: `packages/translation/src/lang/en.json` only. Other locale files are intentionally excluded because Crowdin derives them from English.

Snapshot: 4,462 leaf messages across 24 top-level namespaces (`next-intl` 4.13.1).

## Implementation outcome

Phases 1–5 were implemented together on `feat/consolidate-translations`; phase 6 is intentionally excluded. The area reports below preserve the pre-implementation evidence and recommendations that drove the changes.

- Against the current `release/v2` target, reduced the English catalog from 4,699 to 4,080 leaf messages and exact duplicate groups from 433 to 291.
- Consolidated generic actions, named CRUD labels, fields, entity nouns, and notification titles under `common` while retaining feature-specific prose and accessibility context.
- Moved Assistant copy from `common.assistant` to the top-level `assistant` namespace and replaced its generic controls with shared action keys.
- Standardized the translation facade on `useI18n` and `getI18n`, then reduced unscoped translator calls from 225 to 65.
- Moved verified provider, integration-brand, product-widget, and Kubernetes labels to typed definitions; audited HTTP methods and product names no longer occur in the English catalog.
- Left only two intentional exact overlaps with common actions: Assistant's affirmative “Confirm” choice and feature status uses of “Loading”.
- Changed only `en.json`; Crowdin remains responsible for all other locale catalogs.

A second semantic-consolidation pass removed 140 additional leaves after phases 1–5 in the original audit snapshot. It centralized standalone
management entities and concise actions, shared widget option and component vocabulary, Kubernetes table fields,
and invariant CPU/GPU/RAM/OS/ID/URL labels. Ambiguous lifecycle statuses and grammatically contextual entity uses
remain scoped. New Assistant and utility-widget copy from the updated target was preserved during rebase. Phase 6 remains excluded.

## Method and decision rules

This audit distinguishes four cases:

1. **Do not translate:** protocol tokens, HTTP methods, product/brand names, acronyms, identifiers, units, and other invariant technical values should normally come from typed application data instead of the message catalog.
2. **Reuse a shared message:** context-independent UI actions and labels such as “Cancel”, “Save”, “Name”, or “Try again” should use an existing `common` key when grammar and meaning are identical.
3. **Parameterize a reusable message:** repeated constructions such as “Delete X” can use an ICU argument such as `Delete {name}` when translators can reorder the phrase safely and the inserted name is itself already localized or invariant.
4. **Keep feature-specific:** full sentences, accessibility text, and labels whose meaning changes with context should remain close to the feature. Exact English matches are not automatically interchangeable across languages.

Current `next-intl` guidance supports nested JSON namespaces and recommends scoping `useTranslations` to the lowest useful namespace, while cautioning against excessive namespaces because they make refactoring harder. ICU arguments, `select`, and `plural` are the intended tools for grammatical variation. The package also provides message extraction, but adopting extraction is a workflow choice rather than a prerequisite for consolidation.

### Near-duplicates and feature boundaries

- Keep app/integration confirmation titles and message bodies feature-specific. The shared notification titles describe the operation; the body identifies the entity and may need different grammar.
- Keep user.field.homeBoard and group.field.homeBoard separate: one is a user's preference and one is a group policy/default.
- Keep user account Username/Password labels separate from integration secret Username/Password labels until the same form component owns both.
- Keep media, item, section, board, and layout option labels scoped when the same English noun represents different saved data or different editor ownership.
- Keep item.moveResize.keyboard.instructions/started and board.landmark labels: these are screen-reader and keyboard interaction contracts, not generic prose.
- Keep item.edit.integration.editLabel and integration.page.edit.title: both describe editing an integration, but one is an embedded item action and one is a page title.
- Keep full init.studio and onboardingTour prose scoped. Only short controls such as Continue, Next, Cancel, and Try again are candidates for common action reuse.
- Keep common.assistant labels such as Input, Output, Thinking, Used, Other, Review, and Model scoped. The same English word can be a table heading, generation status, choice, or button.

### Invariant technical values

The catalog should not be the source of protocol or enum tokens. Keep these values in typed application data and localize only the surrounding explanation:

- MCP instructions already correctly render HTTP methods as code constants (`GET`/`POST`) in `apps/nextjs/src/app/[locale]/manage/tools/api/components/mcp-instructions.tsx`; do not add locale keys for them. The same rule applies to HTTP, JSON, ZIP, SQLite, API, MCP, OAuth, ID, CPU, RAM, OS, MB, `%`, and similar acronyms/units.
- Product and provider names must remain invariant metadata: Homarr, Docker, Kubernetes, OpenAI, Anthropic/Claude, Google/Gemini, OpenRouter, xAI, Groq, Mistral, DeepSeek, Together AI, Ollama, LM Studio, Synology, and other brand strings in `management.page.settings.section.assistant.provider.options.*` should not be translated. Descriptions around them may be localized.
- Kubernetes API kinds and enum tokens (`Node`, `Namespace`, `Ingress`, `Service`, `Pod`, `ConfigMap`, `Secret`, `Volume`; status values such as `Ready`, `NotReady`, `Active`, `Terminating`) should remain typed/raw when they are identifiers. The four unused `kubernetes.*.field.state.option.*` entries are safe removals; dynamic Docker `field.state.option.*`, Kubernetes context status, and `log.level.option.*` entries are used and need a deliberate display-policy decision rather than static deletion.
- Do not merge `kubernetes.cluster.resources.services`/`kubernetes.services.label` into `common.services` merely because the English value is `Services`; these are the typed Kubernetes resource name. The same caution applies to Docker `health.layer.docker` versus the management navigation/brand label.

### Feature-specific exceptions

## Cross-catalog findings

### Baseline

| Measure                                                        |    Result |
| -------------------------------------------------------------- | --------: |
| Leaf messages                                                  |     4,462 |
| Unique English values                                          |     3,622 |
| Exact duplicate-value groups                                   |       418 |
| Leaves participating in an exact duplicate group               |     1,258 |
| Duplicate groups crossing top-level namespaces                 |       256 |
| Non-`common` leaves exactly matching some value under `common` |       187 |
| Static no-reference candidates from the three disjoint audits  | Up to 271 |

The duplicate ceiling is 840 leaves (`1,258 - 418`), but it is not a sensible deletion target. English collapses distinctions that other languages need, and identical text can serve different roles: button, heading, field label, status, enum, or accessibility announcement. The prioritized area tables identify the subset that has compatible meaning and verified call sites.

### Strongest common patterns

1. **Bare actions:** 44 leaves outside `common.action` exactly duplicate an existing action value. The audited P0 tables exclude status/choice false positives and are the first mechanical migration.
2. **CRUD labels:** `Edit {name}` and `Delete {name}` are repeated in app, integration, and search-engine lists. These are safe shared ICU messages when `{name}` is a proper/runtime name. Entity nouns such as “board” or “user” should not be passed as raw English arguments.
3. **Notification titles:** create/update/delete title pairs already exist under `common.notification`; app, integration, board, and search-engine flows duplicate them while their more informative message bodies correctly remain feature-specific.
4. **Form labels:** `Name` appears 30 times across the full catalog. `Description`, `URL`, username, password, and common color/layout labels also repeat. Consolidate only identical form/table roles; do not assume that a standalone noun has the same grammatical form everywhere.
5. **Entity labels:** Boards, Apps, Integrations, Users, and Groups are repeatedly translated in navigation, statistics, permissions, backup previews, and search. A `common.entity` family can cover standalone navigation/list labels, but count messages and permission/accessibility headings should remain scoped unless their role is identical.
6. **Feature families:** Beszel metrics/options, table configuration, integration-disconnected errors, Custom Widget credentials, Docker refresh errors, backup confirmation prompts, and Kubernetes resource labels have stronger shared ownership than a global `common` key. Consolidate them under their nearest real domain.
7. **Stale catalogs:** the three audits found up to 271 static no-reference candidates, concentrated in legacy Custom Widget fields/options, legacy section variants, old backup/MCP UI, old user-setting notifications, and unused Kubernetes state labels. Dynamic registries mean these are candidates pending an owner/build check, not unconditional deletions.

### Invariants are data, not messages

HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), product and provider names (Sonarr, Radarr, Docker, Kubernetes, OpenAI, and similar), protocol/acronym tokens, filenames, enum identifiers, URLs, JSONPath examples, and units should come from typed definitions or runtime values. A surrounding sentence remains translatable and can interpolate the invariant value. Standalone product-only `*.name` messages should be removed where the typed widget/integration/provider definition already owns the same display name.

Do not create a translatable `technical` namespace as a replacement; that would preserve the original problem under a new path. The source of truth should be the relevant typed catalog or enum.

### `next-intl` usage assessment

Homarr already uses several parts of `next-intl` well:

- `en.json` augments `next-intl`'s `AppConfig`, providing type-safe message keys.
- ICU plural messages are used throughout the catalog.
- 489 static occurrences use a scoped client/server helper, and dynamic key families are commonly backed by typed registries.

The current abstraction also has avoidable friction:

- `useI18n` and `useScopedI18n` are aliases of the same `useTranslations` function; `getI18n` and `getScopedI18n` have the same issue. The names imply a constraint that the type/API does not enforce.
- There are 225 static unscoped hook/server-call occurrences. Current `next-intl` guidance recommends providing the lowest useful namespace and resolving descendants with dot notation. Components that need feature and shared copy can use two scoped translators instead of one catalog-wide translator.
- `common.assistant` contains 263 of the 381 `common` leaves. Assistant-owned copy should be a top-level feature namespace; only truly reusable actions, fields, entities, notifications, and display labels should remain in `common`.
- The root `NextIntlClientProvider` receives the request messages without a narrowed `messages` prop, so the full catalog is available to the client provider. Namespace-based message slicing may reduce serialized client messages, but it is a separate measured performance change—not a prerequisite for key consolidation.

The current library also offers [message extraction](https://github.com/amannn/next-intl/blob/main/docs/src/pages/docs/usage/extraction.mdx) and `useExtracted`. It should not be adopted as the consolidation mechanism now. Extraction generates/manages catalogs but does not decide that two semantically identical messages should share a key, and Homarr's dynamic families (`widget.${kind}`, permission registries, task names, Kubernetes resources, navigation paths, and similar) need an explicit manifest or registry-aware extractor first. Keep the existing typed-key workflow, add a Homarr-aware audit, and evaluate `unstable_extractMessages` later on a throwaway branch. The relevant current guidance is [translations and namespaces](https://github.com/amannn/next-intl/blob/main/docs/src/pages/docs/usage/translations.mdx) and [extraction](https://github.com/amannn/next-intl/blob/main/docs/src/pages/docs/usage/extraction.mdx).

## Consolidation plan

### Phase 0 — agree on the catalog contract

Document five ownership rules before renaming keys:

- `common.action`: context-free controls, including `editNamed`/`deleteNamed` only for runtime proper names.
- `common.field`: field labels proven to have the same role.
- `common.entity`: standalone product entities, not count sentences or permission prose.
- Feature namespaces: sentences, confirmations, accessibility copy, and domain state machines.
- Typed source data: brands, methods, protocol tokens, identifiers, enum values, filenames, examples, and units.

Treat exact duplication as a review signal. Require semantic role compatibility before sharing a message.

### Phase 1 — reuse existing canonical keys

Migrate the audited P0 call sites in small domain batches:

1. bare `common.action.*` matches;
2. existing `common.notification.create/update/delete.*` titles;
3. `common.noResults`, `common.total`, `common.services`, time units, color-scheme options, `common.unsavedChanges`, and similarly verified exact-role labels.

Change call sites first, then remove the old English leaves. Keep feature-specific notification bodies and accessibility messages. This phase intentionally precedes stale-key removal because several currently unreferenced `common` leaves—such as `common.action.import`, `common.total`, and the hour/minute labels—are the correct canonical target for active duplicates elsewhere.

### Phase 2 — remove stale source messages

Review the 271 static no-reference candidates with the owning area, starting with entire legacy subtrees because they have the lowest migration risk:

1. legacy Custom Widget presentation/field/placeholder families;
2. legacy section category/dynamic families;
3. old backup preview/import and unused MCP UI;
4. old user-setting notification leaves;
5. the four unused Kubernetes state-option labels.

Make the checker registry-aware before deletion. Explicitly preserve dynamic families listed in each area report and any key promoted as a canonical target in Phase 1. Remove only `en.json` source keys in the repo; let the established Crowdin workflow reconcile derived locale catalogs.

### Phase 3 — add the missing shared seams

Add only the shared keys for which multiple verified consumers already exist:

- `common.action.editNamed` = `Edit {name}` and `common.action.deleteNamed` = `Delete {name}`;
- `common.action.copy` and `common.action.refresh` for bare buttons;
- carefully reviewed `common.field.name`, `common.field.url`, and standalone `common.entity.*` labels;
- `widget.beszel.*`, `widget.common.tableOptions.*`, `widget.common.integrationDisconnected`, and other widget-domain families listed in Area 2;
- one Docker refresh-error pair and one backup confirmation prompt;
- a typed Kubernetes resource-label source instead of two translation branches.

For new keys, add them first and allow Crowdin to translate them before removing old translated keys. Reuse an already-translated canonical key whenever possible to minimize translator churn.

### Phase 4 — move invariant values to typed data

Migrate by source registry rather than by global string replacement:

1. integration, widget, search-engine, and provider brand names;
2. HTTP methods and request kinds;
3. Kubernetes resource/status identifiers and Docker/runtime enums;
4. acronyms, units, filenames, URLs, JSONPath, and example values.

Keep localized surrounding prose and interpolate invariant runtime values. Where a phrase contains a localized entity noun, keep a complete localized message or use ICU `select`/`plural`; never pass the English noun as `{entity}`.

### Phase 5 — simplify the translation API and namespaces

1. Standardize on one client and one server translator API called with the lowest useful namespace; retire the misleading scoped/unscoped alias pairs after call-site migration.
2. Move `common.assistant` to a top-level `assistant` namespace, promoting only genuinely shared controls to `common`.
3. Reduce the 225 unscoped call occurrences gradually. A component needing both domains should request a feature translator and a `common` translator explicitly.
4. After consolidation, measure the client message payload and evaluate passing route-specific message slices to `NextIntlClientProvider`.
5. Evaluate `next-intl` extraction only after dynamic registries have an explicit manifest; do not combine extraction adoption with the catalog cleanup.

### Deferred phase 6 — excluded from this implementation

No catalog-audit script or CI gate is included in this PR. If this phase is approved later, it can:

- parse `en.json` and report exact/normalized duplicate groups;
- fail on a feature leaf that exactly duplicates an allowlisted `common.action` or notification key;
- flag standalone invariant tokens/product names when a typed source exists;
- understand declared dynamic-key families before reporting an orphan;
- check ICU argument compatibility when a shared key replaces several keys;
- print catalog size, unique-value count, and scoped/unscoped call counts for trend review.

This implementation is delivered in one PR, with the domain reports retained below so the Crowdin changes and UI review remain understandable. Validation is limited to the affected package typechecks and static checks; no broad application test suite is required for this catalog migration.

### Completion criteria

- Every P0 candidate is either removed, consolidated, or recorded as an intentional exception.
- No invariant HTTP method or product-only display name is sourced from `en.json` when typed metadata already exists.
- `common` contains shared vocabulary rather than Assistant feature copy.
- New UI code cannot introduce an exact duplicate of a canonical common action unnoticed.
- Dynamic keys remain type-backed and are not falsely deleted by extraction/audit tooling.
- Crowdin source synchronization completes without manually editing non-English catalogs.
