# Homarr performance audit before/after report

62 canonical findings: 57 implemented, 1 retained, 4 reverted, 0 unreported. 101 scenario cases passed their supplied checks; 88 cases include paired timings.

Decision ledger: 57 implemented; 1 unchanged (F1); 4 rejected prototypes (WMB1-1, A3, WIDGETS_B_006, WIDGETS_B_008), with original implementations retained. The rejected candidates comprise 2 timer and 2 widget prototypes.


The first combined benchmark run aborted with Node heap out of memory after 67 cases had been completely saved. 52 unchanged complete cases were recovered with the original raw artifact's SHA256 and status preserved; 49 replacement cases were run serially in 5 fresh lane processes. This report accepts only fully saved case evidence with semantic checks and, for every timed case, all 18 raw samples / nine before-after pairs. The original aborted run remains a raw artifact and is not labeled passed. Invocation, warmup, iteration and runtime metadata remain per input process; cross-lane totals are not one same-process timing run.


The table covers every finding once. Values are median wall (W) and process CPU (C) microseconds per case operation, before→after. Small/large pairs retain their labels; findings with more variants show timing ranges and the number with any observed increase. [All exact scenario pairs and increases](VARIANTS.md) remain visible. A range's endpoints may come from different scenarios; it is not a paired speedup. Every operation uses the fixture scope described by its case, which may contain multiple renders, records or mocked requests.

These are local fixture measurements, not production response latency, user-perceived speed, peak heap, or deployment acceptance. Structural/accessibility cases with timing:false are marked “Not timed”. React Profiler durations, when supplied, come from one cold verification probe and are excluded from deterministic work counts and warmed median timing claims. Logical allocated/copied slots count array work calculated from fixture cardinality and the selected source operations; they are not runtime allocation traces, bytes or peak memory. Batch heap/RSS snapshots are process noise and remain in the raw appendix; neither negative deltas nor lower snapshots prove memory savings. Stream cases separately sample process RSS/external/ArrayBuffer growth during one 32/64 MiB lazy-stream probe. Those sampled maxima are not the nine-trial timing medians or exact production peaks; GC and read order affect them.
The notification timer candidate was removed: at 10 rows label calculations increased 20→26, and at 100 rows 200→206, while timer counts fell 10/100→1/1. Existing row timers were retained. These rejected-candidate counters come from a separate replay, not the final paired current-code timings. The candidate reason, counter values and source hashes are preserved in the bundled inputs and report data.

The Wazuh clock candidate was also removed: label calculations at 1/10/100 rows increased 2/20/200→8/53/275; at 100 rows timers fell 100→1 and tick renders 200→25. The rejected fixture's median wall was 128.845675→134.883841 ms (+4.69%), and CPU 193.028→205.0525 ms (+6.23%). The prototype was faster in 6 of 9 recorded paired comparisons, reinforcing the timing variability. These benefits did not justify the added shared-store complexity under the deletion priority. This does not establish a dashboard regression. Original per-row clocks were retained; their final identical-source before/after timing differences are noise. [The inert candidate source/fixture archive and measured record](candidates/wazuh-clock/measured-A3.json) preserve this separate prototype evidence; fixture provenance uses the raw caseSha256 field, separately from production source spans.

## Rejected widget prototypes

The Coolify memo and cluster rendering candidates were removed after these separate candidate measurements. Every selected scenario is shown, including small/large improvements and regressions. Their final-source rows below use the restored original implementation; identical-source timing differences are noise. The candidate fixture, production source hashes, raw pairs and rejection reasons remain archived. Timings cover local React fixture operations and do not establish dashboard performance. Paired wins compare each same-trial before/after pair; changes compare separate side medians, so these statistics can differ.

- **WIDGETS_B_006:** Reverted both added memos under the measured-value and code-deletion gate. Builds fall from 9 to 1 on first 9-render sequence and 9 to 0 when warmed, but typical single CPU median rises 1.5%; card 20 wall median rises 11.6% and CPU 1.6%; card 1 CPU rises 10.1%; card 1000 CPU rises 0.6%. Single 1/single 1000 wall and CPU medians improve, and card 1000 wall improves, but paired results are variable and common card paths regress. Deterministic work/allocation savings do not establish a consistent CPU benefit sufficient for extra hooks and retained Maps. [raw paired records](candidates/widget-render/selected-timed-cases.json); [source hash manifest](candidates/widget-render/manifest.json); [inert case fixture](candidates/widget-render/widget_render.mts.source.txt)
- **WIDGETS_B_008:** Reverted the added wider accumulator loop. Node visits fall sixfold, but 100-node variant wall median rises 30.7%, CPU 23.5%, with only 2 of 9 paired wins for both. Typical 3-node wall/CPU medians improve at submicrosecond scale; tiny wall improves but independent CPU median rises 44.6% despite 7 of 9 paired CPU wins. Mixed numeric outcomes do not justify replacing clear existing reductions. [raw paired records](candidates/widget-render/selected-timed-cases.json); [source hash manifest](candidates/widget-render/manifest.json); [inert case fixture](candidates/widget-render/widget_render.mts.source.txt)

## What changed

The table names the original findings. [Grouped report data](report-data.json) records each final implementation, validation and caveat. [Dispatch](DISPATCH.md) records the 13 lanes and all 62 findings.

API-001 replaces repeated opposite-collection membership searches with shared ID indexes: the membership phase changes from O(n×m) to expected O(n+m), while retaining ordered added/updated/removed outputs. API-003 builds Docker reconciliation Maps in linear configured-record work, then performs candidate lookups and required bucket checks; this does not imply the entire reconciliation is linear for every duplicate/candidate distribution. RSS restrictions and each bookmark query build a membership Set: expected O(n+m) membership work with O(m) auxiliary entries for that scope. Database reads, parsing, serialization, rendering and per-query repetition remain outside those claims.

## Reproduction and provenance

Baseline commit: `bab37f76c607e70d871fb7bdde259fa527051b58`. Before source comes from the frozen archive `/tmp/homarr-performance-before-bab37f7`; the runner checks each before-file SHA256 against `git show baselineCommit:path`. Each case records source-file hashes, selected declaration/span hashes, the case-file hash and harness hashes in the raw JSON. After-source evidence records the measured working tree, including uncommitted changes; commit metadata alone does not identify all measured code.

Runtime(s): v24.18.0. Use pinned Node 24.18.0 and Bun 1.4.2 for dependencies. The source-extraction compiler is an isolated TypeScript 5.9.3 install; it does not replace the application's compiler. Dependencies are shared between before/after; baseline workspace imports point to baseline packages. Timed runs execute serial cases with alternating before/after trial order, warmups, explicit GC when available, and retained raw samples. Process CPU includes operation-loop overhead; short-case changes can be timing variance. Mocked I/O and fixture-clock outcomes do not establish real upstream concurrency, latency or scaling.

Follow the [README setup](README.md#reproduce) first to install pinned dependencies, create the archive/compiler, and link baseline workspace dependencies. After that setup:

```sh
mkdir -p /tmp/homarr-reproduced-audit
for audit_lane in api_core api_io assistant board_forms custom_widgets management notebook_timers routes_assets services widget_aggregates widget_lookups widget_render accessibility; do
  BENCH_COMPILER_ROOT=/tmp/homarr-performance-compiler mise exec -- node --expose-gc scripts/benchmarks/performance-audit/run.mts --before /tmp/homarr-performance-before-bab37f7 --after "$PWD" --lane "$audit_lane" --out "/tmp/homarr-reproduced-audit/$audit_lane.json"
done
mise exec -- node scripts/benchmarks/performance-audit/report.mts --results /tmp/homarr-reproduced-audit
```

The report generator reads committed [inputs.json](inputs.json) by default and needs no temporary worker files. Maintainers can refresh that compact bundle with `--workdir /tmp/homarr-performance-work`. It also accepts repeated `--results FILE` or a results directory. Recovered evidence uses status `recovered_completed_cases` and must identify the unmodified aborted artifact, its hash/status/reason, original completed count, and selected complete count; all selected case records must exactly match the saved original. Original aborted artifacts referenced by this metadata are excluded from final case selection and linked as raw evidence. Other input runs must be passed. For overlapping completed results, the newest timed result per variant supplies the final table; initial prototype data remains in the separate rejection ledger and [candidate measurements](REJECTED_CANDIDATES.md). Rejected widget records are checked against their archived raw JSON and SHA256; final rejected-prototype rows must use baseline-identical source hashes. Re-running current code reproduces retained implementations, not removed prototypes. `--allow-incomplete` is for smoke reports and marks missing coverage explicitly. Per-case iteration counts and fixture scales are recorded in the JSON. Fixture results establish only the tested data scales and behavior; extrapolation to production requires separate evidence.
