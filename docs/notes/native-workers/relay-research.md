# Independent headless workers and a shared blind relay

Research date: 21 October 2026. Source baseline: `feat/headless-hono-backend`, commit `32eccd0f84bb401b1d49f94b7c37a1f905e7eff4`.

This is architecture research, not a capacity result. Repository facts below were inspected at that baseline; the parallel Go implementation and benchmark results are outside this note. No load tests, deployment mutations, live OAuth, or production measurements were performed. Recommendations are explicitly proposals or inferences. Current official documentation was consulted directly; Context7 is handled separately by the lead session after the previously reported quota failure.

## Recommendation

Keep one primary worker per frontend workspace. Many independent installations can use the same relay without sharing their application database, integration credentials, authorization, or dashboard state. The relay should own connection routing, bounded forwarding and admission; workers should own application permissions and data. Start with one observable, bounded relay instance. Add worker-ID routing before adding replicas. Choose Go on measured operational and resource results, not on a presumed sockets-per-language number.

The immediate work with the highest likely benefit is proxy-aware admission, consistent negotiated limits, reconnect backoff and liveness deadlines, transport diagnostics, and a short worker launch/pair/recovery path. Large-file encoding efficiency and distributed routing are later decisions that need workload evidence.

## Connection and bandwidth economics

**Derived topology:** with W connected workers and C connected browsers/service clients, this relay holds approximately W + C upgraded sockets, plus transient handshakes and health HTTP traffic. A worker's browser channels do not require one additional worker TCP connection each. A reconnect destroys that worker's live channels, so the single worker connection is also a shared failure and congestion boundary. This follows from the relay and worker maps above; it is not a throughput measurement.

Application channel multiplexing is different from HTTP/2 multiplexing. The existing native gateway explicitly uses HTTP/1.1 upstreams and WebSocket upgrades. RFC 8441 defines HTTP/2 WebSockets using an extended CONNECT stream; that capability must exist across the actual browser/proxy/server path before budgeting fewer TCP connections. [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441#section-4), [native gateway](../../../deployments/native/gateway.conf).

**Derived encoding overhead:** an HTTP body chunk is base64url-encoded into a JSON message; the encrypted bytes are base64url-encoded again. For large raw chunks, those two encodings approach `(4/3) × (4/3) = 16/9`, or roughly 1.78 times the raw body bytes, before JSON, GCM tags, routing envelopes, credits, WebSocket framing, TLS and TCP. This is arithmetic from the source, not measured wire traffic. Small control messages have a different overhead ratio. [chunk encoding](../../../packages/remote-protocol/src/connection.ts), [ciphertext envelope](../../../packages/remote-protocol/src/protocol.ts), [base64 definition](https://www.rfc-editor.org/rfc/rfc4648#section-4).

WebSocket headers are comparatively small for large chunks: RFC 6455 specifies variable-length headers and masking of client-to-server frames. More significant here are repeated serialization/copies, two base64 layers, encrypted credit exchanges and the shared worker link. All application channels on that link share its ordered TCP transport; multiplexing cannot make a slow or lossy worker uplink disappear. These are engineering inferences from the current topology and [RFC 6455 framing](https://www.rfc-editor.org/rfc/rfc6455#section-5.2).

**Proposal:** instrument raw useful payload bytes, relay forwarded bytes and host NIC bytes separately. Report ingress and egress by direction. Each relayed payload enters the relay and leaves it, but provider billing depends on the deployment boundary: do not automatically call it “double billed egress.” Include subscriptions, media and uploads, not only request-response metadata. A later protocol version could carry binary ciphertext and binary HTTP chunks to remove base64 expansion; keep channel identity, strict frame-size validation and authenticated ordering. This needs protocol compatibility work, not just a Go rewrite.

## Bounds that need attention before broad hosting

### Admission and isolation

**Current-source issue:** relay IP admission uses `requestIP()` directly. In native deployment, a gateway proxies clients to the relay; the relay therefore sees the gateway peer address rather than independently verified original client addresses. The configured per-IP limit can pool unrelated users behind one proxy. NAT can pool legitimate users even without that proxy. [relay admission](../../../apps/relay/src/relay.ts), line 340; [gateway](../../../deployments/native/gateway.conf).

**Proposal:** explicitly configure trusted proxy peers and validate the forwarding chain, or enforce source-IP admission at the trusted edge and use worker/account budgets within the relay. Never accept arbitrary internet-supplied forwarding headers as identity. Keep a global connection ceiling, pending-handshake ceiling, source upgrade ceiling and post-auth worker ceiling. Reserve enough admission headroom for worker reconnection and operations rather than letting unauthenticated sockets consume the entire pool.

**Current-source mismatch:** relay admits up to 64 channels per worker, while worker rejects channel opens after 32 peers by closing its shared relay connection. That can disconnect existing clients when the next channel arrives. Also, worker-to-relay rate accounting aggregates all channels into one socket, while browser-to-relay accounting is per browser socket. Do not assume “256 messages per second” is available independently to every browser in both directions. [worker transport](../../../apps/worker/src/transport.ts), `channel.open`/catch; [relay](../../../apps/relay/src/relay.ts), `connect`/`onMessage`.

**Proposal:** negotiate or centrally configure worker channel/message/byte budgets; reject only the excess channel where possible. Apply tenant fairness using the verified worker identity, not merely source IP or raw channel ID. A blind relay cannot validate native user roles or inspect encrypted request costs; native authorization, expensive tool budgets and response filtering must stay at the worker. Keep hosted MCP approval separate: the gateway is an authorized endpoint that handles results, while the routing relay remains blind. [worker service authorization](../../../apps/worker/src/service.ts), [hosted MCP relay client](../../../packages/remote-platform/src/mcp/relay.ts).

### Queue and frame budgets

Bun documents that server `send()` returns -1 after enqueueing under backpressure and 0 when a message is dropped; its buffer check can permit the configured limit plus one message. The current relay accepts -1 and closes slow receivers when its byte budget is exceeded. This is bounded overload handling, not an end-to-end drain scheduler. [Bun WebSocket backpressure](https://bun.sh/docs/runtime/http/websockets#backpressure), [relay send](../../../apps/relay/src/relay.ts), line 113.

**Proposal:** keep per-socket, per-worker and process-wide queued-byte budgets. A per-socket maximum multiplied by every admitted socket can exceed the host memory allowance even when each socket is individually compliant. Include kernel socket memory, TLS buffers, queues, parser objects and transient encode/decode allocations in RSS/cgroup measurements. Reserve control-frame capacity so cancel/close/liveness messages are not trapped behind unlimited data. Fair scheduling between channels can improve latency; it cannot remove TCP ordering or an exhausted uplink.

The browser WebSocket standard exposes `bufferedAmount` for outgoing buffering but no application-level receive pause/credit method. Preserve Homarr's existing encrypted streaming credits and queue caps rather than relying on the browser to bound receive memory. [WebSocket interface and sending algorithm](https://websockets.spec.whatwg.org/#the-websocket-interface), [connection credit handlers](../../../packages/remote-protocol/src/connection.ts).

**Current-source boundary:** both relay outer messages and encrypted frames are capped at 1 MiB, but channel wrapping adds bytes. A maximum-sized client payload is not automatically a valid maximum-sized worker envelope. Normal 48 KiB chunks are comfortably smaller; adversarial/boundary inputs still need explicit policy. Current `connected` frame advertises a relay payload maximum but does not describe all worker/encrypted/chunk budgets. [relay](../../../apps/relay/src/relay.ts), `connect` and forwarding; [protocol limits](../../../packages/remote-protocol/src/protocol.ts).

**Proposal:** document and negotiate limits for the serialized outer message, encrypted envelope, plaintext message and raw body chunk separately. Validate UTF-8 byte lengths, not only JavaScript string length. Preserve replay rejection, separate directional keys and fresh handshake on reconnect; do not resume old sequence state using a new relay generation.

### Liveness and reconnection

The 20-second worker ping currently keeps traffic flowing, but sending ping does not by itself establish that the other end remains responsive. Add a bounded pong deadline and connect/registration deadline, then distinguish connection failure, relay admission, unavailable worker and worker authorization errors. The browser cannot directly send protocol Ping using the standard API; relay-side WebSocket Ping or an encrypted application heartbeat is needed for browser-facing liveness. [WebSocket Ping/Pong standard](https://websockets.spec.whatwg.org/#ping-and-pong-frames), [worker transport](../../../apps/worker/src/transport.ts).

**Proposal:** randomized exponential reconnect backoff, capped delay, reset after a stable registered connection, and explicit stop on terminal identity/credential rejection. Avoid replaying mutations when reconnecting. Fixed synchronized reconnects are especially costly after a relay restart; RFC 6455 recommends randomized initial delay and progressively longer retry delays after abnormal closure. [RFC 6455 recovery](https://www.rfc-editor.org/rfc/rfc6455#section-7.2.3).

Native nginx has a 300-second read/send timeout; other proxies can have shorter limits. nginx documents an idle upstream timeout and the use of periodic server Ping frames. Configure and verify every hop, including an external HTTPS proxy. A transport heartbeat proves that hop's responsiveness; an encrypted health RPC proves worker/application responsiveness. [nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [native gateway](../../../deployments/native/gateway.conf).

## Deployment and scaling path

### One relay process first

**Proposal:** serve static/frontend assets independently, put TLS and upgrade handling at the edge, and keep relay application routes minimal. Workers should establish outbound WSS and need no public application API exposure for relay-only operation. Existing standalone Compose is a useful starting point, but do not copy demo image names/sample data as a production launch contract. [standalone worker](../../../deployments/worker/compose.yml), [native Compose](../../../deployments/native/compose.yml).

Budget the whole chain. Relay descriptors scale with accepted sockets; an HTTP/1.1 reverse proxy commonly needs both downstream and upstream sockets for each upgraded connection. nginx explicitly counts upstream connections in `worker_connections` and also depends on open-file limits. Linux `fs.nr_open` is only a ceiling; actual per-process allowance depends on RLIMIT_NOFILE. Native nginx currently uses one worker with 1,024 connections. Raising relay limits alone does not increase that edge budget. [nginx core limits](https://nginx.org/en/docs/ngx_core_module.html#worker_connections), [Linux file limits](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#nr-open), [native nginx](../../../deployments/native/nginx.conf).

Check process/container/service descriptor limits, edge limits, kernel socket memory, accept backlog, TLS CPU, memory/cgroup allowance and NIC/provider egress together. Outbound proxy-to-relay connections can also encounter local ephemeral-port constraints for a shared destination; measure actual topology and failure counters before tuning kernel settings. These are deployment checks, not prescribed blanket sysctl changes.

### Multiple relay processes need routing ownership

**Inference from source:** ordinary round robin cannot work reliably: `/workers/ID` may register on process A while `/connect/ID` lands on B. Per-client sticky cookies and IP hashing do not solve this because worker and browser have different origins/IPs. Redis metadata alone cannot move a process-owned WebSocket.

**Proposal, lowest-complexity scale step:** route both path families using the extracted worker ID as the same stable routing key, or assign a stable shard endpoint at enrollment. Do not hash the whole URL, since the two path prefixes differ. nginx provides key hashing with consistent hashing, but the routing key and ownership lifecycle must be designed by Homarr. [nginx upstream hash](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#hash).

Consistent hashing reduces key remapping; it does not migrate existing sockets. During membership changes, new client connections can reach the new shard while the worker's old connection remains on the old one. Plan a coordinated worker reconnect/drain or explicit ownership directory and forwarding. Define a generation/lease per worker so duplicate registrations cannot remain active on two shards. Current generation handling is local, so it is not a distributed fencing mechanism.

If routing flexibility eventually warrants a directory, store minimal worker-to-relay ownership and lease metadata there; forward opaque ciphertext between relay nodes or direct both endpoints to the owning node. Bound inter-node queues, authenticate the internal link and budget its bandwidth. Avoid adding a global application database or cross-worker federation to solve relay routing. Independent worker applications remain independent.

For rolling deploys, readiness should stop new admission; existing sockets need a bounded drain deadline and clients need retry jitter. For an overloaded/hot worker, choose explicit rejection or move that worker as a unit; one workspace should not silently begin executing against another worker. Regional placement is a latency/egress/privacy choice and requires a migration policy, not just more replicas.

## What Go changes, and what it does not

**Potential benefits to measure:** a small deployable relay binary, explicit bounded queues/deadlines, independent read/write loops and useful runtime profiling. Go supports concurrent work with goroutines; its diagnostics include CPU, heap, goroutine, blocking and mutex profiles. Those facilities support investigating bottlenecks, not predicting an improvement in advance. [Go concurrency](https://go.dev/doc/effective_go#concurrency), [Go diagnostics](https://go.dev/doc/diagnostics).

The current Bun server already uses native WebSocket machinery based on uWebSockets. Treat Go-versus-Bun as an implementation comparison under the same wire protocol, not a comparison against a hypothetical JavaScript-only socket parser. [Bun implementation documentation](https://bun.sh/docs/runtime/http/websockets).

**Unchanged constraints:** egress bytes/cost, TCP ordering, worker home uplink, payload encoding, cryptographic work at endpoints, maximum peer counts, proxy descriptor limits, reconnect storms and shard routing. A blind Go relay does not speed up integration APIs, database queries or AES-GCM in the worker/browser. If those dominate, changing the relay language may have little user-visible effect.

**Go port review points:** configure message/read limits explicitly; bound every asynchronous queue; ensure control frames are read while Ping waits; avoid a slow write holding a registry-wide lock; release per-IP/global slots on every failed upgrade, timed-out handshake and close; preserve worker proof, origins, channel isolation and slow-peer closure. With `coder/websocket`, Ping waits for the reader to process Pong, and its default message limit differs from Homarr's limit. Standard `http.Server.Shutdown` does not close or wait for hijacked WebSocket connections, so track and close them explicitly. [coder/websocket API](https://pkg.go.dev/github.com/coder/websocket#Conn.Ping), [message limits](https://pkg.go.dev/github.com/coder/websocket#Conn.SetReadLimit), [Go HTTP shutdown](https://pkg.go.dev/net/http#Server.Shutdown).

## What to measure before making a hosting claim

Use controlled local/staging runs and label their limits. Compare Bun and Go with the same admission settings, frame sizes, origins, TLS/proxy topology and generator. First verify equivalent forwarding and rejection behavior; then measure idle connections, normal dashboard polling, many small subscription messages, large streaming responses/uploads, slow readers, worker disconnects and synchronized reconnect recovery.

Record: connected workers versus clients; accepted/rejected/pending handshakes; per-worker channel distribution; useful bytes versus forwarded/NIC bytes; p50/p95/p99 end-to-end request latency; errors/close categories; queue bytes/high-water marks; CPU and allocations; relay RSS/cgroup plus kernel socket memory; proxy CPU/descriptors; worker/browser CPU and uplink; reconnect recovery time. Keep soak duration, hardware, runtime/compiler versions, socket/FD limits and generator saturation visible. Separate idle-connection density from useful-traffic throughput and from end-to-end application capacity.

Do not present configured maxima, a framework's own benchmark, an echo benchmark, or a localhost result as “supports N deployed Homarr workers.” A credible capacity claim needs workload and error/latency targets, reserve headroom, the first observed bottleneck, and deployment conditions. The code inspection and primary sources in this note establish constraints and decisions; they establish no production capacity number.
