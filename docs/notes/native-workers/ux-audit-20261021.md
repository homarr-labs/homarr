## Prioritized journeys

### P0 — Install one worker and open its hosted workspace

**Current:** `deployments/worker/compose.yml` publishes `127.0.0.1:3002`, defaults the public worker address to `http://localhost:3002`, leaves the relay URL blank, and expects an optional static relay registration secret. Without relay configuration, `pairing.json` contains a direct URL. A hosted browser on another machine resolves that `localhost` to itself; direct access then requires an address reachable from that browser, plus HTTPS/Tailscale setup. The native demo script starts a complete local Homarr, platform, relay and gateway stack; it does not provide the hosted-worker install path. `homarr-worker pair` prints the full JSON object, so the operator must extract its `url` field before opening Homarr.

**Target:** make the worker-only install relay-first: one persistent `/appdata` volume, no published worker port, default hosted platform and shared WSS relay addresses, then one launch command. The worker should connect outbound and print a single private setup URL on first boot or via `homarr-worker pair`; after claim, the command should report “already paired” and point to the owner-invite recovery path. Clicking the URL should open the hosted frontend with the link prefilled; the current frontend already captures the fragment, scrubs it from the address bar, and offers one explicit “Connect worker” action. Show the workspace name and “Connected through Homarr relay,” then open boards. Keep MCP as a later optional branch.

**Blocker outside the UI:** the worker image has no public relay URL by default, and a hosted relay may require the deployment-wide `WORKER_RELAY_REGISTRATION_TOKEN`. I found no pre-boot per-install relay admission/mint endpoint in this checkout. The `/api/workers/challenge` flow happens after browser-to-worker connection and serves hosted account enrollment; it does not bootstrap relay admission. Do not put a shared relay secret in a customer command. Product work must provision per-install relay admission, or make a deliberate rate-limited public-registration design. Source supports Workshop/GitHub OAuth and hosted MCP, but the UX note records that live GitHub/OAuth sign-in and a `homarr.dev` deployment were not exercised; those endpoints and callback configuration remain launch proof, not established behavior.

### P0 — Bind the shared frontend to many independent workspaces

The current “one worker” behavior is browser-origin scoped: the hosted app constructs `WorkerConnectionPool({ singleWorker: true })`, which remembers one global primary key for that origin and hides other saved connections. A link for a second installation in the same browser is treated as a worker replacement. The app also clears the organization preference. That is not yet “one worker per workspace.”

Bind the active worker and browser vault to a workspace route/session first; resolve exactly one pinned worker within that workspace. If an account can access multiple workspaces, switch workspace context at the account/workspace level, never among raw workers. Keep the current explicit replacement confirmation for a changed worker identity inside one workspace. Give the workspace and installation a stable visible name so identical hosted UI instances are hard to confuse.

### P1 — Recover from disconnects and device loss

**Current:** the header badge is only `Connected` or `Offline`. In the connection tab, `Disconnect` closes this browser channel but preserves its saved key; `Forget saved access` deletes the key from this browser. Neither remotely revokes the worker grant. Actual revocation is under Sharing → Device access → Approved devices. Worker access is local to the worker, and its first-owner claim is consumed after use. A new owner device can be invited by an existing owner, but invitations expire within seven days. If the only owner device is lost and no other owner is connected, the current UI/CLI has no recovery flow.

**Target:** say what is offline (browser channel, worker process, relay path) only when the system can prove it; otherwise use “Can’t connect” plus retry and a short diagnostic disclosure. Rename the browser-only action to “Pause this browser” or label its effect beside it. Put “Revoke this lost device” next to the device identity and route it directly to the remote revoke action. Preserve a second owner device as a normal recovery option, and define a local operator recovery command for a sole-owner loss that creates a new owner grant without resetting boards or integration data. Keep revocation inline with explicit consequence copy.

### P1 — Make “user” and “device” invitations legible

**Current:** Users offers local account invites, but the owner must create a local organization before any member invite or user creation appears. Sharing has a separate “Invite device” flow with viewer, existing-user, and owner scopes; it is nested under a collapsed “Device access” disclosure. Both flows produce private links, but they grant different things.

**Target:** keep one small choice at the action point: “Invite a person” creates worker credentials; “Approve a browser/device” grants that device a role. Remove the first-user organization speed bump by creating the local group during first invitation or giving it a sensible default. State whether the link is one-use and expires beside the copy action. Do not merge local users with device grants; their revocation and recovery effects differ.

### P2 — Keep sharing and MCP optional, with accurate trust language

The current board-link UX is already strong: selected boards, bearer-link vs approved-device scope, expiry, on-demand Copy on each active link, and immediate revoke. Preserve the fact that copying retrieves an existing token without renewing its access. The worker URL is a locator; the setup link is private bootstrap authority; a board share is separate, read-only access.

Keep relay-first as the normal route and explain the boundary accurately: worker-to-relay payloads are encrypted end to end, while the relay still observes worker/routing metadata and connection timing. The hosted frontend is a trusted endpoint that renders decrypted data. Hosted MCP is a separate opt-in: its current consent says the service may read authorized tool arguments and results. The source already makes cloud sign-in optional for dashboards/local users and offers Read only / Read and actions, duration, automatic eligible tools, and one approval. The mobile screenshot’s signed-out state reads as a single sign-in gate with a large empty area; label it plainly “Optional — for hosted MCP” and leave a clear route back to boards. Do not add tool checkboxes or a multi-step MCP wizard.

## Three connection-state layouts

1. **Status row (recommended default):** `Online · Homarr relay` with the installation name; when it fails, replace with `Can’t connect` and one Retry action. Keep Change connection in the details area.
2. **Connection path:** three compact stages — `Worker → Relay → This browser` — each with status. Best for troubleshooting; more visual weight than routine use needs.
3. **Summary plus diagnostics disclosure:** one status chip and route at rest; expand for last successful contact, worker ID, and copyable relay address. Best balance for the advanced operator audience, provided online/offline claims are based on real signals.

The rebuild note records local browser acceptance, but not real hosted OAuth or SaaS endpoint acceptance.
