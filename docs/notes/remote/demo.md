# Guided demo acceptance

Added after the initial migration report so the implementation can be tried without reading the technical notes.

- Launcher: `bash deployments/demo/demo.sh up` from this checkout. Requires Docker with Compose v2; missing Homarr images build from the checkout.
- Local address: `http://localhost:43100/remote/` on the Docker computer.
- Running Tailscale demo: `https://brainzilla.llama-stonecat.ts.net:8443/remote/`.
- Tailscale Serve forwards only the new HTTPS port 8443 to the loopback gateway. The pre-existing port 3030 listener is preserved. This is private tailnet access, not Funnel.
- Dedicated Compose project, network and volumes contain the worker, account/frontend service, relay and gateway. Existing Homarr/Workshop data is not mounted.
- First-run preparation selects a small `Demo-dashboard` with a welcome note, clock, bookmarks and sample server status. It removes only the generated gallery in this fresh demo database. A marker preserves later user edits.
- Notes, clocks and bookmarks render readable content; other structured widget output is under “Show data.” `/remote/try` provides a short guide. Network HTTP pages show a plain explanation rather than failing during key creation; localhost works directly.

The launcher passed shell syntax and Compose validation, actual local start/status/pair, repeated start, stop/resume with unchanged worker identity and pairing URL, and confirmation-gated deletion of only disposable validation projects. The default demo remains running. Its final frontend image includes the guide and readable widget renderers; the previously verified worker image is unchanged.

Actual browser checks through the HTTPS Tailscale URL passed secure connection setup, first claim, encrypted relay reads, automatic opening of the four-card sample dashboard, and a 390px layout without horizontal overflow. GitHub sign-in was not needed or verified. The first owner was claimed in an isolated persistent QA browser; a separate one-use owner invitation is prepared for the user, and only a read-only sample share is published on the report page.

Creating an anonymous share in the owner UI and opening it in a fresh guest browser passed. Revoking that share closed the guest connection and cleared the displayed dashboard. A separate seven-day read-only sample share now powers the report's “Open sample dashboard” button; an independent browser followed the button and loaded all four sample cards without sign-in or an additional connection step. The user's seven-day, single-use owner invitation remains separate from the public report. Both credentials were created through the actual application UI.

The report renderer now embeds accessible SVG flowcharts without a CDN or JavaScript diagram runtime. The mobile diagram stacks its labels. Browser inspection confirmed rendered diagrams, visible evidence-note navigation and no report accessibility violations in the automated check. Technical detail remains available behind links from the shorter introduction.

Pairing follow-up: a loaded invitation now shows a ready-to-connect confirmation instead of the required paste form. Closing and reopening the old dialog reproduced loss of the invitation. Pending setup/invitation links now remain in that browser tab until connection succeeds or the user replaces them; refresh resumes the confirmation. Share and durable grant credentials are excluded from this temporary store. Blocked session storage falls back to in-memory reopening. URL fragments still clear before account requests.

The running demo also has an unlisted private setup entry that forwards its mock-worker invitation through a native browser navigation, avoiding manual copying of the long fragment link. It is intentionally delivered only in the private chat, kept outside the public report snapshot in a restricted Docker volume, and served with no-store/no-referrer headers and access logging disabled. This is an operator-issued invitation for this disposable demo; the production account service and worker authentication mechanism are unchanged.

A later reported transport closure revealed a real retry failure: the worker had consumed the invitation and issued an active owner grant, while retrying could generate another browser device key. The original network closure was not established from that metadata. The browser now saves its nonextractable device key before enrollment, saves the issued grant before dashboard reads, and reuses matching saved access when reconnecting. Vault version 2 preserves existing worker entries. A failed grant save retains the pending device and bootstrap. The worker returns the same existing active grant only to the original verified device retrying its exact invitation; other devices and revoked/expired authority remain rejected.

Focused access verification passed 17 tests / 98 assertions, including regressions that failed before the fix. The existing actual worker integration selection passed 17 tests / 116 assertions. Actual deployed browser checks forced a device-key save failure before any socket, then a grant-save failure after enrollment; reload recovered the same grant using the retained key and already-used invitation. Existing browser access survived the vault upgrade and reconnected without redeeming its old invitation. A fresh, unused user invitation now uses direct Tailscale routing at the same private setup entry. Demo worker builds use `homarr:worker-demo-local`, preserving the earlier measured image as a baseline.

An independent live idle probe then reproduced the transport closure at 94.98 seconds through the actual TLS relay path, matching the gateway's 95-second read timeout. The supplied demo and hosted-relay proxy configurations now allow 300 seconds, exceeding Bun's configured 120-second WebSocket heartbeat window. The running gateway passed `nginx -t` and reloaded the new configuration without restarting the worker or altering grants. Repeating the same probe on both direct and relay paths kept each connection open for 140.03 seconds of application inactivity, then fetched the actual board successfully (HTTP 200, 9,177 bytes). The only change between the failing and passing relay probes was the proxy timeout. No application heartbeat or manual ping was added; native WebSocket ping/pong remained automatic.

The next report identified Firefox and the saved worker's **Open** action. Actual Firefox 146.0.1 reproduced authentication and saved access followed by an immediate transport close on the first dashboard request. Firefox does not expose `Request.body`; comparing its `undefined` value with `null` incorrectly marked GET requests as carrying bodies, which the worker correctly rejected. The browser transport now encodes explicit request bodies through `Response`, sends GET/HEAD without a body, preserves multipart boundaries and explicit content types, and falls back to `blob()` for opaque Request inputs. The latter may materialize data in the browser; URL plus original BodyInit preserves streaming. A post-encoding concurrency check retains the 16-request bound.

All 24 focused protocol tests passed, including missing-API GET/JSON/multipart/binary behavior, 32 MiB and existing 256 MiB streaming checks, and concurrent-request rejection without closing the channel. Only the frontend/account container was rebuilt and replaced; worker, gateway, keys and grants remained unchanged. The **same previously failing Firefox profile and saved grant** then opened all four cards without an alert or new pairing. Actual Firefox UI JSON POST share/invitation creation and DELETE revocation also passed. Both independent direct and relay idle probes additionally survived 450 seconds and fetched the board successfully. User recovery is a full Firefox page refresh followed by **Open** on the saved worker.

The browser API difference is also documented in [Mozilla bug 1387483](https://bugzilla.mozilla.org/show_bug.cgi?id=1387483) and [MDN Request.body](https://developer.mozilla.org/en-US/docs/Web/API/Request/body). Native Firefox reproduction and before/after application behavior were the acceptance evidence.

Stop with `bash deployments/demo/demo.sh down`; data is kept. `reset --yes` deletes this demo's own data and keys. Turning off the added Tailscale proxy, if no longer wanted, is a separate `tailscale serve --https=8443 off` operation; do not reset all Serve listeners.
