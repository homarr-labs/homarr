# Integration tests: 24 inspected files and upstream contract checks

Date: 2026-09-23
Branch/base: `audit/testing-prune-v2` based on `origin/release/v2`
Scope: 24 individually inspected test files in `packages/integrations`, selected for the A–M audit assignment plus base integration tests, and five representative upstream client contracts. Navidrome, Nextcloud, and NZBGet overlap the adjacent N–Z assignment; this ledger describes these 24 inspected files and does not claim to be an exhaustive, strictly A–M inventory.
Method: Read-only inventory of `rg --files packages/integrations`; inspected assertions and relevant production client code; checked `vitest.config.mts` runner inclusion; and opened each cited official upstream documentation/source link directly. Compared actual request paths, methods, authentication, and response assumptions with current first-party material. No tests, containers, Docker builds, or networked integration runs were started.
Limitations: This is an assertion/source audit, not runtime validation. Findings do not imply coverage of all integration behavior. Upstream contracts can vary by server release/configuration. Some upstream projects expose their authoritative API spec on each running instance rather than maintaining a stable universal contract. The snapshot records the official materials checked on the date above.

## Test inventory and classification

Classification definitions: **Retain** means assertions plausibly catch a regression in behavior owned by Homarr. **Improve** means useful intent exists but material behavior is weakly asserted or untested. **Consolidate** means overlapping or low-value assertions could be reduced while preserving stronger behavior checks. **Remove/no signal** means assertions do not meaningfully constrain product behavior. No file in this sample was classified remove/no signal. “Mocked” tests exercise Homarr mapping/request construction against authored payloads; they do not validate upstream compatibility. “Live” here means an actual local container or HTTP server, not a deployed service.

### Runner placement

`vitest.config.mts` puts only `packages/integrations/test/aria2.spec.ts`, `home-assistant.spec.ts`, `nextcloud.spec.ts`, and `nzbget.spec.ts` from this sample in the opt-in `integration` project (`pnpm test:integration`). The remaining 20 specs, including mocks and the locally hosted Immich SDK test, are picked up by the generic `dom` project (`**/*.spec.{ts,tsx}`); `@vitest-environment node` changes their environment but not their project. Consequently, the package’s “integration” directory and test names do not mean these are run by the integration project. No files in this 24-file sample were outside all configured Vitest includes. No `.test.*`, Go test, or standalone script test files were found in the inspected paths. These are manual sample counts, not a discovered/run test count from Vitest or an exhaustive package inventory.

### Quantitative classification of individually inspected files

24 files individually classified: 17 Retain, 5 Improve, 2 Consolidate, 0 Remove/no signal, 0 Unreviewed. These are classifications of the inspected sample, not a coverage percentage or a count of independent behaviors. Weak patterns observed include `toHaveBeenCalledTimes` without value assertions (e.g. Immich image proxy calls), `resolves.not.toThrow()` (Glances, aria2, NZBGet), array length-only assertions (Coolify, aria2, NZBGet), and endpoint dispatch stubs keyed to the same path production requests (Coolify). No snapshot-only file or duplicated snapshot suite was found in this sample. Exact output assertions are not automatically redundant when they cover different edge cases, as with Nextcloud recurrence/range and URL normalization.

## Upstream contract spot checks

These five clients were selected as representative high-use integrations across media, home automation, cloud/calendar, and DNS filtering. “Drift” is limited to discrepancies visible between the checked upstream first-party contract and Homarr’s source. A correct route in the current docs does not prove compatibility with every historical server version.

### Home Assistant

Production requests include `GET /api/config`, `GET /api/states`, `GET /api/states/<entity_id>`, `POST /api/services/automation/trigger`, `POST /api/services/homeassistant/toggle`, `GET /api/calendars`, and `GET /api/calendars/<entity_id>?start=&end=` with `Authorization: Bearer …`; service calls use JSON `{entity_id}`. The official REST docs specify bearer auth, state routes, service route/body, and both calendar routes including exclusive date bounds and date versus dateTime results. The inspected routes and payload shape agree. No route drift found. The action unit test verifies only outgoing request construction; the container test checks auth/config only.

Sources: [Home Assistant REST API](https://developers.home-assistant.io/docs/api/rest/), [official REST API source](https://github.com/home-assistant/core/blob/dev/homeassistant/components/api/__init__.py).

### Immich

Homarr initializes the official `@immich/sdk` at `${base}/api`, supplies an API key, and calls server statistics, user search/current user, albums, random search, album info and asset search operations. It creates preview URLs using `GET /api/assets/{id}/thumbnail?size=preview`. Immich’s official API docs state that the generated SDK and published contract derive from the server OpenAPI schema; the repository’s controller source is the endpoint owner. Source-level route use is consistent with the official SDK approach. No definite route drift found in the sampled operations. The direct thumbnail URL is hand-built instead of obtained from the SDK, and neither test proves that current server output/authorization for that route matches the proxy’s needs.

Sources: [Immich API documentation](https://api.immich.app/), [Immich API/SDK documentation and generation model](https://docs.immich.app/api/), [official user controller](https://github.com/immich-app/immich/blob/main/server/src/controllers/user.controller.ts), [official asset controller](https://github.com/immich-app/immich/blob/main/server/src/controllers/asset.controller.ts).

### Jellyfin

Homarr uses the generated TypeScript SDK for user authentication, `GET /System/Ping`, `GET /Sessions`, `GET /Users`, and latest-media lookup; image and profile URLs are constructed as `/Items/{id}/Images/...` and `/Users/{id}/Images/Primary`. The official server source documents `GET /Sessions` as an authenticated session list. The workspace catalog allows `@jellyfin/sdk` `^0.13.0`; the current first-party SDK changelog identifies `1.0.0` as a refresh to the Jellyfin 12 OpenAPI spec and notes that many APIs were renamed or moved. This version gap is a compatibility risk, not evidence of a confirmed break: the changelog alone does not establish that Homarr fails against any server release. The inspected tests do not establish a supported Jellyfin server-version range or prove compatibility with Jellyfin 12.

Sources: [Jellyfin SessionController](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/SessionController.cs), [Jellyfin ItemsController](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/ItemsController.cs), [official TypeScript SDK changelog](https://github.com/jellyfin/jellyfin-sdk-typescript/blob/master/CHANGELOG.md), [SDK session API reference](https://typescript-sdk.jellyfin.org/classes/generated-client.SessionApi.html).

### Nextcloud

Calendar access is delegated to `tsdav` using Basic auth and `remote.php/dav` (preserving a configured base path); events are queried using CalDAV time ranges. Notifications use `GET /ocs/v2.php/apps/notifications/api/v2/notifications?format=json`, Basic auth and `OCS-APIRequest: true`, then parse `ocs.data` fields `notification_id`, `datetime`, `subject`, and `message`. Current Nextcloud OCS docs confirm OCS authentication; the official Notifications v2 client API document describes the route family. No path/auth mismatch found in the sampled notification request. Calendar wire compatibility depends on the server’s CalDAV implementation and the `tsdav` client; the Nextcloud container test covers authored calendar fixtures and useful date behavior, but does not validate notification parsing or alternate auth deployments.

Sources: [Nextcloud OCS API overview](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-api-overview.html), [official Notifications v2 client API contract](https://github.com/nextcloud/notifications/blob/master/docs/ocs-endpoint-v2.md), [Nextcloud WebDAV base URL and authentication](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html).

### Pi-hole (v5 and v6)

The v6 client creates a session through `POST /api/auth`, sends the session ID in the `sid` header on `GET/POST /api/dns/blocking` and `GET /api/stats/summary`, and clears the session with `DELETE /api/auth`. Official Pi-hole auth documentation specifies `POST /api/auth` and session-ID authentication; the official FTL OpenAPI files document auth, DNS, and stats routes. The public overview points readers to the per-instance `/api/docs` spec, which is the authoritative check for a particular installation. Homarr’s version factory selects v5 when `/api/info/version` is absent; the v5 client separately uses legacy `admin/api.php` query endpoints, and current v6 docs do not establish v5 compatibility. No direct route drift found in the sampled v6 calls; version-specific support and tests should remain explicit.

Sources: [official Pi-hole API overview](https://docs.pi-hole.net/api/), [Pi-hole API authentication](https://github.com/pi-hole/docs/blob/master/docs/api/auth.md), [FTL DNS API spec](https://github.com/pi-hole/FTL/blob/master/src/api/docs/content/specs/dns.yaml), [FTL stats API spec](https://github.com/pi-hole/FTL/blob/master/src/api/docs/content/specs/stats.yaml), [FTL auth API spec](https://github.com/pi-hole/FTL/blob/master/src/api/docs/content/specs/auth.yaml), [Pi-hole API version detection in Homarr](../../packages/integrations/src/pi-hole/pi-hole-integration-factory.ts).
