# Testing audit — release/v2

Baseline: `origin/release/v2` at `ea9e2183275f21f7af98f0d58f84414a33e97d87` (verified against the remote on 2026-09-23).

Six parallel reviews covered APIs/auth, widgets/integrations, core/data packages, Next.js/UI, E2E/CI/Go tooling, and agent guidance. The inventory and static scans covered tracked test files; reviewers compared the strongest candidates with production behavior. This is a static audit, not an execution result or a line-by-line proof for every assertion.

This report distinguishes **independent regression signal** from mere test count. A mocked upstream is useful when the assertion checks Homarr's own request construction, mapping, access control, or failure handling; it cannot establish that the real upstream endpoint still exists. File-level classifications are triage judgments, not a measured defect-detection percentage. The earlier ~4% figure was only the cases removed with high confidence, not an estimate that the remainder is valuable.

Focused ledgers: [API/auth/Custom Widgets/validation](testing-audit-api-auth-custom-widgets-validation.md) and [integration tests plus first-party upstream contracts](integration-upstream-contracts-v2.md).

## Inventory and execution

- 435 files named `*.spec.*` or `*.test.*` in JavaScript/TypeScript and 13 Go test files are tracked. A source scan finds roughly 2,519 `test`/`it` declarations and 63 Go `Test` functions; generated cases can differ. Workshop also has seven standalone `.mjs` check scripts, a mock upstream, and two Docker shell harnesses outside that named-spec inventory. The tracked-file inventory must use `git ls-files`: ordinary `rg --files` omits five tracked benchmark specs under the ignored `scripts/benchmarks/` directory. Those five were inspected separately; they assert benchmark provenance, cache conditions, network isolation, and measurement validity rather than dashboard behavior.
- `pnpm test` excludes the integration, E2E, and docs-screenshot projects by default. Docker-backed integration suites and browser E2E have separate commands in `package.json` and `vitest.config.mts`.
- Routine CI's Fast gate runs lint, typecheck, build, and structural checks, but does not run `pnpm test`. The conditional database workflow selects five specific specs. The MySQL conversion E2E runs only in manual container validation. No workflow runs the Go test suite. The presence of a test file therefore does not mean CI checks it.
- Three meaningful database specs under `packages/db/migrations/` and `packages/db/queries/` are excluded from every configured Vitest project: `0004_unify_sections_and_gutters.spec.ts`, `seed.spec.ts`, and `widget-placement.spec.ts`. The `db-node` project only includes `packages/db/test/**/*.spec.ts` and `proxy-reader*.spec.ts`; the `dom` project excludes all of `packages/db/**`.
- No tracked agent skill or template required agents to create test files on every change. The broad Go command in `AGENTS.md` and generic focused-test wording in agent guidance were the actionable prompts; they are narrowed in this branch.

## Upstream endpoints versus mock tests

The separate [upstream contract spot-check](integration-upstream-contracts-v2.md) compares selected Homarr requests with first-party documentation/source. Home Assistant, Nextcloud, and Pi-hole requests sampled there showed no confirmed path/auth mismatch. This does **not** prove compatibility with every deployed server version. Pi-hole explicitly recommends the OpenAPI docs served by the user's own instance because they match its installed version ([Pi-hole API guidance](https://docs.pi-hole.net/api/)).

There is a concrete versioning risk for Jellyfin: Homarr locks `@jellyfin/sdk` 0.13.0, while the [official SDK changelog](https://github.com/jellyfin/jellyfin-sdk-typescript/blob/master/CHANGELOG.md) says 1.0.0 refreshed its generated API for Jellyfin 12 and moved/renamed many APIs. That is a compatibility investigation, **not** a verified current break. Upstream docs are also not always a reliable oracle: a [Linkwarden upstream issue](https://github.com/linkwarden/linkwarden/issues/1650) documents an actual tags-response change that disagreed with its [API docs](https://docs.linkwarden.app/api/get-tags). Homarr's provider accepts both response envelopes, but no direct stats-provider spec protects that logic.

Practical replacement for low-value endpoint mocks: inventory the exact method, path, auth, and response fields used by each provider; compare them with a versioned upstream OpenAPI/source contract when available; then run a small, read-only live smoke against representative supported versions when safe. Keep deterministic local tests only for Homarr-owned mapping, security, pagination, and fallback behavior. A documentation comparison detects *documented* drift, not undocumented behavioral changes, credentials mistakes, or self-hosted version differences. These spot-checks are not a full 87-integration upstream certification.

## Suggested decision rule

For each existing test, ask: (1) Would a plausible wrong implementation fail it? (2) Is that failure important to a user or security boundary? (3) Is the same behavior already checked more strongly elsewhere? (4) Does it run at a useful point in the delivery path? Remove a case when the first answer is no; consolidate when the third is yes; strengthen a weak test only when the behavior matters; and do not count an opt-in/manual suite as PR protection. Apply this to individual assertions, not by deleting every suite that contains mocks or literal expected values.

## Coverage worth retaining

Permission and claim tests, Custom Widget request confinement, HTTP redaction, integration auth and state transitions, Beszel session lifecycle, board interactions, migration smoke, IconPicker mouse/keyboard paths, and E2E layout/onboarding checks assert real contracts. Workshop's standalone scripts check live runtime configuration, migration, ownership, social metadata, and production image behavior; their Docker harnesses are appropriately separate from quick unit checks. Simple assertions in these suites are not automatically tautologies. The Custom API widget intentionally targets self-hosted HTTP services; allowing private addresses alone is not evidence of a test or product bug without a different documented network policy.

## Validation boundary

`git diff --check`, focused Go tests for `internal/tui` and `internal/registry`, syntax checks for the edited `.spec.ts` files, and validation of the edited agent skills passed. JavaScript/TypeScript tests were not run: this worktree has no `node_modules`. No Docker, browser, broad unit, or full Go suite was run for this audit.
