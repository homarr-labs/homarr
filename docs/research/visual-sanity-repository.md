## The earlier debug tool exists in history, not current dev

The original snapshot playground landed in `7c53047d4` (#7112), then was removed by `26ef906d819130479d31700175f177764c210336` (#7130), titled “revert: remove board snapshot playground to restore widget alignment.” That revert touched 44 files and removed 6,196 lines. This is direct Git history evidence of an earlier debug feature affecting product rendering, not a new reproduction of its cause. [Revert][snapshot-revert].

A replacement is present in the locally available `origin/feat/isolated-board-snapshot` at `ec60a4b334bbd561924ac62cffa784459c2585bf`, outside the inspected dev ancestry. Its `/debug/board` route is `ENABLE_BOARD_DEBUG` gated; replay restores captured query data, disables live refetches, rejects mutations, and suppresses subscriptions. That makes it potentially useful for read-only bug fixtures, but it cannot establish successful editing or saving. [Historical route][historical-route], [replay link][historical-replay].

Do not assume that branch can be restored unchanged. Its preview has its own session/settings/query/translation/Mantine/board provider stack and an older `BoardPreviewProvider` signature. The separate provider module explicitly warns against hoisting board CSS into the root. Re-evaluation would include current provider APIs, CSS/bundle isolation, snapshot privacy, storage/network isolation and unsupported states. These are inferred adoption costs supported by its code, not measured costs or a recommendation to revive it. [Historical preview][historical-preview], [provider boundary][historical-providers].

## Why the standalone preview is insufficient for this regression

Current `BoardPreviewProvider` supplies a static board and always selects its first layout. The real `BoardProvider` subscribes to board query data, selects layouts from viewport state, and registers the board name used by updates. Grid actions update complete placement sets through `useUpdateBoard`, whose target name is module-global; the preview provider does not initialize that target. [Board context][board-context], [grid updates][grid-updates], [updater][updater].

Consequently, placing `ClientBoard` under the preview provider is not already a functional editing harness. A read-only fixture could supply the additional providers, but interactive use would need a correct query/cache/update lifecycle. Rendering two editable boards in the same JavaScript realm also requires auditing that global target. Separate instances/browser contexts avoid that particular shared state risk. This is a source-based inference; it has not been prototyped.

The ordinary board path already includes server authorization, server prefetch, Redis query restoration, client hydration, viewport-based layout selection and lazy widgets. A component-only environment bypasses some of those behaviors. A disposable seeded board on the normal route is therefore the smallest existing entrypoint for exercising actual container rendering and saving without first changing production rendering. [Server board path][board-server], [root providers][root-providers], [ClientBoard][client-board].

The narrow candidate regression contract is: an empty or valid one-row container remains 2×1 when viewed; numeric, keyboard and pointer resize can return it to one row; saving and reloading preserve those logical dimensions and corresponding rendered footprint. A small neighboring fixture set would exercise label on/off, nested containers, scrolling, collapse/expand and representative board scales/viewports. These are proposed acceptance cases, not existing passing tests.

Current CI does not enforce that contract. `Fast gate` depends on database validation, the affected-workspace plan, lint/build and typechecks. The plan schedules `typecheck` and `build`, not the ordinary unit or board browser suites. Database validation has its own selected migration checks. The manual-only “Container and migration smoke” job runs only `e2e/mysql-conversion.spec.ts`. [CI plan][ci-plan], [Fast gate and smoke][ci-gate], [database checks][db-checks].

Release publication waits for image builds and binary extraction before publishing version/latest and the release; this workflow has no browser-sanity dependency. Weekly release automation creates and automatically approves/merges the release PR without an in-workflow visual check. These are workflow-file findings; repository rulesets and live run results were not queried. [Release publishing][release-publish], [weekly release][weekly-release].

## Isolation and repeatability constraints

- Use a fresh appdata/SQLite directory and fresh browser context for each base/head run. Existing E2E helpers already establish these boundaries. To compare version upgrades, clone the same old-version fixture and let each instance own its writable copy; do not attach both versions to one database. The helper currently migrates using the checked-out schema, so feeding that file to an older image needs explicit compatibility handling. [Database helper][database], [container helper][container].
- Use synthetic local credentials, board identifiers and integration data. The real widget preview reads the user's actual home board/integrations. Existing backup import consumes an encrypted database archive, so it is not equivalent to a minimal redacted visual fixture. [Preview route][preview-route], [backup import][backup-import].
- For a local-process launcher, isolate the SQLite path, ports, cookies and Redis state. Redis exposes `REDIS_DATABASE_INDEX`, but separate Redis instances are a stronger isolation candidate when background jobs/pubsub are involved. This is a design constraint, not a claim that different database indexes alone isolate every Redis channel. [.env path contract][env-contract], [Redis config][redis-config], [server query cache][board-server].
- `NO_EXTERNAL_CONNECTION=true` disables selected product fetches such as analytics, icon updates, weather and feeds; the helper does not configure a network firewall. Do not describe it as complete egress isolation. Avoid real integration credentials, host Docker sockets and service discovery; explicit network blocking or fully controlled endpoints needs separate design. [Container helper][container], [weather behavior][weather], [feed behavior][feeds].
- Existing mock data is only partly deterministic. Some payloads use a fixed timestamp; Beszel and monitoring mocks use `Date.now()` and `Math.random()`. Clock widgets, locale/timezone, animations, fonts, device pixel ratio, readiness and saved local collapse state also affect captures. Fixture authors must specify what is frozen or masked; a broad screenshot tolerance must not hide geometry changes. [Fixed mock payloads][fixed-mocks], [Beszel mock][random-mocks], [monitoring mock][monitoring-mocks], [collapse tests][collapse-tests].
- Pin base/head commit or image digest plus fixture revision and browser/environment metadata. The existing image helper accepts an image reference, but it does not attest to a full comparison manifest. A code version alone does not freeze its data or browser environment. [Container image selection][container], [CLI provenance][dev-cli].

## Follow-up: targeted selection, seeded authentication and release artifacts

Interview constraints now supplied by the maintainer: the first slice covers board layout/edit flows; release validation is mandatory with explicit exceptions; checks are selected by affected behavior and parallelized with isolated data; independent agents may approve explained appearance changes, while changing a behavior guarantee requires the maintainer. The mechanism below remains research, not implemented policy.

**Available selection inputs.** CI already supplies explicit base/head SHAs to an affected-workspace dry run, extracts build task IDs, and creates four typecheck shards. The JSON is temporary; current outputs contain task lists, not a persistent scenario/coverage manifest. Workspace dependency edges are in `package.json` files, and root/app Turbo inputs include shared runtime/configuration files. No application execution is necessary to read these inputs. [Current selection plan][selection-plan], [workspace dependencies][workspace-dependencies], [root task inputs][task-inputs], [app task inputs][app-task-inputs].

Those inputs need interpretation at the feature level. `@homarr/nextjs` depends on boards, widgets, UI, auth, translation, API and DB; one affected app task does not identify which board interactions to exercise. Conversely, build inputs deliberately exclude specs/stories, and the existing Vitest E2E specs import browser/database helpers then navigate to URLs rather than import the rendered feature. Selecting browser scenarios only through the build task list or test import dependencies can therefore miss fixture/spec edits and changes reached through the running server. [Workspace dependencies][workspace-dependencies], [task inputs][task-inputs], [browser example][media-layout], [E2E setup imports][e2e-imports].

A practical candidate is a small checked-in scenario map: each scenario names its owning paths/workspaces, shared-risk tags, fixture and assertions. Start from the complete base-to-candidate diff, expand shared dependency/risk mappings, and emit selected scenario IDs with reasons; scenario/fixture/harness edits select their own checks. Existing database CI supplies a useful precedent: explicit path rules, deletion-aware Git diff, and conservative handling when the comparison base cannot be resolved. This is a possible implementation route; whether unclassified changes block or select a fallback pack remains a maintainer decision. [Database selector][database-selector].

**Why direct touched files are insufficient.** Shared `SectionGrid` supplies sizing/placement to nested containers; its CSS documents cross-container variable inheritance and editor-chunk stylesheet ordering. The root imports application-wide UI/scroll-area styles, the board theme emits shared theme variables, and board widget cards use shared overflow/container styles. Auth/session and board query providers determine whether edit controls, data and saved state are usable. A local change in any of these can affect boards whose widget files are untouched. These are concrete source relationships; the appropriate scenario breadth still requires a coverage map rather than assuming every shared change requires every test. [Grid CSS][shared-grid-css], [global styles][global-styles], [board theme][board-theme], [widget shell][widget-shell], [providers][root-providers].

**Existing auth and parallel boundaries.** `seedAdminUserAsync` creates a real administrator, completes onboarding and disables tours; `loginAsync` still opens the form, waits for hydration, fills credentials and waits for the requested destination. Current E2E code has no reusable storage-state or session seeder. Credentials authentication creates a random database session and an HTTP-only session-token cookie; reads resolve that token through the database and reject expired rows. A test-only session fixture can plausibly seed the same database row and supply the correctly scoped cookie without adding a production authentication bypass, but needs implementation and focused validation. This skips login as a tested behavior, so it cannot serve as authentication-flow evidence. [Admin seeder][administrator], [login helper][login-helper], [credentials session creation][credentials-session], [session lookup][session-lookup].

The container helper maps an available host port and defaults to its own internal Redis. The SQLite helper uses a unique directory. Together with a fresh browser context and separate output directory per scenario/worker, these are reusable isolation boundaries. Cookies are host-scoped, not port-scoped: tabs against two localhost ports in one context can overwrite the same cookie. Sharing an instance between concurrent mutations also shares DB/cache/global settings even when pages are separate; private board IDs alone do not establish isolation. A worker-owned instance can amortize startup across serial scenarios if its data/session/storage reset contract is defined. No runtime or worker-count benefit has been measured. [Container helper][container], [database helper][database], [internal Redis startup][runtime-startup], [cookie contract][credentials-session].

**Which built artifact can supply a release gate.** PR CI already builds each architecture by digest, checks the PR is still open at the expected head before publishing its mutable preview tag, and combines those digests into a manifest. That is usable PR-review evidence. It is not automatically evidence for the later release candidate: Semantic Release changes version/lockfile/changelog and records a resulting Git ref, and release build jobs check out that ref and emit new architecture digests. The app also injects the root package version during compilation. [PR publication][pr-publication], [release preparation][release-preparation], [release configuration][release-configuration], [version injection][version-injection], [candidate builds][candidate-builds].

The existing release graph has a natural reuse point: pass `build-amd64.outputs.digest` (and any selected additional architecture) to the existing image-configurable E2E harness, then make final publication depend on its result. This reuses the already built candidate image; it does not require a second build. The current graph publishes version/latest and clears draft status only in its final publish job. [Candidate builds][candidate-builds], [image selection][container], [publish job][release-publish].

Evidence can only attest to the image digest, architecture, fixture/scenario revision, environment and checks it actually ran. The current workflows have no machine-readable sanity attestation to establish that identity/coverage relation. Reusing an earlier report requires checking those identities and the selected scenario set; a changed digest or an expanded required set leaves unproven candidate behavior. PR screenshots can remain useful comparison context, but cannot prove the final image's startup/save/reload path. A cached baseline image/capture can be reused when its fixture and rendering inputs still match. These are evidence limitations, not a selected rerun policy.

The release comparison base also differs from ordinary PR validation: current push planning uses `github.event.before`, whereas a release may contain multiple unvalidated feature merges. A release scenario selector needs an explicit last-validated baseline or cumulative covered-change ledger to avoid selecting only the final commit. The choice of baseline, treatment of unknown paths, scope of seeded-auth checks and required artifact coverage are the remaining design questions; source inspection cannot settle their runtime budget. [Current selection base][selection-plan].
