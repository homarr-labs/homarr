# Shared read-only API keys and MCP OAuth

Research date: 2026-10-24. Source snapshot: checkout `d29a9ad9719824c2def59c8fc1d72791ddbfdad3`; [PR #7240](https://github.com/homarr-labs/homarr/pull/7240) head `615af705a7c9f375e3217213e23dc96edb2534ba`, base `4ac71b1f0859561398d7c57800c71132985680f0`. The PR was inspected without checkout. [Issue #7226](https://github.com/homarr-labs/homarr/issues/7226) requests unattended read-only access, including unmodeled integration GETs; its endpoint allowlist suggestion is an alternative, not the only acceptable design. This is research, not an implementation or exhaustive security audit.

## Recommendation

Replace the PR's endpoint-policy editor with one persisted credential access mode, `readOnly`, shared by manual keys and OAuth-issued keys. Enforce its ceiling in the common tRPC procedure builder, keep existing user/resource authorization, and derive MCP discovery from the same policy. Do not equate HTTP GET, tRPC query, or MCP `readOnlyHint` with a complete security boundary. The existing architecture already shares procedures across these transports; no second ACL system is needed. [1][2][3]

**Decide one product boundary explicitly:** strict read-only should initially exclude arbitrary upstream execution. If the requirement includes `integration_request`, allow only GET/HEAD through a narrowly identified conditional policy and label this as method-restricted upstream access, not a guarantee that a service cannot change state or disclose fresh credentials. Do not lower its existing full-integration-access requirement. HTTP itself acknowledges harmful/non-read-only behavior behind safe methods and action-selecting query parameters. [4][5][6]

## Shared enforcement seam and bypasses

1. **Persistence → identity:** add the same non-null `readOnly` boolean/default to SQLite and PostgreSQL, project it in API-key authentication and safe management listings, and propagate server-owned credential identity into context/session. Preserve that identity when narrowing authenticated context; never accept mode from request headers, input, or MCP annotations. A small discriminated credential identity can distinguish browser, manual key and OAuth key without changing the owner permission model. Existing keys should migrate to writable. [1][7]
2. **Procedure → policy:** attach the credential gate to the root builder used by public, protected, onboarding, permission-required, internal and demo-writable procedures. Default read-only credentials to queries, deny mutations and unsupported subscriptions; add a small non-MCP metadata override for exceptional query procedures. Run it before resource middleware or resolver side effects. Do not implement this only under `protectedProcedure`: public procedures can still have authenticated context. tRPC supports reusable middleware plus procedure metadata and runs it for server-side callers. [2][14]
3. **All transports:** REST's OpenAPI router, the application tRPC router and MCP's eager router reuse these builders. Apply policy by procedure semantics/metadata, not a REST endpoint-name allowlist: REST mounts some routers under different names, and `POST /api/users/search` is actually a query. MCP itself uses HTTP POST for read and write calls. [3][15]
4. **Credential precedence:** retain the PR's rule that an explicitly supplied key, including an empty/invalid/revoked key, never falls back to a browser cookie or another credential. Current tRPC does `apiKeySession ?? req.auth`; current MCP skips an empty ApiKey header and tries Bearer. REST is key-only. Current WebSockets are cookie-authenticated; keep keys unsupported and reject their explicit headers rather than silently using cookies. Cookie-only routes remain separate authorities, not additional API-key support. [16][13]
5. **MCP visibility is defense in depth:** filter tools using the same effective read policy, preserve ordinary admin/non-admin visibility, and still reject a hand-crafted direct call at the procedure boundary. Retain harmless reference resources/prompts if desired; hiding authoring UI does not secure executable preview queries. Do not strip the owner's admin permission merely to implement read-only: that would break permitted administrative reads while missing side-effectful public queries. [2][3][9]

## Queries and upstream execution needing explicit treatment

| Surface                                                                                                | Risk / required handling                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `integration.request`                                                                                  | **Mutation**, arbitrary GET/HEAD/OPTIONS/POST/PUT/PATCH/DELETE; DELETE alone requires `confirmed`. It requires full access even for GET, confines URLs, blocks redirects, redacts known secrets and limits request/response sizes. A blanket mutation ban correctly blocks it. If GET/HEAD is intentionally admitted, enforce the exception on parsed input before credential resolution/network I/O, reject bodies and caller headers/method overrides, preserve confinement/full access, and never admit other methods merely because `confirmed=true`. Do not reclassify the whole procedure as a query. [4][5]       |
| `widget.customApi.getData` / `queryRequest`, `customWidget.optionRequest`, `customWidget.previewQuery` | **Real bypass for a query-only policy.** Custom Widget non-integration sources can define POST/PUT/PATCH requests with `kind: query`; only DELETE is always forced to action. The extra non-GET/action constraint applies to integration sources only. These query resolvers execute the stored method/body with saved authentication; preview also records evidence. Initially deny these execution procedures to read-only credentials, or validate every resolved outbound request before executing any of a load's requests. Filtering just MCP's `customWidget_` names misses tRPC widget runtime queries. [17][18] |
| `integration.testConnection`                                                                           | Query/REST GET, but native connection testing can establish upstream authentication sessions. Decide whether authentication/cache/logging are allowed incidental effects; otherwise deny it explicitly. Do not promise zero backend writes as the meaning of read-only. [19]                                                                                                                                                                                                                                                                                                                                             |
| Native reads / sensitive output                                                                        | Preserve existing authorization and output projections. `integration.byId` returns public secret values only; invite and API-key listings exclude bearer secrets; Kubernetes secret listing returns metadata only. Logs and arbitrary upstream responses can still contain sensitive data. Read-only is not “safe to disclose everything.” No additional direct DB-write query resolver was found by the bounded query-body scan; transitive effects were not exhaustively audited. [20]                                                                                                                                 |
| Read-ish mutations                                                                                     | `stats.refresh` is a mutation that queues refresh work; default-deny it along with other mutations. Do not create exceptions from names, `effect: additive`, or `destructiveHint: false`. Add an audited semantic exception only if actually required. ## OAuth consent and persistence

### Minimal change for the existing code flow

- **Keep current CSRF/PKCE protections:** pending/browser/session binding, same-origin consent POST, one-shot decision/code consumption, original redirect/state, bounded duplicate-free parameters, and no-store responses. The consent POST currently rejects any field except `pending`, `consentToken`, `decision`; update that boundary deliberately for a mode selection. [10][11]
- **Freeze granted mode:** parse recognized scopes at authorization start; store requested/maximum mode in `GrantContext`. Display requested access and a read-only-by-default choice on `/auth/mcp`; an explicitly read-only request must never be upgraded by the UI. Save approved mode in the code's server-side context, then insert it into the same `apiKeys` row at exchange. Token-request `scope`/`readOnly` fields cannot override consent. Today consent only has allow/deny and renders owner permissions/full credential breadth; update that copy to effective credential access. [10][11][12]
- **Use clear scopes:** introduce an explicit read scope such as `mcp:tools:read`; retain `mcp:tools` as the legacy broad request if compatibility is needed. Legacy/no-scope new authorizations can default to read-only at consent, with writable access requiring an explicit choice allowed by the request. Return the actual granted scope, including when downscoped. Unknown scopes fail; whitespace-separated supported scopes need a real parser, not string equality. Scope names are server-defined; OAuth requires reporting granted scope when it differs and documenting the no-scope default. [10][22]
- **Discovery and runtime:** advertise read as the minimal Protected Resource Metadata scope and in the initial 401 challenge; authorization-server metadata may describe the full supported set. Never advertise write as required for basic reads. Pass actual grant/client/scopes to MCP rather than hardcoded `mcp:tools`/owner ID. Existing OAuth rows remain writable legacy grants; show their effective mode in both owner and admin connection lists. Most importantly, the persisted mode must follow the token when reused through ApiKey on REST/tRPC, not just Bearer on MCP. [9][12][23]
- **Durability:** mode must live in the DB key row, not solely a scope string in the process store or tool list. `_store.ts` currently holds clients (24h), pending consent (10m) and codes (5m) in process-local maps; restarts invalidate in-flight flows but not exchanged keys. Read-only does not require introducing Redis or redesigning this store. [1][12]

### Refresh tokens: absent today; do not accidentally invent them

Keeping refresh unsupported is the smallest valid scope change; do not advertise `refresh_token` until implemented. If refresh is added later, use durable server-side grant records binding owner, client, audience/resource, consented scope/mode, expiry and revocation, plus hashed rotating refresh-token records with a family/parent relationship. Atomically consume/rotate; reuse revokes the family. Refresh may preserve or narrow scope, never widen mode or survive grant revocation. A read-only grant cannot mint a writable access key, even if the owner later gains permissions. Client registration must remain available for that grant's lifetime, not expire after the existing one-day map TTL. Reuse the current DB/transaction patterns, not a new credential datastore. [12][22][24]

**Separate existing OAuth hardening gap:** resource is checked during code exchange but not stored with the issued key, and MCP authentication cannot validate its audience or OAuth-token expiry. Current consent also allows ordinary HTTP(S) callback URLs, not just HTTPS/loopback HTTP. Current official MCP authorization requires intended-audience validation and 401 for invalid/expired tokens; OAuth Security BCP limits HTTP callbacks to native loopback cases. Record these gaps explicitly rather than claiming that adding `readOnly` makes the OAuth implementation fully compliant. Preserve existing key behavior deliberately; changing legacy token expiry/audience is a separate compatibility decision. [7][9][10][23][24]

## Defaults and focused verification seams

**Defaults:** existing manual/OAuth keys migrate to writable; new creation UI and OAuth consent default to read-only; omitted input on the existing manual creation API should retain writable behavior for compatibility, with the UI sending an explicit choice. Writable still means “up to current owner permissions,” never permission escalation. Do not auto-convert an already-deployed endpoint-restricted key into a broader general read key: preserve its narrower policy or require revocation/reissue. Browser sessions and demo read-only remain independent. [1][2][13]

Recommended regression cases for implementation, reusing existing fixtures rather than building a parallel harness:

- API-key DB/session/revocation: `packages/api/src/router/test/apiKeys.spec.ts`; verify both modes, migration default, safe metadata and current owner-permission ceiling. Run the same storage contract for SQLite/PostgreSQL. [25]
- Procedure ceiling: query succeeds, every writable mutation/public/admin/demo-writable builder fails before effects, direct tRPC/MCP caller cannot bypass it, and ordinary browser/writable contexts remain unchanged. Include Custom Widget POST-as-query and multi-request load cases. [2][17][18]
- Cross-transport proxy: extend `packages/api/src/test/integration-request.spec.ts` (already compares REST/MCP boundaries). If proxy GET/HEAD is enabled, cover every other method, raw/body/header overrides, owner permission loss, confinement/redirects and no outbound calls on denial. [26]
- Auth boundaries and discovery: `apps/nextjs/src/app/api/[...trpc]/route.spec.ts`, `apps/nextjs/src/app/api/mcp/[transport]/route.spec.ts`, `packages/api/src/test/mcp.spec.ts`; add valid/invalid/empty key plus privileged-cookie combinations, tRPC batching, Bearer reuse, read-only tool lists and forced calls to hidden writes. [3][16]
- OAuth: `apps/nextjs/src/app/api/mcp/oauth/flow.integration.spec.ts`; verify approval/denial, downscope persistence through code exchange and DB reload, token-request tampering, consent/session replay, scope metadata, legacy behavior and continued refresh rejection. Existing tests already exercise explicit consent, hashed storage/provenance and single-use code exchange. [27]

No production files or tests were changed for this note. Baseline `bun run lint` and `bun run typecheck` passed (existing lint warnings); `git diff --check` passed. Source inspection does not establish runtime security; implementation still needs the focused checks above.
