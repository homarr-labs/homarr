# Delivery, evidence, and contributor replies

## Investigation and implementation

Start from the accepted outcome and preserved behavior recorded by the value and compatibility gate in `SKILL.md`. Reassess before broadening the change if the proposed fix violates either or costs substantially more than anticipated.

Reproduce the reporter's path before claiming a bug is fixed. Keep a source finding, local fixture, browser reproduction, published image, and reporter confirmation as separate evidence. When reproduction is incomplete, report the exact missing detail and a concrete next check. A useful question resolves a remaining uncertainty; do not ask the reporter to reconfirm an answer already provided.

Inspect current code and overlapping PRs before editing. Prefer updating an existing contributor fix when authorized; refresh its head before pushing and preserve contributor credit. Use isolated branches/checkouts so parallel agents cannot overwrite each other or unrelated user work. Follow `AGENTS.md` for targeted validation: add tests only when requested, run only relevant checks, and use runtime/browser/container validation when it materially verifies the claimed behavior. Avoid broad suites and image builds for a focused documentation or metadata change.

Review fork code at an exact commit before approved CI execution or preview publication. Inspect workflow changes, scripts and other executable changes too. Existing permission applies only within its stated scope; a need for fresh permission should identify the exact action and why it is required. A screenshot in a contributor comment alone does not establish a published current-head preview.

## UI proof and PR body

For a visible UI fix, capture matched before/after screenshots of the reported case: same viewport, fixture data, theme, and relevant settings. State what the fixture proves and what still requires the reporter's environment. Do not substitute a mock-up for a reproduced application screenshot.

Verify the preserved behavior as well as the symptom. For a shared layout change, compare existing saved dimensions and neighboring placements, including a simple configuration that never had the reported problem. Show that the benefit does not depend on silently moving or resizing the user's layout. Select similarly relevant compatibility checks for other domains; a better reporter screenshot and reporter acceptance alone do not establish compatibility.

Use a current `gh` with `--attach` support. Check command help if the installed version is older; the [current CLI manual](https://cli.github.com/manual/gh_pr_create) describes attachment rewriting. A PR body can reference the same files in a table:

```markdown
> _This was generated by AI during triage._

Compact month now retains event indicators at the affected widget size.

| Before                              | After                              |
| ----------------------------------- | ---------------------------------- |
| ![Missing indicators](./before.png) | ![Visible indicators](./after.png) |

Validation: reproduced with the reported integrations at the stated viewport.
```

For example, from the temporary directory containing `pr.md`, `before.png`, and `after.png`, with the implementation already committed/pushed:

```bash
gh pr create --repo homarr-labs/homarr --base dev --head feat/your-fix \
  --title 'fix(calendar): retain compact event indicators' \
  --body-file ./pr.md --attach ./before.png --attach ./after.png
```

The CLI rewrites matching image references to uploaded assets. Read back the published body/comment and check the actual attachment URLs. Local `/tmp` paths, inaccessible local servers, or unrelated branch files are not public evidence. Attachment upload can partly fail after a PR has already been created: inspect the printed URL and existing PR before retrying, to avoid a duplicate. Use `--attach` with issue/PR comments when updating reporter evidence. Skip screenshots for changes with no visible UI behavior.

Keep ordinary PR descriptions focused on the final problem, resulting behavior, and relevant validation. Put an explicitly requested session handoff in the PR body; it does not belong in the committed skill or an unrelated source file. Keep sensitive/private findings out of public bodies and follow the repository's `SECURITY.md` location for private reporting.

## Update a public follow-up

Apply the cross-pass message-continuity rule in `SKILL.md` before publishing. After implementation, tell the person what changed, link the PR and exact usable preview, show relevant evidence, and give short reproduction steps plus the remaining question. If checks/publication are pending, say so rather than asking them to test an unavailable build.

For editing an existing top-level Conversation comment, first list comments and identify the exact AI-authored comment by ID and provenance, especially when automation shares the maintainer account:

```bash
gh api 'repos/homarr-labs/homarr/issues/7258/comments?per_page=100' --paginate

# After confirming COMMENT_ID belongs to the AI note being updated:
gh api --method PATCH repos/homarr-labs/homarr/issues/comments/COMMENT_ID \
  -F body=@/tmp/triage-reply.md
```

Use the AI disclaimer required in `SKILL.md`. The `--edit-last` and `--delete-last` shortcuts select by account, not AI authorship; they can target a human maintainer comment. Delete only the identified AI comment when replacing it is authorized and needed for a new ping. Keep the replacement concise and verify the resulting conversation rather than stacking AI status comments.

## Testing, merge, and release states

Apply the precise [testing labels](../../../../docs/agents/triage-labels.md): current-head required checks plus a published test image establish test readiness; an issue awaiting testing uses `waiting-for-reporter`. A new head requires fresh checks and publication. Preview tags can move, so record the tested head/digest and workflow link; verify architectures when platform behavior matters.

Before merge, refresh the exact head/base, required checks, mergeability, unresolved review threads, maintainer scope decision, and relevant reporter acceptance. Reporter success does not grant an admin bypass. If the author account cannot self-approve, use another eligible reviewer or obtain a specific authorized bypass; do not borrow a bot's approval credentials to evade review rules. Pin the expected head for the merge.

After merge, confirm the actual merged state and clean stale pending labels within scope. Close implemented bug reports after the acceptance/merge contract is satisfied, or follow an explicit maintainer override. A merged PR is not a deployed image or published release. The Project's Done state mirrors closure/merge, so explain any remaining deployment or reporter uncertainty separately.
