# Custom Widget response-cache expiry results

## Fixture and controls

The harness used the actual `executeCustomWidgetRequest` implementation, real Undici transport and response parsing, and a synthetic HTTP server bound only to `127.0.0.1`. The memory fixture used 1, 25, or 100 requests concurrently (`Promise.all`), all with an identical 262,144-byte payload string. The serialized JSON body is 262,172 bytes. Each process used Node 24.18.0 from `mise.toml`, `--max-old-space-size=512`, `--expose-gc`, TTL 1 second, and a 100 ms idle margin. It sampled empty, populated-after-hit, TTL-plus-idle-before-invalidation, and post-invalidation stages after an event-loop yield and explicit GC. The 5-cycle journey used 25 concurrent requests per cycle, waited past TTL after each fill, and did not manually invalidate between cycles. The baseline source hash is `708233b47f082780818c62823d81b9f849aaecacfe5e566879f637cffe56f167`; the timer source hash is `afbae239edb658f669cb09f26ec6b1b03fe1619867fba43e255f9350ebc35403`.

Nine fresh-process pairs alternated before/after order. Raw JSONL is preserved as `cache-expiry-pair-01-before.jsonl` through `cache-expiry-pair-09-after.jsonl`. The first serialized pre-edit baseline is `cache-expiry-baseline-node24.jsonl`; the repeated 5-cycle baseline is `cache-expiry-repeat-baseline-node24.jsonl`. Process arguments, resource usage, source hash, and `/proc/self/limits` are in each raw run's first JSON line. All runs used identical process limits: 512 MiB V8 old-space cap; `/proc` reported unlimited RSS and address space, 8 MiB stack soft limit, and 1,048,576 open-file soft/hard limits. `process.resourceUsage().maxRSS` captured at fixture startup ranged 106,964–110,092 KiB across paired processes; sampled RSS later reached higher values, so this startup value is not the run's peak.

## Evidence

For 25 entries, median `heapUsed` after TTL plus idle was 23,972,096 bytes on baseline and 17,423,072 bytes with the timer. Median idle-minus-empty was 7,704,984 bytes baseline and 1,151,160 bytes after. Explicit invalidation then reduced baseline heap by a median 6,561,552 bytes, versus 1,056 bytes after the timer. The paired idle heap reduction was 6,549,552 bytes (range 6,547,488–6,559,056).

For 100 entries, median idle `heapUsed` was 42,070,424 bytes baseline and 16,213,736 bytes after. Median idle-minus-empty was 24,678,008 bytes baseline; the after value was -1,190,248 bytes, reflecting post-GC/runtime baseline drift. Explicit invalidation reduced baseline heap by a median 26,246,352 bytes, versus 1,296 bytes after. The paired idle heap reduction was 26,230,248 bytes (range 24,475,080–26,625,568).

Across the five repeated expiry cycles, baseline idle heap plateaued at a median 22,495,304 bytes (range 22,417,168–22,550,656), while the timer variant plateaued at 15,957,016 bytes (range 15,869,552–16,002,400). Baseline entries therefore remain retained during each idle period, then the existing next-insertion prune reclaims the preceding expired batch. The observed behavior is bounded stale retention by the existing 1,000-entry capacity, not unbounded growth. The timer releases expired entries during idle.

Memory samples include the Node process, synthetic server, executor, and fixture; they are not Homarr-only RSS. Sampled RSS was noisy and reached 226.8 MB baseline and 234.8 MB timer variant, so the evidence supports heap retention and release, not a steady-state or process-peak RSS improvement. The medians of per-run sampled maximum RSS were 215,764,992 B baseline and 219,398,144 B after, with overlapping 201,252,864–226,828,288 and 208,793,600–234,754,048 B ranges. These GC-stage snapshots miss allocation peaks between samples. External memory ranged 5.9–52.3 MB baseline and 5.9–59.6 MB after; ArrayBuffers remained around 1.3–1.5 MB. These are separate measurements from JS heap and are not attributed to cached parsed payloads.

## Behavior and cost

All 18 paired processes exited successfully with cache-hit checks before expiry, refetch after expiry, refreshed-hit checks, and the in-flight invalidation-generation check (exactly two upstream requests; the new generation remained cached). Separate frozen/current capacity runs each inserted 1,001 unique entries and confirmed the oldest entry refetched, preserving the existing eviction bound. Raw outputs are `cache-expiry-eviction-before.jsonl` and `cache-expiry-eviction-after.jsonl`.

The timer compares a new expiry against the current deadline in O(1), keeps at most one unref'd timer, and clamps timeout delay to Node's 2,147,483,647 ms maximum. When it fires, it scans the cache to prune expired entries and scans again to find the next deadline: O(C), with C bounded by the existing 1,000-entry cap. It never runs capacity eviction, captures response values, or modifies epochs/in-flight state. Partial invalidation may leave an earlier deadline scheduled, causing a harmless early wake; emptying the cache clears the handle. The public schema caps `cacheSeconds` at 3,600 seconds; the executor still handles larger finite direct-call TTLs by waking at the clamped delay and rescheduling.

Idle-window process CPU around the 1-second expiry was noisy. For 25 entries, median CPU was 3.277 ms baseline and 2.582 ms after; for 100 it was 1.313 ms and 7.528 ms, respectively. The 100-entry timer run ranged 5.357–8.184 ms. These totals include process/event-loop work during the idle interval and are not an isolated callback benchmark; they are consistent with the added bounded scan but do not establish precise per-callback cost. The timer trades one bounded expiry wakeup and O(C) cleanup for prompt idle reclamation.

No tests or broad checks were run. The harness's freshness, in-flight generation, and eviction assertions passed in the measurements. No unrelated production files were changed.
