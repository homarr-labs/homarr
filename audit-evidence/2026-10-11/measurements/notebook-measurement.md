# Notebook editor measurement harness

**Status: compatibility smoke only; no valid performance measurement.** Earlier smoke runs failed cancel assertions. Inspection found stale callback capture: the global fixture object copied callbacks only once, leaving baseline save bound to initial React state. Controls now delegate through current render callbacks. The fixture retains raw `initialHtml` in its rollback ref to match production's `options.content`; normalized editor HTML is captured separately. The formal runner launches a fresh Chromium process, context, and page per variant. One small baseline/candidate compatibility pair was run; both variants persisted the normalized editor HTML (3,701 bytes) instead of raw initial HTML (3,110 bytes). The baseline fixture therefore appears to have received an initial `onUpdate` before the no-edit save, so this smoke does not establish production's zero-transaction save behavior or a baseline-vs-candidate difference. See `notebook-compatibility-smoke.json`. No production file, dependency, or test file was changed. No valid performance measurement exists.

The fixture is under `audit-evidence/2026-10-11/measurements/`. It bundles the installed React 19 and Tiptap 3 packages into an isolated Playwright page. It imports Homarr's actual notebook default HTML, `ReadOnlyTaskItem`, the task transaction helper, and text-direction extension. The runner checks source anchors and records hashes for both the preserved baseline notebook and current notebook before accepting results.

The baseline branch mirrors the production `onUpdate` callback that serializes via `editor.getHTML()` and stores the complete string in React state. The candidate branch leaves Tiptap transactions enabled, keeps only the saved rollback content, and serializes on save or read-only task commit. Both use the current `shouldRerenderOnTransaction: true` setting so the comparison isolates serialization/state retention rather than changing editor transaction rendering. A zero-transaction save is a compatibility gate: production initializes React `content` and rollback state from raw `options.content`; without an editor update, baseline save passes that exact string to persistence, while a save-time serialization candidate passes `editor.getHTML()`. The default notebook source contains multiline/indented HTML, so exact-string normalization is a concrete compatibility risk. The harness records raw-vs-initial-normalized and exact persisted-vs-raw equality before any document transaction; reject the candidate if required serialized content changes.

Three documents are measured: the real default notebook plus a task row, and two generated documents with 256 or 2,048 paragraphs. The generated paragraphs keep the document nodes simple while scaling HTML length. Nine paired runs alternate baseline/candidate order for each size by default, with 12 edits per run. Each variant saves once while the editor fixture is editable but before any synthetic document transaction, recording exact persisted HTML equality against raw `options.content` and initial normalized editor HTML. It then refreshes raw input before typing. Each run also exercises save success, edit cancellation, failed save followed by cancellation, external content refresh, successful and failed read-only task toggles, and repeated editor mount/unmount cycles.

The JSON output includes per-edit synchronous editor command durations, `editor.getHTML()` duration and call count during typing, UTF-16 output-unit totals, diagnostic UTF-8 byte sizes for initial/final HTML, and Chromium CDP `JSHeapUsedSize` before typing, after typing, and after lifecycle scenarios. It records DOM editor count plus editor create/destroy events and total harness duration. Forced GC occurs before CDP heap samples. Telemetry arrays are cleared before heap samples so they do not remain as artificial retained data. UTF-16 totals and serialized bytes describe output work; they are not retained-heap measurements. CDP heap is renderer-wide and approximate.

This isolates the editor and state paths; it does not mount Homarr's dashboard, persistence API, full toolbar, or application providers. The edit loop dispatches real Tiptap transactions through the editor API, not physical keyboard events. It measures synchronous command duration rather than input-to-paint latency. Results can support or reject the narrow serialization hypothesis, but cannot establish whole-app CPU, latency, bundle, or memory behavior. No benchmark result exists yet.

The browser injection loads the esbuild bundle as an ESM module; classic injection shadowed the browser's native `DOMParser` with ProseMirror's class. Editor initialization succeeds. Prior broader smoke runs failed cancel-restoration assertions after synthetic edits, while task commit/rollback assertions passed. The compatibility-only smoke did not exercise those checks. Its baseline path produced normalized HTML before saving, which needs an update-event count/initialization diagnosis before using it to make production compatibility claims. Do not make a production change or claim a measured benefit from this artifact.

Once the smoke checks pass, run the baseline phase to confirm the checked-in notebook still matches the preserved per-transaction serialization path and measure baseline-versus-isolated-candidate behavior. After an authorized production change, rerun in the `after` phase, which requires no `getHTML()` in `onUpdate` and a save-time serialization call:

```sh
mise exec -- node audit-evidence/2026-10-11/measurements/notebook-measure.mjs --phase=baseline --pairs=9 --edits=12 --cycles=3 > audit-evidence/2026-10-11/measurements/notebook-baseline.json
mise exec -- node audit-evidence/2026-10-11/measurements/notebook-measure.mjs --phase=after --pairs=9 --edits=12 --cycles=3 > audit-evidence/2026-10-11/measurements/notebook-after.json
```

If the full baseline does not show a measurable benefit or fails one of the state-path checks, stop before changing production code.
