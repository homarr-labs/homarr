# Server process and request memory overview

Scope reviewed directly: assigned API middleware/context, Custom Widget server request path and caches, integration request handlers, and generic request-handler caches. This is static code evidence, not a measured allocation profile. No tests, builds, or benchmarks were run.

## Confirmed findings

### Integration middleware loads more nested item data than authorization consumes

`packages/api/src/middlewares/integration.ts` loads `items` with `item: true` in both the one- and many-integration queries. It removes the `items` relation before passing the integration into the procedure (`_ignore1`), so the full nested item objects do not escape middleware. Query authorization delegates to `hasQueryAccessToIntegrationsAsync` in `packages/auth/permissions/integration-query-permissions.ts`: it reads `items.length` and each `item.boardId`; interaction authorization uses only integration user/group permission arrays via `constructIntegrationPermissions` (`packages/auth/permissions/integration-permissions.ts`). Thus the nested item projection can be narrowed to `items` plus `item.boardId` while retaining all current authorization behavior. This saves row hydration and relation objects in proportion to linked items per integration, particularly for `createManyIntegrationMiddleware`; actual byte savings depend on row width and linked-item cardinality. Keep the full integration/app/secrets/permission projections unless separately proven unnecessary: those fields are either passed through or used by auth/decryption.

### Custom Widget response cache has bounded capacity but lazy expiry

`packages/custom-widgets/src/server/request-executor.ts` owns module-level `cache` and `inFlight` maps. Only successful query responses with positive `cacheTtlSeconds` are cached. Fresh hits return the exact cached response object; a lookup of that same expired key deletes it. Otherwise expired entries are pruned on a later successful insertion; `pruneCache()` scans expiry and then evicts oldest keys while size is at least 1,000. Therefore expiry governs freshness but does not schedule prompt release. Retained parsed response graphs are bounded by 1,000 entries per Node process, but a quiet process can retain expired values until another lookup/insertion or explicit prefix invalidation. Cache keys include source/session/request/runtime parameters/version at their callers (e.g. `packages/api/src/router/custom-widget/preview-query-procedures.ts` and `packages/api/src/router/widgets/custom-api.ts`); arbitrary unique parameters can churn entries up to the cap. Invalidating prefixes also deletes matching in-flight map references and increments a process-wide epoch; existing promises still settle for their callers, but epoch prevents their result from being inserted after invalidation.

Minimal compatible cache improvement: schedule earliest-expiry cleanup or prune expired entries on every cache lookup/insertion path. This changes only retention timing, not response freshness or key identity. An explicit cap increase/decrease would affect reuse/eviction and should be treated as a semantic/performance decision; existing 1,000-entry bound already prevents unbounded cache growth.

### Custom Widget request parsing creates overlapping representations

For non-redirect HTTP responses, `request-executor.ts` reads `responseData.body.arrayBuffer()`, optionally decodes compressed content, wraps that body in an Undici `Response`, and calls `parseResponseBody` (`packages/custom-widgets/src/server/response.ts`). The parser gathers chunks, copies them into a contiguous `Uint8Array`, decodes to a JS string, then `JSON.parse`s into an object graph (or returns the text). `assertJsonBudget` limits parsed JSON to 50,000 nodes and depth 32; the transport response body is limited to 1 MiB and decompression is bounded to 1 MiB. When secrets exist, `redactResponseSecrets` recursively constructs new arrays/objects and strings. During parsing/redaction, raw bytes/chunks, decoded text, parsed objects, and redacted objects can overlap in lifetime; exact peak and whether Undici/Buffer storage shares backing memory depend on runtime paths and require measurement. Cached entries retain the final redacted parsed response. The limits bound per-response input/shape but do not establish a tight RSS ceiling under concurrency; Custom Widget request rate/concurrency controls bound admitted work in production (four per user/item, eight per definition; Redis-backed).

Small compatible optimization candidate: avoid the extra contiguous byte copy by decoding a bounded concatenation/buffer path, or use a streaming text decoder while enforcing byte limit. Evaluate against current fatal UTF-8 behavior, response limits and NDJSON contract before changing. Avoid cloning/redacting when there are no secrets (already done); with secrets the redacted copy is required by current response contract. No allocation reduction is asserted without a focused measurement.

### Generic request-handler cache is more actively bounded

`packages/request-handler/src/lib/request-handler.ts` creates per-handler `cache`, `inflight`, `sharedCacheResolutions`, and `upstreamSettlements` maps. The completed-data cache has a 1,000-entry capacity and a timer scheduled at earliest `staleUntil`, deleting entries after stale-if-error eligibility ends. It evicts oldest entries at capacity. In-flight/shared-resolution/upstream-settlement maps each reject new unique work at 100 entries; settlement references are removed once upstream work settles, with bounded cleanup grace after timeout. `createWidgetRequestHandler` and `createIntegrationRequestHandler` instantiate the generic handler per exported handler definition, so the 1,000-entry cap is per handler instance, not global across all integration/widget definitions. Many distinct handlers can therefore retain independent caches. Shared response payloads are also stored in Redis through `packages/request-handler/src/lib/shared-cache.ts`; Redis memory is separate from Node process heap/RSS. The timer is unref'd. Expiry lifecycle here is materially stronger than the Custom Widget executor cache.

### Request-limit local state is not the production path

`packages/api/src/router/custom-widget/request-limits.ts` selects Redis storage except when `CI` is set or `NODE_ENV === "test"`. Redis keys have expiry. The fallback `CustomWidgetRequestLimiter` in `packages/custom-widgets/src/server/request-limits.ts` has local `rateBuckets` and `concurrency` maps; successful acquisitions filter timestamps to the last minute but do not remove dormant keys. Under a long-running process with many distinct identities/item IDs, local fallback rate-bucket key cardinality can grow. This is confirmed code behavior only in CI/test configuration; do not attribute it to normal production deployments. Concurrency keys are removed on release. Suitable fallback-only cleanup: periodically sweep empty/expired rate buckets or remove a bucket once its final timestamp is outside the window, preserving limits for active identities.

### Preview session local maps are likewise fallback/test-only

`packages/api/src/router/custom-widget/preview-sessions.ts` selects Redis except in CI/test. `CustomWidgetPreviewSessionService` in `packages/custom-widgets/src/server/preview-sessions.ts` uses local `sessions`, `journals`, and `evidence` maps only when no store is supplied. Session expiry is checked on `get`; expired reads remove that session/journal/evidence, but there is no timer/sweeper for sessions never read again. Journals cap at 50 entries and evidence is keyed/deduplicated by evidence key, but session count has no local cap. This can retain session graphs in a long-lived test/local fallback process. Production session/journal/evidence TTLs are delegated to Redis and should be analyzed as Redis/container memory, not Node heap.

### tRPC request context is request-scoped and not a cache

`createTRPCContext` (`packages/api/src/trpc.ts`) constructs a small object per request containing session, device type, optional base URL, onboarding claim token, and singleton DB reference, and logs source/user metadata. It is called by Next.js tRPC route handlers, WebSocket context callbacks, MCP handlers, assistant route, and RSC context. No process-global request-context map or body copy is visible here. Session objects and incoming request/header lifetimes can add per-concurrency heap, but their retained size is not quantified by this code read. The broad error formatter flattens Zod/FlattenError payloads when present; schema/error sizes are bounded by procedure input contracts only where defined.

## Scaling and ownership distinctions

- **Node heap / retained JS objects:** parsed response graphs, map keys/values, session/context objects, promises and closures.
- **External / ArrayBuffer memory:** response ArrayBuffers, Buffers and zlib/native allocations; some V8-managed backing stores may be reported under `arrayBuffers` and also contribute to `external`. Do not sum overlapping counters as disjoint bytes.
- **RSS:** includes heap, external buffers, native TLS/zlib/Undici allocations, code pages and allocator fragmentation. RSS is process-level and may stay elevated after objects become collectible.
- **Redis:** shared request-handler cache, Custom Widget preview sessions/evidence/journals, and production limiter keys live outside the Node process. Redis RSS is not app-process RSS.
- **Container:** aggregates all process RSS plus runtime/sidecar/kernel-accounted memory according to the cgroup metric. Do not use a container peak as a Node heap estimate.
- **Multiplicity:** module-global Custom Widget cache is per app process/worker. Generic handler caches are per handler instance per app process. In a multi-worker deployment multiply retained process-local cache bounds by process count; Redis-backed shared payloads are one Redis deployment's separate memory.

## Measurement plan (no measurement run here)

Use the already-running production analyzer/baseline; do not start a competing heavy workload. Record app PID/container and worker count, Node version, start/end time, cgroup memory current/peak, process RSS, `process.memoryUsage()` (`heapUsed`, `heapTotal`, `external`, `arrayBuffers`), request concurrency, response byte size/encoding/JSON node count, cache state/key churn, and Redis memory separately. Capture repeated idle baselines and post-GC points only if the existing analyzer supports them; avoid interpreting a single RSS sample as retained heap.

Exercise controlled request cycles: (1) cold Custom Widget query with 1 MiB near-limit JSON and secrets vs no secrets; (2) repeated cache hits, expiry with no later inserts, then insertion/eviction; (3) concurrency at configured production limits; (4) many unique runtime parameter keys to capacity; (5) generic handler cold/fresh/stale/error paths and multiple handler instances; (6) Redis-backed preview and limiter paths while watching Redis separately. Compare warm-up, steady-state, quiescent-after-expiry, and repeated-cycle deltas. A fix is supported only if post-cycle retained heap/key counts fall or stabilize while payload/status/freshness contracts remain unchanged. Do not compare heap snapshots alone to container peaks.
