The main route composes board providers through `apps/nextjs/src/app/[locale]/boards/_providers.tsx`; `/init` imports `OnboardingStudio` from `@homarr/onboarding`; the locale root renders `ViewportHint`, `Notifications`, `SpotlightProvider`, and a header that renders `LazySpotlight`. ## Finding 1: Board resize writes the viewport cookie every animation frame

**Call path and trigger.** The locale root mounts `ViewportHint` on every page. It writes the `homarr-viewport-width` cookie immediately and debounces subsequent resize writes by 150 ms. On board pages, `BoardProviders` mounts `BoardProvider`; its `useSyncExternalStore` subscription also receives each window resize and batches layout updates to one requestAnimationFrame. That callback writes the same cookie before notifying React. Dragging a browser edge while a board is open therefore performs a synchronous cookie write on every animation frame as well as the existing debounced final write.

**Cause and dimensions.** For a resize lasting `R` rendered frames, this adds `R` synchronous `document.cookie` assignments, instead of the single trailing assignment already supplied by `ViewportHint`. The store subscription still needs per-frame notifications to switch responsive layouts. The extra write has constant space use; its CPU/main-thread cost is not measured here. Both writes persist the same rounded viewport width with the same path and max age.

**Minimal compatible fix and tradeoff.** Remove the cookie assignment from the board subscription and keep `onStoreChange()` in the frame callback. Let `ViewportHint` remain responsible for the initial value and debounced resize persistence. This preserves live layout switching while eliminating duplicate per-frame storage work. The tradeoff is that server-side viewport hints update after the existing 150 ms quiet period, which already defines root-level behavior.

**Evidence and confidence.** Directly confirmed at `packages/boards/src/context.tsx:24-41,103-105,178-180` and `apps/nextjs/src/components/layout/viewport-hint.tsx:8-24`. The duplicate write path and trigger are high-confidence; user-visible impact is likely small and needs a browser trace to quantify. A baseline measurement should count cookie assignments and main-thread time during a fixed 3-second window resize, before and after removing the board write.

## Finding 2: Spotlight filters complete catalogs on every non-empty query

**Call path and trigger.** `LazySpotlight` loads the Spotlight module on first open (or preloads it after one second while idle) and mounts `<Spotlight />` after the open event. `Spotlight` calls `useSpotlightCatalogs()`, which enables the board catalog for resolved sessions and the search-engine catalog for resolved sessions; it enables app and integration catalogs for eligible authenticated users. The app, board, integration, and external-search groups call the same query hooks and run `filterCatalog` as the query changes. For a non-empty query, the helper lowercases searchable fields and creates a scored object for every option, filters matches, sorts all matches, then keeps only the first eight (ten for external engines). This is repeated across each active catalog group on keystrokes.

**Cause and dimensions.** Filtering is O(N) per option scan plus O(M log M) sorting for `M` matching entries, with O(N) temporary score/value allocations; `N` is each full catalog size. The APIs are unbounded in these paths: `board.catalog` passes no limit, `app.selectable` returns every app, `integration.all` returns all accessible configured integrations, and `searchEngine.catalog` returns all available engines. The UI renders only a small prefix. The app-selectable payload also includes `pingUrl` and `description`, which this Spotlight group neither searches nor displays; it uses app id/name/icon/destination. Current compressed transfer size, cache retention, catalog cardinality, and per-keystroke time were not measured.

**Minimal compatible direction and tradeoffs.** For large catalogs, use a bounded server-side search result shape for Spotlight, preserving current scoring/tie order and permission rules, and request results only when the debounced query is non-empty. Keep the existing selectable catalog available to its other consumers. This reduces transfer, retained response data, and client work at the cost of query requests while typing and requiring server-side parity for matching semantics. A smaller isolated change is a bounded top-k selection in `filterCatalog`, which preserves the current catalog cache but reduces sorting allocations/work from O(M log M) to O(N log k); it does not reduce catalog transfer or retained cache data.

**Evidence and confidence.** Query and filter behavior is at `packages/spotlight/src/lib/catalog.ts:17-35,37-68,71-95`; the app consumer is at `packages/spotlight/src/modes/app-integration-board/apps-search-group.tsx:98-109`; Spotlight invokes the catalog hook at `packages/spotlight/src/components/spotlight.tsx:39-45`; lazy mount/preload is at `apps/nextjs/src/components/layout/header/lazy-spotlight.tsx:24-64`. API contracts are in `packages/api/src/router/board.ts`, `packages/api/src/router/app.ts`, `packages/api/src/router/integration/integration-router.ts`, and `packages/api/src/router/search-engine/search-engine-router.ts`. Complexity is directly evident and the API inputs are unbounded. Practical impact is medium confidence because real cardinalities and browser timings are missing. Baseline should record item counts, serialized response bytes, gzip bytes, cache retained size, and per-keystroke CPU for small (10), medium (100), and large (1,000) synthetic catalogs; compare the existing sort with bounded top-k and a server-search prototype while checking result parity.

## Remaining review notes

The board context uses one query result as its context value and derives the responsive layout from the viewport store; viewport subscriptions remove listeners and cancel pending animation frames on cleanup. The edit-mode provider delegates disclosure lifecycle to Mantine and resets its initial state when the route prop changes. Settings builds a small settings object from public server settings and a selected user-field subset. Notifications are three small wrappers around Mantine's notification store with fixed color/icon overrides. Spotlight's remote group queries use a shared debounced policy, and user/group/integration/media searches apply minimum lengths or result limits. No further actionable issue was established in the remaining assigned code.
