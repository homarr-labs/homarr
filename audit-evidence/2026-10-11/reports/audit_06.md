# Audit 06: widget inputs and widget families A

## Actionable opportunities

### 1. Do not retain unsupported countdown time zones indefinitely

**Files and call path:** [countdown/recurrence.ts](../../../packages/widgets/src/countdown/recurrence.ts) defines a module-level `Map<string, boolean>` and caches both valid and invalid `Intl.DateTimeFormat` lookups. [countdown/component.tsx](../../../packages/widgets/src/countdown/component.tsx) calls `getCountdownEventState` for every configured event whenever the widget clock changes. The option is created in [countdown/index.ts](../../../packages/widgets/src/countdown/index.ts); [options.ts](../../../packages/widgets/src/options.ts) validates each `timeZone` as only a non-empty string and caps a widget at 20 events. The normal editor presents supported timezone choices, but the API save procedure accepts arbitrary unknown option values: `packages/api/src/router/widgets/options.ts` merges `newOptions` from a `z.record(z.string(), z.unknown())` into stored options without applying widget option schemas.

**Trigger and cause:** A board editor with modify access can save countdown events containing distinct unsupported timezone strings through the option-save API. When a mounted countdown evaluates those events, each distinct string is inserted into the process-wide map and remains there after the widget unmounts or the option changes. Repeating this with unique values grows retained entries without a bound. The normal UI does not generate this input, so this is a malformed or direct-API configuration path.

**Dimensions and complexity:** This is process-lifetime retained server/client module memory, depending on which runtime evaluates the recurrence module; the widget runs client-side, so browser heap is directly relevant. Retained memory is O(U) in the number and total length of distinct invalid timezone strings seen by that module instance. The lookup itself is O(1) after insertion. No heap measurement or proof of API request size limits was collected; material impact depends on repeated unique values and is not established.

**Smallest compatible direction:** Cache only successful timezone validations, or cap the map with a small LRU. Not caching failures avoids retaining arbitrary invalid strings while keeping the finite set of ordinary timezone values fast. This repeats the relatively cheap validation for malformed values; a bounded cache adds a little implementation complexity. Preserve the current unsupported-zone behavior.

**Confidence and gaps:** High confidence in the unbounded retention path and accepted input shape; low-to-medium confidence in user-visible impact because the supported editor does not produce invalid values and heap growth was not measured. A baseline should save/mount a controlled series of unique invalid timezone strings, record cache entry count and browser heap before/after, then verify reclamation or a stable cap after unmount/update.

### 2. Avoid repeatedly copying Tracearr dashboard arrays while merging integrations

**Files and call path:** [tracearr/component.tsx](../../../packages/widgets/src/tracearr/component.tsx) queries `widget.tracearr.getDashboard` and folds successful responses into `combinedData`. Each fold creates fresh arrays for accumulated `streams.data`, `streams.summary.byServer`, `violations.data`, and `recentActivity.data` with spread concatenation. The router in `packages/api/src/router/widgets/tracearr.ts` loads every selected integration through `settleIntegrationQueries`; `packages/definitions/src/widget-integration-map.ts` gives Tracearr no `maxIntegrations`. The integration's `getStreamsAsync` in `packages/integrations/src/tracearr/tracearr-integration.ts` parses the upstream streams array without a page-size parameter or local cap. The widget refreshes every 10 seconds.

**Trigger and cause:** With multiple selected Tracearr integrations returning many active sessions, each reduce step recopies all previously accumulated rows. For equally sized responses, the merge work grows quadratically with integration count for each merged array, instead of linearly with total rows. The component also maps streams into sourced display rows; that copy is needed to attach integration labels/keys and is separate from the repeated prefix copies.

**Dimensions and complexity:** This is transient client CPU and allocation churn during each query update, with temporary arrays proportional to accumulated response size. It is not evidence of a retained-memory leak. The transfer is the upstream response size and is unaffected by the local merge. No real response sizes, browser CPU profile, or peak heap comparison were available, so the user-visible cost is unknown.

**Smallest compatible direction:** Build the aggregate with local mutable arrays and append each integration's rows once, or precompute per-field results in a single pass. This keeps source arrays untouched and makes merge work O(total rows); it trades a purely functional reducer for a locally mutated accumulator. Keep summary values and partial-integration behavior identical.

**Confidence and gaps:** High confidence in the repeated-copy complexity and unbounded integration selection; medium confidence that it is material in practice. Measure browser CPU and heap for one versus several integrations with representative and stress-sized stream responses, and record response bytes/rows. There is no production change or benchmark in this audit.

## Reviewed but not promoted

- **Large input files:** `widget-multiReleasesRepositories-input.tsx` received a dedicated full-file pass. Its import modal is an explicit admin action, and only that modal queries Docker containers; selection state stores references to imported rows. The external container inventory size and peak modal heap were not measured, so this was not promoted.
- **Large Beszel system grid:** `beszel-system-grid/component.tsx` received a dedicated full-file pass and caller review. It renders each filtered system, with a fixed metric registry and responsive metric cap in compact mode; the advanced mode renders every applicable metric. The server response and realistic system counts were not measured. No lifecycle or unbounded state retention was found.
- **Large Beszel stats view:** `beszel/_shared/stats-view.tsx` received a dedicated full-file pass and modal caller review. Hidden metrics are passed as `undefined` into chart-data hooks; Docker history is requested only when a Docker metric is visible. The live subscription is skipped when disabled/page-hidden and stores separately capped 60-record system/container buffers, which reset when its key changes. No unbounded buffer was found.
- **Large Docker component:** `docker/component.tsx` received a dedicated full-file pass and caller review. It filters/sorts the fetched inventory and renders a table; action handlers are per-row, but no observed state or listener survives row teardown. The owning table's actual virtualization behavior and realistic container counts were not benchmarked.
- **Large media-server component:** `media-server/component.tsx` received a dedicated full-file pass and caller review. It renders each returned current session and one controlled details popover per row; only the selected row opens details. The API response size and realistic session count were not measured.
- Anchor Note loads Quill dynamically only when advanced display or editing requests the editor; edit history is configured for 200 entries and is tied to that editor instance. No evidence of eager dashboard loading or retained editor state after unmount was found.
- Coolify accordion panels use `keepMounted={false}`; media-missing compact tabs use `keepMounted={false}` and only render the active panel. Video.js is disposed on widget teardown. Widget component loaders are explicit dynamic imports in the manifest; the registry contains type-only imports and literal loaders.
- Wazuh top-list and vulnerability options cap returned list sizes at 50. Media-missing uses a page-size option and API validation bounded to 1–50. Wazuh, Beszel live chart buffers, countdown event count, and world-clock city count have explicit caps in the inspected definitions.
- The widget input registry statically imports the option controls for the widget edit modal, but heavy editor/runtime widget components remain behind explicit widget/component imports. No bundle artifact or chunk-size measurement was produced, so no bundle-size claim is made.
- The remaining assigned input, widget, definition, style, query, and prefetch files were reviewed individually for local state, enabled queries, mapped/rendered collection sizes, component import paths, and cleanup. No additional actionable path with evidence stronger than the two findings above was identified.

## Evidence limits

No production changes, tests, builds, Docker work, or benchmarks were run. The findings are source-backed retention/complexity paths with missing runtime measurements called out above. Bundle bytes, response transfer bytes, transient allocations, and process/browser retained memory are treated as separate dimensions. Per-file coverage is in `audit-evidence/2026-10-11/coverage/audit_06.json`.
