# API foundation, boards, apps, Custom Widgets, and Assistant audit

Scope: every path in `assignments/audit_11.json` was read in full. The two assigned large files received dedicated complete passes: `packages/api/src/router/assistant.ts` (1,038 lines) and `packages/api/src/router/board.ts` (3,133 lines), followed by caller and schema review. The only production edits are the three item projections described below. No tests, builds, or post-change benchmarks were run.

## Findings

### 1. Integration middleware loads full nested item rows for a board access check

**Call path and trigger.** Any API procedure composed with `createOneIntegrationMiddleware*` or `createManyIntegrationMiddleware*` enters the corresponding factory in `packages/api/src/middlewares/integration.ts`. The database query requests `items: { with: { item: true } }`, loading each linked integration-item association and every field of its `item` row. The relation is destructured as `_ignore1` before `next()`, but it is not dead: `hasQueryAccessToIntegrationsAsync` in `packages/auth/permissions/integration-query-permissions.ts` reads `integration.items[].item.boardId` to enforce board-inherited query access. The factories are used by integration and widget query/action procedures throughout `packages/api/src/router/` (for example, calendar, downloads, and media server).

**Cost and dimensions.** For one integration, the avoidable work grows with the number of linked item associations; for the many-integration path it grows with the sum of associations for all requested integrations. This adds database result materialization and transfer to the API process, transient server RAM, and ORM/object construction CPU. It does not increase the final tRPC response or network payload because the relation is discarded before the procedure handler returns. The supplied pre-change source-measurement baseline used 250 linked items with 32 KiB option data each: materialized query result size was 8,243,961 bytes and held post-GC heap delta was 8,276,016 bytes. These are database-query-result and in-process heap measurements, not HTTP/tRPC network bytes. The main dashboard schema permits many items per board, so this relation is not structurally capped by this middleware.

**Cause and smallest fix.** The nested item projection included all columns even though access checks consume only `item.boardId`. Implemented: all three matching nested item relation projections in `middlewares/integration.ts` (one- and many-integration factories) and `router/integration/integration-router.ts` now select only `boardId`, retaining the association rows. App, secrets, user permissions, and group permissions remain as before. The selection change preserves the `integration.items[].item.boardId` auth contract.

**Compatibility and tradeoffs.** This does not change the tRPC input/output, authorization decision, ordering, or freshness; it narrows internal fields while retaining `boardId` for access checks. No API compatibility change is expected. The post-change paired measurement is pending the root harness; no reduction is claimed yet. Validate parity for board-inherited access and compare selected columns, database result bytes, and process heap/CPU at the same fixture. Confidence: high for avoiding unused columns; measured magnitude remains pending.

### 2. Anonymous app visibility scans and parses all app/bookmark widgets on each lookup

**Call path and trigger.** `app.byId` calls `AppRepository.getByIdAsync()`, which delegates to `getByIdsAsync()` and `AppAccessControl.canUserSeeAppsAsync()`. `app.byIds` uses the same path. For anonymous callers, `getAllAppIdsOnPublicBoardsAsync()` queries all `app` and `bookmarks` items without filtering to public boards in SQL and without projecting columns. It fetches each item row plus `board.isPublic`, filters private boards in JavaScript, parses each public item’s SuperJSON `options`, and collects app IDs. Signed-in callers bypass this scan.

**Cost and dimensions.** Each anonymous lookup performs work proportional to all app/bookmark widget rows across the instance, including private-board rows, and parses option payloads on public rows. Repeated `byId` requests repeat the scan. The avoidable dimensions are DB result transfer/materialization, transient API RAM, and SuperJSON parse CPU; no bytes leave the API from this scan itself. `byIds` has no input array maximum, but the repeated whole-table scan is independent of requested IDs and is the primary issue. No live row counts, byte counts, timings, or heap measurements were collected.

**Cause and smallest fix.** The access check needs only IDs parsed from app/bookmark options on public boards, but it loads complete item rows and performs visibility filtering afterward. Use a narrow select for `kind` and `options`, join/filter public boards in the database, and consider resolving only requested app IDs while preserving bookmark semantics. The exact query change should retain the rule that a bookmarked app counts as visible only when that bookmark widget is on a public board.

**Compatibility and tradeoffs.** Preserve the current anonymous rule, logged-in fast path, and public-board visibility. A DB-side join changes query shape but not output or authorization ordering. Verify parity for direct app widgets, bookmark widgets, private/public boards, and mixed requested IDs; measure rows and bytes read as total private and public widget counts grow. Confidence: high for repeated broad scan; workload impact is unmeasured.

## Large-file review notes

### `assistant.ts` — complete 1,038-line pass

Thread loading selects every message row for an owned thread, orders by `(createdAt, id)`, parses each complete SuperJSON `content`, and returns all messages. `appendMessage` accepts `content: z.unknown()` and stringifies the full value without an explicit content-byte limit. Concrete clients confirm that `assistant-provider.ts` loads the complete transcript into assistant-ui’s history adapter and `assistant-history.tsx` uses the same endpoint to export the whole conversation. The database schema has no message-count or content-size bound. This is an unbounded-per-thread RAM/parse/transfer path, but complete history is currently needed by both rendering and export, so pagination/truncation would change user-visible history semantics and require client adapter work. There is no measured transcript-size distribution or request-size evidence here; I am recording it as a scaling constraint rather than a confirmed defect.

Other examined state has explicit bounds: model discovery slices the accepted model list to 1,000 and caches only the latest list; generation telemetry cache is LRU-like and capped at 512 entries with five-minute expiry; generation IDs per message are capped at eight. Assistant context lookup caps apps and integrations at 250, items at 500, and referenced entities at 30 per type. No unexpected retained assistant cache was found.

### `board.ts` — complete 3,133-line pass

The full-board loader intentionally reads board sections, items, layout rows, their widget options, and user/group permissions because `getHomeBoard` and `getBoardByName` feed the complete dashboard and editor. In contrast, the management overview uses a row-bounded preview (`12` default, `48` maximum), selects only preview columns, and resolves app icons separately. Placement serialization stores only in-flight per-board promise tails and deletes the entry in `finally`; protected-layout repair promises are likewise removed in `finally`. Responsive layout and full-content save inputs use arrays without explicit item/section count limits, and save diff helpers use repeated array scans; this is a possible CPU scaling dimension for unusually large boards, but no demonstrated board-size trigger or baseline was available to classify it as a defect.

## Other scope observations

- Integration access relations required for permission checks remain in use; the discarded linked-item relation is isolated above.
- Custom Widget authoring templates are bounded at 50,000 characters in template validation; preview query/action response JSON is budgeted in the owning server package. Preview sessions, journals, evidence, request concurrency, and response caches have explicit TTL/size policies in their owning service implementations. No persistent in-process preview-session retention was found in the assigned API wrappers.
- Custom Widget management list/get/migration queries load secret relations with `with: { secrets: true }` although their mappers use only secret metadata. The secret schema allows at most 24 secret inputs per widget, and this count is therefore bounded; encrypted values remain server-side and are never returned. The transfer is avoidable but low scale relative to the two findings above, so it is not reported as an actionable finding.
- OpenAPI, MCP and the app router were inspected for eager/lazy registration. The main app router uses lazy feature routers; MCP intentionally eagerly registers selected routers for synchronous extraction. The MCP import of `customWidgetRouter` reaches `metadata-procedures` → `authoring-resources` → `authoring-catalog` → a static `component-catalog.generated.json` import. The generated JSON is 861,611 UTF-8 bytes and contains 475 components, 440 global props, 509 types, and 4,104 component prop descriptors. This is raw source-asset evidence; bundle delta, parse CPU, startup latency, and retained heap were not measured. The compact catalog response projects names/category/safety, and selected detail endpoints return bounded subsets, so this remains a loading observation rather than a separate finding.

## Evidence limits

This is source/query-shape evidence only. No production-like database fixture, SQL trace, runtime heap profile, network capture, generated bundle analysis, or benchmark was run. The two findings identify code paths with avoidable work and give a measurement plan; they do not quantify deployment impact.
