# Audit 02 — Management catalogs and integrations

## Scope and confidence

All 70 assigned files were read individually, including the dedicated complete 653-line pass of `manage/users/[userId]/general/_components/header-composer.tsx` and its page/form caller. File-level inspection evidence is in `coverage/audit_02.json`. Follow-up inspection covered the owning group/app/board API procedures, `UserAvatarGroup`, the board name availability hook, and Mantine Collapse 9.6.0 implementation. A dedicated synthetic browser fixture measured the frozen BoardCard baseline and a one-prop candidate across 1/25/100 cards, both permission states, and nine fresh-process pairs.

Three actionable resource findings remain. The BoardCard footprint is measured in an isolated synthetic browser fixture; group payload and integration-selector impact are code-path findings without runtime sizing. No live-server RAM, real production network transfer, route bundle, or CPU figures were measured. No tests or builds were run. The only production edit is the narrow BoardCard `keepMounted={false}` prop supported by the paired synthetic-browser evidence.

## Finding: collapsed BoardCard panels retain unused duplicate-form trees

**Call path and trigger:** `/manage/boards` calls `api.board.getManageOverview()` and renders one `BoardCard` per accessible board. Each card wraps `DuplicateBoardForm` in a collapsed Mantine `Collapse`, including when the user lacks `board-create`. The installed Mantine 9.6.0 implementation defaults `keepMounted` to true and wraps retained children in hidden React Activity. The baseline retains each form's DOM and creates an unobserved pending `board.exists` query-cache entry while collapsed.

**Measured behavior:** The nine-pair run found zero hidden requests in both baseline and candidate, at every card count and permission level; the suspected eager-query/network claim is rejected. Baseline hidden queries had zero observers, consistent with Activity pausing effects. At initial collapsed render, 25-card DOM was 1,122 baseline vs 647 candidate, and 100-card DOM was 4,422 vs 2,522. Initial after-GC heap median at 100 cards was 58,231,628 bytes baseline vs 52,082,400 candidate with create permission, and 58,181,380 vs 52,036,864 without. The paired candidate heap deltas were -6,152,976 bytes (range -9,157,192 to -6,128,264) and -6,143,732 bytes (range -9,148,628 to -6,126,128), respectively. These are whole-fixture totals, not per-card costs. Full calibration and formal paired details are in [board-card-browser-calibration.md](../measurements/board-card-browser-calibration.md) and [board-card-browser-pairs-9.json](../measurements/board-card-browser-pairs-9.json).

**Dimensions:** The confirmed benefit is client DOM, retained client heap, and unused pending query-cache records. Server RAM, database reads, CPU, compressed transfer, and route bundle are unchanged/unmeasured: the browser fixture saw no hidden requests, and the prop does not add data or imports. Baseline hidden trees are mounted/retained rather than repeatedly allocated after each collapse. Candidate defers allocating the form tree until opened; after opening, normal form and availability-query allocation still occurs. Query entries for actually opened names remain cached under the five-minute gcTime during the bounded run.

**Minimal compatible fix applied:** Set `keepMounted={false}` on the existing BoardCard `Collapse`. This uses Mantine's built-in lifecycle behavior and keeps the same transition path. Baseline `duplicateFormKey` increments on every reopen, so an edited draft already resets to the source board name; the nine-pair run confirmed this along with existing-name validation, available-name feedback, submit state, and exactly one mutation. At 100 cards, first-open medians were 120.9 ms baseline and 148.3 ms candidate, but paired candidate-minus-baseline median was -1.9 ms with a -64.6 to +56 ms range; no consistent latency penalty was measured. Transition timing remained `height 200ms, opacity 200ms`; some in-animation height samples differed by 2px, and post-navigation DOM snapshots were too early to establish a steady baseline plateau.

**Confidence and limits:** Confidence is high that the built-in lifecycle removes collapsed form DOM and query-cache records in this fixture; confidence in real installation memory savings is medium because the isolated fixture mocks unrelated route pieces and does not measure a full Next.js production route. Compressed network bytes, server memory, and bundle size are outside this finding because no hidden request existed and the source delta adds no data or dependency.

## Finding: group overview sends every membership record to a client that displays at most five avatars

**Call path and trigger:** `/manage/users/groups` calls `api.group.getAll()` and passes its result through `GroupsList` to `GroupsTable`. The owning `group.getAll` procedure loads every group's complete `members` relation and selects each user's id, name, email, and image. The catalog uses ids/names/positions for sorting and filtering. Each row passes the full member array to `UserAvatarGroup`, which renders `users.slice(0, 5)` and only reads the total array length for the `+N` badge.

**Needed data:** The first five users need name/image and possibly email for configured Gravatar behavior. Remaining entries are only needed as a count. The current client payload therefore grows with all memberships, including email and user objects for members six onward. `group.getAll` has only this assigned route caller, so a specialized overview shape can be made without changing other in-repository callers.

**Dimensions:** Server-side database materialization and mapping currently scale with all membership rows. The full nested relation is serialized to the client and retained in the group query props/state, so transferred payload and client heap also scale with total memberships. Mapping and slicing are O(M) in total membership count; no large-list CPU measurements exist. This is excess payload/state, not an identified lifecycle leak. The effect is likely modest for small installations and can become material for large groups or many memberships.

**Minimal compatible fix:** Make the overview return only the avatar preview fields for up to five users and an aggregate member count; adapt `UserAvatarGroup` or this caller to consume `{ previewUsers, memberCount }`. A SQL-side count plus bounded related-user query is needed to reduce server materialization too; merely slicing after `findMany` would reduce transfer/retention but retain full server allocation. Preserve email only for preview users if Gravatar is enabled.

**Baseline measurement and tradeoffs:** Seed representative groups with increasing membership counts and compare server result bytes/heap, serialized RSC payload bytes, and browser retained heap after load. Keep count and avatar order identical. Confidence is high for unnecessary client fields and rows; practical impact is medium/low until real membership distributions are known. Query-shape complexity is moderate because the count and first-five preview need database support.

## Finding: hidden existing-app selector fetches the full selectable app catalog

**Call path and trigger:** `/manage/integrations/new?kind=...` renders `NewIntegrationForm`. For users with `integration-create` but without `app-create`, `hasApp` starts false and the app linking section is collapsed. `AppForm` still mounts `IntegrationAppSelect`, whose `clientApi.app.selectable.useQuery()` has no `enabled` condition. `app.selectable` returns every app with id, name, icon URL, destination URL, ping URL, and description. These options are only displayed when the user enables app linking to an existing app.

**Dimensions:** This eagerly performs a request and retains all selectable app records in the client query cache, so network bytes and client heap scale with app catalog size. Server work is one full catalog query per new-integration form mount. The existing-app selector genuinely needs the option list when opened; the avoidable portion is fetching it before the control is shown. No bundle size issue is claimed because the data is runtime-loaded. No app-count or payload measurement is available.

**Minimal compatible fix:** Pass an `enabled` condition to `IntegrationAppSelect` based on `hasApp` and existing-app mode, and preserve the query cache once loaded. With `app-create`, the initial mode is new-app entry; the list is only needed after the user selects existing. Without `app-create`, it is only needed after enabling linking.

**Baseline measurement and tradeoffs:** Compare the initial request count and response bytes on the new integration route across both permission states, then enable the relevant selector and confirm options still load. The selector may briefly show its existing loader on first open. Confidence is high in the eager-fetch path and medium in impact, dependent on app count.

## Dedicated large-file pass: user header composer

The complete `header-composer.tsx` (653 lines), full stylesheet, and the user general-settings page/form caller were read. The component receives only the current user's header preferences and a managed-board overview requested with `fullPreview: false`; the overview API limits preview rows to 12 by default. It derives maps/arrays for the bounded set of boards and active header items and renders drag-and-drop sensors/providers only while the preview is visible. Its pointer listener is attached to the zone container in an effect and removed in cleanup. The dashboard thumbnail renders a projected, row-limited preview. These allocations follow the editable preview's normal bounded workload; no measurable or unbounded retained data was demonstrated. No timeout, object URL, or uncleaned event subscription was found.

## Other reviewed data and asset paths

The app catalog uses `getPaginated` with a maximum page size of 100 and sends only the selected page to the server-rendered list. The integration management list loads all integrations and filters/sorts them server-side; result count is installation-bounded and no oversized field duplication was demonstrated in the listed UI. Integration create/edit form data and certificate PEM content appear only on those routes and on the corresponding error/action state; there is no generated asset or persistent binary buffer in the reviewed files. Media listing is page-size bounded to 100, and image bytes are referenced through local media URLs rather than embedded into each row. No further actionable finding was established in the remaining user, group, board, app, integration, and media files.
