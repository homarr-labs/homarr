# Build and startup memory overview

## Scope and evidence

This is a direct source/configuration audit of the checked out baseline (`bab8e2a2dad837365a2237263b58b658d23abe69`). Installed versions are Next.js 16.3.6 and Turborepo 2.11.7. I used Next's installed, version-matched `node_modules/next/dist/docs/01-app/02-guides/memory-usage.md` and package-bundling guide, plus Turborepo's installed `docs/README.md` and package/task graph and task configuration pages. Context7 requests are unavailable because the monthly quota was exhausted (already communicated); API guidance below is verified against the installed Next package and its bundled official docs.

No production build, test, Docker build, or memory benchmark was started in this subtask. The coordinator's Next experimental analyzer baseline completed; its server graph is under `apps/nextjs/.next/diagnostics/analyze/data/`. This report now includes emitted module/chunk evidence from those analyzer data files, but has no RSS/heap or process-startup measurement. The analyzer output is not a runnable production artifact.

## Findings

### Production server startup preloads every page entry

`apps/nextjs/next.config.ts:45-51` sets `experimental.preloadEntriesOnStart: true`. The installed Next 16.3.6 memory guide states that the server preloads each page's JavaScript modules into memory at startup, trading a larger initial footprint for faster responses; it also states that disabling it delays loading until requests and does not reduce eventual memory if users visit all pages. This is a direct supported memory lever, but the repository has no measurement showing its current cost or whether it is a dominant source.

Smallest compatible candidate, if cold-start memory is the measured problem: set `preloadEntriesOnStart: false` and compare time-to-ready/first-hit latency plus process RSS/heap on the same route-use sequence. Tradeoff is first-hit module loading and eventual convergence when all routes have been exercised. Confidence in API semantics: high (installed official docs); confidence that this improves Homarr's real workload: unmeasured.

### Embedded services are deliberately eager in production, split out in development

Call path: Next invokes `register()` in `apps/nextjs/src/instrumentation.ts:1-7`; it returns unless runtime is `nodejs` and `NODE_ENV` is `production`, then imports and awaits `instrumentation-node`. That function (`apps/nextjs/src/instrumentation-node.ts:1-34`) concurrently imports `@homarr/tasks` and `@homarr/websocket`. It intentionally does not await the tasks service's longer `startupPromise` (instead logs failure and exits), while it does await WebSocket readiness. Thus `import()` defers module loading until the production instrumentation hook, but both service modules are still loaded at every production server startup. `apps/nextjs/next.config.ts:17-30` aliases both service packages to `instrumentation-noop.ts` in development; `bun run dev` also starts only Next.js, with companion services run separately per the repo instructions.

No smaller safe fix is indicated by source alone: tasks and WebSocket are production capabilities, and moving them to another process changes runtime topology/operations. Keep the startup sequence unless measurement shows one service dominates and product/runtime owners accept a split-process option. The two-service startup is in the critical path because `register()` awaits both import flows and WebSocket readiness; tasks' post-import startup work is detached. Confidence: high for the call path, no timing/RSS evidence.

### Both database dialect schemas are emitted into the awaited WebSocket startup graph

`packages/db/schema/index.ts:1-14` statically imports both `./postgresql` and `./sqlite`, then chooses a schema via `createSchema`. `packages/core/src/infrastructure/db/mapping.ts:1-10` selects the configured key synchronously. The analyzer confirms all five static dependencies of the schema entrypoint in the instrumentation context, including both dialect schema modules; neither is tree-shaken. The startup call path is `instrumentation.ts` -> dynamic `instrumentation-node.ts` -> dynamic `apps/websocket/src/main.ts` (awaited for WebSocket readiness) -> static `@homarr/db` -> `packages/db/index.ts` -> schema index -> both dialect modules. The WebSocket entrypoint imports `db` at module top level. Analyzer output for this graph places `schema/index.ts` (1,822 bytes), `schema/postgresql.ts` (25,902 bytes), and `schema/sqlite.ts` (24,708 bytes) together in each of seven server chunks; one representative output chunk is `packages_1c12vyu._.js`. Their combined contribution there is 52,432 raw bytes and 9,529 `compressed_size` bytes. This is emitted code evidence and a concrete eager startup dependency, not an RSS/heap delta.

The smallest plausible fix is to select and dynamically import only the configured schema module during schema-index module evaluation, with a type-only import/cast to preserve the existing exported `schema` type and name. ESM module evaluation will wait for top-level `await` before consumers evaluate, so callers can keep their current synchronous use after import completes. This changes module evaluation timing and must be checked against Next/Turbopack, Bun/tsx and any CJS migration bundles before adoption; the analyzer run does not test that compatibility. Do not replace this with fire-and-forget imports. Confidence: high that both dialect definitions are emitted and startup-reachable; actual memory benefit and compatibility remain unmeasured.

### The integration barrel defeats the lazy factory boundary for widget mock imports

`packages/integrations/src/index.ts:2-51` statically re-exports integration classes. `packages/integrations/src/base/creator.ts` separately uses an explicit `integrationCreators` map with literal `import()` calls; its `createIntegrationAsync` dispatches by integration kind (around lines 360-405). The analyzer resolves this distinction: the integration root module has 56 static module dependencies and 0 async dependencies in each instrumentation, app-RSC, and app-route context; the creator has 2 static dependencies and 90 async integration dependencies. In the instrumentation analyzer output, all 56 of the root barrel's direct integration source dependencies have emitted chunks (0 missing). Their unique source contribution is 188,024 raw bytes / 71,042 `compressed_size` bytes. 44 sources occur together in each of nine `[root-of-the-server]__*.js` output chunks, with 137,156 raw / 52,955 compressed bytes per chunk. For example, the Plex implementation is emitted in ten output chunks, including the root-of-server chunks and an integration-specific chunk. The barrel's own chunk also contains the root entry (111 bytes), `src/index.ts` (1,060 bytes), and `mock/widget-data.ts` (7,566 bytes). These are analyzer chunk byte counts, not a measured memory cost; repeated output chunks must not be summed into a process footprint.

Global source search finds 18 non-test runtime imports from `@homarr/integrations`; all are widget API routers importing `mockWidgetData`, with `wazuh.ts` also importing `toWazuhPublicError`. Remaining root-entry imports found are type-only. These routers are loaded through lazy edges in `packages/api/src/root.ts` and `packages/api/src/router/widgets/index.ts`. So the broad static import set is emitted and can be loaded when a widget router is resolved; the analyzer does not establish that all these classes are evaluated during process startup.

If this coupling is later selected for a focused bundle experiment, the smallest compatible entrypoint candidate is additive: export `./mock` for `src/mock/widget-data.ts` and `./wazuh-errors` for `src/wazuh/wazuh-errors.ts`, switch the 18 runtime widget-router imports to those subpaths, and keep every existing root export intact. This preserves the existing package root contract while removing those production callers' source dependency on the barrel. `@homarr/integrations/factory` remains the caller path for dynamic integration constructors, so its 90 async imports remain selected by integration kind. This audit did not make that change or run an after-change analyzer; emitted graph impact, byte delta, and runtime memory benefit are therefore unmeasured. The current result is verified baseline coupling only, not a recommendation to make a second bundle change during the compact runtime catalog measurement. Confidence: high on current emitted barrel membership and caller inventory; no measured before/after effect.

### Widget and Custom JSX registries contain lightweight descriptors and dynamic loaders

`packages/widgets/src/registry.ts:75-220` maps widget kinds to literal dynamic `import()` loaders; `:223-300` separately maps component loaders. Its comment explains that the two loaders start concurrently on a cold widget load. This means registry enumeration does not itself statically import each widget implementation in source; it does retain loader functions and a broad import context. Actual chunk/loading behavior must still be confirmed in the analyzer. `packages/custom-widgets/src/core/component-registry.ts:1-65` eagerly maps `customJsxAuthoringCatalog` into descriptor arrays and Maps/Sets for validation/lookup. This is deliberate registry metadata, not eager import of every component implementation. Its cost is likely bounded data/collection allocation, but no byte/heap measurement was made.

Minimal compatible direction only if metadata size is measured as material: avoid duplicate derived collections or limit catalog use at consumer boundaries while preserving the validator/authoring contracts. No change warranted from inspection alone.

### Build, dev, production runtime, source maps, cache, and deployment artifacts are separate costs

- Production compilation is `apps/nextjs/scripts/assemble-standalone.mjs` -> Turbo `build` task -> `apps/nextjs/scripts/compile-standalone.mjs`, which copies Next's standalone launcher, then artifact assembly. `Dockerfile` uses Node 24.18 Alpine in the builder and ships `.output/standalone`; final image does not contain the full repository source tree. Build-time RSS is a Node builder measurement and cannot be inferred from production RSS.
- `bun run dev` executes `next dev`; dev HMR/Turbopack caches and dev services differ from production. `turbopackFileSystemCacheForBuild: true` is build cache configuration, not evidence of production resident memory. Dev behavior should be measured in a separate run.
- Production `scripts/run.sh` sets `NODE_OPTIONS="--max-semi-space-size=4 ..."` immediately before starting the Next server; this caps V8's young-generation semi-space to 4 MB but is not a process RSS/heap cap. It starts Redis/nginx and the Next child in the same container, so container memory is not Next-process memory. Use process RSS/heap for the server plus separately record container totals if evaluating deployment limits.
- Next memory guide notes source maps consume build memory. It says source maps are generated during prerender by default and identifies `productionBrowserSourceMaps`, `experimental.serverSourceMaps`, and `enablePrerenderSourceMaps` as controls. This app does not set those options in `apps/nextjs/next.config.ts`; source-level absence alone does not show which maps the current production build emits or their build cost. The guide's suggested toggles change debugging behavior; don't add them absent a measured build-phase issue and output review.
- Standalone inclusion is governed by Next's generated traces: `apps/nextjs/scripts/standalone-artifact.mjs` collects `required-server-files.json`, `.nft.json` traced dependencies and middleware assets; it skips `.next/cache`, `.next/dev`, and nested standalone files while preparing dependency artifacts. `assemble-standalone.mjs` copies app/server routes, `.next/static`, and `public`. Thus static assets, generated server route code, source maps, and server process heap are different quantities. `apps/nextjs/public` is 1.7 MB across 28 files at source checkout; that is raw source asset inventory, not compressed deployed size or RAM. `apps/docs` is separately configured with `output: "export"`; its static export is not part of the Homarr Next server runtime.

The docs site's `apps/docs/src/lib/source.ts` creates Fumadocs loaders over checked-in `docs/` and `blog/` collections, and `apps/docs/src/lib/openapi.ts` imports a 268,402-byte OpenAPI JSON artifact and prepares operation pages. The docs app is `output: "export"` in `apps/docs/next.config.mjs`, so this content processing and OpenAPI source generation belong to a separate docs build/export, not the Homarr server runtime. Docs routes also expose generated LLM Markdown and search (`src/app/llms*`, `src/app/api/search/route.ts`), which can make the docs app itself more expensive when requested if those routes are not statically exported; that app was not measured. Other library modules are small runtime helpers: `pocketbase.ts` memoizes Workshop clients per normalized URL; `analytics.ts` is client-only and initializes PostHog once; `runtime-config.ts` reads injected browser config; metadata and author helpers are static values. `apps/docs/public` is 2.1 MB and the docs content tree is 23 MB in the checkout; the public generated widget catalog JSON is 861,611 bytes. These are source artifact sizes, not in-memory or served-size measurements.

Turborepo 2.11.7 docs say `dependsOn: ["^build"]` orders dependency builds, while `outputs` declares cacheable files. Here the app override is decisive: `apps/nextjs/turbo.json` makes `build` depend on `build:dependencies`, which depends on `build:compiled`; `build:compiled` owns `.next/**` outputs while excluding `.next/cache`, `.next/dev`, and `.next/standalone`; `build:dependencies` owns `.output/dependencies/**`; final `build` is uncached and owns `.output/standalone/**`. This explains artifact boundaries and orchestration, not runtime heap directly. No Turbo configuration recommendation follows from this memory audit.

CI's `tooling/github/setup/action.yml` separately restores optional Next compiler caches at `apps/nextjs/.next/cache` and `apps/docs/.next/cache`; `tooling/github/docker-build.sh` forwards available Turbo cache credentials as BuildKit secrets. These may change build time/peak build memory between cold and warm builds, so benchmark reports must record cache state. They do not demonstrate a production process memory improvement.

## Evidence gaps and next useful evidence

1. The baseline analyzer proves both database dialect schemas are emitted on the WebSocket startup graph and all 56 direct integration barrel dependencies are represented in instrumentation output chunks. It does not measure live heap or show whether each API widget lazy edge is loaded at startup.
2. For any future bundle experiment, compare analyzer graphs before and after; runtime memory must be measured separately after ready and after a fixed set of widget procedures because those imports are lazy. This is outside the current compact runtime catalog comparison.
3. Capture separate, comparable measurements: builder process peak RSS/heap by build phase; production Next child RSS/heap immediately after ready and after fixed route visits; dev Next process RSS/heap after ready and after representative HMR; record Node version, environment, fixture, request sequence, limits, and cache state. Avoid using the all-process container number as a Next-only metric.
4. Inspect completed production artifacts for `.map` files and report their bytes separately from `.next/static`, server bundles, `.output/dependencies`, and `public`; do not infer these from source checkout sizes.
5. If changing preload settings is considered, compare enabled/disabled cold start and first request as well as warmed memory. If changing module boundaries, prove the resulting analyzer graph and validate all consumers before claiming benefit.
