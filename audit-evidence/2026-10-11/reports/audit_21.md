# Audit 21: common, definitions, validation, locales, server settings

## Result

One low-severity allocation finding is identified in `packages/common/src/bounded-response.ts`. It enforces a strict input byte cap, but creates an avoidable full-response copy while joining stream chunks. No production files were changed and no tests, builds, or benchmarks were run.

## Finding: bounded JSON response reader duplicates the capped byte payload

The reader first retains each `Uint8Array` chunk in `chunks`, then allocates a contiguous `Uint8Array(byteLength)` and copies all chunk bytes into it. That adds up to one response-cap worth of transient raw-byte allocation during assembly. Decoding then creates a string, and `JSON.parse` creates the object graph. Whether V8 collects the no-longer-used chunk references or contiguous bytes before parsing depends on runtime liveness and GC; peak RSS was not measured.

Concrete path: a request handler or API route fetches untrusted JSON and calls the package helper. The in-scope call sites set caps of 512 KiB for timetable data (`packages/request-handler/src/timetable-url.ts`) and 2 MiB for both custom API responses (`packages/api/src/router/widgets/custom-api-security.ts`) and Traefik responses (`packages/integrations/src/traefik/traefik-bounds.ts`). At the 2 MiB cap, the assembly step can hold the incoming chunk backing stores and a further 2 MiB contiguous buffer. The later decoded string and parsed result add payload-dependent memory. Concurrent requests multiply the transient cost.

- **Trigger and dimensions:** A valid, near-cap response reaching any of those consumers. This is a RAM allocation finding; response transfer is still capped, and CPU remains linear in response bytes. There is no evidence of persistent retention after the function returns.
- **Cause and complexity:** O(M) stream reads and copy work for a response of M bytes; `chunks` plus the contiguous body temporarily account for roughly 2M raw bytes before decoding. Parsing and object overhead are inherent in returning a parsed JSON value.
- **Smallest compatible fix:** Decode chunks incrementally with one `TextDecoder` using `{ stream: true }`, append the final decoder output, and parse the resulting text. This can remove the additional contiguous byte buffer while retaining the byte-count guard. It trades one clear typed-array copy for chunk string pieces and requires careful final decoder flush behavior. A streaming JSON parser would be a larger API/behavior change and is not justified by current evidence.
- **Measurements and confidence:** No runtime allocation, RSS, or concurrency measurements are available, so the user-visible impact is unquantified. The avoidable allocation is directly established by the implementation; impact confidence is low to medium because the strict cap is 2 MiB and traffic/concurrency distributions are unknown.
- **Baseline plan:** Replay representative small, median, and near-cap payloads through the current and proposed readers under the same Node version. Record peak RSS and heap/external memory deltas, allocated bytes, CPU time, and throughput at expected concurrent request counts; verify parsed values and rejection behavior remain identical. Include compressed/streamed transport behavior only if the production fetch path exposes it.

## Locale and definitions loading assessment

`packages/translation/src/mapping.ts` creates a lazy dynamic import for each of the 36 supported language JSON files. The Next.js request configuration (`apps/nextjs/next.config.ts`) points to `packages/translation/src/request.ts`, which loads only the requested locale; non-English requests also load English for fallback. The client translation entry imports English as a type only. The language payloads total 12,081,804 source bytes (about 11.5 MiB); individual locale files range from 288 KiB to 464,200 bytes. This is source size, not emitted transfer size or parsed heap size. The source structure therefore avoids eagerly loading all locale catalogs in one request graph, though module-cache retention after different locales have been requested and actual client/server chunk sizes were not measured.

The definition registries and widget/integration mappings are static, bounded metadata. `integration.ts` received the required dedicated pass across all 1,227 lines. Its registry and kind lists are evaluated as module data; derived arrays/maps are built once, with lookup helpers returning only small arrays where needed. `widget-integration-map.ts` likewise computes fixed support maps once. The generated sitemap file exports a TypeScript type, so that large path union has no runtime emitted JavaScript; its runtime helper imports the path type only. No measurable bundle or startup cost was established for the runtime registries, and no production bundle was built.

`removeEmptyTranslations` in `request.ts` does create a new object accumulator through object spread for each child entry. On the checked English catalog this has a maximum object width of 78 and corresponds to 37,944 accumulated property copies across 2,037 objects. That deterministic source-shape count is not a runtime benchmark, and it does not establish material request cost; the implementation is therefore recorded as reviewed with no actionable finding.
