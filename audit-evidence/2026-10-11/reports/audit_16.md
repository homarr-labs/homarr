## Finding: Workshop listing fetches and renders every listing

**Call path and trigger:** `apps/docs/src/app/(home)/workshop/page.tsx` renders `WorkshopRoute`, which renders `WorkshopApp`. `WorkshopApp` calls `useWorkshop`; its initial effect calls `refresh()`, which calls `backend.listAll({ sort: "newest" })`. `WorkshopApp` keeps all returned records in React state and maps all filtered results to cards. The admin route also calls `listAll` and renders every submission.

**Cause and dimensions:** `packages/workshop/src/backend.ts` offers `list()` with a 24-record default page, but `listAll()` calls PocketBase `getFullList(batch: 200)`. Therefore initial listing transfer, client state, sorting, and DOM work grow with the full number of Workshop records: O(N) response/state/rendering and O(N log N) sorting when filters change. The fallback is more expensive: when the listings view returns a compatibility 400/404, `loadListingsFallback()` tries the view and then raw `submissions`; that raw path includes the full `content` field, which `parseListings()` removes only after it was transferred and parsed. No upper bound on total listings or fallback content is enforced in these callers.

**Evidence and dimensions:** The frontend code path and both backend branches were inspected. The normal listing view omits `content`, so the full-content transfer risk is conditional on the compatibility fallback. No live Workshop row count, response byte size, browser heap, render timing, or number of concurrent visitors was measured. The repository baseline has no such measurements. The issue is unbounded by code; severity depends on actual dataset size and whether deployments hit the fallback.

**Smallest compatible fix:** Use the existing paginated backend `list()` for the public listing and load further pages as the user requests them. Keep summary records in the listing response. For the compatibility path, project/select summary fields before fetching if PocketBase supports it, or page the raw collection and avoid downloading `content`. Apply equivalent pagination to the admin view only if moderator datasets warrant it.

**Tradeoffs and measurement plan:** Pagination changes filtering and sort semantics: server-side query options should preserve the current title/description/author search, type, outdated, and sort behavior across all pages. Before selecting page size, capture listing count, compressed and raw response bytes, number of cards rendered, transfer time, and peak browser heap for first page and full traversal. Separately force the compatibility path and measure bytes with small, median, and maximum-length contents. Complexity is O(P) per page with P bounded; loading all pages still costs O(N) cumulatively. Confidence is high in the unbounded code path and medium on material production impact without dataset measurements.

## Finding: the global Kapa mascot starts a continuously animated WebGL scene on every page

**Call path and trigger:** `apps/docs/src/app/layout.tsx` uses a default nonempty Kapa website ID and mounts `DocsMascot` under the root provider. `DocsMascot` immediately imports `./scene`, fetches the SVG, and constructs the Three.js renderer in an effect. The launcher is fixed to the viewport, so its intersection observer normally keeps the scene visible. For users without reduced-motion preference, `scene.ts` continues scheduling animation frames while the page is visible; it renders at approximately 30 fps (`now - lastRender >= 32`) even when the user is idle. The scene is dynamically split, but the effect requests its chunk and mascot asset on every page mount.

**Cause and dimensions:** This retains the WebGL renderer, scene geometry/materials, canvas, and associated GPU resources for the lifetime of every page view; it also performs ongoing animation and render work while idle. Page visibility and intersection observers pause work, and cleanup disposes geometry/materials, skeletons, renderer, listeners, and observers. Reduced-motion users get a static initial render. There is no leak indicated by the inspected lifecycle. Transfer bytes for the scene chunk/SVG, retained heap/GPU memory, and idle CPU/GPU time were not measured. The homepage feature is documented as slowly spinning, so reducing idle work changes an intentional behavior.

**Smallest compatible fix:** If measurements show meaningful cost, keep the static logo as the initial state and load/create the 3D scene after explicit pointer or keyboard intent. Preserve the Ask AI launcher, keyboard access, reduced-motion behavior, and the existing dispose path. A less visible alternative is to keep the scene but stop its animation after the greeting and resume on interaction.

**Tradeoffs and measurement plan:** Deferring activation removes the idle animation until interaction and adds scene-load latency on first use. Measure route-level compressed JS/SVG transfer, JS heap and GPU process memory after activation, and a 30-second idle CPU/GPU profile on a representative desktop and mobile device, with normal and reduced-motion settings. Compare current and deferred activation while checking pointer, keyboard, Kapa loading failure, client navigation, hidden-tab pause, and unmount cleanup. The code evidence is high confidence; performance impact is medium confidence because current browser profiles and transfer measurements are absent.

## Reviewed paths and data loading

- Search is route-level and `Provider` uses React `lazy()` with Fumadocs `preload: false`; the static search index is downloaded by the browser search client. The README states the search client loads on first open and caches its index. No eager global search import was found.
- Mermaid is registered as an MDX remark plugin in `source.config.ts`; there is no direct client-side Mermaid import in the reviewed app source. Its likely cost is in MDX build processing, which was not benchmarked.
- Scalar is imported through the API reference route's `OpenAPIPage`; Nivo is imported by the homepage hero's stock chart; Three is imported only by the dynamically loaded mascot scene. These are route- or interaction-specific entry points. Their actual chunk sizes were not measured.
- The Custom JSX catalog is kept as a separate 861,611-byte public JSON artifact. The interactive reference fetches it on the catalog page rather than embedding the data in the general route shell. The server-side Markdown adapter imports it to render catalog information into processed Markdown and LLM output. Its compression ratio and generated search/Markdown contribution were not measured; the complete catalog is intentional user-facing content.
- The API schema asset is 268,402 bytes uncompressed. `llms-full.txt` and static search intentionally materialize documentation/API content at build time. No build peak-memory or output-size evidence was available to establish an actionable build-memory finding.

## Dedicated large-file passes

### `apps/docs/src/components/workshop/DetailPage.tsx`

The full 1,079-line file was read. `WorkshopNotFoundRouter` maps a requested Workshop URL from the static 404 shell to `MarketplaceDetailPage`; the detail component requests one submission, optional current-user votes, and that submission's comments. It derives the widget safety summary and code display from that single record. New screenshot object URLs are tracked in a set and revoked on removal, edit close, and unmount. Copy timers are cleared on unmount. `ScreenshotGallery` loads the selected image eagerly and other previews lazily; detail page screenshots have no explicit eager-loading/byte cap in this UI. The PocketBase records have service-defined limits outside this call site; no real detail payload or image byte measurements were obtained. No additional actionable memory issue was established in this route.

### `apps/docs/src/components/workshop/WorkshopApp.tsx`

The full 580-line file was read. Its initial listing path is the unbounded `listAll` finding above; it filters and sorts client-side and renders every result. Screenshot galleries only show one image at a time and mark thumbnails lazy. Submission cards use lightweight summaries, and no content string is kept for listing rows after parsing. The submit dialog is mounted only when opened. The related admin screen also loads all submissions and reports, then groups reports by filtering the complete report array for each submission (O(N×R)); actual moderator data sizes are unknown. Image selection creates local object URLs and its parent revokes them on removal/unmount, though creation filtering checks MIME/count but not the 5 MiB size shown by `ScreenshotEditor`; server-side upload bounds need separate validation, not inferred as a memory finding here.


## Revisited UI, helper, and stylesheet paths

The full source of the previously excluded UI primitives and MDX helpers was read and their imports/call sites were traced. The shared UI files are small wrappers around native elements or Base UI primitives, with no module-level side effects, unbounded loops, or heavyweight imports of their own. Their client boundary is introduced only where Base UI or React state/hooks require it; they are consumed by Workshop surfaces or the homepage and do not change the global docs shell loading path. MDX `Tabs` enumerates its child tabs to create triggers and panels, with work proportional to the authored tab count; the observed callers author a fixed small number. `FieldError` deduplicates the supplied error list and memoizes that result, bounded by form errors. These code paths did not establish another actionable performance finding.

The assigned stylesheets were read in full. `global.css` contains design tokens, Fumadocs/Scalar overrides, responsive rules, and a reduced-motion override. The component-reference, mascot, technical-diagram, getting-started, home hero/review-list, and flow-connector styles are CSS-module scoped. Home dataflow and technical-diagram connectors use CSS animations; both flow animation styles and homepage animations have reduced-motion handling. The homepage hero preview is hidden at widths up to 1280px. These are bounded route-level effects; no evidence indicates a bundle, transfer, memory, or build regression beyond the separately described global mascot renderer. No browser frame/CPU profiles were available to quantify animation cost.

The MDX admonition and link adapters are thin render wrappers. `AddingIntegration`, `AddingWidget`, and `WidgetInteractionGuide` emit fixed short content; the latter returns null when advanced view is disabled. `supported-integrations.tsx` defines 25 icon/name records; its inspected homepage caller renders seven app cards, and the home dataflow separately renders six fixed service icons, so the runtime image count is not the full catalog length. Those images are remote CDN assets and their transfer bytes were not measured. `splitToNChunks` has no callers in the docs tree, and `types.ts` exports only interfaces/type imports. No additional actionable issue was established from these paths.
