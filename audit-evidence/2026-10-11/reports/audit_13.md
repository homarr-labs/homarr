# Audit 13: API tools and administrative routers

Inspected all 26 assigned files in full. `user.ts` received a separate full-file pass in four contiguous ranges. Reviewed package exports/dependencies, assigned router composition, and concrete dashboard, table, picker, widget, and upload callers where relevant. No production code, tests, builds, or benchmarks were run.

## F1 — Kubernetes dashboard downloads and retains full lists for counts

**Call path and trigger.** An admin opening the Kubernetes cluster dashboard runs `cluster.getCluster` and `cluster.getClusterResourceCounts` concurrently (`apps/nextjs/src/app/[locale]/manage/tools/kubernetes/cluster-dashboard/cluster-dashboard.tsx:25-34`). `getClusterResourceCounts` issues eight cluster-wide LIST calls concurrently: pods, ingresses, services, ConfigMaps, namespaces, nodes, secrets, and PVCs. It returns only each list's item count (`packages/api/src/router/kubernetes/router/cluster.ts:151-178`). `getCluster` independently lists every pod and consumes only `items.length` for the pod-capacity gauge (`cluster.ts:24-28, 74, 136`), so the same dashboard load asks Kubernetes for the entire pod collection twice.

**Dimensions and impact.** This is linear in total objects returned. Each call transfers and deserializes full Kubernetes API objects although the count result is eight small numbers. `Promise.all` holds all eight full response object graphs until every call settles, increasing transient server RAM with cluster size; secret `data` fields are received then discarded. The duplicate pod request adds another full transfer, decode, and response allocation at dashboard startup. No retained application cache or browser payload of those full records was found: tRPC returns only counts and cluster aggregates. The resulting server-side full responses are transient, not evidence of persistent RAM growth.

**Smallest compatible direction.** Request metadata-only Kubernetes list representations for count-only resources where the configured Kubernetes API/server and generated client support content negotiation. Also share or consolidate the pod count so the dashboard obtains it once. If metadata negotiation is not compatible, process lists sequentially to lower peak simultaneous response retention; that reduces peak RAM but does not reduce bytes transferred or decode CPU. Preserve admin authorization and current count semantics.

**Evidence and confidence.** The redundant use and response shape are directly established by source and caller inspection (high confidence). No live cluster measurement was available. Baseline and comparison should record per-resource response bytes, server `heapUsed` and `external` memory peak during dashboard load, request count/latency, and object counts; report transfer, transient RAM, and CPU separately. No benchmark or production metrics were collected.

## F2 — Pod inventory performs serial, repeated ReplicaSet reads

**Call path and trigger.** Admin pod inventory fetches all pods, then awaits owner-kind resolution inside a sequential `for...of` loop (`packages/api/src/router/kubernetes/router/pods.ts:29-52`). For each pod whose owner is a ReplicaSet, `getOwnerKind` constructs an `AppsV1Api` client and calls `readNamespacedReplicaSet` (`pods.ts:77-103`). Multiple replicas commonly share one ReplicaSet name and namespace, but the current path does not cache that lookup.

**Dimensions and impact.** With `R` pods requiring ReplicaSet resolution, the worst case is `R` additional Kubernetes reads serialized after the pod list. Request count is O(R), latency accumulates serially, and repeated replica owners duplicate network payload and response allocation. The final pod projection itself is proportional to pod count and carries columns used by the inventory table; no issue is claimed for that returned array. No long-lived retention is established.

**Smallest compatible direction.** Memoize owner resolution by namespace plus ReplicaSet name for the duration of one procedure call. If remaining distinct lookups materially affect latency, resolve unique owners with a bounded concurrency limit. Keep recursive owner classification behavior and the current `Pod` fallback on lookup failure; avoid unbounded fan-out against the Kubernetes API.

**Evidence and confidence.** The serial await and repeated lookup path are directly established (high confidence for mechanism, medium for impact because cluster pod/ReplicaSet counts were not measured). Measure inventory wall time, count of ReplicaSet API reads versus unique owner references, bytes received, and server peak heap for small and large clusters. No runtime measurements were collected.

## F3 — Multi-file media upload buffers the whole request before one insert

**Call path and trigger.** The media library upload control enables multiple selection (`apps/nextjs/src/app/[locale]/manage/medias/_actions/upload-media.tsx`); shared `UploadMedia` appends all selected files to one multipart request. The API invokes `file.arrayBuffer()` for every file concurrently and retains the resulting buffers in `files` and `insertMedias` until one bulk insert resolves (`packages/api/src/router/medias/media-router.ts:55-76`). The schema permits each file up to 32 MiB but has no aggregate file count or total-byte cap (`packages/validation/src/media.ts:8-35`). Nginx accepts request bodies up to 256 MiB (`nginx.conf:26`), so one accepted request can contain several large files.

**Dimensions and impact.** Network transfer is intrinsic to upload and is not claimed as avoidable. On the server, file `ArrayBuffer`s are created concurrently and retained through DB insertion; the potential transient external/buffer memory scales with total uploaded bytes per in-flight request, up to the configured request-body limit, plus request parser/DB-driver overhead. Concurrent uploads multiply that pressure. Input file bytes are intentionally retained in the database, so this is not a leak; no process-lifetime retention follows from inspected code. There is no aggregate limit in the application schema, although the proxy bounds a single request.

**Smallest compatible direction.** Add an application-level aggregate file-count/byte limit consistent with deployment constraints and process conversion/insertion in bounded batches if large multi-file uploads must remain supported. Preserve current accepted formats, per-file limit, response IDs, permissions, and transactional/partial-insert semantics deliberately; changing batching must account for the current one-statement insert behavior. Do not claim this reduces client-to-server transfer.

**Evidence and confidence.** Buffer creation and retention through insertion are direct source evidence (high confidence for mechanism, medium for severity because maximum concurrent requests and runtime memory were not measured). Measure request bytes, file count/size, process `external` and RSS peak during one and concurrent maximum-size uploads, plus DB insert latency. No measurements were collected.
