# Whole application journey audit

## Scope and evidence limits

This report connects representative paths through the actual route, API, widget and client callers. The repo baseline is commit `bab8e2a2dad837365a2237263b58b658d23abe69` on `dev` (see [baseline.json](../baseline.json)). It contains runtime versions and configuration, but no representative board sizes, request traces, heap/RSS profiles, route transfer sizes, or latency results. Findings below establish code behavior and scaling dimensions; they do not quantify application-wide savings. No application code, tests, or builds were run for this report. Leaf reports were cross-checked against direct caller paths rather than used as a substitute for them.

## User journeys and strongest candidates

### Login and board load

`/boards/<name>` resolves through `[name]/(board)/_definition.tsx` into `createBoardContentPage` in `_creator.tsx`. On a valid board load, the server starts the session, board, viewport and integration reads concurrently. It loads the full board because rendering and edit mode consume its sections, items, options, layouts and permissions. It groups board items by kind for server prefetch, restores an eligible Redis snapshot into a request-local QueryClient, then prefetches data for items visible in the selected viewport layout. The initial shell is streamed while widget data refreshes; the snapshot has a 3-day TTL and a 512 KiB serialized cap. Login redirect only occurs on a missing board when the visitor has no session; the requested board path is preserved as `callbackUrl`.

The prefetch visibility predicate in `packages/widgets/src/server-prefetch.ts` excludes items whose current layout has no placement and items nested inside collapsed containers. It does not filter the board payload itself. The client section index in `apps/nextjs/src/components/board/sections/use-section-items.ts` indexes every item with a placement in the current layout; this means a responsive layout can retain items and their options while their widget query prefetch is skipped. The direct code evidence therefore supports a server-query avoidance win on mobile, not a proof that hidden widget components, source data, or query-cache entries are absent from the browser. The current layout and initial visible widget kinds are derived using the same selected layout; changing responsive layout must continue to expose the correct placements and query behavior.

The linked-item projection candidate is safe in principle only at the integration middleware boundary: `packages/api/src/middlewares/integration.ts` loads linked association rows, and `packages/auth/permissions/integration-query-permissions.ts` reads the linked item's `boardId` for inherited query access. Projecting `boardId` alone preserves that authorization decision and keeps associations; dropping the relation or treating it as unused would break access for integrations used through viewable boards. This reduces server-side database result materialization and object construction only. It does not shrink the tRPC output, browser payload, or necessarily database I/O by the same proportion. The candidate should be checked for one- and many-integration calls and public/direct versus board-inherited permission cases.

A board snapshot and API response cache can shift work across navigation boundaries. The snapshot is shared via Redis and filters by board content fingerprint, allowed integration IDs and cache generations before restoring; stale restored data is refreshed. The client query cache and per-process integration response caches are separate lifetimes. Measuring only the first board request can therefore conflate a cold route with warm upstream/Redis state. Snapshot retention is bounded by TTL/bytes at this layer; no whole-app memory conclusion follows from those bounds.

### Mobile hidden items and widget editing

`getInitiallyVisibleWidgetKinds` and `prefetchInitialWidgetData` skip non-visible placements, while the board client still has the full `Board` object in context for layout switching and edit operations. In `useSectionItems`, every board item is scanned and indexed by current layout. A board with many desktop-only widgets can therefore still pay full-board server serialization, React context retention and client index work on a phone even when their data requests are deferred. Filtering the initial board response to visible items is not compatible: the same response/context supports switching layouts and editing, and this would discard the metadata needed to render another layout unless the omitted records were fetched through a new path.

Widget option editing is interaction-triggered: `WidgetContextMenu` opens the lazy edit modal only when requested and preloads on focus/pointer entry. That keeps editor-only chunks out of the initial board path, but the board itself intentionally loads definitions/resources for rendered items. Any proposed on-demand boundary must preserve context-menu option filtering, query refresh after option changes and layout preview behavior. This audit did not find evidence to justify changing the board-wide item model solely from hidden-item prefetch behavior.

### Admin board overview and duplicate form

`/manage/boards` awaits `board.getManageOverview`, then renders one `BoardCard` per returned board. The API uses a bounded preview and projected columns; it is not the same full-board query used by the dashboard. The card renders `DuplicateBoardForm` inside a collapsed Mantine `Collapse`. Since Mantine 9.6 `Collapse` keeps children mounted by default, each card initializes `useBoardNameStatus`; valid initial names enable a `board.exists` query. That query scans all board names. Thus N cards can cause N name checks, each scanning N rows, including forbidden requests for viewers without `board-create`, although the duplicate menu is unavailable to them.

Mounting the form only after the duplicate panel is opened is a narrow compatible fix. It defers the name availability request until the user intends to duplicate and avoids initializing forms for users without create permission. Preserve the check after opening and on name edits, plus the existing mutation success/error and refresh behavior. The cost shifts from route entry to first open. The source establishes possible O(N²) scan work and N requests, but actual board counts, DB query count, request bytes and route latency were not measured.

### Custom JSX response cache, admin authoring and reconnect/refresh

`packages/custom-widgets/src/server/request-executor.ts` keeps parsed successful query responses in a module-level `Map`; keys are only used for query requests, identical in-flight calls are coalesced, responses are bounded by the response parser's 1 MiB/depth/node constraints, and the map is capped at 1,000 entries. Cache entries carry expiry, but expired entries are pruned only on a cache miss for the same key or during a later successful cache insertion. If traffic goes idle after filling the map, expired parsed objects remain reachable for the remaining lifetime of that Node module/process. At the maximum entry count this permits up to roughly 1,000 entries of response data (individual response cap 1 MiB, before JS object overhead) to remain until the next insertion or process exit; it is a process-local upper-bound scenario, not an observed deployment footprint.

The smallest lifecycle correction is scheduled expiry cleanup (or equivalent cleanup that runs without another successful insertion), retaining existing per-key TTL, 1,000-entry bound, cache key partitioning and explicit invalidation. A timer adds one process-level handle and periodic work; it should be unref'ed and cleanup should delete only expired entries. If using a periodic sweep, measure sweep CPU against realistic cache sizes and ensure shutdown/worker behavior stays clean. Merely clearing on navigation is incompatible with a server cache shared across requests and would still leave idle expiry dependent on requests. Cache is process-local: multiple Next.js workers/replicas each own an independent map; a server restart clears it, but deployment-wide retained bytes are worker count times per-process state. Do not report this as browser heap or Redis memory.

Cache invalidation is explicitly invoked by preview refresh and widget changes; `cacheEpoch` prevents in-flight responses invalidated during a mutation from being reinserted. Any expiry cleanup must not alter these semantics, request de-duplication, authentication-sensitive cache versions, or refresh freshness. Preview admin requests are session-scoped in their keys; real widget request keys also include a cache version. The code path remains shared by API request routes, so a cleanup policy belongs beside the process-local map, not in a page component.

Dashboard reconnect behavior is separately owned by TanStack Query in `packages/api/src/query-cache.ts`: supporting app/integration metadata refetches on reconnect, Docker container state avoids reconnect/focus bursts and instead uses one shared 30-second refresh interval, and Beszel stats are excluded from ordinary query recovery because they use a live subscription. This means a paired board-load measurement must include offline/reconnect transitions and distinguish ordinary query recovery from Custom JSX server response cache expiry; expiring that server cache must not disable the client reconnect policy or duplicate the Beszel subscription.

The generated component catalog is a separate concern: audit source identifies an 861,611-byte JSON catalog (475 components) reachable through the eager MCP Custom Widget metadata route, while the compact metadata/search endpoint returns subsets. That static import can be resident in processes that load the relevant MCP router; it is not the same memory as parsed upstream response entries and is not evidence that every normal board page downloads the full catalog. Before adding a lazy boundary, map all consumers that require synchronous MCP extraction and measure emitted bundle/startup/RSS. Current data only establishes raw source size and import reachability.

### Notebook typing and save

The notebook's widget definition is lazy and its Tiptap editor chunk is dynamically loaded only when that widget is rendered. Once mounted, `Notebook` stores `options.content` in React state and `onUpdate` calls `editor.getHTML()` and updates that state for each editor transaction; `shouldRerenderOnTransaction: true` also enables transaction rerenders. The ProseMirror editor already holds the document. For a document of N bytes, typing therefore repeats O(N) HTML serialization and allocates a full string while retaining the latest serialized string alongside the editor model. The default sample is 4,438 bytes, but real content size is not capped in the inspected widget contract.

Serializing on save is the smallest compatible direction, but read-only task-checkbox commits also save immediately. Keep editor state authoritative while typing; serialize once for explicit save or checkbox commit. Preserve `previousContentRef` rollback on failed save, external option synchronization when not editing, read-only checkbox success/failure, and `setOptions` persistence. The change trades per-transaction work for one save-time serialization and should not alter query/network frequency except the same existing save mutation. No typing latency or heap profile was collected; the source proves duplicate work, not its user-visible magnitude.

## Combined effects and measurement protocol

The five proposed changes operate on different resources and lifetimes: middleware projection reduces API-process ORM materialization; on-demand duplication reduces route-entry requests and DB scans; widget visibility skips some server prefetches but retains full board data for responsive/edit semantics; response cache expiry frees process-local parsed objects; notebook serialization reduces active browser CPU/state churn. Summing their independent percentages would be invalid, and none supports a whole-application RAM estimate. They can interact: a board with many widgets can still generate concurrent visible queries and hold full widget options; snapshots and client query caches may hide cold-load gains; multiple workers multiply module caches; an editor save shifts serialization cost to an explicit action; on-demand forms shift one availability query to first use.

A useful baseline/candidate pair should use the exact same commit pair and installed Node/Bun versions from `baseline.json`, fixture, browser and server worker count. Record board item/layout/container counts; visible versus hidden widget kinds; auth state and permission class; Redis snapshot cold/warm state and integration cache generation; custom response cache entries/bytes and idle interval; request/query counts and serialized/compressed bytes; process RSS/heap by worker; browser heap and input-to-paint/typing latency. Pair cold and warm board navigation separately. For each focused candidate, preserve its contracts: inherited integration access; board layout switching and edit state; duplicate availability validation; Custom JSX TTL, isolation, invalidation and refresh; notebook save, rollback and task-checkbox behavior. Capture route bytes, network bytes and process/browser memory separately rather than treating one as a proxy for another.

## Confidence and remaining validation

High confidence in the identified call paths and avoidable mechanisms (projection, mounted forms, cache pruning trigger, notebook transaction serialization, visibility-prefetch predicate). Medium confidence in likely resource importance because actual workloads are absent. No live browser profile, database trace, RSS/heap series, worker count, production catalog cardinality, or realistic notebook-size distribution was available. The correct next evidence is paired route traces and per-worker/per-browser measurements under the representative protocol above; source counts and local asset sizes must not be presented as measured whole-app savings.
