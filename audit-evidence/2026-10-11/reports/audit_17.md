## Finding: LDAP authentication failures can retain connected sockets

**Affected files:** `packages/auth/providers/credentials/authorization/ldap-authorization.ts`, `packages/auth/providers/credentials/ldap-client.ts`, and the caller `packages/auth/providers/credentials/credentials-provider.ts`.

**Call path and trigger:** Auth.js invokes `createLdapConfiguration().authorize()` for an LDAP sign-in (`credentials-provider.ts:24-33`), which calls `authorizeWithLdapCredentialsAsync`. That function creates a service-bound LDAP client and may create a second user-bound client (`ldap-authorization.ts:23-31,75-86`). The service client is disconnected only after user and group searches (`:95-109`); the user client is disconnected only after a successful bind (`:76-86`). The provider catches authorization failures and returns `null`, but no `finally` reaches either client's `disconnectAsync` (`credentials-provider.ts:32`). Therefore failed service bind, user search errors, missing/ambiguous user, invalid email, failed user bind, group search errors can bypass one or both cleanup calls.

`LdapClient.disconnectAsync()` delegates to ldapts `Client.unbind()` (`ldap-client.ts:70-75`). The installed ldapts implementation destroys its socket in the `finally` of `unbind()` (`node_modules/ldapts/src/Client.ts:724-737`). Its connection path sets `connected` once a socket is established before bind completion (`:827-875`); the caller's rejected-bind catches do not unbind. This establishes that these exceptional paths skip the operation that destroys the socket. The `Client` constructor does not set an application-specific timeout in `ldap-client.ts:21-24`; the installed default timeout is zero.

**Dimensions and scale:** Each affected failed service bind retained one server socket and one client socket handle after the authorization promise had returned. In isolated baseline workers, 1, 25, and 100 failed attempts retained exactly 1, 25, and 100 sockets/handles. In nine alternating isolated process pairs, the cumulative 1/11/51/151-attempt baseline stages retained exactly 1/11/51/151 sockets/handles in every run; the patched path retained zero at every stage. The synthetic server does not model server idle timeouts, so real deployment retention duration remains unknown. Heap/RSS changes were small and noisy; the measurements do not support a claim of lower total process RAM. Network transfer is the existing bind traffic; cleanup adds a local LDAP unbind request on rejected service binds.

**Smallest compatible fix:** Put each client's complete use in a `try/finally` that always calls `disconnectAsync()`, including bind failure. Keep the current user/service separation, query attributes, LDAP filters, password validation, group synchronization, and provider-level failure-to-null behavior. Avoid sharing clients across credentials or weakening authentication checks.

**Expected tradeoff:** Socket/client retention becomes bounded by the active request and cleanup path. Successful login already performs both disconnects, so its cleanup count should stay unchanged. Failure paths gain cleanup; rejected service-bind latency is measured below, while successful-login and other failure-path latency remain unmeasured. No auth-boundary change is needed.

**Initial worker measurements and limits (before the final lint helper correction):** Harness and raw records are in `audit-evidence/2026-10-11/measurements/ldap-lifecycle.mts` and `ldap-lifecycle-before-lint-fix-results.json`; independent baseline runs for 1, 25, and 100 attempts are in `baseline-{1,25,100}.json`. The paired run used Node v24.18.0, nine alternating baseline/after process pairs, and repeated cumulative stages of 1, 11, 51, and 151 failures. These worker memory numbers include both the authorization client and the synthetic server in the same process; they are fixture totals and cannot be interpreted as production per-client retained bytes or RSS savings. At 151 failures, the median baseline/after fixture values were: RSS 116,711,424/117,174,272 bytes; post-GC heap used 17,755,432/17,133,128 bytes; external 13,119,793/13,224,127 bytes; total stage elapsed 57.77/46.11 ms; per-attempt p50 0.322/0.417 ms and p95 0.567/0.740 ms. RSS and external memory were not lower after the change, and timings were noisy; the deterministic socket/handle result is the strongest evidence. All nine paired runs had 151 retained sockets/handles on baseline and zero after cleanup. High confidence that the enumerated paths previously skipped unbind and that the patch closes the synthetic rejected-bind socket. Remaining gaps are actual directory-server idle behavior, production traffic, post-failure LDAP search-error paths, and successful-login latency. The worker workload completed and wrote the complete raw result JSON; the runner then exited nonzero on a typo in its final status-print variable. That variable is corrected in the harness; the recorded pairs are complete and validated.

## Reviewed database and auth behavior

- Auth session and API-key lookups project bounded user/session fields. Permission resolution is an explicit distinct-key query. `auth()` is request-cached through React; no process-wide user/session cache was found.
- Credential password lookup currently selects a full user record though the authorization path only compares the hash and returns id/name. This is one row per login; the extra fields are bounded and no material transfer or allocation cost was established.
- Integration query access loads user board permissions and the current groups' board permissions, then maps permission board ids and performs repeated `includes` checks. The API caller includes both per-request integration query middleware and media-search integration lookup. These arrays scale with a user's board permissions/integrations, but no representative cardinality or CPU profile was available to show material cost; no finding is claimed.
- Server settings have a whole-settings path that loads all rows and finds each fixed settings key; keyed callers select a single row. Settings are a fixed, small domain set. Widget placement is an onboarding/seed operation and performs item/layout inserts per widget and target, not a retained request cache.
- `packages/db/proxy-reader.ts` lazily retains one reader per process and exposes `closeProxySettingsReaderAsync`; the PostgreSQL proxy pool is capped at one connection. The proxy caller caches the two settings reads. The regular PostgreSQL driver passes `max: 0`; installed `pg-pool` normalizes falsy max to its default of 10 (`node_modules/pg-pool/index.js:89`), so this is not an unlimited pool.
- `packages/db/schema/index.ts` statically imports both backend schema modules before selecting one through `createSchema`. Both modules construct table/relation objects during module evaluation, so the unused driver's definitions are initialized in each runtime. The files define schema metadata rather than row data, and the application database factory is synchronous. Heap, startup CPU, and bundle delta for this duplicate initialization were not measured; it remains a measurement question, not an actionable finding.
- Migration package scripts generate and bundle separate driver migrations. The checked-in SQL migration files total approximately 288 KiB across PostgreSQL and SQLite (1175 lines combined). The SQL inventory is primarily DDL; historical SQLite migrations `0012_ambiguous_black_panther.sql` and `0023_fix_on_delete_actions.sql` rebuild the user table by copying its rows before renaming the replacement table. That work is a one-time migration cost proportional to user-table size; no row-count or migration-duration measurement was taken. No migration was generated or run.

## Measurement plan and limits

The LDAP failure case is now measured against a controlled loopback LDAP server that returns BER BindResponse invalidCredentials (49). The loopback server and caller share a worker process, so worker memory includes both sides. The run covered service-bind rejection only; a live LDAP fixture would be needed to exercise later search and user-bind failures. For the schema import question, use fresh processes per driver and compare startup time, heap after import, RSS, and server bundle size against a one-backend schema-loading variant. No schema-loading measurement or production LDAP measurement was taken, so no absolute schema RAM, bundle, transfer, or CPU savings are claimed.
