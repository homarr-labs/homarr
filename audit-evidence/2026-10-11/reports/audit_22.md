# Audit 22 — Workshop services

## Scope and confidence

All 23 assigned paths were read individually in full. Dedicated full-file passes covered `apps/workshop/homarr_provider.go` (759 lines) and `packages/workshop/src/backend.ts` (901 lines), followed by caller review. I inspected the owning `@homarr/workshop` exports, the PocketBase 0.26.9 list option types/implementation, and PocketBase 0.39.9's JS runtime pool and static file path. No production edits, tests, builds, or runtime benchmarks were run.

The repository baseline has no Workshop Go heap, concurrent request, browser heap, list transfer, or production data-size measurements. The findings below establish code-level dimensions and provide measurement plans; production impact remains dataset/load dependent. Public Workshop list loading overlaps with the listing finding already reported by audit 16; this report adds the service-side raw-content fallback and keeps that overlap explicit for consolidation.

## Finding: provider requests retain raw, decoded, and encoded copies while waiting upstream

**Call path and trigger:** `apps/workshop/main.go` registers `registerHomarrProvider`, which binds authenticated `POST /api/ai/v1/chat/completions` to `homarrProvider.chat`. Once admitted, `chat` reads the request body, unmarshals it into `providerRequest`, unmarshals it again into `map[string]any`, validates and sanitizes that map, then marshals it into `upstreamBody`. The same handler synchronously waits for the configured HTTP client, whose timeout is five minutes. The 100-request global in-flight counter is held until the handler returns.

**Cause and dimensions:** The raw byte slice, dynamic decoded object graph, and marshaled upstream byte slice are simultaneously live across quota work and the network wait. `maxChatRequestBytes` permits up to 12,000,000 bytes per request; the map adds per-key, per-value, slice, and interface overhead, while `providerRequest` adds a bounded message/role representation. At the configured concurrency, raw and outgoing byte slices alone have a 2.4 GB theoretical cap; including the decoded map gives a larger heap peak, but its amplification and typical accepted request size are unmeasured. The input text/image checks reduce ordinary payload sizes, but the request-size cap still bounds accepted JSON with structural/numeric data, and the two-per-user cap does not lower the 100-request aggregate. This is Go service RAM; it is separate from PocketBase/SQLite memory, client/browser buffers, network transfer, and upstream response processing.

**Smallest compatible fix:** After producing `upstreamBody`, clear references to the raw body, decoded map, and first-pass `providerRequest` before the potentially long upstream wait. This preserves request validation and provider behavior while allowing those representations to be collected. A follow-up can parse model/stream/message-count from one representation to remove the duplicate initial decode, if implementation complexity is justified by measurements. Do not change request-size, in-flight, or timeout semantics as part of this memory fix.

**Tradeoffs and measurement plan:** Clearing references permits reclamation at the next GC; it does not force an immediate collection, and the outgoing body remains retained for transport. Measure Go `HeapAlloc`, `HeapInuse`, RSS, allocation bytes, GC pause/CPU, request bytes, and time spent waiting at concurrency 1, 10, and 100. Use representative text-only, five-image, structural/numeric-heavy near-cap, and rejected over-cap requests against a delayed local provider. Record container memory limits and distinguish the response-body path (bounded to 8 MiB, streamed or read/aliased) from request retention. Confidence is high in overlapping object lifetimes and concurrency; actual peak amplification is unmeasured.

## Finding: listing compatibility fallback downloads full submission content before projecting summaries

**Call path and trigger:** `WorkshopBackend.list()` uses the summary `workshop_listings` view with a page request, and `listAll()` uses that view in batches of 200. On a PocketBase 400/404 compatibility error, both call `loadListingsFallback()`. It first retries `workshop_listings` with `getFullList`; if that also returns 400/404, it calls `submissions.getFullList({ expand: "author" })`. Concrete callers include the docs public Workshop (`useWorkshop.refresh` calls `listAll`), docs moderation (`WorkshopAdmin.load` calls `listAll`), and Homarr management UI (`useWorkshopQuery` uses `list`). The current Workshop migration defines a summary view without `content`, while the raw `submissions` collection permits content up to 1,000,000 characters.

**Cause and dimensions:** When an older/incompatible deployment reaches the raw-collection branch, the entire set of submissions and author expansions is fetched and parsed into client memory, including every full `content` string. `parseListings()` subsequently validates each row as `WorkshopSubmissionSummary`, which drops content only after PocketBase has transferred and JSON-parsed it. For N records with content lengths cᵢ, raw JSON transfer and transient client object memory include O(sum(cᵢ)) bytes in addition to summary fields; a one-page `list()` call still loads all fallback rows before filtering/slicing. This is TypeScript client/browser heap and network transfer, distinct from the Go provider RAM issue. Current view-based operation avoids the content field; the path is conditional on view incompatibility.

**Smallest compatible fix:** Add PocketBase `fields` projections to the raw submissions fallback so it requests only the summary fields plus the author name needed by `enrichAuthor`; PocketBase 0.26.9's installed `ListOptions` supports `fields`. Keep the current fallback, filters, sorting, batch traversal, and page results intact. Validate the exact field/expand syntax against the supported PocketBase server versions before shipping. This removes content transfer and client content retention without silently changing pagination or stale-data semantics; it does not bound the number of summaries loaded.

**Tradeoffs and measurement plan:** A field allowlist must include fields used by `workshopSubmissionSummarySchema` plus author expansion, and must remain compatible with older collection schemas. Capture compatibility behavior on each supported server version. Measure response bytes and browser JS heap for N=1, 100, and 1,000 records with content at small, median, and maximum lengths; compare the raw fallback before/after projection, and separately measure the normal view. Record cold/warm cache, browser, response compression, and transfer timing. Confidence is high that the branch fetches and parses content; frequency and user impact are unknown. The broader intentional `listAll()` scaling/render behavior is also called out in audit 16 and is not duplicated here.

## Dedicated full-file pass: `apps/workshop/homarr_provider.go`

The complete 759-line file was read. Beyond the request path above, provider admission is released through a deferred call, per-user in-flight map entries are deleted at zero, HTTP redirects are disabled, and upstream calls have a five-minute timeout. Successful non-stream responses are read with an 8 MiB bound and JSON re-encoded to alias the upstream model; streaming responses are copied line by line with an 8 MiB aggregate bound and flushed. Error details read at most 16 KiB and are reduced to a sanitized structured message. These bounded response buffers are per-request; neither path is shown to enqueue or cache full responses. Quota state is persisted in PocketBase collections, not retained in a growing Go map. The provider instance retains configuration and only transient request counters.

## Dedicated full-file pass: `packages/workshop/src/backend.ts`

The complete 901-line file was read. `WorkshopBackend` owns one PocketBase SDK client, disables automatic cancellation, and does not maintain its own listing cache. TanStack Query consumers own result retention and query keys; abort signals are used by paged/list/detail/usage queries, while mutation/list-all operations use the SDK timeout or caller lifecycle. `list()` requests one page in the normal path, but both compatibility and `listAll()` paths can materialize all summaries. Detail loading intentionally fetches one full record and its summary listing; report summaries use the narrow `workshop_report_summaries` view, separating author-visible report details from moderator report records. Votes/comments are fetched with `getFullList` for a user or one submission respectively, so their cardinality is data dependent; no retained queue or explicit cross-request cache was found in this class. PocketBase SDK `send()` parses the JSON response before returning it, adding a response-text-to-object transient during these fetches.

## Other reviewed dimensions

- The migration's public `workshop_listings` view excludes submission content; report summary projection similarly selects only report details visible to the submission author/admin. `submissions.content` is capped at 1,000,000 characters and screenshots at five files of 5 MiB each, but actual counts and transfer sizes were not measured.
- Docker stages place the built docs export under `/pb_public`; `main.go` serves it through PocketBase's filesystem static handler. The inspected handler opens/serves files per request; this audit found no source evidence that the whole export is eagerly retained in Go heap. Filesystem page-cache/RSS behavior was not measured.
- `main.go` configures a prewarmed pool of 15 Goja runtimes. PocketBase 0.39.9 creates those runtimes at bootstrap, but this audit did not measure their heap contribution; no startup-RAM finding is made from the pool count alone.
- Hook handlers create per-event email/social metadata strings. The report email query is capped at 100 admins; no long-lived message queue or unbounded in-process collection appeared in the assigned hooks.
