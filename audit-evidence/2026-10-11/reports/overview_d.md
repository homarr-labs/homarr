# Overview D: API, RSC hydration, and WebSocket payload paths

Scope: direct audit of the assigned board routes, page/layout construction, API procedures, client consumers, and WebSocket setup. No production edits or runtime measurements were made. The checked-in audit baseline gives dependency versions and fixture requirements, but contains no raw HTTP/RSC/WebSocket payload samples. Therefore the byte findings below are code-path findings, not measured traffic claims.

## Board request and RSC path

For `/boards` and `/boards/[name]`, the route definitions supply `getHomeBoardAsync` or `getBoardByNameAsync` to `createBoardLayout` and `createBoardContentPage`. Both layout and page request the board. The API-side helpers in `packages/api/src/board-server.ts` wrap each read in React `cache`, so a request can share the same board read. The router checks view permission before returning a full board; `getFullBoardWithWhereAsync` selects the board with creator, sections and per-user collapse state, item integrations/layouts, board layouts, and the caller's user/group permissions. It then parses options and strips relation-only fields such as `boardId`, `layout.boardId`, item integration join records, and section collapse-state records before returning the `Board` object.

`_layout-creator.tsx` passes that full returned board to client `BoardProviders` as `initialBoard`. The client provider uses layout IDs and board permissions to initialize the board context and edit mode. The nested page uses the board to start widget prefetches, select the viewport layout, restore a Redis query snapshot, and render `ClientBoard` from context. Thus the full board model crosses the RSC boundary once as client-provider state; the page does not pass a second board prop to `ClientBoard`. It includes content from all layouts because client layout switching and editing need it. Removing hidden-layout content from this board object would change client state/API semantics and is not a safe payload fix.

### Confirmed narrower prefetch opportunity

`_creator.tsx` groups every `board.items` entry by kind and calls `prefetchForKind` before computing the current viewport layout. `packages/widgets/src/prefetch.ts` handles `app` and `bookmarks` by issuing direct DB reads for their distinct app IDs, then registers `app.byId` or `app.byIds` query entries. Neither helper checks whether the item has a placement in the selected layout or whether a container ancestor is collapsed.

By comparison, `packages/widgets/src/server-prefetch.ts` has `isInitiallyVisible(board, item, layoutId)`, which requires a placement in that layout and walks container ancestors to exclude collapsed content. `prefetchInitialWidgetData` applies this check before starting integration/widget requests. Its initial kind list for resource preload uses the same visibility rule.

The safe candidate is to apply the existing selected-layout/collapsed-ancestor predicate when forming the app/bookmark prefetch groups. Keep all placements and options in `BoardProviders`; only avoid app DB/query prefetches for entries that will not render in the initial layout. The query keys and returned app objects for visible placements stay identical, so auth, API output, query freshness, and client switching behavior remain intact; switching layouts can use the existing client query path. Expected tradeoff: the first switch to a layout whose app data was not prefetched may wait for that lookup. Before implementing, verify the existing visibility helper is reusable across package boundaries or move the predicate to the owning shared board package; do not copy subtly different collapse logic.

This is a proven over-broad prefetch call, but the assigned source does not establish how often its promises resolve before the initial `dehydrate(queryClient)` or how many bytes they add. Measure it with paired boards that have many app/bookmark entries exclusively on a hidden layout and entries inside collapsed containers, comparing query-cache contents and RSC response sizes before/after filtering.

## API and client query payload candidates

### `group.getAll`: strong display/projection mismatch

`packages/api/src/router/group.ts:getAll` loads every group with all members and each member's `id`, `name`, `email`, and `image`, then maps membership rows to user objects. Its only direct application caller is the admin group-list server page. That page passes the result to `GroupsList`; `_groups-table.tsx` renders each group with `UserAvatarGroup(..., limit={5})`. `packages/ui/src/components/user-avatar-group.tsx` uses only the first five member names/images plus the array length to render `+N`; it does not show the remaining members in a tooltip or another list view.

The remaining full member details are therefore retained in the Server Component result and RSC props without being used by this screen. This does not prove a public API contract is unused elsewhere, so do not narrow `getAll` silently. Smallest compatible fix: add an admin-only overview projection returning group identity, member count, and up to five avatar fields; migrate only the group list page to it and keep `getAll` semantics unchanged. This adds a procedure and a second query contract; alternatively, a server-local read avoids adding a general API endpoint if no external consumer needs it. Preserve group ordering as currently returned or make it explicit only if separately approved. Measure with groups of 5, 6, and hundreds of members; compare serialized RSC bytes and confirm the detail route still fetches full membership.

### `app.selectable`: `pingUrl` appears unconsumed here, but is an API field

`packages/api/src/router/app.ts:selectable` selects and returns `id`, `name`, `iconUrl`, `description`, `href`, and `pingUrl`. Direct client consumers are `WidgetAppInput`, `BookmarkAddButton`, and `BoardSelectionToolbar`. Their visible code reads app ID/name/icon, bookmark name/href/icon, or ID/name/icon respectively; none reads `pingUrl`, and none visibly reads `description` in these call sites. However, the procedure declares an output schema and OpenAPI description that explicitly includes both fields. `BookmarkAddButton` also adds the complete selected app object to widget option state, so the full consumer chain must be traced before any field removal.

This is a plausible API payload trim, but dropping either field from this procedure changes typed/OpenAPI output semantics, which the audit constraints prohibit silently. Safest compatible option, if a measurement justifies it, is a new narrow selection procedure tailored to the client fields, retaining `app.selectable` for its current contract; then migrate only the verified consumers. Confirm serialized bookmark option normalization before deciding whether a narrower object is retained in board state.

### Authenticated board integration prefetch

`prefetchInitialWidgetData` starts `integration.all` on every authenticated board request. The procedure filters by permissions and returns `{id,name,kind,url,permissions}` sorted by kind/name/id. The board grid portal's only direct board-level `integration.all` query is enabled only when the user is authenticated and in edit mode; widget context menus, editor forms, Custom Widget sources, and other UI surfaces also use it when opened. The query uses the normal API auth path and can be cached on the client.

This is a candidate to defer to edit mode because normal dashboard display does not need the all-integration picker dataset. However, the code alone cannot establish whether that prefetch consistently resolves before the initial RSC dehydrate or its transfer size. Do not remove or narrow API results. First measure cold and warm authenticated board visits in view and edit modes, including query timing, and separately measure later edit-mode fetch latency. Check that removing it does not turn edit-mode startup into a visible delay; a targeted editor prefetch is preferable to changing access/filter behavior.

## Database projection that does not cross the response boundary

`getAccessibleMediaRequestSearchIntegrationsAsync` in `integration-router.ts` queries integration `app`, `secrets`, access rows, and `items` with nested `item` records. It is used by media-request integration discovery/search. The returned integrations are later mapped in `searchMediaRequests` to media search results; `allMediaRequestSearchIntegrations` also maps each integration to only `id`, `name`, `kind`, `url`, and interaction permission. The nested item/board-related fields are server-side inputs to access evaluation, not direct serialized output. If query cost is demonstrated, the DB projection can be tightened while preserving the access predicate and ordering. This is a DB-read optimization, not an HTTP/RSC payload saving. Keep integration authorization and exact-match count behavior unchanged.

## WebSocket and other transport boundaries

The Next client routes tRPC subscriptions over `wsLink` except `widget.beszel.subscribeSystemStats`, which uses `httpSubscriptionLink`. The WS server at `apps/websocket/src/main.ts` creates an authenticated tRPC context from the session cookie and serves the same API router; this establishes transport, not a blanket subscription payload shape. Current subscriptions include log history plus messages, Docker log strings, cron `TaskStatus`, and Beszel live metric events. Their schemas/emit sites define different payloads and should be measured separately. In particular, log history is a batch of full `LoggerMessage` records, while later events are one message; Beszel uses a bounded queue of four pending events. Do not infer that the HTTP `integration.all` or board RSC candidates affect WS bytes.

## Raw bytes versus transferred bytes; measurement plan

`dehydrate`, SuperJSON, and RSC serialization produce application-level serialized data. `Buffer.byteLength` limits in `_query-snapshot.ts` apply to the SuperJSON snapshot string stored through Redis; they are neither the complete initial RSC payload nor network transfer measurements. The browser's `httpBatchStreamLink` uses SuperJSON and streams tRPC results; production HTTP response compression and HTTP framing affect transferred bytes. WebSocket frames use SuperJSON via `wsLink`, with WebSocket framing and negotiated compression as separate factors. The inspected code does not establish negotiated compression or actual compressed byte counts.

For an evidence baseline, use the same production build, fixture DB, auth, viewport cookie, board layouts, integrations, cache state, and concurrency. Capture (1) RSC response body bytes before content decoding and content-encoding/transfer-size metrics, separately for full navigation and client navigation; (2) tRPC request/response body sizes and browser transferred sizes for `integration.all`, `group.getAll`, and app selection; and (3) WebSocket frame payload lengths and frequency for each subscription. Record raw serialized size and transferred size separately, and do not sum RSC-embedded state with later client requests unless the capture shows both. Compare cold/warm and view/edit cases. No local build, browser capture, seeded data, or raw traffic capture was available for this audit.

## Other candidate checks and limits

- Root `layout.tsx` passes the branding settings object to `SettingsProvider` and `CustomMantineProvider`, and emits `branding.customCss` as a global style. The current audit did not establish that `customCss` or the other branding fields are unused by all client consumers; removing these props based only on the stylesheet is not supported.
- `getFullBoardWithWhereAsync` deliberately removes DB relation bookkeeping before returning board state. This is already a server-only projection and does not support a client payload saving claim.
- Board permissions are checked before full-board reads, and group access relations are filtered to the current user. Any projection change must preserve those checks and the per-user section collapse state. No field/limit/pagination changes are recommended to existing endpoints.
- No production fix, test, benchmark, Docker build, or E2E run was performed, per scope.
