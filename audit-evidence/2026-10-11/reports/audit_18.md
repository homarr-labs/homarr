## Finding F-1: RSS requests buffer and parse full feeds with 100-way fanout

**Affected files:** `packages/api/src/router/widgets/rssFeed.ts`, `packages/request-handler/src/rss-feeds.ts`, and the installed `node_modules/@extractus/feed-extractor/src/utils/retrieve.js`.

**Call path and trigger:** The public `rssFeed.getFeeds` procedure accepts up to 100 URLs and starts all feed handlers at once with `Promise.allSettled`. Its API schema does not cap `maximumAmountPosts` (the widget editor separately suggests a 1–9,999 range), so direct callers can also request an arbitrarily large returned count. For each URL it calls `rssFeedsRequestHandler`, which calls `extract()` before trimming the result to `maximumAmountPosts`. The installed feed-extractor implementation calls `res.arrayBuffer()`, decodes the complete buffer into a JavaScript string, and parses the complete JSON or XML feed. For XML, parsing materializes an object tree before normalization. Thus the entry-count limit controls the returned entries but does not cap bytes downloaded or work done per feed. The URL array limit bounds one call to 100 feeds, while payload bytes per feed remain unbounded.

The RSS result is cached in a process-local request-handler cache with at most 1,000 entries and the default 10-second TTL. That limits entry count and normal retention time, but each cache entry's size is determined by the requested output count and feed fields. The full input buffer, decoded string, and parse tree are temporary but may overlap across the 100 concurrent fetches; normalized output can then remain in the L1 cache briefly. There is no evidence that the Redis shared cache is used for RSS: this handler is created without a `cacheNamespace`.

**Dimensions and evidence:** During each fetch, response bytes occupy an ArrayBuffer/Buffer allocation and the decoded text occupies V8 heap; parsing creates additional heap objects, and normalized results create another representation. The peak scales with the sum of concurrently processed feed sizes and parser expansion, not only `maximumAmountPosts`. `Promise.allSettled` also retains each settled result until the slowest feed completes. Aggregate feed sizes, peak `heapUsed`, `external`, `arrayBuffers`, RSS, response transfer, and parse CPU were not measured. These memory counters overlap in Node and must be reported separately rather than summed into an independent total. No absolute savings are claimed.

**Smallest compatible fix:** Read feed bodies through a streaming byte limit and cancel the body when the limit is exceeded; limit concurrent feed fetches with a small worker pool while preserving the input/result association and final chronological ordering. Keep the existing post-count and description limits as output controls. A byte cap needs a user-appropriate limit and error behavior because legitimate feeds vary in size; the current code provides no existing cap to reuse.

**Authorization, ordering, freshness, and tradeoffs:** Anonymous and ordinary users have URLs restricted to feeds configured on accessible boards; board creators/modifiers may supply arbitrary URLs. The procedure still accepts up to 100 URLs from the caller. The proposed byte cap would reject unusually large feeds and could reduce available entries for those sources. A worker pool would reduce peak concurrent transfer and parser memory while increasing latency for batches of many feeds. The current response sorts combined entries by publish date and truncates the aggregate, so the fix should retain that output ordering. The short L1 TTL remains useful to avoid repeated fetches but does not constrain a single response's ingestion size.

**Confidence and gaps:** High confidence in the unbounded-per-feed ingestion and concurrent allocation path; the installed dependency source confirms the whole-body buffer and decode. The actual risk depends on feed sizes, URL count, runtime limit, and traffic. No production feed-size distribution or before/after memory, transfer, or latency measurements were available.

## Finding F-2: weekly icon refresh loads every uploaded media blob to compute local icon checksums

**Affected files:** `packages/icons/src/repositories/local.icon-repository.ts`, `packages/icons/src/icons-fetcher.ts`, `packages/cron-jobs/src/jobs/icons-updater.ts`; callers and data shape inspected in `packages/api/src/router/medias/media-router.ts`, `packages/validation/src/media.ts`, and both DB media schemas.

**Call path and trigger:** `@homarr/tasks` initializes the cron group and starts jobs. The `iconsUpdater` job runs on startup and weekly, calls `fetchIconsAsync()`, then keeps all returned repository groups while it loads the existing icon repositories with their icon rows, flattens those rows, computes skipped checksums and pending inserts/deletes, and applies a transaction. The local repository return value contains metadata only, not the source Buffers; the peak full-blob materialization is during `LocalIconRepository.getAllIconsInternalAsync()` before it returns. `fetchIconsAsync()` runs all six repository fetches concurrently, including `LocalIconRepository`. That repository calls `db.query.medias.findMany()` without a column projection, so every row includes its `content` blob. It maps all rows through `mapMediaToIcon`, which hashes the complete content with MD5 but returns only the name, URL, size, and checksum. The media table stores content as a SQLite Buffer blob or PostgreSQL bytea.

The media upload schema allows each file to be up to 32 MiB and does not set a maximum file count. Upload processing already hashes each file through `mapMediaToIcon` and writes the resulting checksum into the icons table when the local icon repository exists; deletion removes the corresponding icon row. The periodic refresh therefore rereads all uploaded bytes for checksum comparison, even though it primarily needs local icon metadata and a checksum already stored for ordinary uploads. If the local icon repository row did not exist at upload time, the updater can also initialize it and backfill icons, so that path must be preserved in a repair.

**Dimensions and evidence:** The local query materializes all media rows and their Buffers together during the repository fetch and MD5 pass, giving a peak raw payload footprint proportional to the sum of all uploaded file sizes. Once `LocalIconRepository.getAllIconsInternalAsync()` returns, its local row array is out of scope and only the small icon metadata objects are returned; raw Buffers are eligible for collection before the updater finishes its later database reconciliation, though actual GC timing is not measured. Those Buffer bytes are external/ArrayBuffer memory; Buffer wrappers, result objects, icon objects, remote repository metadata, database icon rows, and pending insert/checksum arrays also occupy V8 heap. The six repository responses are concurrently processed and their returned groups are retained; remote repositories return indexing metadata, while the local result contains metadata only after hashing. The periodic updater's separate DB icon query loads icon metadata, not media blobs. These dimensions are distinct and were not measured. No live database was queried for media count or total bytes.

**Smallest compatible fix:** Avoid transferring all media contents on every refresh. Preserve the existing upload/delete lifecycle and initial backfill behavior by either (a) persisting a stable local-media checksum at write time and selecting only id/name/size/checksum metadata during refresh, or (b) reading missing legacy media in bounded keyset batches so only a bounded number of content Buffers are resident at once. The first option needs a compatibility plan for existing records and must retain change detection if media content can be updated in place; the current API creates and deletes media but exposes no content-update operation. A one-time reconciliation may be required for legacy records or a missing local icon repository.

**Ordering, freshness, and tradeoffs:** The job synchronizes remote icon repositories and deletes stale local icon rows in the same transaction. The fix must still create the local repository when absent, backfill all existing media icons, and keep checksum comparison/deletion semantics. A persisted checksum uses storage at upload time and makes scheduled refresh cheap; batched reads preserve content-derived checksums but add query/transaction complexity and still hash all bytes over the full job. This weekly job also runs at process startup, so memory cost can recur after deployments or restarts rather than only once a week.

**Confidence and gaps:** High confidence in the full-blob query and repeated checksum work. The process-level peak is expected to scale with total stored media bytes plus metadata, but no row count, total byte count, peak memory, startup duration, or CPU profile was measured. SQLite and PostgreSQL Buffer behavior may differ in transfer and allocator details; the same high-level retained-byte issue applies to both.

## Reviewed lifecycle and cache behavior

- PostgreSQL's `createPostgresDbConnection()` specifies `max: 0`, but the installed `pg-pool` normalizes falsy `max` to 10 (`node_modules/pg-pool/index.js:89`); it is not an unlimited connection pool. DB clients are constructed by the shared DB factory and retained by their owning runtime.
- The Redis channel module owns a fixed set of process clients. Integration/widget generation reads have a 1,000-entry LRU-like cache and in-flight request coalescing. Pending invalidations are capped at 1,000 per domain and switch to a global overflow generation; Redis generation keys expire after 30 days. The old history list callers use a 15-entry cap. The queue-channel helper stores a serialized queue without a TTL, but no production caller was found in `packages/` or `apps/`.
- Redis logging retains at most 5,000 serialized messages in Redis and publishes each message. Its client is lazy and process-scoped. This is bounded external Redis history, distinct from Homarr process heap.
- The shared request handler caps its process-local cache at 1,000 entries and both request/in-flight work at 100, expires cache entries on a timer, and bounds shared-cache lock lifetime. It does not cap bytes per cached response. Shared payload values live in Redis and expire at the entry's `staleUntil`; Redis memory must be measured separately from process memory.
- Docker endpoint clients are initialized once from static environment configuration. Container inventories/stats are request scoped. CPU baselines are stored in a module Map and expired after 10 minutes on the next poll. Docker log streams are destroyed on explicit unsubscribe, oversize messages, and parser error paths. Discovery requests return container and parsed service arrays without retaining them in a process cache.
- Image proxy URL/HMAC records have 24-hour Redis TTLs. Forwarding buffers the complete upstream image as an ArrayBuffer and has no byte limit; the API route returns that buffer. Peak external/ArrayBuffer memory therefore scales with concurrently forwarded image sizes, but representative upstream sizes and concurrent-route measurements were unavailable, so I do not claim this as a separate actionable finding.
- `fetchWithTrustedCertificatesAsync` creates a per-call certificate agent when a caller supplies no dispatcher. The TLS `SecureContext` cache is keyed by certificate contents and capped at four entries. Most assigned request paths consume JSON/text bodies; the timetable path explicitly bounds JSON to 512 KiB, destroys temporary pinned dispatchers, and cancels failed response bodies. Per-call agent/socket overhead was not measured and is not reported as a finding.
- WebSocket process state is the `ws` client set plus tRPC subscription state. `ChannelSubscriptionTracker` deduplicates Redis subscriptions, removes callback entries on unsubscribe, and unsubscribes Redis when the final callback leaves. SIGTERM broadcasts reconnect then closes the WebSocket server. No accumulating subscription map path was found in the assigned lifecycle.
- Cron registry/task state is fixed to the registered jobs. Analytics coalesces simultaneous snapshots through a single `pendingSnapshot` promise and aggregates database counts rather than loading full tables. Ping URL list has no production writer in the current tree; the ping task clears it at startup before reading it.
- Several request handlers return provider-sized arrays (for example Wazuh/media lists, RSS, and release metadata). Their cache entry counts and/or provider query limits do not establish a byte bound. Only RSS had a concrete caller-controlled fanout plus dependency-confirmed whole-body buffering sufficient for a finding here.

## Measurement plan and limits

For F-1, replay representative feed fixtures at measured byte sizes with 1, 10, and 100 URLs and a fixed maximum post count. Record transfer bytes, elapsed/parse CPU time, peak `heapUsed`, `external`, `arrayBuffers`, RSS, and event-loop delay; counters overlap and should be compared individually. Repeat with a byte cap and worker pool, including one oversized feed and one slow feed to verify cancellation and ordering.

For F-2, use a seeded SQLite and PostgreSQL media dataset with recorded row count and `SUM(size)`. Run one startup icon refresh in a fresh process and record process `heapUsed`, `external`, `arrayBuffers`, RSS, transferred DB bytes if available, CPU time, and job duration. Compare full-row loading against a metadata/checksum or fixed-size batch implementation while checking that new local media, existing media, deleted media, and first-time repository backfill produce the same icon set. No measurements were run, so absolute RAM, transfer, CPU, or startup savings remain unknown.
