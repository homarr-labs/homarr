# Client bundles and dependency boundaries

## Direct findings

The strongest bundle finding was the Custom JSX runtime importing the full authoring catalog through `component-registry.ts`. Before the change, the generated JSON contributed 863,195 raw / 89,058 compressed-estimate bytes to deferred client chunk `1no5g3qscy3pr.js` (whole chunk: 871,041 / 92,566). The compatible fix now generates a compact runtime projection from the same canonical catalog and routes runtime registry plus JSX required-prop analysis through it. The projection preserves all 475 descriptors, required props, safety and blocked-prop metadata, binding modes, aliases, and names; the archived parity comparison passed 4,311 binding cases. The full authoring JSON and docs JSON remained byte-identical to baseline.

The after analyzer emits the runtime projection in deferred chunk `04c180k4sfkkp.js` at 234,629 raw / 19,256 compressed-estimate bytes. That is 636,412 raw / 73,310 compressed-estimate bytes less than the old catalog chunk for the renderer path. The full authoring JSON still emits in a separate 866,241 / 90,588 chunk because the board's lazy widget-edit flow reaches the authoring workbench. The async importer chain is `lazy-widget-edit-modal.tsx` → `widget-edit-modal.tsx` → `widget-custom-widget-configuration-input.tsx` → workbench component reference. The production dependency graph confirms there is no static or async path from the full authoring JSON to `custom-jsx-renderer.tsx`; its static path now runs through the compact projection → registry → runtime components → renderer. If a user opens the widget editor, both catalog chunks are reachable: 1,100,870 raw / 109,844 compressed-estimate bytes combined, an increase of 229,829 / 17,278 over the old single catalog chunk. Route reachability does not establish that both chunks are initially requested. Cold-cache request behavior remains unmeasured. Before and after raw analyzer data and selected projections are preserved under `audit-evidence/2026-10-11/production-analyzer-before/`, `production-analyzer-after/`, and `overview_a-after-projection.json`.

The analyzer also measures the deferred runtime namespace chunk `2w_9fr-5dpits.js` at 404,584 raw / 173,103 compressed bytes. It contains 136,747 / 60,460 bytes from `@mantine/core`, 56,638 / 25,633 from `@mantine/charts`, 111,496 / 45,387 from Recharts, 18,776 / 8,822 from `@mantine/dates`, and 28,005 / 9,991 from `@mantine/hooks`. This directly confirms the `* as Core`, `* as Charts`, `* as Dates` namespace imports plus `Reflect.get` path produce a large feature chunk. It does not establish that all of those bytes are avoidable: the generated catalog currently allows 405 Core, 26 Charts, and 32 Dates component names. An explicit generated name-to-component map could make the supported export set statically visible, but may retain most of the same implementation because the allowed surface is broad. Treat it as a follow-up only if comparing the map against actual package exports reveals unsupported modules in this chunk; preserving every currently allowed JSX component is a compatibility constraint.

Weather is deferred at the widget boundary through a literal component loader. Within that boundary, however, `weather/component.tsx` statically imports both `AdvancedWeather` and `CompactWeather`. The analyzer places them together in `3o6sfc2d7bvrd.js` (22,163 raw / 7,279 compressed); `AdvancedWeather` contributes 9,875 / 2,856 of those bytes. The module graph shows AdvancedWeather's CompositeChart dependency in the same async widget load path. A `next/dynamic` split conditioned on `displayMode === "advanced"` would defer at least the AdvancedWeather module bytes from compact weather and would place its chart dependency behind the same condition. The analyzer's current source-to-output mapping does not provide a reliable weather-only transfer total for the shared chart module parts, so the full saving and request delay remain unmeasured. This is a smaller candidate than the catalog split.

The app-level provider graph is intentionally mostly shared. `layout.tsx` composes auth, settings, Jotai, tRPC, Day.js localization, next-intl, Mantine, modal, spotlight, and assistant providers for all locale routes. `trpc.tsx` imports development-tools only under a `NODE_ENV === "development"` conditional and uses `dynamic(..., { ssr: false })`; its implementation imports TanStack Query Devtools. This is a good production boundary. The remaining provider imports are direct runtime requirements of the global layout; no unnecessary provider dependency is proven by source inspection.

Translation loading is locale-scoped at runtime. `translation/src/mapping.ts` constructs a loader map of computed imports for all supported languages, and `request.ts` calls only the selected locale and, when incomplete, the fallback locale. This syntax exposes all files to bundler context discovery but does not establish that all locale JSON is transferred on every route. `NextIntlClientProvider` sits in the global layout, so selected/fallback message data is part of the rendered client boundary. Largest raw locale sources are Greek (464,200 bytes), Russian (439,792), Ukrainian (433,982), and Vietnamese (355,723); these source sizes are not compressed transfer sizes or JS sizes. Keep the locale loader as-is unless the production graph or a Flight capture shows unrelated locale modules or excessive client payload.

`next.config.ts` enables `optimizePackageImports` for Mantine Core, Mantine hooks, and Tabler icons and otherwise does not configure a bundle analyzer or custom client chunk strategy. That configuration is relevant context but is not evidence of a size reduction. `dayjs-loader.tsx` imports the locale hook, which imports `localeConfigurations`; actual localization is loaded through the configuration's locale-specific importer. `mantine.tsx` and `session.tsx` each use Day.js functionality, so Day.js itself is also a shared provider dependency.

## Measurements and evidence limits

Before and after production analysis used the same pinned Next.js 16.3.6 command and environment. The after output is preserved at `audit-evidence/2026-10-11/production-analyzer-after/`; selected raw and source projections, including route-specific catalog edges and importer paths, are in `overview_a-after-projection.json`. Next's `compressed_size` is a gzip-oriented estimate, not a browser transfer measurement; Brotli was not emitted. The analyzer's route graph shows the old authoring JSON on the board route because edit actions can asynchronously reach the workbench. The module dependency graph distinguishes this editor path from the Custom JSX renderer path. It does not provide a reliable initial/shared/route transfer total or prove when the lazy editor chunks are requested. No browser cold-cache network trace, Brotli measurement, or browser heap/RAM profile was taken. Checked-in locale JSON sizes remain raw source sizes only; the selected/fallback runtime locale behavior is established by code, not measured network payload.

The compact runtime catalog split is supported by the production graph: it removes the full authoring JSON from the renderer's static and async dependency closure while retaining the authoring catalog for the editor. The emitted runtime renderer chunk is 636,412 raw / 73,310 compressed-estimate bytes smaller than the prior catalog chunk. The workbench path now has both artifacts and costs about 229,829 raw / 17,278 compressed-estimate bytes more in the analyzer graph, so browser request timing and actual cache behavior are still needed to characterize user-visible impact. The namespace candidate remains a follow-up: an explicit generated name-to-component map could expose the allowed export set, but no size claim is justified without comparing it against actual package exports. The weather split has a measured lower bound of 9,875 raw / 2,856 compressed-estimate bytes of AdvancedWeather code, with shared chart savings and request timing still unknown. RAM remains unmeasured.
