# Client memory and lifecycle overview B

## Scope and confidence

Directly traced the assigned provider, board, modal, Custom JSX runtime, custom API widget, and notebook paths through their callers. Read the app layout provider composition, notebook dynamic widget loader, board management page/card/form/menu, and the shared query-cache policy. Checked installed Mantine Collapse source for the `keepMounted` default; Context7 was unavailable because its quota had been reached, so no current external API guidance is claimed. No production code, tests, builds, browser cycles, or heap measurements were run.

## Finding: every collapsed board card mounts a duplicate form and starts a query

**Reachable path and trigger:** `/manage/boards` renders a `BoardCard` for each board. Each card renders `DuplicateBoardForm` under Mantine `Collapse`, initially with `expanded={false}`. The installed Collapse implementation defaults `keepMounted` to `true` (React 19 Activity hidden mode), so the form mounts while closed. `DuplicateBoardForm` initializes the name to the current board name and calls `useBoardNameStatus`; that hook debounces the name and enables `board.exists` for valid names. This runs even when `board-create` is absent, although the menu action is hidden in that permission state.

**Retained objects and scale:** The form retains its React form state and query observer while the card is mounted. The React Query cache retains a boolean result under the name-specific key after the observer leaves, subject to the provider's five-minute default `gcTime`. For N visible cards, initial page load can create N availability queries; the server endpoint loads/scans board names per query, yielding up to N reads and O(N²) name comparisons. Result payloads are small, so this is a strong unnecessary-work/query-retention candidate, not a large-byte leak. The query count and elapsed cost were not measured here.

**Smallest compatible fix:** Only mount the form after the duplicate panel opens, with the existing `board-create` check. Opening already increments `duplicateFormKey`, indicating the form is intended to reset between openings; conditional mounting also releases its observer when closed. Alternatively, add an `enabled` argument to the name-status hook and gate it on both panel-open and permission state, which preserves a mounted form but keeps its state. Both approaches trade eager first-open validation for a query when duplication is actually requested.

## Finding: notebook retains a serialized copy and rebuilds it on each editor update

**Reachable path and trigger:** The notebook is lazily loaded through the widget registry and `notebook/index.ts` → `component.tsx` → `notebook.tsx`. On every Tiptap `onUpdate`, `editor.getHTML()` serializes the full document and `setContent` stores it in React state. The editor already holds the ProseMirror document. The serialized `content` is then passed back as the `useEditor` content and used for save/rollback state.

**Dimensions and evidence:** For document size N, each update performs O(N) serialization and creates a temporary O(N) HTML string; the latest string remains retained as component state while the editor is mounted, in addition to the editor model. The setter also schedules React work on each update. This is repeated allocation and one duplicate representation, not evidence of monotonic retained growth or a leak. The baseline default content is 4,438 bytes; user content has no bound found in the widget definition. No representative document-size distribution, input-to-paint timing, allocation profile, or heap snapshot was available.

**Smallest compatible fix:** Remove the `onUpdate` state serialization and serialize only at save or read-only task commit. Keep the editor as the editing source of truth and preserve `previousContentRef` rollback/external-option synchronization. This reduces per-transaction CPU and temporary allocation, while retaining one serialization when a save is needed. Validate the save, cancel, failed-save rollback, external update, and read-only checkbox paths before shipping; they were not exercised in this audit.

## Lifecycle and cache audit

- `TRPCReactProvider` is composed by the locale root layout and owns the client `QueryClient`, tRPC client, and lazy WebSocket client across ordinary route navigation. On provider unmount it closes the WebSocket and clears the query cache. Session identity/permission changes render the scope guard and reload the page. Unobserved query records use a five-minute GC window; this intentionally retains visited route/widget data briefly. Repeated navigation can temporarily retain distinct data during that window, but no unbounded cache path was established. Dashboard support-query reconnect policies are explicit; widget queries disable reconnect/focus refetch, while small app/integration metadata queries permit them. No reconnect listener leak was found.
- The board viewport subscription removes its resize listener and cancels a queued animation frame. `BoardProvider` invalidates the board query on pathname change/unmount; the invalidation enables refresh on a later return and leaves the normal cache-GC policy in control. `updateBoardName` retains only a module-level string, not a board payload.
- The notebook's custom read-only event listener and Tiptap selection listeners have cleanup functions. Its task-item node view removes the checkbox listener and calls the parent destroy handler.
- Development tools are dynamically imported only in development. While open, they subscribe to query/mutation caches and observe DOM changes; cleanup unsubscribes, disconnects the observer, and cancels a queued animation frame. The full-body MutationObserver can add diagnostic CPU work while the panel is active, but no measurements were taken and it is not a production path.
- Session expiry timeout is cleared when the session effect changes or unmounts. Mantine's color-scheme manager exposes no-op subscription methods; no retained listener is registered there. Dayjs locale loading and the Jotai provider add no per-navigation listener/timer in the inspected code.
- Modal `CLOSE` and `CLOSE_ALL` remove closed entries from `state.modals`. `keepMounted` retains an earlier modal only while a newer modal is active; closing still removes the entry. The zero-delay opening timeout in `ActiveModal` has no cleanup, but it is a one-event-loop-turn transient closure, not a persistent closed-modal heap leak. The provider is route-scoped on board/widget routes, so route exit also unmounts it.
- No `URL.createObjectURL`/`revokeObjectURL` pair or URL-backed object lifecycle was found in the assigned client paths.
- Custom JSX input registrations are held in a per-renderer `Map` and removed by each registration cleanup; queued reconciliation checks a version and a mounted flag. Input edits copy the small active values/types records. They also rerun safe JSX rendering and `createBoundaryKey`, whose `JSON.stringify(bindings)` builds a temporary string proportional to binding data before hashing it. This is a possible CPU/allocation cost for large binding payloads, not retained serialized data; no data-size or keystroke benchmark justifies a fix yet. Published subquery results are scoped to the current widget identity and replaced/removed by request id; the underlying query cache observes the shared five-minute GC.

## Measurement needed before calling anything a leak

Use the same browser/build, account, board set, and fixture for baseline and candidate. Warm the app, collect a post-GC heap snapshot, then repeat a fixed sequence of `/manage/boards` load → open/close duplicate panel → navigate away/back, dashboard notebook mount → fixed typing sequence → navigate away/back, and modal open/nest/close. Repeat enough cycles to distinguish a stable cache/DOM plateau from growth; compare post-GC retained size and retaining paths for `DuplicateBoardForm`, query entries/observers, notebook HTML strings/editor states, detached DOM nodes, timers, listeners, and WebSocket objects. Record request count and latency for board availability queries, and input-to-paint/transaction duration for notebook typing. A leak claim requires retained objects or bytes continuing to grow across equivalent cycles after expected query GC and collection; one snapshot or allocation spike is insufficient. No such raw browser evidence was available for this review.
