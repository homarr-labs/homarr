# Audit 15 — Infrastructure integrations and statistics

## Scope and evidence quality

The assignment contains 115 files; all 115 were individually read in full. `coverage/audit_15.json` records per-file status and evidence, with no exclusions. Large integration files Beszel (643 lines) and Wazuh (938 lines) received dedicated full-file passes. Relevant call sites were followed into API routers, the integration factory/creator, and integration deletion. This is a static code audit: no production changes, tests, builds, heap/CPU profiling, or representative endpoint measurements were performed. No conclusion below claims measured RAM or request sizes.

Three retention/resource findings were identified. Their code-level existence is high confidence; severity and user impact remain uncertain without runtime frequency, payload, and lifecycle measurements.

## Finding 1: Beszel SSE parser accepts unbounded incomplete lines and frames

**Call path and trigger:** `packages/api/src/router/widgets/beszel.ts` creates the live subscription and invokes `BeszelIntegration.subscribeRealtimeMetrics`; the integration decodes stream chunks and passes them to `PocketBaseSseParser.push`. In `packages/integrations/src/beszel/pocketbase-realtime.ts:10-27,42-63`, `buffer` grows until a newline and `dataLines` grows until a blank frame delimiter. A configured Beszel endpoint that emits a very long unterminated line, or keeps sending `data:` lines without the delimiter, therefore prevents dispatch while retaining all accumulated input.

**Cause and dimensions:** Neither line nor frame has a byte/character cap. The consumer queue's four-event limit (`packages/api/src/router/widgets/beszel.ts:19,211,240`) applies only after dispatch and cannot constrain a partial frame. Parser-retained strings are O(N) in bytes received for each open subscription; decoding and string concatenation can create transient copies. This is a retained-input issue, not an inference from dependency size. The stream is intentionally long-lived, so ordinary wall-clock timeout is not a valid bound. No baseline frame sizes, heap measurements, or concurrency counts are available.

**Minimal compatible fix and constraints:** Bound line and aggregate frame bytes in `PocketBaseSseParser`; on overflow, fail that stream and use the existing abort/retry cleanup. Preserve UTF-8 chunk handling and normal event semantics. Select the limit from representative real snapshots, since too-low a cap could reject valid high-container-count snapshots. Validate raw/decoded frame distributions and peak retained parser state at one and concurrent subscriptions, then verify normal frames, split code points, oversized unterminated lines/frames, reconnect, and client abort. Confidence is high on the unbounded code path, medium on material impact.

## Finding 2: Synology API-definition cache grows with integration ID churn

**Call path and trigger:** `SynologyIntegration` obtains a client via `getClient` (`packages/integrations/src/synology/synology-integration.ts:101`); API calls resolve endpoint definitions through `packages/integrations/src/synology/synology-client.ts:353-388`. The module-level `apiDefinitionCache` at line 52 keys definitions by integration ID and API name. Successful lookups remain in the map indefinitely. The client is created through the integration factory per request (`packages/integrations/src/base/creator.ts:312-313`), while the cache outlives those clients. Deleting an integration does not clear this map: the authorized delete path in `packages/api/src/router/integration/integration-router.ts:415-438` removes database and shared response-cache state but does not call the Synology cache.

**Cause and dimensions:** For each distinct ID, only a fixed set of API definitions used by this client is reachable, and each value contains small path/version metadata. Thus growth is O(I × A), where I is the number of distinct IDs encountered during the process lifetime and A is the fixed API-name set; the cache does not retain response payloads. This is an unbounded cardinality/lifetime issue, but no runtime count or process memory measurement establishes material impact.

**Minimal compatible fix and constraints:** Add a bounded LRU/TTL or targeted invalidation on successful integration deletion, ideally with a cap as a fallback for IDs that disappear through other lifecycle paths. Keep cache lookup behavior for active integrations. Eviction may cause a later request to refetch Synology's API info endpoint; it must not change authentication ordering or cache user response data. Verify map cardinality during repeated create/use/delete churn and ensure concurrent misses do not corrupt definitions. Confidence is high on indefinite retention, low-to-medium on impact because each value is small and A is fixed.

## Finding 3: TrueNAS integration deletion leaves reusable sockets and map entries

**Call path and trigger:** `TrueNasIntegration.getClient` creates a client for requests (`packages/integrations/src/truenas/truenas-integration.ts:103-116`). `TrueNasClient` holds module-static `connectionMap` and `apiMap` keyed by integration ID (`packages/integrations/src/truenas/truenas-client.ts:36-37`). Successful connections are retained for reuse (`:69-80`); normal cleanup shown in this client is failure/server-close handling and explicit connection testing (`:56-58,98-104`). The API deletion mutation authorizes first, deletes the integration, then clears shared integration response cache (`packages/api/src/router/integration/integration-router.ts:415-438`), but does not evict these maps. Trigger: make a successful TrueNAS request, then delete the integration while its remote websocket remains open. Its socket and static entries can remain until the remote closes or the process exits.

**Cause and dimensions:** This retains a live network resource and per-ID map state, rather than merely a small metadata cache. With D deleted integrations whose peers remain open, retained connections/map entries scale O(D); active socket buffers are runtime-dependent and were not measured. The code does not establish how frequently the remote closes idle sessions, so no byte estimate or impact magnitude is claimed.

**Minimal compatible fix and constraints:** Provide an ID-scoped cleanup operation on `TrueNasClient`/a connection manager and call it only after the delete permission check and successful database deletion (alongside existing cache invalidation). Cleanup should close the socket and remove both maps, while safely handling an in-flight connection promise. An idle TTL is a useful fallback for missed lifecycle paths. Preserve reuse while an integration is active and avoid cleanup before authorization or before delete success. Verify concurrent request/delete ordering, in-flight connection settlement, and remote-close behavior; measure open sockets and map cardinality under delete churn. Confidence is high that deletion currently lacks cleanup, medium that sockets persist because peer idle-close behavior is not established.

## Other reviewed areas

Beszel REST listings and Wazuh query/result cardinalities have explicit page/result limits in the reviewed paths. Wazuh still fully parses returned JSON and individual strings/raw response bodies are not byte-capped; no payload measurements established a separate actionable finding. AdGuard parses three concurrently fetched endpoint bodies. Stats integrations parse provider responses, whose sizes vary and were not measured. These are confirmed buffering/materialization paths, not measured memory findings; this audit does not infer RAM from dependency size or transient allocations from retained state.
