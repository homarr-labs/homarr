# Overview E: background services and integrations

Direct review of the assigned source paths and their callers. No code changes or runtime measurements were made. Static behavior below is verified from source; byte-level memory impact and production frequency are unmeasured.

## Confirmed lifecycle findings

### TrueNAS WebSocket state survives integration deletion and edits

- **Trigger/call path:** a TrueNAS widget request constructs an integration through the factory and calls `TrueNasIntegration` methods. `TrueNasClient` stores a process-static `connectionMap` and `apiMap`, keyed by integration ID ([truenas-client.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/integrations/src/truenas/truenas-client.ts:33)). Successful connections are retained and only evicted when the socket closes or an explicit connection test evicts it ([lines 68–80, 98–104]).
- **Cause/lifetime:** deleting an integration removes its DB row and invalidates its widget cache, but does not notify `TrueNasClient` ([integration-router.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/api/src/router/integration/integration-router.ts:415)). An open upstream socket and its map entry therefore remain until the remote closes it or the process exits; `apiMap` has no normal cleanup path at all. Updating a TrueNAS integration also leaves the same ID mapped to a socket authenticated with the old URL/credentials; the update handler only invalidates request caches.
- **Scaling/evidence:** retained state grows with the number of distinct TrueNAS IDs that have opened a connection and have not had the remote socket close. Per active integration this is one socket plus one entry in each map. There is no evidence of an unbounded per-request accumulation for a stable ID because the connection is reused. No production counts, socket lifetimes, or heap measurements are available.
- **Smallest compatible fix/tradeoff:** add an explicit `TrueNasClient` eviction API and invoke it after successful update/delete for TrueNAS IDs; remove both maps and close the old socket. Keep the socket reuse behavior. Updating after DB commit avoids dropping a working connection if persistence fails, but concurrent in-flight requests may fail while the socket closes; evicting before commit has the inverse failure mode. Consider making the lifecycle hook part of integration-owned cleanup if other persistent integrations are added.

### LDAP authorization leaks clients on failure paths

- **Trigger/call path:** each LDAP login creates a service-bind `LdapClient`; after finding a user it creates a second client for password validation ([ldap-authorization.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/auth/providers/credentials/authorization/ldap-authorization.ts:18)). `disconnectAsync` is called only after successful user bind and group search (lines 86 and 109). The client wrapper owns an `ldapts.Client` and exposes `unbind()` as its disconnect ([ldap-client.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/auth/providers/credentials/ldap-client.ts:16,70)).
- **Cause/lifetime:** search errors, multiple/no user results, invalid email, group search errors, and other exceptions after service bind bypass its disconnect. A failed user-password bind throws before its disconnect too. Repeated failed logins can therefore leave sockets/client resources open until underlying library or runtime cleanup; exact socket retention behavior is not measured here. A failed service bind also bypasses cleanup.
- **Scaling/evidence:** the possible retained count scales with the rate of failed logins and how long the LDAP client/socket remains alive. Each flow can leak one client, or two when it reaches user bind. No live LDAP reproduction or resource measurement was performed.
- **Smallest compatible fix/tradeoff:** put each client’s complete bind/search/use sequence in `try/finally` and call `disconnectAsync()` in `finally`, including failed bind. Preserve the existing `CredentialsSignin` mapping and ensure cleanup errors do not replace the authentication error (log cleanup failure). This bounds client lifetime to one authorization attempt, subject to the LDAP library’s unbind completion.

## Memory and concurrency pressure (verified paths, magnitude unmeasured)

### Icon refresh materializes local media BLOBs while fetching all repositories

- **Trigger/call path:** the weekly icon updater runs at startup (`runOnStart: true`) and calls `fetchIconsAsync()` ([icons-updater.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/cron-jobs/src/jobs/icons-updater.ts:15,20–22)). That function uses `Promise.all` over six repositories; the local repository runs `medias.findMany()` with no projection/limit, then maps every row through MD5 over `media.content` ([icons-fetcher.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/icons/src/icons-fetcher.ts:50), [local.icon-repository.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/icons/src/repositories/local.icon-repository.ts:16–21,28–35)).
- **Cause/scaling:** all local media rows, including content BLOBs, are loaded as a result set before hashing. During this interval the other five remote index requests and their parsed response objects are also live. Local BLOB bytes scale with total stored media bytes; CPU and metadata output scale with number of media records. Returned icon metadata and later icon DB rows remain live beyond BLOB mapping; the BLOB result set can become collectible only after mapping completes. This is application-process memory, distinct from DB page cache, remote service memory, or Redis. No measurements of local media size/count or peak heap/RSS are present.
- **Smallest compatible fix/tradeoff:** page through media rows using stable keyset pagination, selecting only the columns needed for hashing and metadata, and hash each page before fetching the next. Keep the same checksum and complete inventory semantics. This lowers the transient BLOB peak while retaining metadata for all icons; it adds query overhead and requires a stable unique ordering. Alternatively a persistent checksum would reduce refresh CPU but changes schema/write paths and needs consistency handling, so it is not the minimal first step.

### RSS `maximumAmountPosts` limits output after full feed fetch and parse

- **Trigger/call path:** `rssFeed.getFeeds` accepts up to 100 URLs and fetches each concurrently with `Promise.allSettled` ([rssFeed.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/api/src/router/widgets/rssFeed.ts:25–45)). Each call invokes `extract(url, …)` and only afterward maps and slices entries to the requested count ([rss-feeds.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/request-handler/src/rss-feeds.ts:12–35)). The general request handler supplies a 60-second timeout, 100 in-flight cap, and process-local cache bounded to 1000 keys by default ([request-handler.ts](/home/habs/.codex/worktrees/5fcf/homarr/packages/request-handler/src/lib/request-handler.ts:28–33,125–133)).
- **Cause/scaling:** post count bounds returned/cache-retained entries, but does not bound response bytes or the parsed feed object while `extract` buffers/parses. One query can start up to 100 feed handlers concurrently; overlapping queries can increase concurrent work until the handler’s in-flight guard rejects excess work. Peak transient parser memory is approximately the sum of active response/parser buffers plus returned objects across feeds; exact parser buffering behavior depends on the installed `feed-extractor` version and was not measured. This is application-process memory; upstream feed memory is separate. Existing timeout/concurrency bounds limit duration/count, not per-response bytes.
- **Smallest compatible fix/tradeoff:** use a parser path that can stop after the configured number of entries and stream the response, or enforce an explicit maximum response-byte budget before parsing and return a clear feed error when exceeded. Keep the current post count semantics and allow users to see which feed exceeded a configured safety bound. A byte ceiling changes behavior for unusually large feeds, so its value/error should be explicit and validated against actual feed sizes before rollout; no silent truncation or hidden feed-count reduction is justified by current evidence.
