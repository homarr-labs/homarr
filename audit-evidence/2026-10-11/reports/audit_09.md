# Audit 09: Custom Widget core and server

## Finding: successful query cache retained parsed responses after expiry while idle

**Call path and trigger.** `packages/api/src/router/custom-widget/preview-query-procedures.ts` builds a `custom-jsx:preview:<session>:<request>:<params>:<connection-version>` key and passes `request.cacheSeconds` to `executeCustomWidgetRequest`. `packages/api/src/router/custom-widget/management-queries.ts` does the same for option queries with a 30-second default. On a successful cacheable query, `packages/custom-widgets/src/server/request-executor.ts` stores the already parsed and redacted response object in the module-level `cache` map. Request schema allows `cacheSeconds` through 3600 seconds.

**Cause and measured evidence.** Before the fix, the cache held at most 1,000 entries and expired entries were reclaimed only on later insertions or matching-key lookups. A 1-second TTL followed by 100 ms idle left parsed responses in the cache until explicit invalidation or another insertion. In nine alternating fresh-process pairs using Node 24.18.0, `--max-old-space-size=512`, and the actual executor with a loopback HTTP fixture, median 100-entry `heapUsed` after expiry was 42,070,424 bytes before versus 16,213,736 bytes after the fix. Explicit invalidation freed a median 26,246,352 bytes before the fix versus 1,296 bytes after. With 25 entries, the paired idle heap reduction was 6,549,552 bytes. The fixture sent 25 or 100 requests concurrently via `Promise.all`; each response contained a 262,144-byte payload string and a 262,172-byte serialized JSON body. This is controlled fixture evidence, not a claim about typical production response sizes. The 1 MiB input response limit and entry cap are not an aggregate memory budget.

**Dimensions and limits.** Five repeated 25-entry expiry cycles showed baseline idle heap plateauing around 22.50 MB rather than growing per cycle; the existing next-insertion prune reclaimed the preceding expired batch. The bug is bounded stale retention during idle by the existing 1,000-entry cap, not an unbounded leak. Measurements include the fixture server and executor in one Node process. Per-process sampled maximum RSS medians were 215,764,992 bytes baseline and 219,398,144 bytes after, with overlapping ranges; this does not establish an RSS improvement or a process peak. The result supports heap reclamation only. There is no client bundle or network-transfer cost from this server cache.

**Smallest compatible fix.** Implemented one unref'd timer for the earliest cache expiry in `request-executor.ts`. Insertions compare the new deadline in O(1); when the timer fires, it prunes expired entries and scans for the next deadline in O(C), with C bounded by the existing cap. The callback does not run capacity eviction, capture response values, or change cache epochs/in-flight requests. Long finite TTLs are clamped to Node's 2,147,483,647 ms timer limit and rescheduled. The existing entry cap and request/cache semantics remain in place.

**Tradeoffs and validation.** The timer adds one unref'd handle and an O(C) expiry cleanup/next-deadline scan, at most once per expiry batch; partial invalidation can cause a harmless early timer wake. Idle-window process CPU measurements were noisy (100-entry median 1.31 ms baseline versus 7.53 ms after over the 1.1-second wait), so they do not isolate callback cost; the expected bounded scan cost is explicit. All 18 paired runs passed cache-hit, expiry-refetch, refreshed-hit, and in-flight generation assertions. Separate baseline and fixed runs each inserted 1,001 unique keys and verified oldest-entry eviction. Raw samples, runtime/source hashes, controls, and limitations are in `audit-evidence/2026-10-11/measurements/cache-expiry-results.md` and its adjacent JSONL files. No production-distribution or maximum-size workload was measured.

**Confidence and gaps.** High that the pre-fix cache retained expired parsed responses under idle conditions and that the timer reclaims them in the measured fixture. Real-world impact depends on response sizes and cache activity; production payload distributions were not measured. The cache stores already-redacted response data; the fix does not alter the credential-redaction boundary or cache keys.

## Generated catalog and client import trace

The canonical generated catalog at `packages/custom-widgets/src/core/component-catalog.generated.json` is 861,611 bytes raw; the docs copy at `apps/docs/public/custom-widgets/component-catalog-v1.json` is byte-identical and 861,611 bytes. The catalog contains 475 components, 4,104 component props, 440 shared props, 509 interned types and 52 blocked capabilities. Runtime client path: `custom-jsx-display.tsx` → `@homarr/custom-widgets/runtime` → `jsx/runtime-components.tsx` → `core/component-registry.ts` → `core/component-catalog.ts` → generated JSON. Runtime uses component names, safety, supported prop names, blocked properties and binding metadata; the authoring surface also needs rich descriptions and type details.

This is a confirmed static import path, but the emitted client chunk, tree-shaken bytes, gzip/Brotli transfer size and browser parse/initialization cost were not measured. No bundle finding is asserted from source JSON size alone. The architecture checker explicitly requires the canonical catalog and rejects a second generated runtime catalog. The metadata generator's Mantine namespace reflection is only called by its CLI and is not on the production import path. No build was run.

## Large-file passes

- `scripts/ai-assistant-evaluation.ts` (1,565 lines): read in five complete ranges and checked against its evaluator caller. Its message compactor checks for history above 48,000 serialized characters and removes older reloadable tool payloads by retention age; it does not enforce a hard post-compaction cap. It writes trace artifacts intentionally. The retained tool/preview state is per attempt.
- `scripts/ai-evaluation-cases.ts` (1,223 lines): read in three complete ranges and searched for imports. It consists of deterministic fixtures and expectation data, imported only by evaluator scripts and package specs; it is not a production data import.
- `scripts/ai-evaluation.ts` (999 lines): read in three complete ranges and checked against evaluator caller. Prompt/result artifacts are written per case; judge calls are bounded to seven per panel and no production caller imports this script.
- `scripts/generate-component-metadata.ts` (735 lines): read in three complete ranges. TypeScript program creation and Mantine namespace reflection happen only when running the catalog generator; its original authoring and public JSON outputs are identical (the retained projection later adds a third output).
- `src/core/assistant-authoring-phase.ts` (737 lines): read in three complete ranges. It derives staged tool availability from caller-provided lifecycle events; it does not keep process-global histories.

## Other observations and scope

- The server response reader collects chunks, copies them into a contiguous byte array, decodes a string and then parses JSON. This creates short-lived copies, but the body and decompression stages are capped at 1 MiB, JSON depth at 32 and node count at 50,000. No separate allocation finding is made without representative peak-heap evidence.
- Preview sessions have a ten-minute TTL and a 50-entry journal cap; production callers configure Redis TTL storage. The in-memory fallback is selected only for CI/test environments.
- Request concurrency/rate limits are Redis-backed in production. Request bodies are capped at 10 KiB, requests at 64, and source count at 8.
- The only production edit is `packages/custom-widgets/src/server/request-executor.ts`. No test suite, build, Docker compilation, or E2E run was performed; validation used the dedicated loopback measurement harness and its behavior assertions.
