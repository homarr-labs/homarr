---
title: Headless and native workers
---

Homarr can run its normal Next.js frontend with independent encrypted workers. Set `HOMARR_FRONTEND_MODE=workers` to use this frontend mode; each worker runs the Bun backend and keeps its own board and integration data. The existing HTTP backend remains available for the classic frontend.

## Try the native setup

With Docker running, start the sample installation from the Homarr checkout:

```sh
bash scripts/native-demo.sh up
bash scripts/native-demo.sh pair primary
```

Open the private setup link in your browser. It pairs the primary worker with the normal Homarr frontend at `http://localhost:43105/`. Use localhost on the computer running Docker. The worker bar at the bottom switches between connected workers; the primary worker keeps your boards.

Add the sample integration worker in the same browser:

```sh
bash scripts/native-demo.sh pair integrations
```

Open its setup link. Adding it keeps the primary worker selected. To use its services on boards, open **Manage → Integrations** on the primary worker, use **Services from your other workers**, select the integration worker, load its integrations, choose the ones to share, then approve and add them. The source worker retains the credentials and access approval.

`bash scripts/native-demo.sh down` stops the containers and preserves their data. For a different device or a production host, use an HTTPS reverse proxy that supports WebSocket upgrades.

## Deploy the frontend and workers

The source deployment uses separate `frontend` and `platform` targets from `Dockerfile.frontend` and the `worker` target from the root `Dockerfile`. The native Compose stack adds a gateway and relay. Start it with your public frontend origin and relay address:

```sh
HOMARR_PUBLIC_URL=https://homarr.example.com \
HOMARR_PUBLIC_RELAY_URL=wss://homarr.example.com/relay \
docker compose -p homarr-native -f deployments/native/compose.yml up -d --build
```

Set `WORKER_PLATFORM_URL` on each worker to the URL of your normal Homarr frontend. The worker image's older default, `https://homarr.dev/remote/`, points to the previous remote frontend and does not match this setup. The native Compose file supplies the correct value for its gateway.

Keep the worker, platform, and broker volumes. Back up the platform MCP database with its broker key; losing that key prevents the platform from restoring existing hosted MCP approvals. The [native deployment README](https://github.com/homarr-labs/homarr/blob/main/deployments/native/README.md) covers the Compose services, proxy routing, and storage.

The configured Workshop PocketBase and its GitHub provider can identify account and organization membership. That metadata alone does not grant private worker access: each worker still requires explicit approval for a device or service.

The relay forwards encrypted worker traffic and can see routing IDs, connection timing, and ciphertext lengths. Hosted OAuth MCP requires a worker relay connection; direct or Tailscale-only access does not make a worker reachable by the hosted service. The MCP gateway can read the tool arguments and results you approve, and stores its separate limited worker credential encrypted at rest. It never receives the browser's owner key.

## Keep the classic HTTP backend

The classic frontend can continue to use a separately deployed HTTP backend through `HOMARR_BACKEND_URL`. This path uses the existing backend API and its Redis configuration; it does not require worker mode. See [environment variables](/docs/advanced/environment-variables) for the backend settings.

For the source development setup, see [getting started](/docs/advanced/development/getting-started).
