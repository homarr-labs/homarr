## Create a Custom Widget manually

1. Add the API source.
2. Select its network scope.
3. Select its authentication mode.
4. Enter the credentials.
5. Declare the named requests.
6. Define the widget options.
7. Write JSX with `data`, `status`, `options`, and temporary `inputs`.
8. Select **Test and preview**.
9. Wait for the load requests to stop.
10. Open the Data tab to examine responses and request errors.
11. Preview the compact, standard, and wide layouts.
12. Examine the runtime and accessibility diagnostics.
13. Save the definition.
14. Select the definition and its widget options in the board widget picker.

Homarr does not show existing plaintext credentials. It shows only the configuration status.

The preview action shows a loading state during load requests. The Data tab indicator shows green or red after completion.

The preview renders again when request data becomes available.

## Create a Custom Widget with ChatGPT

Enter a short request. You can also enter an API documentation URL.

Select **Copy AI prompt**. The menu also provides **Copy with embedded skill**, a complete release-matched offline prompt.

Both prompts support offline authoring. They do not require MCP resources, MCP tools, or file-system access.

Paste one prompt into ChatGPT or a different model. Tell the model to return exactly these two blocks:

1. A fenced `json` block with one complete widget and `template: "__HOMARR_TEMPLATE__"`.
2. A fenced `jsx` block with the readable template.

Select **Paste AI response** to fill the workbench. Enter the credentials.

Test the requests. Preview the widget.

If the save operation fails, copy the validation errors. Give the error text to the model.

Homarr does not make a separate correction prompt. Homarr does not assume that the model can read local skill files.

The standard prompt contains fewer than 8,000 characters. It includes the installed Mantine version and the capability rules.

It does not include a complete prop list, MCP workflow, server URL, or credentials. The prompt with the embedded skill is intentionally longer. It starts with your widget request, then includes:

- `SKILL.md` and all eleven release-matched reference files, including the canonical widget JSON Schema
- The Custom Widget, Mantine, skill, and catalog-schema versions
- The compact canonical component catalog
- Canonical runtime examples

The generated Markdown references remain readable offline. The compact JSON catalog gives tools the identical machine-readable component records used by Homarr.

The embedded prompt ends with this sentinel and an exact total character count:

```text
--- END HOMARR CUSTOM WIDGET OFFLINE BUNDLE ---
Characters: <exact clipboard character count>
```

The count includes the whole prompt and the count itself. If the sentinel is missing or the number does not match the clipboard length, copy the prompt again before sending it to a model.

The embedded content explicitly tells a model to author directly from the offline bundle. It does not claim that MCP tools, Homarr resources, repository files, or file-system access exist in the chat.

## Configure widget options

Widget options use a restricted object JSON Schema. Homarr supports the following controls:

- Text
- Text area
- Number
- Switch
- Select
- Multi-select
- Slider
- Date
- Time
- Color
- URL
- Nested group
- Conditional field
- JSON value

Credentials are not widget options. Homarr rejects credential names and static credential values in widget options.

Configure authentication in the API source. Homarr then keeps the values encrypted and excludes them from exports and board configuration.

Dynamic selects use `x-homarr.optionsSource` and a named query. Add `itemsPath` when the response contains the result array in an object.

Set `valuePath` and `labelPath` relative to each item. These requests run only during widget option configuration.

The requests use the same protected server executor as runtime named requests.

### Bind named request parameters

Request parameters map each parameter name to `string`, `number`, or `boolean`. Query and body templates use `{ "$param": "name" }` references.

A parameter declaration does not give a value to the parameter. A matching widget option or temporary input does not create a binding.

For a load query, bind each parameter in `optionsBinding`. Use an option reference or a type-compatible primitive literal:

For a manual query or action, supply all parameters with the component `params` prop. Use `SubFetch`, `ActionButton`, or `ToggleSwitch`.

Only this prop can send JSX values to a request. These values can include temporary inputs and loop variables.

Dynamic widget option requests run without a JSX invoker. Add an `optionsBinding` entry for each declared parameter.
